# 이미지 만들기 — 프롬프트를 누가 쓰는가

작성일: 2026-09-16

> **한 줄 결론**: AI 를 **최종 프롬프트 쪽으로 옮기되, 통째로가 아니라 「장면 문단」 하나만** 맡긴다. 첨부 번호·크기·사용자 원문은 코드가 계속 보장한다 — 그건 취향이 아니라 **계약**이고, 틀리면 결과가 나쁜 게 아니라 **틀린 그림**이 나온다.

> **범위**: 이미지 만들기(`/poster`)만. 카드뉴스는 레퍼런스 기반이라 제외, 상세페이지 글 경로는 기획이 먼저 서고 여러 장을 만들어야 해서 제외(2026-09-16 사용자 결정).

---

## 요구사항

- 사용자가 **완성된 프롬프트**를 들고 오면 그것을 살린다. AI 가 다시 써서 지우지 않는다
- 반대로 프롬프트를 모르는 사람은 **한두 줄**만 쓰면 된다. 나머지는 AI 가 채운다
- **둘 중 어느 쪽인지 사용자가 미리 배우게 하지 않는다.** 시스템이 알아채고 묻는다
- AI 가 **과하게 부풀리지 않는다.** 짧게 쓴 요청은 짧게 간다
- AI 가 **옵션을 알고** 쓴다. 지금은 결·모델·크기를 못 본 채 장면을 쓴다
- 첨부 번호·크기·사용자 원문의 정확성은 **지금과 똑같이** 지킨다

## 1. 지금 무슨 일이 일어나는가

```
01 한 줄 지시
      ↓  planPoster()            ← LLM (claude-sonnet-5)
슬롯 11칸 (kind·headline·subline·sideTexts·scene·subject·action·
           typeInteraction·dominantColor·accentColor·forbidden)
      ↓  04 기획 확인            ← 사람이 칸을 고친다
      ↓  buildPosterPrompt()     ← 코드가 틀에 맞춰 조립 (LLM 아님)
영문 프롬프트 한 덩어리
      ↓  pickEndpoint(model, hasReferences)
fal
```

**LLM 은 최종 프롬프트를 쓰지 않는다.** 칸만 채우고, 문장은 `prompt.ts` 가 규칙대로 붙인다.

### 1.1 기획 LLM 은 절반만 본다

`packages/poster-core/src/planning.ts:70~82` 가 실제로 적는 것:

```
사용자 지시: …
비율: …
첨부한 그림 (번호는 화면에 보이는 것과 같습니다): …
첨부한 그림을 어떻게 쓸지 — 사용자가 적은 말: …
```

**못 보는 것**: 결(`look`) · 모델(`modelId`) · 변형 장수 · 실제 픽셀 크기.

그래서 사용자가 「애니」를 골라도 기획은 그걸 모른 채 장면을 쓴다. 결 지시는 뒤에서 `imageLookDirective` 가 **따로 덧붙는다**(`prompt.ts:313`). 둘이 어긋날 수 있는 구조다 — 기획이 "필름 그레인, 실제 사진 같은"이라 써 놨는데 결은 「애니」인 경우.

### 1.2 같은 화면의 두 칸이 정반대로 동작한다

01 에 글 칸이 둘이다.

| 칸 | 어디로 | 원문이 |
|---|---|---|
| **한 줄 지시** (`instruction`) | 기획 LLM → 슬롯 11칸 | **사라진다** |
| **추가 지시 · 선택** (`userInstruction`) | 프롬프트 맨 앞·맨 뒤 그대로 | **남는다** |

이름만 보면 앞이 본칸이고 뒤가 곁가지인데, **완성된 프롬프트에는 정반대다.** 화면은 그 사실을 어디에도 적지 않는다.

**2026-09-16 실측**: 사용자가 약 200줄짜리 JSON 프롬프트를 「한 줄 지시」에 넣었다. 기획이 그것을 11칸으로 요약했고, 칸에 자리가 없는 것(`photography.lighting`·`skin.texture`·`negative_prompt`)은 **소리 없이 버려졌다.**

### 1.3 이미 잘 돼 있는 것 — 건드리지 않는다

`sceneLines` 의 `push` 는 **빈 슬롯을 건너뛴다**(`prompt.ts:220`). 짧게 쓰면 채워지는 칸이 적고 프롬프트도 짧게 나간다. **「과하게 부풀린다」는 걱정이 슬롯 쪽에서는 이미 지켜지고 있다.**

부풀릴 수 있는 것은 **고정 부분**이다 — `designerPersona()` 5줄은 늘 붙는다.

## 2. 결정 — AI 를 옮기되 「④ 구역」만

최종 프롬프트를 일곱 구역으로 보고, **한 구역만** AI 가 쓴다.

```
① 사용자 원문 (맨 앞)            코드    userInstructionHead
② 역할·태도                      코드    designerPersona
③ 첨부 번호·역할 지시            코드    ⚠ AI 금지
④ 장면 · 피사체 · 문구 · 분위기   ★ AI가 쓴다
⑤ 결 지시                        코드    imageLookDirective (실측 문구)
⑥ 금지 · 크기 · 우선순위          코드
⑦ 사용자 원문 (맨 뒤)            코드    userInstructionTail
```

### 2.1 ③을 AI 에 맡기면 안 되는 이유

`packages/poster-core/src/generate.ts:172` 에 이미 적혀 있다:

> 프롬프트와 같은 배열에서 뽑는다. 둘이 갈리면 **「Image 2」라고 적힌 지시가 다른 그림에 붙는다.**

프롬프트의 `[Image 2 — PRESERVED PERSON]` 은 fal 에 보내는 `input.image_urls[1]` 과 **반드시 같은 것을 가리켜야 한다.** 한 번호만 밀리면 **엉뚱한 사람 얼굴을 지키라고** 말하게 된다.

같은 성격인 것들 — 전부 코드가 계속 보장한다:

| 무엇 | 틀리면 |
|---|---|
| 첨부 번호·역할 | 다른 그림에 지시가 붙는다 |
| `Output size 1152x1536` | 잘리거나 다른 크기로 나온다 |
| 사용자 원문 맨 앞·맨 뒤 두 번 | 2026-09-04 실측이 정한 배치가 깨진다 |
| 실사 문구 | 3종 비교로 고른 문장이 바뀐다 |
| 우선순위 줄 | 어느 지시가 센지 모호해진다 |

**이건 취향이 아니라 계약이다.** LLM 이 다시 쓰면 조용히 빠지거나 바뀔 수 있고, 그때 아무도 모른다.

### 2.2 ④를 AI 가 쓰면 무엇이 좋아지나

| | 지금 | 바꾼 뒤 |
|---|---|---|
| AI 가 보는 것 | 지시·비율·첨부 | **+ 결·모델·크기·장수** |
| 결과물 | 슬롯 11칸 | ④ 구역 영문 산문 |
| 번호·크기 정확성 | 코드가 보장 | **그대로** |
| 모델별 최적화 | 코드 분기가 필요 | **AI 에게 모델을 알려주면 됨** |
| 과함 억제 | 칸을 채우려 든다 | **「짧으면 짧게」를 말로 정할 수 있다** |

마지막 두 줄이 이 설계의 값이다. 모델별 최적화를 **코드 갈래 6개**로 만들지 않고 **한 문장의 지시**로 푼다.

### 2.3 그래도 모델별 분기는 아직 안 만든다

이 저장소에는 실측 기록이 많다 — 2026-09-04 실사 문구 3종 비교, 2026-09-10 모델 속도·배치 준수 비교, 지시를 양끝에 두는 이유. **그런데 「같은 프롬프트를 모델별로 다르게 썼더니 더 좋았다」는 기록은 한 줄도 없다.**

기록된 모델 차이는 **능력**이지 **문장**이 아니다:

- sunburst 가 배치 지시를 유일하게 지켰다 (표본 2)
- nano 계열은 글자가 고딕으로 나온다
- nano 는 2K 고정, 비율이 목록 제한

그래서 이번에는 **모델 이름과 알려진 특성만 ④ 작성 LLM 에 넘긴다.** 코드 분기는 만들지 않는다. §7 의 실측으로 필요가 확인되면 그때 만든다.

## 3. 화면 — 알아채고 묻는다

### 3.1 두 갈래

```
┌──────────────────────────────────────────────┐
│ 무엇을 만들까                                 │
│ ┌──────────────────────────────────────────┐ │
│ │ { "subject": { "description": "An un…    │ │
│ │                                           │ │
│ └──────────────────────────────────────────┘ │
│                                               │
│ ⓘ 완성된 프롬프트로 보입니다.                  │
│   AI가 다시 쓰면 세부 지시가 사라질 수 있습니다.│
│                                               │
│   [ 쓴 그대로 생성 ]   [ 다듬어서 생성 ]       │
└──────────────────────────────────────────────┘
```

**판별은 하되 결정은 안 한다.** 오판해도 사용자가 고르므로 손해가 없다. 알림이 안 떠도 아래 「직접 쓴 프롬프트」 칸으로 같은 일을 할 수 있다(§3.3).

### 3.2 두 갈래가 하는 일

| | 쓴 그대로 생성 | 다듬어서 생성 |
|---|---|---|
| 기획 LLM | **안 돈다** | 돈다 |
| ④ 구역 | **사용자 원문 그대로** | AI 가 쓴 산문 |
| ①②③⑤⑥⑦ | 그대로 붙는다 | 그대로 붙는다 |
| 04 기획 확인 | **건너뛴다** (고칠 것이 없다) | 04 에서 ④를 고친다 |
| LLM 값 | **0** | 1 회 |

**「쓴 그대로」도 ③⑥은 붙는다.** 첨부를 붙였으면 번호·역할이 필요하고, 크기 줄은 없으면 모델이 제멋대로 만든다. 사용자 원문은 ④ 자리에 놓이고 ①⑦에도 그대로 들어간다.

### 3.3 칸 이름과 설명

| 지금 | 바꾼 뒤 |
|---|---|
| **한 줄 지시** (설명 없음) | **무엇을 만들까 · 한두 줄**<br>«편하게 쓰세요. AI 가 구도·색·문구를 정해 04 에서 보여드립니다» |
| **추가 지시 · 선택**<br>«여기 적은 말이 다른 모든 지시보다 우선합니다» | **직접 쓴 프롬프트 · 선택**<br>«여기 적은 것은 **AI 가 고치지 않고 그대로** 모델에 갑니다» |

### 3.4 입력칸 크기

지금 두 칸 다 3줄(`rows={3}`)인데 화면 아래 절반이 비어 있다. JSON 을 붙여 넣으면 3줄 창에서 스크롤하며 봐야 한다.

- 「무엇을 만들까」 6줄
- 「직접 쓴 프롬프트」 10줄
- 둘 다 내용에 따라 늘어나되 화면 높이의 절반을 안 넘는다

## 4. 04 기획 확인 — 무엇이 바뀌나

### 4.1 잃는 것과 지키는 것

지금 04 는 칸 11개를 각각 고친다(`poster-client.tsx:122~130`). 빈 칸은 접어 둔다(`splitFilledSlots`). **「틀린 칸만 고치기」가 이 화면의 강점이다.**

④가 문단이 되면 그 강점이 약해진다. 그래서 **AI 가 소제목을 달게 한다**:

```
장면
  해 질 녘 바닷가, 낮은 각도에서 …

인물
  20대 여성 한 명, 카메라를 보지 않고 …

문구
  헤드라인 「가을 사진전」을 상단 3분의 1에 …

분위기
  필름 그레인, 빛바랜 색 …
```

고칠 곳을 찾기는 쉬우면서 칸의 경직성은 없다. **소제목은 AI 가 정하지 않는다** — 네 개로 고정하고, 내용이 없으면 그 덩어리를 비운다.

### 4.2 최종 프롬프트 보기 (읽기 전용)

04 맨 아래에 접힌 칸을 하나 둔다.

```
▸ 모델에 보낼 프롬프트 보기
```

펼치면 실제로 나갈 영문 전문이 보인다. **읽기 전용이다** — 여기서 고치면 ③⑥의 보장이 깨진다.

이게 있어야:
- 사용자가 과함/부족함을 **직접 판단**한다
- 「쓴 그대로」와 「다듬어서」를 **비교**한다
- §7 의 실측이 가능해진다

값은 거의 안 든다. 프롬프트는 이미 만들어지고 있다.

## 6. 순서

**작은 것부터 간다.** 5번이 가장 크고, 2번이 5번의 필요성을 재는 근거가 된다.

| | 무엇 | 크기 | 왜 이 순서 |
|---|---|---|---|
| 1 | **404「결과 없음」 오안내 수정** | 작음 | 이미 배포된 코드의 잘못된 안내다. 독립적 |
| 2 | **04 에 최종 프롬프트 보기** | 작음 | 3~5 를 판단할 근거를 먼저 만든다 |
| 3 | **입력칸 크기 · 칸 이름과 설명** | 작음 | 화면만. 1~2 와 안 부딪힌다 |
| 3-a | **03 규격 손보기** (§8.1~8.3) | 작음 | 3 과 같은 화면 작업이라 함께 |
| 3-b | **여백 재기** (§8.4) | 작음 | 3·3-a 가 끝난 **뒤에** 잰다 |
| 4 | **알아채고 묻기 + 두 버튼** | 중간 | `verbatim` 경로를 연다. 04 는 아직 지금 모양 |
| 5 | **④를 AI 가 쓰게** | **큼** | 2 로 몇 번 돌려 본 뒤 착수 |

**1~4 는 서로 독립이다.** 5 만 앞의 것들을 전제한다.

## 7. 재야 할 것

5번을 하기 전에 2번으로 답을 낸다. **측정 없이 만들지 않는다** — 이 저장소가 계속 지켜 온 방식이다.

| 질문 | 어떻게 |
|---|---|
| 지금 프롬프트가 과한가 | 같은 지시로 뽑고 04 에서 전문을 읽는다. 사용자가 안 시킨 것이 몇 줄인가 |
| 「쓴 그대로」가 더 나은가 | 같은 JSON 을 두 갈래로 보내 결과를 견준다 |
| 모델별 분기가 필요한가 | 같은 프롬프트를 다섯 모델로. 같은 문장이 모델마다 다르게 읽히는가 |
| ④ 산문이 슬롯보다 나은가 | 5 착수 전 손으로 써 본 ④로 한 번 돌려 본다 |

## 8. 03 규격 화면 — 함께 손볼 것 (2026-09-16 추가)

### 8.1 광고 모드와 「광고 규격으로 내보내기」는 값이 크게 다르다

운영 서버는 `AD_EXPORT=1` 이다(`/etc/fixup-image-agent/app.env` 실측). 광고 관련 길이 **둘**인데 값이 전혀 다르다.

| | 어디 | 무엇 | 값 |
|---|---|---|---|
| **광고 모드** | 03 규격의 「만들 것」 토글 | 규격마다 **새로 그린다** | 규격 수 × 변형 수 |
| **광고 규격으로 내보내기** | 사이드바 `/ad` | 이미 만든 그림에서 **잘라 뽑는다** | 거의 안 든다 |

`new-client.tsx:263` 이 `adProjectBodies` 로 **마스터마다 프로젝트를 따로 만들어 하나씩** 생성한다. 규격 3개 × 변형 2장이면 **6장 값**이다.

화면이 장수는 적는다(`그림 3장 × 변형 2장 = 6장`). **그런데 옆에 거의 공짜인 길이 있다는 것은 안 적는다.**

**할 일**: 광고 모드를 켰을 때 한 줄 안내.

> 이미 만들어 둔 그림이 있으면 **「광고 규격으로 내보내기」**가 거의 값이 안 듭니다. 여기서는 규격마다 새로 그립니다.

### 8.2 비율에 용도 길잡이를 단다

`packages/sns-core/src/ratios.ts:30~50` 의 `POSTER_RATIOS` 는 **이미 「용도 + 비율」 형식**이다. 유튜브만 빠져 있다.

**새 항목을 만들지 않는다.** 유튜브 썸네일은 1280×720 = 정확히 16:9 라, 같은 픽셀을 다른 이름으로 두면 목록에 **같은 것이 둘** 생기고 사용자는 뭐가 다른지 묻게 된다.

대신 비율 줄 **아래에 길잡이 한 줄**을 단다. 버튼은 안 늘어난다.

```
비율
[인스타그램 피드 4:5] [정사각형 1:1] [스토리·릴스 9:16] …

  유튜브 썸네일·가로 배너 → 16:9    인스타그램 피드 → 4:5
  스토리·릴스·쇼츠 → 9:16           인쇄물 → A4
```

### 8.3 「인스타 피드」 → 「인스타그램 피드」

**같은 라벨이 두 곳에 있다**(`ratios.ts:18` 의 `CARD_RATIOS`, `ratios.ts:31` 의 `POSTER_RATIOS`). 하나만 고치면 카드뉴스와 이미지 만들기가 **다른 이름으로 같은 비율**을 부르게 된다. **둘 다 고친다.**

설명서에도 「인스타 피드에 올린다」가 있다(`guide/cardnews/page.tsx:446`). 그건 문장이라 그대로 둔다 — 버튼 이름이 아니다.

### 8.4 아래 여백 — **먼저 재고 나중에 정한다**

01 화면은 아래 절반이 비어 있다. 나머지 네 단계는 **아직 안 봤다.**

**공간을 채우려고 안내를 넣지 않는다.** 읽지도 않는 글이 늘어날 뿐이다. 그리고 §3.4 의 입력칸 키우기만으로도 01 의 빈 공간이 상당히 줄어든다 — **칸을 키운 뒤에 남는 공간**을 봐야 한다.

**순서**: §6 의 2·3 을 먼저 하고 → 다섯 단계를 실제로 열어 여백을 잰다 → 그때 무엇을 넣을지 정한다. 넣을 것이 없으면 안 넣는다.

## 11. §7 실측 (2026-09-16)

### 11-1. 지금 프롬프트가 과한가 — **잤다**

같은 조건으로 뽑아 구역별로 세었다. 「보통」은 기획이 칸을 채우고 첨부 둘,
사용자가 「한국어가 깨지지 않게」를 적은 경우다.

| 경우 | 글자 | 줄 |
|---|---|---|
| 최소 (장면 한 칸, 첨부 없음) | 1,581 | 16 |
| **보통** (칸 아홉, 첨부 둘) | **3,911** | 38 |
| 그대로 생성 (첨부 둘) | 3,087 | 21 |
| 그대로 생성 (첨부 없음) | 1,068 | 9 |

**보통 경우의 구역별:**

| 구역 | 줄 | 글자 | 비중 |
|---|---|---|---|
| ① 사용자가 친 말 | 4 | 297 | 8% |
| ② 역할·태도 | 5 | 443 | 11% |
| **③ 첨부·우선순위** | 8 | **1,670** | **43%** |
| ④ 장면·문구 | 17 | 800 | 21% |
| ⑤ 결 지시 | 1 | 509 | 13% |
| ⑥ 금지·크기 | 2 | 90 | 2% |

### 11-2. 무엇을 알게 됐나

**가장 큰 덩어리는 ④가 아니라 ③이다(43%).** 첨부 한 장마다 역할 문단이
통째로 붙는다 — 「PRESERVED PERSON」은 혼자 한 문단이고, 「POSTER REFERENCE」도
그렇다.

**5번(④를 AI 가 쓰게)의 값어치가 생각보다 작다.** ④는 전체의 21%뿐이고, 그
안에서도 슬롯 값은 짧다(「Scene: 해 질 녘 바닷가」). 나머지는 글자 규칙
(「Render this text exactly as written…」)이라 AI 가 쓸 자리가 아니다.

**「과하다」의 정체는 고정 문단이다.** ②(11%)와 ⑤(13%)는 입력과 무관하게 늘 같은
길이로 붙는다. 최소 경우(1,581자)에서도 ②+⑤가 950자다 — **60%**다.

### 11-3. 아직 못 잰 셋

나머지 셋은 **그림을 보고 사람이 판단할 일**이라 코드로 못 잰다.

| 질문 | 왜 못 재나 |
|---|---|
| 「그대로 생성」이 더 나은가 | 같은 JSON 으로 두 갈래를 뽑아 **결과를 견줘야** 한다 |
| 모델별 분기가 필요한가 | 같은 프롬프트를 다섯 모델로 돌려 **차이를 봐야** 한다 |
| ④ 산문이 슬롯보다 나은가 | 손으로 쓴 ④로 뽑아 **지금 것과 견줘야** 한다 |

이 셋은 크레딧이 드는 일이라 사용자가 판단한다. 04 의 「모델에 보낼 프롬프트
보기」가 그 근거를 만들어 준다.

### 11-4. 그래서 5번을 어떻게 할까

**실측이 5번의 전제를 흔들었다.** 설계 §2.2 는 ④를 AI 가 쓰면 「모델별 최적화를
코드 분기 없이 한 문장으로 푼다」고 했는데, ④가 21%뿐이면 그 한 문장이 닿는
범위도 21% 다.

**그래도 5번은 뜻이 있다.** 다만 기대를 바로잡는다:

- **되는 것**: 기획이 결·모델·크기를 보고 장면을 쓴다(지금은 못 본다).
  칸 열한 개를 채우려 드는 대신 「짧으면 짧게」를 말로 정할 수 있다.
- **안 되는 것**: 프롬프트 전체가 줄지 않는다. ③·②·⑤는 그대로다.

**먼저 할 것이 따로 있다.** ②·⑤가 최소 경우의 60%를 차지한다. 그 고정 문단이
정말 다 필요한지는 **11-3 의 실측 없이 판단할 수 없다** — 줄였다가 품질이
떨어지면 되돌릴 근거도 없다.

### 11-5. 5번을 해 보고 **접었다** (2026-09-16 실측)

11-4 가 고른 좁은 형태 — 「기획에 결을 알려 준다」 — 를 실제로 구현해서
Claude Sonnet 5 로 돌려 봤다. **채우는 칸이 줄었다.** 그래서 되돌렸다.

#### 무엇을 쟀나

지시 하나를 고정하고(「해 질 녘 바닷가에 놓인 필름 카메라」, 레퍼런스 없음,
1:1), 결만 바꿔 가며 기획이 채운 칸 수를 셌다. 순서 효과를 없애려고 섞어서
돌렸다.

| 붙인 자리와 문구 | 실사 | 애니 | 손그림 | 안 넘김(기준선) |
|---|---|---|---|---|
| 없음 (기준선) | — | — | — | **2.5~2.8칸** |
| 머리말에 `그림체: …` + 「어긋나지 않게 쓰세요」 | — | 0.1칸 | — | — |
| 머리말에 사실만 (`…로 그려집니다.`) | — | 0.8칸 | — | — |
| 규칙 칸 끝에 「다른 화풍을 적지 마세요」 | 1.0칸 | 4.4칸 | 1.7칸 | — |
| `forbidden` 칸 설명 안으로 | 5.3칸 | **0.75칸** | 6.3칸 | — |

문구를 옮길 때마다 **어느 결이 살고 어느 결이 죽는지가 뒤바뀐다.** 다섯 번을
고쳐도 모든 결에서 기준선을 넘는 문구를 못 찾았다.

#### 왜 이런가

기획 프롬프트에는 이미 「알 수 없는 칸은 지어내지 말고 비워 두세요」가 있다.
결을 알려 주는 말은 **그 조심성과 겹친다.** 지시가 결과 겉돌 때
(「필름 카메라」인데 애니) 기획은 안전한 쪽 — 비우는 쪽 — 으로 쏠린다.

지시를 바꿔 보면 더 뚜렷하다. 「벚꽃 아래에서 손을 흔드는 교복 입은 학생」은
**결을 안 넘겨도 기준선이 0칸**이다. 기획은 원래 말을 아낀다.

#### 결정: 안 넣는다

되돌린 이유가 둘이다.

1. **얻을 것이 이미 있다.** 유일하게 일관됐던 성과는 `forbidden` 에
   「다른 화풍 금지」가 들어간 것인데(21/21 전부 결에 맞게 옳았다),
   `imageLookDirective` 가 **이미 영어로 같은 말을 한다**
   (`No photographic realism, no 3D shading`). 중복이다.
2. **고치려던 것이 안 일어난다.** 「기획이 『필름 그레인』이라 써 놨는데 결은
   애니」를 걱정했는데, 결을 안 넘긴 40여 번 중 화풍·재질 낱말이 칸에 들어간
   적이 **한 번도 없다.** 없는 병에 약을 쓴 셈이다.

#### 대신 남는 물음

**기획이 너무 말을 아낀다.** 「벚꽃…교복 입은 학생」에 0칸은 지나치다.
이건 결과 무관한 **별개의 결함**이고, 고치려면 「지어내지 말고 비워 두세요」를
손봐야 한다. 그 문장은 2026-09-08 실측(인물 요약 뭉개짐)의 결과라 값 없이
건드리면 안 된다. **다음 차례로 넘긴다.**
