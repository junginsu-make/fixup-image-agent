# 상세페이지 서버 저장: 재리뷰 반영과 단계별 합격 조건

상태: S1~S6 로컬 구현·직접 코드 리뷰·검증 완료. 운영 SQL 적용·배포는 하지 않았다.
근거: double-shell의 2026-10-02-pdp-server-documents-codex-handoff.md 및 실제 코드 재리뷰.
생성 오류 수정은 별도 단계이며 서버 저장의 완료 증거로 세지 않는다.

## 시작 조건

사용자가 “계속 이어서 작업”하도록 지시하여 커밋·병합 없이 로컬 순차 구현을 이어갔다.
생성 수정은 a8aae23f 기반 fix/pdp-generation-remediation에 그대로 보존했다.
서버 저장은 별도 feat/pdp-server-documents 작업 공간에 생성 수정까지 포함해 구성했다.
커밋·master 병합·운영 DB 적용·배포는 수행하지 않았다.
최종 증거는 같은 폴더의 2026-10-02-pdp-remediation-validation.md를 본다.

## 반드시 보완할 계약

### 1. 작업과 라이브러리 항목의 관계

현재 library-sync-plan은 삭제된 섹션이 있으면 incompatible을 반환하고 새 작업을 만든다.
source_id도 유일하지 않다. 따라서 'ID만 보존하면 같은 작업이 갱신된다'는 전제를 쓰지 않는다.
서버 문서 하나가 현재 보여 줄 결과 묶음을 정하고, 섹션 삭제·재기획·버전 복원도
같은 문서의 새 버전으로 처리한다. 이전 결과는 문서 revision으로 보존한다.
합격: 3장 생성 → 가운데 삭제 → 재생성 후 같은 작업에 2장만 표시되고, 옛 3장으로 복원 가능.

### 2. 두 창 충돌과 생성 결과 반영 순서

현재 생성 라우트는 문서 저장과 별도로 syncDocumentLibraryLater를 호출한다.
문서 PUT에만 409를 붙이면 뒤늦은 창의 그림이 먼저 라이브러리를 바꿀 수 있다.
서버 문서가 관리하는 작업은 승인된 문서 버전이 결과 표시의 기준이어야 한다.
기존 생성·라이브러리 경로와 새 문서의 갱신이 서로 덮어쓰지 않는 경계를 명시하고 시험한다.
합격: 두 창이 같은 버전을 열고 각각 생성할 때, 늦은 쪽은 사본으로 남으며
원 문서·라이브러리·과정 보기 모두 먼저 저장된 버전에 일치한다.

### 3. 그림 분리와 완전 복원

createPdpDocument만 호출해도 sections.generatedImage와 textDraft.keyVisual,
textDraft.styleReference.imageBase64, assets.previewUrl 등에 그림이 남는다.
별도 서버 직렬화 계약으로 모든 그림 위치를 열거하고 파일 참조로 바꾼다.
복원은 바이트뿐 아니라 MIME·파일명·섹션 ID·편집 레이어·양쪽 blueprint의 연결을 보존한다.
서명 URL과 blob URL을 영구 문서에 저장하지 않는다.
합격: 이미지/텍스트/대표 이미지/스타일/인물/편집 레이어를 포함한 왕복 비교,
빈 브라우저에서 복원·재생성, 큰 초안에서도 문서 JSON에 base64가 없음.

### 4. v2/v3 사본 선택과 이관

현재 get은 v3 플래그가 꺼져 있어도 v3를 우선해 최신 v2를 가릴 수 있다.
이관은 읽기 출처와 updatedAt을 함께 고려하고, 구별 불가능한 상이한 사본은 보존한다.
기존 브라우저 자료를 지우지 않는다. 사용자가 연 자료만 올린다.
중복 이관은 애플리케이션 사전 조회뿐 아니라 DB의 사용자별 고유 제약으로 방지한다.
합격: 오래된 v3+새 v2, 오래된 v2+새 v3, 동시 이관, 재시도, 다른 사용자,
서버 장애에서 로컬 원본·최신 내용이 사라지지 않음.

### 5. 이전 버전의 실제 복원

최근 20개의 이전 버전 보관에 더해 목록·조회·복원 API와 사용자 진입점을 구현한다.
복원은 과거 revision 번호로 되감는 것이 아니라 과거 내용을 새 revision으로 저장한다.
복원에도 현재 revision 검사를 적용하고, 해당 버전이 참조하는 그림이 존재하는지 검증한다.
합격: 과거 문구·그림·레이어를 복원한 후 재생성, 동시 편집과 복원 충돌, 타인 버전 접근 거절.

### 6. 그림이 없는 작업의 목록

기존 library-sync는 known.length=0이면 항목을 만들지 않는다.
새 문서 목록을 라이브러리에 연결해 입력·기획 중인 문서도 표시한다.
문서와 기존 결과 항목이 모두 있을 때 중복 카드를 만들지 않는다.
합격: 집 PC의 빈 IndexedDB에서 회사 PC의 입력·기획 단계 작업이 나타나고 해당 단계로 열린다.

## 구현 순서

각 단계는 실패 시험 → 구현 → 코드 리뷰 → 검증을 마친 뒤 다음으로 진행한다.

1. S1 계약·SQL·로컬/원격 저장소: 소유권, 사용자별 이관 고유 제약, 원자적
   revision 비교/이전 본 보관/갱신, 최근 20개, 권한 차단. SQL도 로컬 실행 검증.
2. S2 업로드·문서 API: 최초 문서 식별과 업로드 권한의 순서, 고정된 서버 생성 경로,
   업로드 완료·실제 크기/형식 확인, 불완전 업로드를 저장 완료로 처리하지 않음,
   제한된 본문 읽기, 다른 문서/사용자 경로 거절, 삭제의 실패·재시도.
3. S3 브라우저 저장 창구: 모든 이미지 분리/복원, 새 플래그, 최신 사본 선택,
   네트워크 지연 중 편집 보존, 초기 저장 중 문서 식별 변경 처리.
4. S4 불러오기·이관·충돌 사본·버전 복원: 소유 확인, 단계와 ID 복원,
   새 사본으로 전환 이후의 저장도 올바른 문서로 연결.
5. S5 라이브러리·관리자: 같은 문서 갱신, 생성과 저장의 경쟁 차단,
   그림 없는 문서, 관리자 읽기/자기 것으로 복사, 원본 소유자와 경로 변환 검증.
6. S6 통합: 빈 브라우저 왕복, 두 창 충돌, 네트워크/업로드/저장 실패,
   처음 만들기 변경 경계 비교, 타입/lint/전체 시험, 로컬 화면 검증.

운영 SQL 적용·커밋·병합·배포는 로컬 구현/검증과 별개의 상태로 보고한다.

## 범위 밖

리디자인 서버 저장, 기존 테이블의 경로 보안, 기존 브라우저 assets 청소,
캐릭터 과정 보기의 커밋·배포는 이 작업에 섞지 않는다.
