# 포털 광고 소재 규격 만들기

작성일: 2026-09-06 (독립 리뷰 2건 반영 후 전면 개정)

> **한 줄 결론**: 광고 규격은 「비율 버튼을 늘리는 일」이 아니다. **필요한 규격 거의 전부를 모델이 직접 만들 수 없다.** 모델이 만들 수 있는 마스터 다섯 장을 만들고 sharp 로 규격을 깎아 내는 **2단 구조**로 간다. 기존 파일은 **한 글자도 고치지 않는다.**

> **초판 폐기 사유** (독립 리뷰 2건):
> 1. 「모델의 한계는 3:1」이 틀렸다 — `nano-banana-2` 는 `4:1`·`8:1` 도 만든다. 다만 **안 A 를 택해 쓰지 않기로 했다**(§2.3)
> 2. 「가능」으로 분류한 규격 셋이 `multipleOf: 16` 을 통과 못 했다 — 인용한 제한을 표에 적용하지 않았다
> 3. 「기존 파일 변경은 한 줄」이 거짓이었다 — 관문이 **다섯 곳**이다. 대신 **무접촉 경로**를 찾았다(§4.2)
> 4. AI 표기(`markAsAi`)가 설계에 아예 없었다
> 5. 마스터 배정 둘이 틀렸다(확대 필요 · 방향 반대)

## 요구사항

네이버·구글·카카오에 올릴 광고 소재 이미지를 만든다.

- 포털·상품마다 요구 규격이 다르다. 한 번 만들면 여러 규격을 함께 얻어야 한다
- **필수 규격과 선택 규격을 구분**해서 보여 준다 — 없어도 등록되는 것을 필수처럼 보이게 하지 않는다
- 화질은 떨어지지 않는다. 다만 **포털이 용량을 강하게 제한**하므로 그 안에서 최선을 낸다
- **내보내기 전에 반드시 검증한다** — 규격이 정확한지, 그리고 사용자가 원한 그림이 맞는지 (§5)
- **생성은 기존 이미지 만들기 기능을 그대로 쓴다.** 생성 파이프라인을 새로 만들지 않는다
- **기존 시스템에 영향을 주지 않는다.** 순수 추가 기능이다 (§4)

## 1. 결정적 사실 — 광고 규격은 거의 전부 직접 생성할 수 없다

`packages/sns-core/src/models.ts:64` 의 GPT Image 2 제한:

```
pixelSizeLimits: { minPixels: 655360, maxPixels: 8294400, maxEdge: 3840, multipleOf: 16, maxAspect: 3 }
```

**다섯 제한을 전부 적용해** 계산했다.

| 규격 | 픽셀 수 | 비율 | 16의 배수 | 직접 생성 |
|---|---|---|---|---|
| 1200×1200 | 1,440,000 | 1.00 | ✓ | **가능** |
| 960×1200 | 1,152,000 | 0.80 | ✓ | **가능** |
| 720×1280 | 921,600 | 0.56 | ✓ | **가능** |
| 1200×628 | 753,600 | 1.91 | **628 % 16 = 4** | 불가 |
| 1200×600 | 720,000 | 2.00 | **600 % 16 = 8** | 불가 |
| 1250×560 | 700,000 | 2.23 | **1250 % 16 = 2** | 불가 |
| 1029×258 | 265,482 | 3.99 | ✗ | 불가 — 픽셀·비율·배수 |
| 750×160 | 120,000 | 4.69 | ✓ | 불가 — 픽셀·비율 |
| 214×214 | 45,796 | 1.00 | ✗ | 불가 — 픽셀·배수 |
| 300×300 | 90,000 | 1.00 | ✗ | 불가 — 픽셀·배수 |
| 228×152 | 34,656 | 1.50 | ✗ | 불가 — 픽셀·배수 |
| 188×110 | 20,680 | 1.71 | ✗ | 불가 — 픽셀·배수 |

**열둘 중 셋만 가능하다.** 초판은 여섯이라고 적었는데, `multipleOf: 16` 을 표에 적용하지 않았다 — 바로 위에 인용해 놓고서.

이 제한은 저장소가 실제로 강제한다. `packages/sns-core/src/__tests__/ratios.test.ts:69-80` 이 `POSTER_RATIOS` 전 항목에 다섯 제한을 전부 단언한다.

**그래서 2단 구조 말고는 길이 없다.**

## 2. 구조 — 마스터 생성 / 규격 파생

```
[1단] 마스터 생성                [2단] 규격 파생
모델이 만들 수 있는 큰 그림  →   sharp 로 자르고·줄이고·용량 맞춤
(기존 기능 그대로, 과금)          (신규, 비용 0)
```

**비용이 결정적이다.** 사용자가 규격 10개를 골라도 생성은 마스터 2~3장뿐이다. 규격마다 생성하면 10번 과금된다.

### 2.1 두 단이 각각 답하는 질문

| 단 | 질문 | 답이 있는 곳 |
|---|---|---|
| 1단 | 어떤 그림을 몇 장 생성할 것인가 | §6 마스터 |
| 2단 | 모델이 못 만드는 규격을 어떻게 채울 것인가 | **§3** |

### 2.2 파생 방법은 둘뿐이다

```ts
type Derive =
  | "resize"   // 비율이 같다. 줄이기만 한다
  | "crop";    // 비율이 다르다. 자른 뒤 줄인다
```

**어느 마스터에서 깎느냐가 전부다.** 1:1 에서 1.91:1 을 뽑으면 세로 절반이 날아가지만, 1.91:1 마스터에서 뽑으면 그대로다. 마스터를 목표 비율에 가장 가깝게 고르는 것이 §6 의 일이다.

### 2.3 극단 비율을 쓰지 않기로 한 결정 (안 A)

`nano-banana-2` 는 `4:1`·`1:4`·`8:1`·`1:8` 을 만든다(`models.ts:52`, `model-choice.ts:9-18` 머리말). 그것을 쓰면 카카오 비즈보드(3.99)·GDN 리더보드(8.09)를 직접 생성할 수 있다.

**쓰지 않기로 했다.** 근거:

| | 안 A (택함) | 안 B (기각) |
|---|---|---|
| 방법 | `gpt-image-2` + `match-source` 경로 | `POSTER_RATIOS` 에 `hidden` 항목 추가 |
| 기존 파일 수정 | **0곳** | `ratios.ts` · `new-client.tsx` · **기존 시험 `ratios.test.ts:69`** |
| 만들 수 있는 비율 | 3:1 까지 | 8:1 까지 |
| 실측 필요 | 없음 | `2K` 의 실제 출력 픽셀을 모름 → $0.16 |

「기존 시스템에 영향을 주지 않는다」가 요구사항이고, **안 A 는 그것을 문자 그대로 지킨다.** 안 B 가 열어 주는 규격(비즈보드·GDN)은 §3.4·§3.5 에서 어차피 이 문서 범위 밖으로 나간다.

**안 B 로 돌아올 조건**: 1단계를 만들어 실제로 뽑아 봤을 때 크롭 품질이 못 쓸 정도라면. 그때는 실측부터 한다.

## 3. 모델이 못 만드는 규격을 어떻게 만드는가

### 3.1 못 만드는 이유는 셋이고, 답이 각각 다르다

| 이유 | 판정 기준 | 답 |
|---|---|---|
| 픽셀이 모자라거나 16의 배수가 아님 | `w×h < 655,360` 또는 `% 16 ≠ 0` | **크게 만들어 줄인다** (§3.2) |
| 비율이 마스터와 다름 | 목표 비율 ≠ 마스터 비율 | **가장 가까운 마스터에서 깎는다** (§3.3) |
| 투명 배경이 필요 | `png-alpha` | **이 문서 범위 밖** (§3.4) |

### 3.2 크게 만들어 줄인다 — 문제가 아니라 오히려 이득이다

줄이는 것은 **손실이 아니라 슈퍼샘플링**이라 오히려 선명해진다. 지금 목록 썸네일이 하는 일과 같다(`apps/web/lib/grid-thumbnail.ts`).

```
1200×628 ← ad-191x1 (2048×1072) 을 축소
214×214  ← ad-1x1   (1200×1200) 을 축소
300×300  ← 같은 마스터
```

**불변식 — 절대 확대하지 않는다.**

마스터를 목표 비율로 **크롭한 뒤의 크기**가 목표보다 작으면 확대 보간이 걸려 흐려진다. 광고는 심사에서 「이미지가 흐림」으로 반려되는 항목이다.

초판은 네이버 메인 배너(1250×560)에 1216×608 마스터를 붙여 **1.03배 확대**가 필요했다. 표를 손으로 적었기 때문이다.

> **정정(1단계 구현 중)**: 초판은 이 자리에 「마스터의 원래 크기와 비교하면 안 된다」고 적었다. **틀렸다.** 크롭 결과는 마스터 안에 들어가는 가장 큰 직사각형이라 `마스터 ≥ 목표` 와 `크롭 후 ≥ 목표` 는 **같은 조건**이다(무작위 20만 건으로 확인, 다른 경우는 부동소수점 경계 3건). 초판의 잘못은 비교 대상이 아니라 **검사를 아예 안 한 것**이었다.

확대가 필요한 경우는 **만들지 않고 실패로 알린다.** 조용히 흐린 그림을 주는 것이 가장 나쁘다.

### 3.3 비율이 다르면 깎는다 — 남는 곳은 세 군데뿐이다

안 A 에서 실제로 크롭이 일어나는 규격은 **셋뿐이다**(§6.2 배정표).

| 규격 | 마스터 | 남는 면적 |
|---|---|---|
| 1250×560 (네이버 메인) | `ad-2x1` | 89.6% |
| 376×220 (브랜드검색 모바일) | `ad-191x1` | 89.5% |
| 456×304 (브랜드검색 PC) | `ad-191x1` | 78.5% |

나머지 일곱은 전부 `resize` 다 — **구도가 바뀌지 않는다.**

크롭이 셋뿐이고 최저가 78.5% 라, 초판의 「프롬프트에 중앙 띠 지시를 덧붙인다」는 **뺐다.** 지시를 목표별로 달리하면 마스터가 특정 목표 전용이 되어 §2 의 재사용 논거가 무너진다. 이 정도 손실은 §5.2 미리보기에서 사람이 보고 판단하면 된다.

**어디를 기준으로 자르는가**: 중앙이 기본이다. `AdSpec.safeArea` 가 있으면 그 영역이 살아남는 쪽으로 치우쳐 자른다.

### 3.4 투명 배경 두 곳 — 이 문서 범위 밖

카카오 비즈보드(1029×258)와 네이버 스마트채널(750×160)은 **투명 배경 PNG** 를 요구한다.

**모델이 알파를 만드는지 확인되지 않았다.** `models.ts` 에 출력 형식 필드가 없고, `apps/web/lib/fal/queue.ts:34` 는 URL 만 받는다. 저장 경로가 `.png` 로 못 박지만 그건 명명 규칙이지 알파 유무의 근거가 아니다. **외부 확인이 필요하다.**

확인 결과와 무관하게, 이 둘을 제대로 만들려면 **투명 캔버스에 문구와 오브젝트를 배치하는 엔진**이 필요하다. 카카오 비즈보드의 네 유형(오브젝트형·썸네일형·마스킹형·텍스트형)이 원래 그 구조이고, 카카오 자체 배너 제작툴도 그렇게 동작한다.

**그건 배너 빌더라는 다른 제품이다.** 이 문서에서 다루지 않는다. 화면에는 「아직 지원 안 함」으로 보인다(§9).

### 3.5 그 밖에 만들지 않는 것

| 규격 | 왜 |
|---|---|
| GDN 고정 배너 (300×250 · 728×90 · 160×600 · 300×600 · 320×100) | **전부 선택 규격**이다. 반응형만으로 등록된다. 넣으면 규격이 15개 넘게 늘어 화면이 복잡해지는데, 필수는 하나도 안 늘어난다 |
| 1200×300 (구글 로고) | **로고는 생성 대상이 아니다.** 브랜드 로고를 모델이 지어내면 안 된다. 업로드받는다 |

### 3.6 판단을 코드로 못 박는다

```ts
export type DerivePlan =
  | { kind: "resize"; master: string }
  | { kind: "crop";   master: string; keep: number }
  | { kind: "upload";  reason: string }        // 로고
  | { kind: "unsupported"; reason: string };   // 투명 PNG 등

export function planDerivation(spec: AdSpec): DerivePlan;
```

**시험으로 고정할 것 다섯**

1. `AD_SPECS` 의 모든 항목이 답을 받는다 — **빠진 규격이 없다**
2. 마스터가 **모델 제한 다섯을 전부 통과**한다 (`minPixels`·`maxPixels`·`maxEdge`·`multipleOf`·`maxAspect`). §1 이 이 설계의 근거인데 마스터를 나중에 손대면 근거가 조용히 무너진다
3. **어떤 규격도 확대되지 않는다.** 지금 실린 규격만 보는 것으로는 모자라다 — 확대 금지를 통째로 걷어내도 지금 배정은 안 바뀐다(뮤테이션으로 확인). **어떤 마스터로도 못 덮는 규격**을 넣어 그 가지를 실제로 밟아야 한다
4. **마스터와 규격의 방향이 같다.** 다만 이것은 **결과 성질을 보는 시험이지 코드의 분기가 아니다** — 최대 유지율 선택이 이미 흡수한다(가로 마스터는 세로 목표에서 유지율이 언제나 더 낮다). 코드에 두면 도달 불가능한 가지가 되어 시험이 못 덮는다
5. `format: "png-alpha"` 인 규격은 **반드시** `unsupported` 다 — 크롭으로 새어 나가면 투명 없이 등록 실패한다

## 4. 격리 계약 — 「영향을 주지 않는다」를 검증 가능한 문장으로

「조심하겠다」는 약속은 지킬 수 없다. 무엇을 하면 위반인지 미리 못 박고, **어긴 순간 시험이 깨지게** 한다.

### 4.1 계약 일곱

| # | 계약 | 어떻게 확인하는가 |
|---|---|---|
| 1 | **기존 파일을 고치지 않는다** | `git diff` 에 기존 파일이 없다 (§4.2) |
| 2 | **광고가 의존하는 모델 능력이 안 바뀐다** | `IMAGE_MODELS` 의 `id`·`supportedRatios`·`pixelSizeLimits` **만** 고정. **가격표는 제외** |
| 3 | **기존 비율 목록이 안 바뀐다** | `POSTER_RATIOS`·`CARD_RATIOS` 스냅숏 |
| 4 | **마이그레이션이 없다** | `supabase/migrations/` 에 파일이 늘지 않음 |
| 5 | **기능을 통째로 끌 수 있다** | 플래그를 끄면 새 라우트가 404, 화면에 진입점 없음 |
| 6 | **새 기능의 실패가 기존 기능을 죽이지 않는다** | §4.4 — 단계마다 뜻이 다르다 |
| 7 | **내보낸 광고의 AI 표기 상태가 원본과 같다** | §4.3 |

**계약 2에서 가격표를 뺀 이유**: `IMAGE_MODELS` 를 통째로 고정하면 fal 가격이 바뀔 때마다 깨진다. 가격은 정당하게 바뀌는 값이다(`models.ts:29` 주석에 확인 날짜가 적혀 있다). 몇 번 깨지면 사람이 반사적으로 스냅숏을 갱신하게 되고, **그 순간 이 자물쇠는 광고 기능이 `supportedRatios` 를 건드려도 조용히 통과시킨다.**

### 4.2 무접촉 경로 — `match-source` 를 쓴다

`ratioId` 문자열이 통과해야 하는 관문이 **다섯 곳**이고, 전부 `POSTER_RATIOS` 를 직접 본다.

| 관문 | 무엇이 막는가 |
|---|---|
| `poster-core/src/schemas.ts:50,55` | `z.enum(POSTER_RATIO_IDS)` — API 입구에서 거부 |
| `apps/web/app/api/poster/projects/poster-service.ts:28` | 비용 추정 호출 |
| `poster-core/src/pricing.ts:51,72` | `resolvePosterSize` — 「모르는 비율입니다」 |
| `sns-core/src/model-choice.ts:138` | `canMake` 가 `POSTER_RATIOS.find` — 못 찾으면 「만들 수 있는 모델이 없습니다」 |
| `poster-core/src/generate.ts:101` | `buildPosterJob` |

초판은 `resolveFrom` 을 export 하면 된다고 적었다. **그 경로는 `resolveFrom` 을 부르지 않는다.** 다섯 중 하나도 열리지 않는다.

**대신 이미 열려 있는 문이 있다.** `ratioId = "match-source"` 는 다섯 관문을 전부 통과하고, `generate.ts:97-99` 가 `sourceSize` 가 있으면 `sizeFromSource(sourceSize, model)` 로 갈라진다.

마스터 다섯을 그 함수에 실제로 넣어 확인했다:

```
ad-1x1    1200×1200 → 1200×1200
ad-191x1  2048×1072 → 2048×1072
ad-2x1    1600×800  → 1600×800
ad-4x5    1088×1360 → 1088×1360
ad-9x16   1152×2048 → 1152×2048
```

**입력 픽셀이 그대로 나온다. 기존 파일 무접촉으로 마스터를 만들 수 있다.**

**이 문의 한계 둘** (실측으로 확인):

- `sizeFromSource` 는 `pixelSizeLimits` 가 있는 모델에서만 동작한다 → **`gpt-image-2` 전용.** nano 계열은 「첨부한 비율을 그대로 쓸 수 없습니다」
- `maxAspect: 3` 검사가 그대로 걸린다 → **3:1 까지만.** 4:1 을 넣으면 「비율이 3:1 을 넘습니다」

이 한계가 §2.3 의 안 A 를 규정한다. 같은 검사가 `packages/layout-core/src/image-request.ts:71` 에도 있다.

**부작용 하나**: 비용 추정이 `match-source` 의 자리표시 픽셀(1088×1088) 기준으로 잡힌다(`pricing.ts:51`). 실제 마스터가 그보다 크면 **추정이 실제보다 낮게 나온다.** 화면에 「예상」임을 명시하고, 위험표에 올린다.

### 4.3 AI 표기 — 계약 7

`apps/web/lib/watermark.ts:31` 의 `markAsAi` 가 저장 직전에 **파일 안에** 「AI 이미지」 배지를 굽는다. 포스터도 예외가 아니다. 배지는 **오른쪽 아래**에 너비 비례로 놓인다(`packages/sns-core/src/watermark.ts:55-85`, 너비의 5.5%, 여백 2.2%).

초판은 `markAsAi` 를 「읽기 전용으로 재사용」 목록에 넣어 두고, 그것이 **파생의 입력 바이트에 이미 박혀 있다**는 사실을 다루지 않았다. 둘이 터진다.

1. **크롭이 표기를 잘라낸다.** `watermark.ts` 주석이 「화면에만 덧씌우면 내려받는 순간 사라져 목적이 사라진다」고 적은 그 실패를, 다른 경로로 재현한다
2. **축소가 표기를 뭉갠다.** 214×214 에서 배지 높이는 5px 이하 — 지워지지도, 읽히지도 않는다

배지는 관리자가 켰을 때만 붙는다(기본 off). 그래서 CRITICAL 은 아니지만 **소유자가 없다.**

**결정: 파생 후 `markAsAi` 를 다시 태운다.** 규격마다 배지 크기가 달라야 하는데, 파생 후에 태우면 그것이 저절로 맞는다(`badgePlacement` 가 캔버스 너비에 비례한다). 광고에 AI 표기를 넣을지 자체는 법무·정책 문제라 이 문서 밖이다.

### 4.4 계약 6은 단계마다 뜻이 다르다

- **1~2단계**: 파생이 생성보다 **뒤**에 온다. 파생 실패 = 광고 내보내기만 실패. 이미 만든 결과물은 멀쩡하다
- **3단계**: 생성이 **먼저**다. 파생 실패 = **이미 과금된 생성이 쓸모없어짐**

3단계에서는 「기존 기능이 안 죽는다」로 충분하지 않다. **생성 전에 `planDerivation` 을 먼저 돌려, 만들 수 없는 규격이면 과금 전에 막는다.** 이 저장소는 같은 판단을 이미 한다 — 「만들 수 없는 조합은 제출조차 하지 않는다」(`apps/web/lib/__tests__/poster-flow.test.ts`).

### 4.5 생성은 기존 기능을 그대로 쓴다

```
[기존 그대로]                          [신규]
포스터 만들기  →  결과물  →  광고 규격 파생 → 검증 → 내려받기
```

**1~2단계는 생성을 아예 안 부른다.** 3단계에서 부를 때도 기존 `submitPoster` 를 그대로 부른다 — `ratioId: "match-source"` 와 `sourceSize: 마스터 픽셀` 을 넘기는 것뿐이다.

재사용하는 것 — **전부 읽기 전용**: `IMAGE_MODELS`·`modelById`, `sizeFromSource`, fal 클라이언트 팩토리, `markAsAi`, `encodeForStorage`, 라이브러리 저장·조회.

## 5. 검증 — 두 겹이고, 성격이 다르다

**규격이 맞는 것과 사용자가 원한 그림인 것은 다른 문제다.** 228×152 로 정확히 잘렸는데 주인공 얼굴이 반쯤 날아갔을 수 있다.

### 5.1 규격 검증 — 기계적, 필수, 예외 없음

내보내기 직전에 **만들어진 바이트 자체**를 검사한다. 계획을 검사하는 것이 아니다 — 계획은 맞았는데 인코딩에서 어긋나는 것이 실제로 일어난다(이 저장소의 WebP 작업에서 16비트 강등·투명 픽셀 소실이 그렇게 났다).

| 검사 | 기준 | 어기면 |
|---|---|---|
| 픽셀 | `width === target.width && height === target.height` **정확히** | 실패 |
| 형식 | `spec.format` 과 일치 | 실패 |
| 용량 | `bytes.length <= spec.maxBytes` | 실패 |
| 메타데이터 | **지워졌는지** — 200KB 예산에서 ICC·EXIF 는 사치다 | 실패 |

**여기서 두 검사를 일부러 뺐다.**

- **확대 금지**는 `planDerivation`(§3.6 불변식 3)에 이미 있다. 같은 규칙을 두 곳에 두는 것은 이 문서가 §4.1 에서 경고한 바로 그 형태다 — 초판이 자기 경고를 자기 안에서 어겼다. 계획 단계에서 막는 것이 맞다
- **안전영역 「가장자리가 거의 단색인가」**는 값이 없다. 광고 소재는 실사·그라디언트 배경이 흔해 정상 소재에서 상시 경고가 뜬다. **상시 뜨는 경고는 사용자가 모든 경고를 무시하게 만들어, 같은 목록의 진짜 실패까지 무력화한다.** 안전영역은 §5.2 의 반투명 띠가 정확히 답한다

**메타데이터를 지우는 것은 이 저장소의 다른 파생 경로와 반대다.** `grid-thumbnail.ts:37-38` 은 `keepMetadata()` 로 ICC 를 지킨다 — 목록 썸네일은 색이 틀어지면 안 되기 때문이다. **광고는 200KB 안에 들어가는 것이 우선이다.** 두 경로가 다르다는 것을 시험으로 못 박는다.

**실패를 조용히 넘기지 않는다.** 규격 하나가 실패하면 그것만 빼고 나머지를 주되, **무엇이 왜 빠졌는지 화면에 적는다.** 광고 심사에서 반려되고 나서 아는 것보다 낫다.

### 5.2 사람 눈이 의도 검증이다

**미리보기 없이 내려받을 수 없다.**

파생된 규격 전부를 실제 크기 비율로 격자에 깔고, 안전영역을 반투명 띠로 덮어 보여 준다.

초판은 여기에 **시각 모델 검수**를 더하려 했다. 뺐다 — 초판 스스로 「미리보기가 진짜 관문이다」라고 적어 놓고, **사용자가 곧 눈으로 볼 것을 모델에게 돈 주고 먼저 보게 하는 구조**였다. 게다가 참고하려던 `packages/pdp-core/src/pdp.qa.ts` 는 Google GenAI 를 쓴다(fal 이 아니다) — 광고 경로에 두 번째 벤더와 키가 붙는다.

**되돌아올 조건**: 사람들이 미리보기 격자를 대충 넘기는 것이 관찰되면. 그때 붙인다.

**미리보기가 잡아야 할 것 넷**

1. **잘림** — 주인공·로고·글자가 잘렸는가 (크롭한 셋에서만 가능)
2. **가독** — 글자가 읽히는가. **214×214 는 1200×1200 에서 5.6배 축소다.** 헤드라인이 안 읽히는 214×214 는 규격 검증을 전부 통과하고 광고로 나간다. 이 제품은 그림 안에 글자를 굽는다(`PosterSlots.headline`·`subline`)
3. **안전영역** — 주요 요소가 가장자리 금지 구역에 있는가
4. **의도** — 사용자가 적은 지시(문구·분위기·상품)가 이 그림에 남아 있는가

**파생을 두 번 돌리지 않는다.** 미리보기가 만든 버퍼를 그대로 ZIP 에 넣는다. §8.1 이 「내려받을 때 만든다」고 적고 여기가 「내려받기 전에 보여 준다」고 적으면, 그대로 합쳤을 때 같은 파생이 두 번 돈다. 요청 스코프 안에서 한 번만 돌게 한다.

> **정정 (2단계-A 구현 중 실측)**: 초판은 「규격 10개 × 이분 탐색 6~8 ≈ 요청당 70~90회」로 어림했다. **틀렸다.** 규격 17개를 전부 요청해도 sharp 인코드는 **20회**다 — 17개 중 sharp 를 타는 것이 14개뿐이고(로고는 업로드, 투명 둘은 미지원), 이분 탐색이 붙는 것은 용량 상한이 빡빡한 `naver-gfa-main` 하나다. 12MP 마스터에서 4.4초.
>
> **그래서 막아야 하는 것은 요청의 크기가 아니라 빈도다.** 규격 수 상한은 CPU 천장을 이미 `AD_SPECS.length` 가 정하고 있어 아무것도 못 막는다. 실제 방어는 `lib/layout/render-gate.ts` 의 동시 실행 제한(회원당 1 · 전체 2)이고, 그 파일 머리말이 「진짜 희소 자원은 libuv 스레드풀」이라고 적은 것이 이 경로에도 그대로 맞는다.

### 5.3 검증도 순수 함수로 뽑는다

```ts
export interface SpecCheck { ok: boolean; failures: string[]; }

/** 만들어진 바이트를 검사한다. 계획이 아니라 결과물이다. */
export async function checkAgainstSpec(bytes: Buffer, spec: AdSpec): Promise<SpecCheck>;
```

**시험으로 고정할 것**: 검사 네 개가 **각각 독립적으로** 실패를 잡는지. 한 검사를 무력화하는 뮤테이션마다 시험이 깨져야 한다. 「전부 통과하는 정상 입력」 하나만으로는 아무것도 검증하지 못한다 — 이 저장소에서 헛도는 시험을 다섯 번 만들었다.

### 6.1 마스터 다섯

|---|---|---|---|---|
| `ad-1x1` | 1200×1200 | 1.000 | 1,440,000 | ✓ |

| `ad-2x1` | 1600×800 | 2.000 | 1,280,000 | ✓ |

다섯 모두 `minPixels 655,360` · `maxPixels 8,294,400` · `maxEdge 3,840` · `multipleOf 16` · `maxAspect 3` 을 통과한다(계산으로 확인).

`ad-4x5`·`ad-9x16` 은 `POSTER_RATIOS` 의 기존 값과 같다. **다만 그 배열을 참조하지 않는다** — 광고 모듈이 자기 상수로 들고 `match-source` 로 넘긴다(§4.2). 계약 1·3 을 지키기 위해서다.

### 6.2 배정 (계산 결과)

「확대가 없으면서 크롭 손실이 가장 적은 마스터」를 기계적으로 골랐다. **사람이 눈대중으로 정하지 않는다** — 초판에서 그렇게 했다가 둘을 틀렸다.

| 규격 | 용도 | 마스터 | 크롭 후 | 면적 |
|---|---|---|---|---|
| 1200×1200 | 구글/카카오/GFA 정사각 | `ad-1x1` | 1200×1200 | 100% |
| 300×300 | GFA 썸네일 | `ad-1x1` | 1200×1200 | 100% |
| 214×214 | 파워링크 이미지 | `ad-1x1` | 1200×1200 | 100% |
| 1200×628 | 구글 가로 · GFA 배너 | `ad-191x1` | 2048×1071 | ~100% |
| 960×1200 | 구글/카카오 세로 | `ad-4x5` | 1088×1360 | 100% |
| 720×1280 | 카카오 9:16 | `ad-9x16` | 1152×2048 | 100% |
| 1200×600 | 카카오 2:1 | `ad-2x1` | 1600×800 | 100% |
| 1250×560 | 네이버 메인 | `ad-2x1` | 1600×716 | 89.6% |
| 376×220 | 브랜드검색 모바일 | `ad-191x1` | 1832×1072 | 89.5% |
| 456×304 | 브랜드검색 PC | `ad-191x1` | 1608×1072 | 78.5% |

**모든 배정이 축소다. 확대가 필요한 규격은 하나도 없다.** 크롭은 셋뿐이고 나머지 일곱은 `resize` 다.

1200×628 의 「~100%」: 정수 내림 때문에 크롭 비율이 1.9122, 목표가 1.9108 로 0.07% 어긋난다. 최종 리사이즈가 흡수하므로 §5.1 의 「정확히 target」 검사는 통과한다.

**마스터가 다섯이지만 한 번에 다 만들지 않는다.** 고른 규격에서 필요한 마스터만 역산한다. 구글 반응형 필수 2개만 고르면 `ad-1x1`·`ad-191x1` 둘뿐이다.

### 6.3 초판에서 고친 것 둘

1. **`ad-2x1` 이 1216×608 이었다.** 그러면 네이버 메인 배너(1250×560)에 **1.03배 확대**가 필요하다 — §3.2 의 불변식을 설계자가 스스로 어겼다
2. **300×600 을 `ad-2x1` 에 배정했었다.** 그것은 **세로**(0.5)인데 `ad-2x1` 은 가로(2.0)다

둘 다 「그럴듯해 보이는 표」였고 계산을 돌려서야 드러났다. **그래서 배정을 상수로 적어 두지 않는다** — `planDerivation` 이 실행 시점에 계산하고, 시험이 확대 없음을 검사한다.

## 7. 데이터 — 규격을 한 곳에 모은다

`apps/web/lib/ad/specs.ts` (신규)

```ts
export interface AdSpec {
  id: string;
  portal: "naver" | "google" | "kakao";
  /** 광고 상품. 화면에서 묶는 단위. */
  product: string;
  label: string;
  target: { width: number; height: number };
  /** **그 상품을 등록하려면 반드시 있어야 하는가.** 필수/선택을 가르는 유일한 근거. */
  required: boolean;
  format: "jpg" | "png" | "png-alpha";
  /** 포털이 거는 용량 상한. 넘으면 등록이 거부된다. */
  maxBytes?: number;
  /** 주요 요소를 두면 안 되는 가장자리. 미리보기 띠와 크롭 기준에 쓴다. */
  safeArea?: { top: number; right: number; bottom: number; left: number };
  /** 이 수치를 마지막으로 확인한 날. 규격은 자주 바뀐다. */
  verifiedAt: string;
  /** 공식 문서 주소. 확인할 때 여기서 시작한다. */
  source: string;
  note?: string;
}
```

`verifiedAt` 과 `source` 를 필드로 두는 이유: 광고 규격은 **조용히 바뀐다.** 카카오 비즈보드는 2023-12-27 에 1029×222 노출이 끝나고 1029×258 로 바뀌었다. 날짜와 출처가 없으면 언제 것인지 알 수 없다.

**`master` 와 `derive` 는 필드로 두지 않는다.** §6.3 의 이유로 `planDerivation` 이 계산한다.

### 7.1 규격 목록

**구글** — 공식 문서 확인됨

| 상품 | 규격 | 필수 | 용량 | 비고 |
|---|---|---|---|---|
| 반응형 디스플레이 | 1200×628 (1.91:1) | **필수** | 5MB | |
| 반응형 디스플레이 | 1200×1200 (1:1) | **필수** | 5MB | |
| 반응형 디스플레이 | 960×1200 (4:5) | 선택 | 5MB | |
| 반응형 디스플레이 | 1200×300 (로고) | 선택 | 5MB | **업로드** (§3.5) |

로고를 안 넣으면 구글이 기본 아이콘을 넣는다. 등록은 된다.

## 8. 파생 엔진 — 용량을 맞추는 것이 진짜 일이다

`apps/web/lib/ad/export.ts` (신규, `server-only`)

지금 저장 인코더(`image-encoding.ts` 의 `encodeForStorage`)는 **무손실 전용**이다. 광고에는 못 쓴다. (같은 파일의 `makeThumbnail` 은 손실이지만 목록용 규칙이라 용량 상한 개념이 없다.)

| | `encodeForStorage` | 광고 내보내기 |
|---|---|---|
| 목적 | 픽셀 보존 | **용량 상한 준수** |
| 방식 | 무손실 WebP | 손실 JPG/PNG, 품질 이분 탐색 |
| 메타데이터 | 지킨다 | **지운다** |
| 실패 시 | 원본 유지 | 실패를 알린다 |

네이버 GFA 200KB 권장은 **1200×628 크기에서 결코 넉넉하지 않다.** 품질을 이분 탐색으로 낮춰 상한 안에 넣고, 그래도 못 맞추면 **조용히 넘기지 않고 화면에 알린다.**

```ts
export async function exportForAd(
  master: Buffer, spec: AdSpec, plan: DerivePlan,
): Promise<{ bytes: Buffer; quality: number } | { failed: string }>;
```

`limitInputPixels` 를 반드시 건다 — 이 저장소에서 두 번 빠뜨렸던 자리다.

### 8.1 저장하지 않는다

파생물을 **표에 저장하지 않고 내려받을 때 만든다.**

썸네일 작업(2026-09-04~06)에서 파생물을 저장했다가 삭제 경로 네 곳에서 고아 파일이 생겼고, 카드뉴스는 흐름 JSON 안에 자리가 있어 회원 편집과 부딪히는 문제를 여섯 번 고쳤다. 광고 규격은 **작업 하나당 10개까지**다. 같은 실수를 10배로 반복할 이유가 없다.

새 표도, 새 컬럼도, 고아 파일도 없다 — 계약 4가 저절로 지켜진다.

## 9. 화면

지금 `apps/web/app/poster/new-client.tsx:184-196` 은 `POSTER_RATIOS` 9개를 `flex flex-wrap` 으로 늘어놓는다. 줄바꿈은 되지만, 규격 10개를 같은 방식으로 더하면 **무엇이 비율이고 무엇이 광고 규격인지 구분이 안 된다.**

```
┌ 비율 ─────────────────────────────────┐
│  ○ 일반          ● 광고 소재            │   ← 모드 토글
├───────────────────────────────────────┤
│  ☑ 구글 반응형 가로 1200×628    필수    │   ← 필수는 기본 체크
│  ☑ 구글 반응형 정사각 1200×1200 필수    │
│  ☐ 구글 반응형 세로 960×1200    선택    │
│  ☑ 네이버 GFA 배너 1200×628     필수    │
│  ☐ 네이버 메인 1250×560         선택    │
│  ⚠ 카카오 비즈보드 1029×258  — 미지원   │
├───────────────────────────────────────┤
│  만들 그림 2장 · 내보낼 규격 4개         │   ← 비용이 규격 수와 무관함을 보여 준다
└───────────────────────────────────────┘
```

규격이 10개 안쪽이라 **체크박스 한 목록이면 된다.** 초판의 포털 복수 선택 + 상품 그룹핑은 뺐다.

**설계 원칙 넷**

1. **필수는 기본으로 켜 두고, 끄면 경고를 보인다.** 끄는 것 자체는 막지 않는다 — 사용자가 이미 가진 소재를 쓸 수도 있다
2. **「만들 그림 N장」을 항상 보여 준다.** 규격을 10개 골라도 생성은 2~3장이라는 것이 이 기능의 핵심인데, 안 보여 주면 사용자는 10배 과금을 걱정한다
3. **지원 안 하는 규격도 목록에 두고 회색으로 보인다.** 숨기면 「이 시스템은 비즈보드를 모르는구나」가 되고, 보이면 「아직 안 되는구나」가 된다
4. **일반 모드는 지금 그대로 둔다.** 포스터·카드뉴스 사용자에게 광고 UI를 강요하지 않는다

## 10. 단계

각 단계마다 독립 리뷰와 뮤테이션 검증을 거친다(2026-09-04~06 작업에서 이 방식이 화면에 안 보이는 고장을 여러 건 잡았다).

**모든 단계에서 §4 격리 계약이 먼저다.** 계약을 어기는 변경이 필요해지면 그 단계를 멈추고 설계를 다시 본다.

### 0단계 — 격리 자물쇠 (새 기능 코드 0줄)

- `POSTER_RATIOS`·`CARD_RATIOS` 스냅숏 시험
- `IMAGE_MODELS` 는 **의존 필드만** — `id`·`supportedRatios`·`pixelSizeLimits`. **가격표 제외** (§4.1 계약 2)
- 광고 기능이 하나도 없는 지금 상태에서 **먼저 넣는다.** 나중에 넣으면 이미 바뀐 값을 고정하게 된다

### 1단계 — 규격 데이터 · 파생 판단 · 검증 (화면 없음)

- `apps/web/lib/ad/specs.ts` — `AdSpec`, `AD_SPECS`, `AD_MASTERS` (§6·§7). 순수
- `apps/web/lib/ad/derive.ts` — `planDerivation()` (§3.6). 순수
- `apps/web/lib/ad/export.ts` — `exportForAd()` (§8). `server-only`
- `apps/web/lib/ad/check.ts` — `checkAgainstSpec()` (§5.3). `server-only`
- **기존 파일 변경 0곳**

**`packages/sns-core` 가 아니라 `apps/web/lib` 에 두는 이유**: sns-core 는
`src/index.ts` 하나로만 내보낸다(`package.json` 에 `exports` 가 없다). 거기에
`export * from "./ad-specs"` 를 더하면 **계약 1(기존 파일 무접촉)을 어긴다.**
광고 모듈은 앱 안에서만 쓰이므로 `apps/web/lib` 이 맞는 자리다.

**순수 모듈과 `server-only` 모듈을 가른다.** 이 저장소는 `server-only` 를 붙인
모듈을 시험에서 못 부른다 — `grid-thumbnail.ts` / `grid-thumbnail-path.ts` 가
같은 이유로 갈라져 있다.

**자물쇠**: §3.6 의 다섯 + §5.3 의 넷. 용량 시험은 **글자가 많은 실제 시안**으로 한다. 단색 이미지로 시험하면 상한이 늘 통과해 아무것도 검증하지 못한다.

### 2단계 — 내려받기 (생성을 부르지 않는다)

- 라이브러리·결과 화면에 「광고 규격으로 내보내기」 진입점
- 규격을 고르면 파생 → §5.1 검증 → **미리보기 격자(§5.2)** → 내려받기
- 여러 개면 ZIP. **의존성을 새로 붙이지 않는다** — `jszip` 이 이미 있고
  `app/create/PdpEditor.tsx:6`·`app/library/ResultViewer.tsx:153` 의 일괄 내려받기가 그것을 쓴다
- **기존 결과물만 읽는다.** 계약 1·6 이 자동으로 지켜진다

**다만 값이 제한적이다 — 실측했다.**

`1200×1200` 정사각 결과물 하나로 규격 17개를 전부 요청하면 **12개가 나온다.** 못 나오는 다섯:

| 규격 | 왜 |
|---|---|
| `google-rda-logo` | 로고는 업로드 대상이다 (§3.5) |
| `kakao-bizboard` · `naver-smartchannel` | 투명 배경 (§3.4) |
| **`kakao-display-9x16`** (720×1280) | 원본이 세로로 짧다 — 늘려야 하므로 만들지 않는다 |
| **`naver-gfa-main`** (1250×560) | 원본이 가로로 좁다 |

뒤의 둘이 2단계의 한계를 정확히 보여 준다. **정사각 결과물은 정사각 계열만 잘 덮는다.** 세로로 긴 것과 가로로 넓은 것은 그 비율의 마스터를 **생성해야** 나온다 — 그것이 3단계다.

응답 크기도 쟀다: 12장에 원본 합 **6.06MB**, base64 **8.08MB**, 2.6초(정사각 1200 마스터). 규격을 많이 고를수록 응답이 커지므로 화면은 한 번에 다 고르는 것을 기본값으로 삼지 않는 편이 낫다.

**간판 효과는 3단계부터다.**

### 3단계 — 만들기 화면의 광고 모드

- §9 의 UI
- 고른 규격에서 필요한 마스터를 역산해 **기존 `submitPoster` 를** `ratioId: "match-source"` + `sourceSize` 로 부른다 (§4.2)
- 「만들 그림 N장」 표시
- **생성 전에 `planDerivation` 을 먼저 돌려 과금을 막는다** (§4.4)

## 11. 위험과 미결

| | 내용 | 대응 |
|---|---|---|
| **높음** | 네이버 규격이 미검증이다 | 콘솔에서 확인 후 `verifiedAt` 을 채운다. `sourceKind: "reference"` 가 데이터에 그 사실을 남긴다. **브랜드검색 둘을 두 배로 뽑는 판단이 「이상」이라는 읽기에 기대므로 함께 확인할 것.** 소유자와 날짜를 정할 것 |
| **높음** | 규격이 조용히 바뀐다 (비즈보드 1029×222 → 258 전례) | `verifiedAt`·`source` 를 필드로 강제. 6개월 지난 규격은 화면에 「확인 필요」 |
| 중간 | `match-source` 경로라 **비용 추정이 실제보다 낮게** 나온다 (§4.2) | 화면에 「예상」임을 명시. 실제 청구는 요청 행에 남는다 |
| 중간 | 확대 보간이 걸리면 흐려지고 **심사에서 반려**된다 | 마스터를 항상 목표보다 크게. 그럼에도 확대가 필요하면 만들지 않고 실패로 알린다 (§3.2) |
| 중간 | 용량 상한을 못 맞추는 그림이 있다 (글자 많은 디자인) | 조용히 넘기지 않고 실패를 알린다 (§8) |
| 중간 | 크롭하는 셋(1250×560 · 188×110 · 228×152)이 구도를 버린다 | 미리보기로 사람이 본다 (§5.2) |
| 중간 | 요청 하나가 sharp 인코드 20회·4.4초를 쓴다. 넷만 겹쳐도 libuv 스레드풀이 굶는다 | 파생을 한 번만 돌리고 `withRenderSlot`(회원당 1 · 전체 2)으로 동시 실행을 막는다 (§5.2) |

| 낮음 | 구글 「텍스트 20% 이하」 등 심사 정책 | 이 문서는 **규격만** 다룬다. 심사 정책은 별도 |

### 결정이 필요한 것

**둘뿐이고, 둘 다 1단계를 막지 않는다.**

1. **광고에 AI 표기를 넣을 것인가** (§4.3) — 법무·정책 문제. 기본이 off 라 지금은 안 붙는다. 켤 때 정한다
2. **투명 PNG 두 규격(비즈보드·스마트채널)을 언제 할 것인가** (§3.4) — 배너 빌더라는 별도 제품. 이 문서 밖

**이미 정해진 것** (초판에서 미결이던 것들):

- 극단 비율 → **안 A. `gpt-image-2` + `match-source`, 3:1 까지** (§2.3)
- GDN 고정 배너 → **제외.** 전부 선택 규격이고 필수가 하나도 안 늘어난다 (§3.5)
- 크롭 임계선 60% → **삭제.** 근거 없는 숫자였고, 안 A 에서 최저 크롭이 78.5% 라 쓸 자리가 없다
- 시각 모델 검수 → **제외.** 미리보기가 관문이다 (§5.2)
