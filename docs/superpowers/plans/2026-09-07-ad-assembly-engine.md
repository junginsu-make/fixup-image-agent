## 0. 왜 지금 하는가

3단계가 끝난 시점에 **필수 규격 9개 중 7개만 나온다.**

| 필수 규격 | 비율 | 3단계 결과 |
|---|---|---|
| 구글 가로 1200×628 | 1.91:1 | 나옴 (구도 100%) |
| 구글 정사각 1200×1200 | 1:1 | 나옴 (100%) |
| 카카오 정사각 1200×1200 | 1:1 | 나옴 (100%) |
| 네이버 네이티브 1200×1200 | 1:1 | 나옴 (100%) |
| 네이버 이미지 배너 1200×628 | 1.91:1 | 나옴 (100%) |
| 네이버 브랜드검색 모바일 376×220 | 1.71:1 | 나옴 (**89.5%** — 좌우 잘림) |
| 네이버 브랜드검색 PC 456×304 | **1.50:1** | 나옴 (**78.5%** — 좌우 잘림) |
| **카카오 비즈보드 1029×258** | **3.99:1** | **안 나옴** |
| **네이버 스마트채널 750×160** | **4.69:1** | **안 나옴** |

**부분만 나오는 도구는 쓸 이유가 없다.** 사용자는 어차피 다른 도구를 열어야 하고, 그러면 처음부터 거기서 다 만든다.

### 0.1 3단계 설계의 판단이 틀렸다

§3.4 는 이렇게 적었다.

> 투명 배경은 **조립 엔진이 필요해** 아직 지원하지 않는다.

전제가 사실이 아니었다. **그 엔진이 이미 이 저장소에 있다** — 카드뉴스가 쓰는 `apps/web/lib/layout/compose.ts` 다. 3단계를 쓸 때 `packages/sns-core`·`poster-core` 만 보고 `lib/layout` 을 안 봤다.

## 1. 실측 — 이 문서의 모든 주장은 돌려 보고 적었다

3단계 설계에서 **코드를 안 읽고 쓴 문장이 두 번 틀렸다**(§4.2 의 `sourceSize`, §4.5 의 기각 사유). 같은 실수를 반복하지 않기 위해, 이 문서의 핵심 주장은 전부 실행해서 확인했다.

### 1.1 fal 배경 제거 — 우리 계정에서 실제로 됐다

`FAL_KEY` 로 직접 호출했다. **검색 결과가 아니라 실행 결과다.**

```
fal-ai/birefnet/v2         성공  2.2초
fal-ai/imageutils/rembg    성공  2.8초

결과: 2048×1072 PNG · 채널 4 · hasAlpha=true
      알파 최소값 0  ← 진짜 투명 픽셀이 있다
```

두 엔드포인트 다 됐다. `birefnet/v2` 가 더 빠르고 [머리카락 같은 세부에 강하다고 문서가 적는다](https://fal.ai/models/fal-ai/birefnet).

**단가는 아직 모른다** — 이 문서의 미결이다(§9).

### 1.2 조립 — 모델이 못 만드는 3.99:1 이 실제로 나왔다

배경을 지운 오브젝트를 1029×258 투명 캔버스에 얹었다.

```
비즈보드 조립: 1029×258 PNG · 채널 4 · hasAlpha=true
알파 최소=0 (투명)  ·  109KB / 상한 300KB
오브젝트: 237×237 (캔버스 높이의 92%, 오른쪽 정렬)
```

**모델의 3:1 상한이 상관없어진다.** 캔버스는 우리가 만들고, 모델은 그 안에 놓을 물체만 그리면 된다.

### 1.3 모델은 규격 크기를 그대로 못 만든다 (3단계에서 이미 확인)

`sizeFromSource` 에 14개 규격을 그대로 넣어 본 결과 **6개만 일치**한다.

```
1200×628 요청 → 1712×896 이 나온다   (628 이 16의 배수가 아님)
456×304  요청 → 1008×672 가 나온다   (최소 655,360 픽셀 미달)
214×214  요청 → 816×816 이 나온다
```

「각 규격을 모델로 직접 만든다」는 길은 **존재하지 않는다.** 4단계도 마스터 → 파생 구조를 그대로 쓴다.

### 1.5 배경 제거는 **글자를 지운다** — 실측했고, 이것이 설계를 바꾼다

§9 에 「설계를 바꿀 수 있다」고 적어 둔 항목이다. 확인했다. **바꾼다.**

같은 마스터에 `birefnet/v2` 를 돌리고 남은 것을 흰 바탕에 얹어 봤다.

```
남은 불투명 픽셀: 14.7%
남은 것 : 인물 한 명 (손에 든 알약 포함)
사라진 것: 「건강한 선택, 매일의 작은 습관」 헤드라인
          본문 두 줄, 하단 배지 다섯, 바닥 띠 문구
```

**당연한 결과다.** 배경 제거 모델은 「주된 피사체」를 남긴다. 글자는 배경으로 본다.

#### 무엇을 뜻하는가

「마스터에서 오브젝트를 떼어 배너에 얹는다」는 **문구를 잃는다.** 광고 배너에 그림만 있고 글자가 없으면 그것은 광고가 아니다.

#### 그래서 갈래 A 를 다시 쓴다

```
초판(틀림)  마스터 → 배경 제거 → 캔버스에 얹기        ← 문구가 사라진다
개정        마스터 → 배경 제거 → 오브젝트
            + 문구를 **조립 단계에서 다시 얹는다**     ← 글자는 sharp 가 그린다
```

**글자를 그리는 것은 이미 있다.** `compose.ts` 의 텍스트 레이어가 폰트·줄바꿈·크기 맞춤을 한다(§1.4). 조립이 쓸 것은 「모델이 그린 글자」가 아니라 **우리가 그리는 글자**다 — 오히려 그쪽이 낫다:

- 모델이 그린 한글은 자주 깨진다. 광고 심사에서 반려된다
- 규격마다 글자 크기가 달라야 하는데, 파생으로 줄이면 함께 줄어 안 읽힌다
- 문구를 고치려고 다시 생성하지 않아도 된다

#### 대신 새 미결이 생긴다

**문구를 어디서 가져오는가.** 포스터 작업의 `slots.headline` 이 있지만, 그것은 **그림에 그려 넣으라고 모델에 준 말**이라 배너에 그대로 쓸 수 있는지 확인해야 한다. §9 에 올린다.

### 1.4 조립 엔진의 실제 모양

`composeCard(input)` 를 끝까지 읽었다.

```ts
interface ComposeInput {
  size: CardSize;              // { width, height } — 카드 전용 값이 아니다
  slots: LayoutSlot[];         // background | image | logo | text
  copy: CardCopy;              // 글자 원본
  images?: Record<number, Buffer>;
  logos?: Record<number, Buffer>;
  fontDir?: string;
}
```

**쓸 수 있는 것:**
- `size` 가 임의 픽셀이다. 1029×258 을 그대로 넣을 수 있다
- `slot` 넷 중 `image`·`logo`·`text` 가 광고 배너에 그대로 맞는다
- `resize(..., { fit: "contain", background: { alpha: 0 } })` 로 **투명을 이미 쓴다**(`:188`)
- 폰트·줄바꿈·글자 크기 맞춤이 이미 있다

**걸리는 것 하나:**

```ts
// compose.ts:258 — 최종 캔버스
create: { …, channels: 4, background: "#FFFFFF" }   // 흰색 고정
```

투명 캔버스를 만들려면 이 값이 달라야 한다. **그런데 이 파일은 카드뉴스가 쓴다**(§2).

## 2. 격리 계약 — **이 기능 밖으로 새면 안 된다**

3단계는 기존 파일 아홉을 고쳤고 그때마다 문서에 적고 리뷰를 받았다. **4단계의 목표는 0건이다.**

운영자의 지시가 명확하다:

> 배경 없애고 비율 조정하고 그런 것들은 **이 광고소재 리사이징 기능에만** 해당해야 합니다. 다른 시스템에도 영향을 주면 오히려 충돌이 일어나거나 꼬일 수 있습니다.

### 2.1 계약 여섯

| # | 계약 | 어떻게 확인하는가 |
|---|---|---|
| 1 | **`compose.ts` 를 고치지 않는다** | `git diff` 에 그 파일이 없다. 감싸개를 새로 둔다(§4.1) |
| 2 | **배경 제거 모델을 `IMAGE_MODELS` 에 안 넣는다** | `packages/sns-core/src/__tests__/ad-isolation-lock.test.ts` 가 `IMAGE_MODELS` 를 `toEqual` 로 통째로 맞대므로 **모델을 더하면 실제로 깨진다**(리뷰 확인). 넣으면 포스터·카드뉴스의 모델 목록에 뜬다 |
| 3 | **카드뉴스의 슬롯·템플릿을 안 건드린다** | `packages/layout-core` 에 diff 없음 |
| 4 | **스위치 하나를 유지한다** | `AD_EXPORT` 로 4단계도 함께 꺼진다. 새 플래그를 만들지 않는다 |
| 5 | **마이그레이션이 없다** | `supabase/migrations/` 에 파일이 늘지 않음. **`git status` 로도 본다** — `git diff` 는 미추적 파일을 못 잡는다 |
| 6 | **3단계 경로가 안 바뀐다** | 조립을 안 타고 **4-a 의 영향도 안 받는 규격 13개**의 결과 바이트가 같다. 아래 예외 |

#### 계약 6 의 **유일한 예외** — `naver-brand-pc`

초판은 「조립을 안 타는 규격 **12개**」라고 적었다. **수도 틀렸고 계약이 스스로를 어긴다.**

`AD_SPECS` 는 **17개**다. 조립 둘(비즈보드·스마트채널)과 업로드 하나(구글 로고)를 빼면 **14개**다.

그리고 그 14개 중 **하나는 바이트가 반드시 바뀐다** — 4-a 가 `naver-brand-pc` 를 `crop:ad-191x1@78.5%` → `resize:ad-3x2@100%` 로 바꾸는 것이 **4-a 의 목적**이다. 계약 6 을 글자 그대로 읽으면 **4-a 가 계약 위반**이 된다.

**예외를 여기 적어 둔다.** 안 적으면 4-a 를 검증하는 사람이 계약 6 을 근거로 되돌린다.

### 2.2 계약 1을 지키는 방법 — 감싸개

`compose.ts:258` 의 흰 배경이 유일한 걸림돌이다. **고치지 않고 우회한다.**

```
apps/web/lib/ad/assemble.ts        ← 새 파일
  ├ 투명 캔버스를 직접 만든다 (sharp create + alpha 0)
  ├ 오브젝트를 얹는다 (composite)
  └ 글자 레이어를 **새로 쓴다** (약 45줄 — 아래)
```

**왜 `composeCard` 를 통째로 안 쓰는가.** 그 함수는 「흰 카드 한 장」을 전제한다. 광고 배너는 투명 캔버스이고, 슬롯 개념도 더 단순하다(오브젝트 하나 + 글자 몇). 억지로 맞추면 `compose.ts` 를 고치게 되고 그것이 계약 1 위반이다.

#### 글자 그리기는 **부를 수 없다. 다시 쓴다**

초판은 「`compose.ts` 의 텍스트 레이어를 **부르기만** 한다. 이미 export 돼 있다(`textFor`)」고 적었다. **둘 다 틀렸다.**

`compose.ts` 의 public 은 넷뿐이다 — `ComposeInput`(:32) · `ComposeResult`(:46) · `textFor`(:67) · `composeCard`(:194). 글자를 실제로 그리는 **`drawText`(:116)는 모듈 사설**이고 `drawImage`·`drawLogo` 도 마찬가지다.

그리고 `textFor` 는 **픽셀을 한 개도 만들지 않는다.** 원고에서 문자열 하나를 골라 보이지 않는 글자를 걸러 주는 함수다(`:67-71`, `string | undefined`).

그러면 길이 둘인데 하나는 계약 위반이다.

| | 결과 |
|---|---|
| `compose.ts` 에 `export` 를 붙인다 | **계약 1 위반.** `git diff` 에 그 파일이 뜬다 |
| **감싸개가 글자 레이어를 새로 쓴다** | **이쪽이다.** 필요한 조각이 전부 공용 export 다 |

```
packages/layout-core/src/fit.ts:34,53   targetFontSize · fitFontSize
apps/web/lib/layout/fonts.ts:17,31      defaultFontDir · resolveFont
```

**약 45줄의 복제다**(`compose.ts:116-165` 와 같은 모양). 복제가 싫어서 `export` 를 붙이면 **카드뉴스가 쓰는 파일의 공개 표면이 넓어진다** — 그것이 이 단계에서 가장 피해야 할 일이다.

3단계에서 「60줄 복제면 됐다」를 뒤늦게 알고 기각 사유를 고친 적이 있는데, **여기는 방향이 반대다.** 그때는 복제를 과대평가했고 지금은 복제가 정답이다.

### 2.3 계약 2를 지키는 방법 — 엔드포인트 문자열

`FalQueueClient.submitJob(endpoint, input)` 이 **엔드포인트를 문자열로 받는다**(`lib/fal/queue.ts:6`). 모델 목록에 등록할 필요가 없다.

```ts
// lib/ad/background.ts — 광고 경로에서만 쓴다
const BACKGROUND_REMOVAL = "fal-ai/birefnet/v2";
```

#### **그런데 결과는 그 클라이언트로 못 읽는다**

초판이 `queue.ts:6` 의 **인터페이스 선언**만 보고 구현(:30)을 안 봤다. 응답 원본을 찍어 확인했다.

```
fal-ai/birefnet/v2 응답의 키: [ 'image', 'mask_image' ]
data.images = undefined
```

`jobResult` 는 `(data.images ?? []).flatMap(...)` 이다(`queue.ts:33`). birefnet 은 **`image`(단수)** 로 돌려주므로 이 클라이언트는 **예외 없이 빈 배열**을 준다. 던지지도 않는다 — 「배경 제거가 조용히 아무것도 안 돌려주는」 고장이 된다. 이 프로젝트에서 반복된 「화면은 멀쩡한데 보증이 없다」와 같은 모양이다.

**그래서 `lib/ad/background.ts` 는 결과 읽기를 자기가 한다.** `createFalClient` 를 직접 잡고 `data.image.url` 을 읽는다. `jobResult` 를 고치면 카드뉴스·포스터가 함께 영향받으므로 계약 밖이다.

**업로드는 재사용한다** — `lib/fal/upload.ts` 의 `createFalUploader` 는 그대로 쓸 수 있다(실측 확인).

**이 오류가 §1 의 실측을 통과한 이유**: 실측 스크립트가 `client.subscribe()` 를 직접 불렀다. 저장소의 큐 클라이언트를 안 탔다. **「fal 에서 된다」와 「우리 코드로 된다」는 다른 문장이다.**

`IMAGE_MODELS` 는 「사용자가 고르는 그림 모델」의 목록이다. 배경 제거는 사용자가 고르는 것이 아니라 **광고 파생의 한 단계**다. 거기 넣으면 포스터 만들기 화면의 모델 버튼에 「BiRefNet」이 뜬다.

## 3. 무엇을 만드는가 — 두 갈래

### 3.1 갈래 A: 투명 배너 (비즈보드 · 스마트채널)

```
마스터 (기존 3단계 그대로)
   ↓  fal-ai/birefnet/v2
오브젝트 (투명 PNG · 인물만 남는다. 글자는 지워진다 — §1.5)
   ↓  trim + resize(fit: inside)
   ↓  투명 캔버스에 composite
   ↓  **문구를 sharp 로 그려 얹는다**  ← §1.5 에서 추가된 단계
1029×258 PNG-24 (투명)
```

**글자를 우리가 그리는 것이 오히려 낫다** — 모델이 그린 한글은 자주 깨지고, 파생으로 줄이면 함께 줄어 안 읽힌다(§1.5).

**모델의 3:1 상한을 우회한다.** 캔버스가 우리 것이므로 4.69:1 도 만들 수 있다.

[카카오 공식 가이드](https://kakaobusiness.gitbook.io/main/ad/moment/performance/talkboard/content-guide)의 소재 유형이 **「오브젝트형·썸네일형·마스킹형·텍스트형」**인데, 위 경로가 정확히 **오브젝트형**이다.

### 3.2 갈래 B: 3:2 마스터 (브랜드검색 PC)

`naver-brand-pc` 는 456×304 = **정확히 3:2** 다. 지금은 3:2 마스터가 없어 `ad-191x1`(1.91:1)에서 잘라 쓴다 — **구도의 21.5% 를 버린다.**

```
새 마스터 ad-3x2 = 1536×1024   ← 확정. sizeFromSource 가 그대로 돌려준다
   → naver-brand-pc 456×304 을 100% 로 뽑는다
```

**이건 조립이 아니라 마스터 표에 한 줄 더하는 일이다.** 갈래 A 와 독립이라 먼저 해도 된다.

**독립이라는 것을 계산으로 확인했다** — `ad-3x2` 를 넣고 17개 규격의 배정을 전후로 돌렸다.

```
naver-brand-pc   crop:ad-191x1@78.5%  →  resize:ad-3x2 @100%    ← 유일한 변화
나머지 16개       그대로
```

**다른 규격을 조용히 끌고 가지 않는다.** 456×304 가 정확히 3:2 라 crop 이 아니라 resize 가 된다.

**대가**: 그 규격을 고르면 그림이 한 장 더 생성된다. 필수 9개를 다 고르면 마스터가 2장 → 3장이 된다.

### 4.1 새 파일 (기존 파일 0건 목표)

### 4.2 고칠 가능성이 있는 기존 파일 — **각각 근거를 적는다**

| 파일 | 무엇 | 피할 수 있는가 |
|---|---|---|
| `lib/ad/specs.ts` | 비즈보드·스마트채널의 `supply`/지원 여부, `ad-3x2` 마스터, **두 규격의 `note`**(`:181`·`:247` 이 「아직 지원하지 않는다」로 남아 **화면에 그대로 나간다**) | **피할 수 없다.** 규격 데이터가 여기 있다. 다만 광고 전용 파일이라 다른 시스템에 안 닿는다 |
| `lib/ad/derive.ts` | `png-alpha` 를 `unsupported` 로 막는 줄 | **피할 수 없다.** 같은 이유 |
| `lib/ad/batch.ts` | 조립 갈래로 보내기 **+ 마스터별 오브젝트 캐시**(§8) | 같은 이유 |
| **`app/ad/export-rules.ts`** | `specRows` 의 `supported` 판정 | **초판이 뺐다.** 아래 |

#### `master-plan.ts` 는 안 고친다 — **단 조립 갈래가 `master` 를 들어야만**

```ts
// master-plan.ts:56  upload·unsupported 는 여기서 걸러진다
// master-plan.ts:61  const master = AD_MASTERS.find((e) => e.id === plan.master);
// master-plan.ts:65  if (!master) blocked.push({ reason: "마스터를 찾지 못했습니다." });
```

조립 갈래를 `{ kind: "assemble" }` 로만 두면 `:56` 은 통과하고 **`:61` 에서 `plan.master` 가 `undefined` 라 막힌다.** `adSubmitPlan` 이 「하나라도 막히면 전부 막는다」이므로 **비즈보드를 고른 순간 생성 버튼 전체가 잠긴다.**

그래서 **`{ kind: "assemble"; master: string }`** 이다. 조립도 마스터에서 오브젝트를 떼므로 마스터가 필요하고, 그러면 `master-plan.ts` 를 안 고쳐도 된다 — **우연이 아니라 요구사항이다.**

4-d 시험: 「비즈보드를 고른 `adSubmitPlan` 이 `ready: true` 이고 마스터를 돌려준다」.

#### 화면이 조립 갈래를 모르면 **회색으로 남는다**

```ts
// app/ad/export-rules.ts:37
const supported = decided.kind === "resize" || decided.kind === "crop";
```

`derive.ts` 에 조립 갈래를 더해도 **이 줄이 그것을 모른다.** 그러면 두 화면이 비즈보드·스마트채널을 계속 「아직 지원하지 않습니다」로 그리고, `defaultSelection` 이 `row.supported` 로 거르므로 **필수인데 기본 선택에서 빠진다.**

3단계에서 **네 번 반복된** 「판단은 순수 함수로 잘 뽑았는데 그것을 부르는 줄을 안 잠갔다」와 정확히 같은 자리다. 4-d 의 완료 조건에 「조립 갈래가 `supported` 이고 `defaultSelection` 에 든다」 시험을 둔다.

#### **「다른 화면이 import 하지 않는다」는 사실이 아니다**

초판이 그렇게 적었다. 틀렸다. `derive.ts` 를 **`"use client"` 파일 둘이 직접 들인다.**

```
app/ad/ad-export-client.tsx:11    "use client"  →  lib/ad/derive
app/poster/ad-spec-picker.tsx:7   "use client"  →  lib/ad/derive
app/poster/ad-mode.ts             →  lib/ad/master-plan  →  derive
```

즉 `derive.ts`·`specs.ts`·`master-plan.ts` 는 **브라우저 번들 안**이다. 여기에 fal·sharp 가 **한 줄이라도 새면 번들이 깨진다.**

이것이 3단계에서 `poster-service.ts` 가 스위치 하나를 읽으려다 sharp 를 통째로 끌고 온 그 사고와 **같은 구조**다. 초판은 그 사고를 인용하면서 **정반대 결론**을 적었다.

**그래서 `lib/ad/` 를 두 층으로 가른다.**

| 층 | 파일 | 규칙 |
|---|---|---|
| **순수** (클라이언트 그래프) | `specs.ts` · `derive.ts` · `master-plan.ts` · `feature.ts` | **데이터와 계산만.** fal·sharp·`server-only` 금지 |
| **서버** | `background.ts` · `assemble.ts` · `export.ts` · `check.ts` · `batch.ts` | sharp·fal 을 쓴다. 클라이언트가 안 들인다 |

**4-d 의 완료 조건에 시험을 둔다** — `derive.ts` 를 들였을 때 sharp 가 로드되지 않는지. 3단계에서 `feature.ts` 를 뗄 때 쓴 방법(모듈 그래프 시험)을 그대로 쓴다.

**`lib/layout/`·`packages/layout-core`·`packages/sns-core` 에는 손대지 않는다.**

## 5. 어려운 것 — 「어디에 무엇을 놓는가」

파생은 「줄이고 자르기」라 답이 하나다. **조립은 배치를 정해야 한다.**

### 5.1 카드뉴스는 템플릿이 있고, 광고는 없다

`packages/layout-core/src/template.ts` 가 카드 배치를 정한다. 광고 배너용 템플릿은 없다.

### 5.2 1단계는 **가장 단순한 배치 하나**로 시작한다

실측(§1.2)에서 쓴 배치가 그것이다.

```
오브젝트: 캔버스 높이의 92%, 오른쪽 여백 24px, 세로 가운데
왼쪽 여백: 비워 둔다 — 광고주가 나중에 글자를 얹는 자리
```

**왜 이것부터인가.** 비즈보드 오브젝트형의 표준 구도가 「오른쪽 물체 + 왼쪽 여백」이고, 검증할 것이 적다. 글자·로고는 2단계로 미룬다.

### 5.3 §5.2 의 규칙은 **높이만 정해서 위험하다**

초판의 「높이 92% · 오른쪽 여백 24px」은 **폭을 오브젝트 비율에 그대로 끌려다니게 둔다.** 배경 제거로 나온 실제 오브넥트(422×899, 비율 0.469)를 재고 비율만 바꿔 가며 쓸어 봤다.

**비즈보드 1029×258**

| 오브젝트 비율 | 배치 | left | 폭 점유 |
|---|---|---|---|
| 가는 세로 0.25 | 59×237 | 946 | **5.7%** |
| **실측 인물 0.469** | 111×237 | 894 | **10.8%** |
| 9:16 전신 0.56 | 133×237 | 872 | 12.9% |
| **정사각 1.00 ← §1.2 가 쓴 값** | 237×237 | 768 | 23.0% |
| 가로 4.5:1 | 1067×237 | **−62** | 103.7% |
| 가로 6:1 | 1422×237 | **−417** | 138.2% |

`left` 가 음수가 되는 경계: **비즈보드 4.24:1 · 스마트채널 4.94:1.**

**두 방향으로 터진다.**

- **아래쪽** — 세로로 긴 피사체(사람 전신, 병, 튜브형 제품)에서 폭 5~13%. 1029px 배너에 **111px 짜리 물체 하나**가 오른쪽 끝에 붙고 89% 가 빈 투명이다. 「오른쪽 물체 + 왼쪽 여백」이 아니라 **빈 배너에 점 하나**다. §6.2 의 「오브젝트가 사라지지 않았다」는 이것을 **통과시킨다** — 오브젝트는 분명히 있으니까
- **위쪽** — 4.24:1 을 넘으면 `left` 가 음수가 되고 `composite` 가 **조용히 자른다.** §6.2 가 그것을 검사 항목으로 적어 뒀지만, **§5.2 의 규칙 자체가 그 상황을 만든다.** 검사로 잡을 것이 아니라 배치가 애초에 안 만들어야 한다

**§1.2 의 실측이 하필 정사각(폭 23%)이라 이 문제가 안 보였다.** 정사각은 이 분포의 한가운데이고, 배경 제거가 남기는 피사체는 대체로 그보다 세로로 길다 — 마스터가 4:5·9:16 이면 특히.

### 5.4 배치 규칙 — **상자에 맞춘다**

```
상자 = { width: canvas.width − MARGIN*2, height: round(canvas.height * HEIGHT_RATIO) }
배율 = min(상자.height / object.height, 상자.width / object.width)   ← 두 방향 모두
```

`fit: "inside"` 와 같은 계산이다. 초판은 이 중 **높이 항만** 썼다. 고친 규칙으로 같은 격자를 다시 쓸었다.

```
비율 4.5 → 981×218  left 24   폭 95.3%   안전
비율 6.0 → 981×164  left 24   폭 95.3%   안전
넘침: 0건 (전 격자)
```

#### 정해야 했던 둘 — 정한다

**① 오른쪽 여백 24px 은 불변식인가** → **그렇다.** 여백을 지키고 오브젝트를 더 줄인다. 불변식이 하나 늘고 계산이 단순해진다. 여백이 상황마다 달라지면 규격별로 배너가 다르게 보인다.

**② 폭 점유의 하한을 둘 것인가** → **함수는 두지 않는다. 화면이 알린다.**

순수 함수는 숫자만 돌려주고, **폭이 캔버스의 15% 미만이면 §6.2 가 알린다.** 3단계의 `SHRINK_WARNING` 배지(`export-rules.ts:110`)가 이미 같은 모양이라 화면 쪽에 본이 있다.

**왜 잘라서 맞추지 않는가.** 세로로 긴 피사체를 가로로 늘리면 사람이 찌그러지고, 가운데를 자르면 얼굴이나 제품이 잘린다. **둘 다 광고로 못 쓴다.** 사람에게 알리고 다른 마스터를 고르게 하는 편이 낫다.

**15% 의 근거는 약하다.** 실측표에서 정사각 23%, 4:5 가 18.5% 이므로 4:5 까지는 통과하고 9:16 전신이 걸린다. 다만 「무엇이 광고로 보이는가」라 **근거를 못 댄다** — §9 의 카카오 콘솔 확인과 함께 볼 항목이다.

### 5.5 배치 규칙은 순수 함수로 뽑는다

3단계에서 **판단을 컴포넌트 안에 두면 시험이 못 간다**는 것을 네 번 겪었다.

```ts
// lib/ad/layout-rules.ts
export function objectPlacement(
  canvas: { width: number; height: number },
  object: { width: number; height: number },
): { left: number; top: number; width: number; height: number }
```

**시험으로 잠글 불변식 다섯.** 캔버스 둘 × 오브젝트 비율 **격자**로 쓴다 — `derive.ts` 머리말이 「무작위 표본은 경계를 못 잡는다, 격자로 쓸어야 보인다」고 적은 그 방법이다.

| # | 불변식 |
|---|---|
| 1 | `left ≥ 0 && top ≥ 0` |
| 2 | `left + width ≤ canvas.width && top + height ≤ canvas.height` — **§6.2 의 「캔버스 밖으로 안 나간다」를 검사가 아니라 여기서 보증한다** |
| 3 | 비율 보존 — 늘이거나 찌그러뜨리지 않는다 |
| 4 | `height ≤ round(canvas.height * HEIGHT_RATIO)` |
| 5 | **정수만 돌려준다** — `composite` 가 소수를 못 받는다 |

## 6. 검증 — 조립은 파생보다 검사할 것이 많다

### 6.1 기계 검사 (기존 `checkAgainstSpec` 을 그대로 쓴다)

- 픽셀이 정확한가
- **투명 픽셀이 실제로 있는가** — `hasAlpha` 로는 부족하다. `stats().channels[3].min === 0` 까지 본다(3단계 `check.ts` 가 이미 그렇게 한다)
- 용량 상한 (비즈보드 300KB)

### 6.2 조립에만 필요한 검사

| | 왜 |
|---|---|
| **오브젝트가 캔버스 밖으로 안 나간다** | `composite` 는 넘쳐도 조용히 자른다 |
| **오브젝트가 사라지지 않았다** | 배경 제거가 실패하면 **전부 투명한 PNG** 가 나온다. 검사가 없으면 「빈 배너」가 규격 검증을 전부 통과한다. **`trim` 은 방어가 안 된다** — 완전 투명한 800×600 을 `trim({threshold:1})` 에 넣으면 **800×600 이 그대로 나온다**(리뷰 실측). 던지지도, 0×0 이 되지도 않는다 |
| **왼쪽 여백이 실제로 비었다** | 광고주가 글자를 얹을 자리다 |
| **`shrink` 를 조립 항목에서는 비운다** | `batch.ts:167` 이 `sourceWidth / target.width` 로 축소 배율을 내는데, 조립은 줄인 것이 아니라 **조립한 것**이라 그 수치가 거짓이다(2048 마스터 → 비즈보드 1.99). 눈에 보이는 고장은 없다 — 화면이 `SHRINK_WARNING = 4` 를 넘을 때만 배지를 띄우고 조립 규격은 어떤 마스터에서도 4 를 못 넘는다. **그래도 거짓 수치를 들고 다니지 않는다** |
| **오브젝트가 캔버스 폭의 15% 이상이다** | 세로로 긴 피사체는 폭 5~13% 까지 쪼그라든다(§5.3) — 「빈 배너에 점 하나」가 되는데 「오브젝트가 있다」 검사는 통과한다. **막지 않고 알린다**(§5.4) |

| **조립이 실패해도 다른 규격은 나온다** | 실패 지점이 생성 **뒤**로 옮겨간다(§9.3). 하나 때문에 전부 못 받으면 이미 쓴 돈이 통째로 버려진다 |

**두 번째가 제일 위험하다.** 3단계에서 반복된 「화면은 멀쩡한데 보증이 없다」와 같은 부류다.

### 6.3 사람 눈

3단계의 미리보기 화면을 그대로 쓴다. **투명 배경은 체크무늬로 깔아야** 흰 배경과 구분된다 — 안 그러면 투명한지 흰색인지 알 수 없다.

| **4-d** | 배선 (`derive`·`batch` 가 조립 갈래로) · **화면의 `supported` 판정**(§4.2) · **모듈 그래프 시험**(§4.2) · **fal 시한**(§9.2) | `lib/ad/` 2건 + `app/ad/` 1건 |
| **4-e** | 미리보기에 체크무늬 · 「조립됨」 표시 | `app/ad/` 1건 |

**4-a 는 독립이다.** 조립과 무관하므로 먼저 해도 되고, 이것만 해도 필수 하나가 안 잘린다. 계산으로 확인했다(§3.2).

**4-c 와 4-c′ 를 쪼갠 이유**: 글자는 §9 의 「배너 문구를 어디서 가져오는가」가 안 풀리면 못 만든다. **오브젝트 조립은 그것 없이도 끝까지 검증된다.** 막힌 것 하나가 나머지를 붙잡지 않게 한다.

### 9.1 AI 배지가 투명 배너에서 안 보인다 (실측)

3단계 계약 7 은 「파생 뒤에 `markAsAi` 를 다시 태운다」이고 라우트가 그렇게 배선했다(`api/ad/export/route.ts:150`). 조립 결과를 같은 길로 보내면 이렇게 된다.

```
badgePlacement(1029×258) → 58×13 @ (948, 222)
그 자리 raw channels: 1          ← greyscale().raw() 가 알파를 버린다
isBrightCorner: false             ← 전부 0(검정)으로 읽힌다
그 자리 실제 알파: mean 10.4      ← 거의 완전 투명
```

`markAsAi`(`lib/watermark.ts:43-48`)는 구석을 `greyscale().raw()` 로 재는데 **알파가 빠져 「투명 = 검정」으로 읽는다.** 그래서 흰 글자가 유지되고, 결과는 **투명 위의 15% 불투명 흰 글자**다. 카카오 대화목록(밝은 바탕)에 얹히면 보이지 않는다.

**그리고 `checkAgainstSpec` 은 배지 전후 모두 `ok` 였다.** 화면은 「검증 통과」라고 말하고 표기 의무는 조용히 무너진다 — 이 프로젝트에서 반복된 그 부류다.

**답이 될 만한 것 셋** (정해야 한다):
- 투명 캔버스에서는 **알파를 살려 잰다**(알파 가중 평균)
- 배지 자리에 **불투명 판을 함께 깐다**
- 조립 규격은 배지를 **오브젝트 위에만** 놓는다

어느 쪽이든 `watermark.ts` 를 고치면 **계약 밖의 파일**이라 §4.2 에 근거를 적어야 한다. 배지는 기본이 off 라 지금 당장 터지지는 않지만, 켜는 날 조용히 무너진다.

### 9.2 fal 대기가 CPU 게이트를 쥔다 (실측)

라우트가 `withRenderSlot(userId, () => exportBatch(...))` 이다(`route.ts:150`). 게이트는 **회원 1 · 전체 2** 이고 머리말이 「지키는 자원은 libuv 스레드풀」이라고 못 박는다.

조립을 `exportBatch` 안에 넣으면 그 슬롯 안에서 **네트워크**가 흐른다.

```
업로드 + birefnet 2.6초 + 결과 내려받기 ≈ 5초
기존 sharp 2.6초에 얹히면 한 요청이 8초 가까이 전체 슬롯 2 중 하나를 잡는다
```

카드뉴스 미리보기가 훨씬 자주 429 를 받는데 **그동안 스레드풀은 논다.** 게이트가 지키기로 한 자원과 실제로 쥐는 자원이 다르다.

**더 나쁜 것: fal 쪽에 타임아웃이 없다.** `createFalQueueClient`·`createFalUploader` 둘 다 `retry: { maxRetries: 0 }` 뿐이고 폴링 상한이 없다. fal 이 안 끝나면 **그 회원의 슬롯이 영구히 잠긴다**(`PER_USER_LIMIT = 1` 이라 본인은 재시도조차 못 한다).

**정해야 할 것 둘**: (a) 배경 제거에 절대 시한(예: 60초) — 넘으면 그 규격만 실패, (b) fal 대기 구간을 슬롯 밖으로 뺄 것인가.

### 9.3 「과금 전에 막는다」가 조립에서 무너진다

3단계는 `planMasters`/`adSubmitPlan` 으로 **생성 전에** 막았고, `master-plan.ts` 머리말이 그 이유를 「생성이 먼저라 파생 실패 = 이미 과금된 생성이 쓸모없어짐」으로 적었다.

조립이 열리면 비즈보드·스마트채널이 고르는 자리에서 `ready` 가 된다. 그런데 **실제 실패 지점은 생성 뒤의 배경 제거로 옮겨간다.** 배경 제거가 될지는 그림을 봐야 알므로 생성 전에 걸러낼 방법이 없다.

**최소한 이것은 §6 의 보증에 넣는다**: 조립이 실패해도 **다른 규격은 그대로 나오고**, 무엇이 왜 빠졌는지 말한다. `exportBatch` 가 이미 규격별 `status: "failed" + reason` 구조라 그릇은 있다. 남은 「높음」 셋은 전부 **바깥에서 확인해야 하는 것**이다 — fal 대시보드, 카카오·네이버 광고주 콘솔. 코드로는 못 푼다.

## 10. 이 문서가 3단계에서 배운 것

| 3단계에서 틀린 것 | 4단계에서 하는 것 |
|---|---|
| 「조립 엔진이 없다」 — 코드를 안 읽고 단정 | §1.4 에서 그 엔진을 끝까지 읽고 인용 |
| `sourceSize` 공급 경로를 안 세고 「무접촉 가능」 | §2 의 계약마다 **확인 방법**을 적음 |

| 판단을 컴포넌트 안에 둠 (네 번 반복) | §5.3 — 배치 규칙을 순수 함수로 |
| 검색과 실측을 안 가름 | §9 에서 갈라 둠 |
| **「돌려 봤다」와 「코드를 읽었다」를 안 가름** | **이 문서가 또 그랬다.** §1 은 전부 재현됐는데(리뷰 확인) **CRITICAL 둘이 §2 에서 나왔다** — `textFor` 가 픽셀을 만드는 줄 알았고, `jobResult` 를 구현 안 보고 인용했다. 실측은 「fal 에서 된다」를 증명하지 저장소 코드로 된다를 증명하지 않는다 |
