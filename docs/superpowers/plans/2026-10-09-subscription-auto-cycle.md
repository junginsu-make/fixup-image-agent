# 월 구독 배정 = 크레딧 지급, 매달 자동 갱신

2026-10-09 사용자 결정:
1. 관리자가 월 구독을 배정하면 **그 자리에서** 플랜만큼 크레딧이 들어간다
2. 구독이 켜져 있는 동안 **매달 자동으로** 다시 들어간다 (「결제 확인」 없이)
3. 구독 크레딧은 **배정한 날부터 한 달** 쓸 수 있다 (말일 소멸 아님)

## 지금 (바꾸기 전)

- 배정(`credit_admin_subscription`)은 플랜만 붙인다. 크레딧은 관리자가 그 달 「결제 확인」
  (`credit_admin_confirm_period`)을 눌러야 `subscription_periods` 한 줄이 생기고,
  회원 잔액을 읽을 때(`credit_ensure_paid_period`) 지급 lot 가 된다.
- 기간은 그 달 1일~말일(한국 시간). 25일에 배정하면 75크레딧을 6일만 쓴다.
- 운영: 구독 중인 회원 0명, 결제 기간 0줄 (2026-10-09 조회) — 옮길 데이터가 없다.

## 바꾸는 것

### 1단계 · DB (새 마이그레이션 `202610090001_subscription_auto_cycle.sql`)

- `user_subscriptions.assigned_by uuid` 칸 추가 — 자동 기간의 `confirmed_by` 로 쓴다(배정한 관리자).
- 새 함수 `credit_subscription_cycle(p_user)`:
  - 구독이 `active` 이면, 배정 시각부터 센 **지금 주기** `[시작 + n달, 시작 + (n+1)달)` 를 구한다.
    n 은 늘 처음 배정 시각에서 센다(1/31 → 2/28 → 3/31, 밀리지 않음).
  - 그 주기의 `subscription_periods` 한 줄을 넣는다 — 크레딧 = 플랜 월 크레딧, 금액 = 플랜 가격,
    `source_key = 'auto-cycle:<회원>:<n>'` 이라 몇 번 불러도 한 번만 들어간다.
  - 해지·중단이면 새 주기를 만들지 않는다. **이미 들어간 주기는 끝날 때까지 쓴다**(약관의 「결제한 주기가 끝날 때 해지」와 같다).
  - 회원이 몇 달 안 들어와도 **지금 주기 하나만** 만든다(지난 주기는 이미 끝나 쓸 수 없다).
- `credit_ensure_paid_period` 가 맨 앞에서 위 함수를 부른다 → 잔액 조회·생성 예약 때 자동 갱신.
- `credit_admin_subscription`:
  - 새로 배정하면 시작 시각 = 지금, `assigned_by` 기록, **바로 첫 주기를 지급**.
  - **같은 플랜을 다시 눌러도 시작 시각을 바꾸지 않는다** — 안 막으면 누를 때마다 크레딧이 또 나간다.
  - 다른 플랜으로 바꾸면 새 플랜으로 새 주기를 시작한다(아래 「정할 것」).
- `credit_admin_confirm_period`(수동 결제 확인)는 **새 기간을 만들지 않게 막는다** — 자동과 겹치면 두 번 지급된다.

### 2단계 · 관리자 화면·회원 화면·설명서

- 회원 관리: 「2. 결제 확인·월 크레딧」 칸과 버튼을 없애고, 배정 안내를
  「배정하면 바로 ○크레딧이 들어가고, 구독이 켜져 있는 동안 매달 배정일에 다시 들어갑니다」로.
- 시스템 → 구독 플랜 안내, 일괄 배정 바 안내, 확인 카드 문구를 같은 뜻으로.
- 회원 구독 카드: 「이번 달 결제 확인」 대신 **이번 주기(시작~끝)와 다음 지급일**.
- 설명서 `guide/account`·`guide/credits`: 「그 달 말일」「결제 확인해야 들어온다」→ 「배정일부터 한 달, 매달 자동」.
  → 배포 뒤 도우미 색인 다시 넣기.
- `packages/shared/credit-policy.ts` `subscriptionExpiresAt`: 다음 달 1일 → 지급 시각 + 1달.

### 3단계 · 약관

제5조「결제 주기는 매월 1일부터 말일까지 … 결제를 확인한 뒤 지급」,
제6조「지급된 달의 말일까지 … 달 중간에 지급된 경우에도 그 달 말일에 소멸」을
「결제 주기는 구독을 시작한 날부터 한 달 … 주기마다 지급」「주기가 끝나는 날까지」로 고친다.
시행일과 변경 내용 줄을 새로 단다. (회원에게 유리한 쪽 변경 — 쓸 수 있는 기간이 늘어난다.)

## 시험

- DB: 로컬 Postgres 시험(`scripts/tests/*.test.mjs`, `testPostgres`)으로 — 배정 즉시 지급,
  같은 플랜 다시 누름 = 추가 지급 없음, 한 달 뒤 자동 지급, 1/31 시작 주기, 해지 뒤 새 주기 없음·남은 주기 사용,
  수동 결제 확인 막힘, 여러 번 불러도 한 번만.
- 앱: 문구·화면 시험, `pnpm -r typecheck`, 전체 web 시험, `check:cost-forecast`.
- 독립 검토(DB 변경은 database-reviewer 도).

## 배포 순서

1. PR 검사 통과 → 머지
2. **마이그레이션 SQL 을 Supabase SQL Editor 에서 먼저 실행** (사용자가 붙여 넣기 — 앱 설정에 Supabase DB 접속 주소가 없다)
3. 앱 배포 → 확인 → 개발 일지 → 도우미 색인

## 주의

- 같은 Supabase 를 별도 상세페이지 제품(detail-page-studio)도 본다. 바뀐 `credit_ensure_paid_period` 는
  그쪽 예약에서도 불린다 — 구독이 있는 회원에게 같은 지갑이므로 같은 동작이 맞다. 함수 이름·인자는 그대로 둔다.
- 결제 수단이 없으므로, 입금이 끊긴 회원은 관리자가 「해지」나 「중단」을 눌러야 다음 주기가 멈춘다.

## 정할 것 (사용자)

- **구독 중에 다른 플랜으로 바꾸면** 이전 플랜의 남은 크레딧을: (가) 그대로 두고 새 플랜 크레딧을 더 준다 / (나) 남은 것은 거둬들이고 새 플랜 크레딧만 준다.
