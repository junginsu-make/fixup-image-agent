## 작업 공간과 완료 범위

생성 오류 5건과 서버 문서 저장 S1~S6을 구현했다. 서버 저장을 켜면 사진/글 입력,
기획, 원본 사진, 대표 이미지, 결과 이미지, 편집 레이어, 설정을 다른 브라우저에서
복원할 수 있다. 원본 바이트는 재인코딩하지 않는다. 복원 때 SHA-256·크기·형식을 검사한다.

두 창의 늦은 저장은 사본으로 남고 주소도 사본으로 바뀐다. 같은 창의 저장·보관·복원은
순서대로 실행한다. 미저장 생성 결과를 되찾을 때도 원본을 덮지 않고 복구 사본을 만든다.
이전 버전을 고르면 같은 문서에 새 버전으로 저장한다. 최근 이전 버전 20개를 남긴다.

## 인계 설계에서 구체화한 사항

- 서버 전송 형식은 schemaVersion 3의 메타데이터·자산 목록·body로 나눈 저장용 봉투다.
  body는 기존 v3 필드를 보존하고 이미지 칸만 참조로 바꾼다. 기존 화면 상태를 전면 교체하지 않았다.
- 파일은 별도 비공개 `pdp-documents` 버킷을 쓴다. 회원에게 직접 쓰기 정책을 만들지 않는다.
  소유 경로를 서버가 만들며 서명 업로드에 upsert를 허용하지 않는다.
- 라이브러리 표를 비동기 생성 완료 순서로 갱신하지 않는다. 승인된 서버 문서의 현재 버전을
  기존 라이브러리 읽기 API에도 반영한다. 같은 초안의 이전 결과 항목은 목록에서 중복 제거한다.
  섹션 삭제/재기획은 문서 ID를 바꾸지 않고 이전 버전으로 보존된다.
- 초기 저장 완료 전에는 서버 문서의 편집기 생성을 열지 않아 문서 번호가 중간에 바뀌는 경쟁을 막는다.
- 삭제 뒤에는 본문·이전 버전을 지우고 식별 표시를 남겨 오래된 창의 재저장을 거절한다.
- 로컬 개발에서만 20MiB 파일을 받을 수 있도록 Next 본문 상한을 24MB로 둔다.
  운영에서는 Storage로 직접 올리므로 기존 16MB 상한을 유지한다.

재생성의 이미지 제공자는 시험 응답으로 대체했다. 유료 AI를 호출하거나 운영 데이터를
사용하지 않았다. 스크린샷·결과는 `%TEMP%\pdp-claude-final-evidence`에 있다.

해당 수정을 제거하면 실패하는 것을 확인하고 복원했다. 직접 리뷰 중 저장/복원 동시
실행으로 불필요한 사본이 생기는 결함도 별도 실패 시험을 만든 뒤 고쳤다.

## 재실행

프로젝트 루트에서 다음 스크립트를 사용할 수 있다.

- `node scripts/tests/pdp-server-boundary.mjs` — 생성 검증 사본과 비교.
- `node --test scripts/tests/pdp-documents-sql.test.mjs` — `PDP_PGLITE_MODULE`에 로컬 PGlite 모듈 URL 필요.
- `node scripts/tests/pdp-documents-browser.mjs` — localhost:3117의 개발 서버 필요.
  서버에는 `LOCAL_STORE=1`, `LOCAL_AUTH_BYPASS=1`, `PDP_SERVER_DOCUMENTS=1`,
  `PDP_JOBS_ENABLED=0`을 주고 `LOCAL_STORE_ROOT`는 테스트 전용 디렉터리로 지정한다.

SQL 검증 도구는 `%TEMP%\pdp-sql-check`에만 설치했다. 저장소 의존성이나 lockfile은 바꾸지 않았다.

## 아직 하지 않은 것

- 커밋·푸시·master 병합·배포·운영 SQL 실행.
- 운영 Supabase의 실제 업로드·RLS·용량/전송량 한도 확인.
- 운영 AI를 이용한 최종 생성 확인 및 Linux 배포 빌드.
- 다른 사람/에이전트의 독립 리뷰.
- 리디자인 서버 저장, 기존 테이블의 경로 보안, 기존 브라우저 revisions/assets 정리.

운영 적용 SQL은 `supabase/migrations/202610030001_pdp_documents.sql`이다.
사용자가 검토·승인 후 운영에서 직접 실행한다. 새 기능은 기본값 0으로 꺼져 있다.
진단 커밋을 포함한 생성 수정부터 통합하고, 캐릭터 작업 및 현재 master와의 차이를
확인한 뒤 배포 절차를 진행해야 한다. 현재 운영 SHA는 이번 작업에서 재조회하지 않았다.

이전 버전에서만 쓰던 자산과 중단된 업로드의 고아 파일 정리는 인계 범위대로 후속이다.
삭제와 이미 발급된 업로드 서명의 완료가 겹쳐 남는 파일도 그 정리 정책에 포함해야 한다.
