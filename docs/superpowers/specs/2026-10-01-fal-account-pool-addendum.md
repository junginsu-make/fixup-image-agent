## 0. 한 줄

비유: 계산대가 여러 개인 가게. 손님(그림 한 장 제출)이 오면 **줄이 가장 짧은 열린 계산대**로 보낸다. 한 계산대가
멈추면(한도·잔액·키 오류) 손님을 **곧바로 옆 계산대로** 옮긴다 — 손님은 모른다. 모두 꽉 찼을 때만 「잠시 뒤 다시」.
영수증(fal 요청 번호)에 어느 계산대였는지 적어 두어, 결과는 **같은 계산대에서** 찾는다. 계산대가 하나도 없으면
지금처럼 서버 키(`FAL_KEY`) 하나로 판다.

먼저(S3a) 남은 **동기 호출**(`fal.run`, 한도를 넘으면 곧바로 429)을 대기열 제출 + 상태 확인으로 바꾸고, 그다음(S3b)
계정 풀과 관리자 화면을 붙인다. 두 단계는 따로 배포한다.

## 1. 사용자 결정 (2026-10-01, 그대로)

| # | 결정 |
|---|---|
| U1 | 관리자 화면 「fal 계정」: 이름(구분용, 예 「fal-1 (ai.dev 계정)」) · API 키(입력 때 한 번만 보이고 그 뒤로는 **끝 4자리만**) · 사용 켜기/끄기(끄면 새 작업 없음, 진행 중은 끝까지) · 동시 한도(기본 20, 고칠 수 있음) · 상태(진행 중 수, 마지막 오류 종류와 시각: 키 오류 / 잔액 소진 / 한도) |
| U2 | 자동 배정: 새 제출마다 **켜진 계정 중 여유가 가장 큰 곳**. 429·한도, 잔액 소진, 키 오류면 그 계정을 쉬게/막고 **같은 제출을 곧바로 다음 계정으로**(사용자는 실패를 못 봄). 모두 차면 「잠시 뒤 다시」. 잔액·키 오류는 관리자 메일(기존 감시·SMTP 길, `ALERT_EMAIL`) |
| U3 | 제출한 작업은 **보낸 계정으로** 묻는다(작업마다 계정 기록). 키를 바꾸거나 꺼도 진행 중 작업은 깨지지 않는다. 진행 중이 있는 계정은 지울 수 없다 |
| U4 | 등록된 계정이 없으면(표가 비면) 지금처럼 서버 `FAL_KEY` — 배포 첫날 생성이 멈추면 안 된다 |
| U5 | 보안: 키는 AES-256-GCM(추가 인증 데이터 = 계정 id)으로 잠가 저장, 열쇠는 **새 서버 환경변수**. 열쇠가 없으면 풀을 끄고 `FAL_KEY` + 경고(죽지 않음). 키는 브라우저로 가지 않는다. 관리자만(두 명 모두, `profiles.role='admin'`·active). 변경은 `credit_admin_events` 에(`fal_account_add/update/disable/delete` 등). 저장 때 **싼 요청 한 번**으로 키 확인 |
| U6 | 동기 fal 호출(`lib/pdp/fal.ts`, `lib/redesign/image-generator.ts` 등)을 대기열 제출 + 상태 확인으로. 화면의 기다림·응답 모양과 크레딧·비용·정산 계약은 그대로 |

## 3. 본 설계(§3.3)에서 정해지거나 바뀐 것

| 항목 | 본 설계 §3.3 | 이 보충 | 까닭 |
|---|---|---|---|
| 순서 | 「먼저 동기 호출을 없앤다」 | **S3a**(동기 → 대기열, 키는 `FAL_KEY` 하나) → **S3b**(계정 풀 + 관리자). 각각 배포 | 429 를 없애는 쪽이 먼저 효과가 크고, 풀 없이도 독립으로 낼 수 있다 |
| 동시 한도의 뜻 | 「부드러운 상한, 공정 분배·대기 표시에만」, `IN_QUEUE` 가 보이면 자동으로 낮춤 | **우리 쪽에서 센 진행 중 수가 한도에 닿으면 그 계정에 새로 보내지 않는다.** 모든 켜진 계정이 차면 「지금 이미지 생성이 몰려 있습니다. 잠시 뒤 다시 시도해 주세요.」(429). **자동으로 낮추기는 하지 않는다**(S7 재측정 뒤 다시 본다) | 사용자 결정 U2. 자동 낮추기는 결정 목록에 없고, 같은 계정을 쓰는 영상 서비스 몫은 관리자가 한도에서 빼 넣는다(화면에 적음) |
| 진행 중 | — | `fal_requests` 에서 끝나지 않았고 잡은 지 **30분 이내**인 줄 | 포스터는 화면이 물을 때만 결과를 가지러 가서(`lib/running-jobs.ts`), 창을 닫으면 「끝남」을 영영 못 적는다. 30분은 카드뉴스가 fal 상태를 포기하는 시간(`QUEUE_GIVE_UP_MS`)과 같다 |
| 켜진 계정이 없을 때 | 「표가 비면 `FAL_KEY`」 | 표가 비었거나 **켜진 계정이 하나도 없으면**(모두 꺼짐·모두 키를 풀 수 없음) `FAL_KEY`. 이때는 DB 에 칸을 잡지 않는다 | U4. 「모두 끔」을 생성 멈춤으로 쓰지 않는다 — 멈춤은 「AI 전체 멈춤」 스위치가 한다 |
| 켜진 계정이 다 막혔을 때 | — | 「잠시 뒤 다시」. `FAL_KEY` 로 새지 않는다 | 첫 계정은 지금의 `FAL_KEY` 로 등록한다(본 설계) — 막힌 그 키로 다시 보내는 셈이 된다. 막힘은 메일로 알렸다 |
| 열쇠가 없을 때 | 「행이 있는데 열쇠가 없으면 조용히 돌아가지 않고 알린다」 | 풀을 끄고 `FAL_KEY` 로 만든다(U5) + **행이 있으면** 서버 기록 한 줄과 관리자 메일 한 통. 관리자 화면에 빨간 경고, 등록·키 바꾸기 단추 잠금 | 둘을 함께 지킨다 — 멈추지 않되 조용하지 않다 |
| 어느 계정으로 보냈나 | 「요청(시도)마다 기록」 | 새 표 `fal_requests`(fal 요청 번호 → 계정). 포스터·카드뉴스의 기존 기록 모양은 **안 바꾼다** — 요청 번호로 찾는다. 기록이 없으면 `FAL_KEY`(풀 이전 요청) | 기존 JSON 기록 모양을 바꾸면 화면·정산 코드 여러 곳이 함께 움직인다. 번호는 fal 전체에서 겹치지 않는 UUID 다 |
| 키 바꾸기 | 언급 없음 | **진행 중이 있으면 거절**(지우기와 같다). 화면: 「먼저 사용을 끄고 진행 중이 0 이 되면」 | U3 「키를 바꿔도 진행 중은 안 깨진다」 — 다른 fal 계정의 키로 바뀌면 진행 중 요청을 더는 물을 수 없다 |
| 지우기 | 「진행 중 요청이 참조하는 계정은 지울 수 없다」 | 같다 + **행은 남기고 키를 비운다**(이름은 다시 쓸 수 있다) | 지난 요청이 어느 계정이었는지 남긴다 |
| 변경 기록 | 「변경 기록 표 따로」 | 새 표 없이 `credit_admin_events`(액션 `fal_account_add`·`_update`·`_enable`·`_disable`·`_key`·`_check`·`_delete`, 암호문은 싣지 않음) | U5. AI 멈춤 스위치(C4)와 같은 표 |
| 재암호화 스크립트 | 「`key_version` 칸과 재암호화 스크립트」 | `key_version` 칸만 둔다. 열쇠 회전은 **키 다시 넣기**(`DEPLOY.md` 「fal 계정 풀 열쇠」) | 계정이 몇 개뿐이라 스크립트(옛·새 열쇠를 함께 다루는 운영 도구)보다 화면에서 다시 넣는 쪽이 안전하다 |
| 확인(무료 요청) | 「잔액 소진 잠김은 드러나지 않는다 — 화면에 적는다」 | 같다(§2 실측 근거) | — |
| 제출 방식 | — | 제출만 `fetch` 한 번(`POST https://queue.fal.run/<엔드포인트>`), 상태·결과·취소는 공식 클라이언트(계정마다 인스턴스) | §2: 공식 제출은 같은 키로 3번 재시도해 「곧바로 다음 계정」이 안 된다 |
| 비용 한 줄 | 제출 자리 | **한 곳**(`lib/fal/http.ts` 의 제출)에서. 상세페이지·리디자인도 이제 제출 시점에 적는다 — fal 이 결과에서 거절(422)한 장도 한 줄 남는다(포스터·카드뉴스는 이미 그렇다). fal 요청 번호가 unique 라 두 번 안 적힌다 | ai-control §3.4 「fal 큐 작업은 제출 시점에」 |
| 기다림 | — | 화면이 기다리는 요청 안에서 상태를 묻는다 — 만드는 중이면 1초, fal 줄에 서 있으면 3초(S3a 최종 리뷰: 100명이 몰려 대부분 줄에 있을 때 상태 확인이 진행 중인 장수만큼 초당 쌓인다). fal 쪽 대기 상한 120초, 우리 쪽 상한 300초(넘으면 취소 한 번 보내고 실패). 배경 제거는 60초·0.5초 | 300초는 지금 동기 호출의 사실상 끝(Node `fetch` 머리 대기 300초)과 같다. 1초 폴링은 장당 지연을 1초 안쪽으로 둔다 |
| 실패를 어떻게 읽나 | 「429·일시 오류는 기다렸다 다시, 계정 잠김·키 무효는 그 계정을 빼고」 | 표 §4.2 | — |

## 4. 동작

### 4.1 데이터 (`supabase/migrations/202610010001_fal_account_pool.sql`, 새 표·새 함수만)

- `fal_accounts` — id(앱이 만든 UUID, 암호화의 추가 인증 데이터), 이름(살아 있는 것끼리 유일), 암호문·IV·태그(base64), `key_version`,
  끝 4자리, 사용, 동시 한도(1~200, 기본 20), 상태(`ok`·`rate_limited`·`locked`·`invalid`·`decrypt_failed`), 쉬는 끝 시각,
  마지막 오류(종류·시각·원문 300자), 만든·바꾼 사람·시각, 지운 시각. RLS 켬, anon·authenticated 회수
- `fal_requests` — 제출(시도)마다 한 줄: 계정, 엔드포인트, fal 요청 번호(unique, 제출 전엔 비어 있음), 잡은 시각, 끝난 시각
- 함수(서버 권한만): 칸 잡기(짧은 잠금 하나로 줄 세움, 남은 칸이 가장 큰 계정) · 번호 붙이기 · 칸 돌려주기 · 끝남 ·
  계정 표시(상태가 **이번에** 바뀌었으면 참 — 메일 한 번) · 관리자 등록·설정·키 바꾸기·다시 확인·지우기(모두
  `credit_require_admin` + `credit_admin_events` 한 줄) · 관리자 목록(암호문 없음)·변경 기록

### 4.2 제출 하나

1. 켜진 계정이 없으면 → `FAL_KEY` 로 제출(오늘과 같다, DB 안 봄)
2. 칸 잡기 → 없으면 「잠시 뒤 다시」(429)
3. 그 계정 키로 제출
   - 성공 → 번호를 붙이고(3번 시도, 실패해도 같은 프로세스는 메모리로 찾는다) 돌려준다. 비용 한 줄
   - 실패 → 칸을 돌려주고, 아래 표대로. 계정 탓이면 **이번 제출에서 그 계정을 빼고 2번으로**

| fal 응답 | 뜻 | 계정 | 메일 | 다음 계정으로 |
|---|---|---|---|---|
| 429 | 한도 | `rate_limited`, 60초 쉼(그 뒤 제출이 되면 `ok`) | 없음 | 옮김 |
| 401 | 키 오류 | `invalid`(관리자가 키를 바꾸거나 「다시 확인」할 때까지 뺌) | 상태가 바뀐 첫 번 | 옮김 |
| 403 + 본문에 lock·balance·credit·exhaust·billing·payment | 잔액 소진 | `locked`(위와 같다) | 첫 번 | 옮김 |
| 그 밖의 403 | 권한 거절 | `invalid` | 첫 번 | 옮김 |
| 422·400 | 내용 거절 | 그대로 | 없음 | **안 옮김** — 다른 계정도 같다 |
| 5xx·네트워크 | fal 장애 | 그대로 | 없음 | **안 옮김** — fal 이 이미 받았을 수 있어 두 번 과금될 수 있다 |
| 키를 풀 수 없음 | 열쇠가 바뀜·값 손상 | `decrypt_failed`(목록 읽을 때) | 첫 번 | 그 계정은 처음부터 빠짐 |

### 4.3 묻기·끝내기

- 같은 프로세스가 보낸 요청은 메모리에서, 아니면(재시작 뒤·다른 프로세스) `fal_requests` 에서 계정을 찾는다. **꺼진 계정도**
  묻는 데는 쓴다. 기록이 없으면 `FAL_KEY`. 계정이 지워졌으면 410(「만든 그림이 남아 있지 않습니다」 쪽 안내)
- 끝(성공·실패·포기·상한 초과)이면 「끝남」을 적는다. 상세페이지·리디자인·캐릭터·배경 제거는 요청 안에서, 포스터·카드뉴스는
  상태 조회가 `completed` 를 볼 때
- 참고 그림 올리기는 켜진 성한 계정 키로(올린 주소는 공개라 다른 계정의 제출에도 쓴다), 없으면 `FAL_KEY`

### 4.4 관리자 화면 (`/admin/system` 「fal 계정」 카드, AI 사용 비용 카드 아래)

- 등록: 이름·API 키(가려진 칸, 자동 완성 끔)·동시 한도 → **무료 확인 한 번** → 통과하면 계정 id 로 잠가 저장. 원문은 서버 액션
  안에서만 산다(주소·기록·오류 문구에 없음). 「확인하고 등록」
- 목록: 이름 · `····끝4자리` · 사용/꺼짐 · 상태 · 진행 중 n / 한도 · 마지막 오류(종류·한국 시각·원문 앞부분)
- 단추: 저장(이름·한도) · 사용 끄기/켜기(확인 창) · 다시 확인 · 키 바꾸기(진행 중 0 일 때만) · 지우기(진행 중 0 일 때만, 확인 창)
- 열쇠가 없으면 빨간 경고 + 등록·키 바꾸기·다시 확인 잠금
- 변경 기록 최근 20줄(시각·누가·무엇·계정 이름)
- 한계 문구: 확인은 무료 요청이라 잔액 소진은 실제 생성에서만 드러남 · 꺼도 진행 중은 끝까지 · 한도는 실제 fal 한도보다
  크게 넣지 말 것(영상 서비스와 같은 계정이면 그 몫을 빼고)

## 5. 바뀌지 않는 것 (계약)

- **비용**: `ai_cost_events` 한 줄은 제출 자리, fal 요청 번호 unique(ai-control §3.4). 배경 제거는 지금처럼 `onEnqueue` 에서
- **AI 멈춤**: `credit_reserve` 의 `ai_paused`, 카드뉴스 상태 조회의 멈춤 → 기존 중지 경로(`stopQueuedGeneration` + 정산). 둘 다
  fal 길 밖이라 그대로다(카드뉴스 상태 조회는 `FalQueueClient` 모양만 쓴다 — 모양은 같다)
- **크레딧·정산**: 상세페이지 생성기 모양(한 장 → base64)과 오류 코드(`AI_QUOTA_EXCEEDED`·`PDP_IMAGE_GENERATION_FAILED`·
  `AI_KEY_MISSING`), 리디자인 오류 문구, 포스터 `classifyFalFailure`(상태 코드로 가름) — 모두 같은 말로 남는다. 「잠시 뒤 다시」는
  429 를 실어 기존 「몰렸다」 길로 간다
- `FAL_KEY` 는 S3 동안 **계속 필요하다**(대체 길, 옛 요청, 카드뉴스·포스터의 키 확인 `requireSnsProviderKeys`·`requireKeys`,
  `/api/health/ready`)

## 6. 하지 않는 것

- 동시 한도 자동 낮추기(§3 표), 계정별 하루 지출 상한, fal 잔액 조회(운영 키 권한 없음)
- 재암호화 스크립트(§3 표)
- 작업 접수 방식(S4) — 상세페이지는 여전히 화면이 기다리는 요청 안에서 만든다. 재시작에 이어지는 것은 S4 다
- 리디자인·캐릭터의 서버 전체 동시 수 상한(본 설계 §4 의 S5)
- 웹 프로세스 여럿·배치기에서의 메모리 공유(칸 세기는 처음부터 DB 가 하므로 그때도 맞다)

## 7. 위험

| 위험 | 대비 |
|---|---|
| 맞는 운영 키가 확인 요청에 404 가 아닌 다른 값을 받는다 | 확인 규칙은 「401·403 만 거절」. 그 밖(5xx 등)은 「지금 확인할 수 없음」으로 저장을 미룬다 — 틀린 키를 받아들이지는 않는다. 운영 첫 등록에서 확인(S3b 계획 마지막 Task) |
| 403 본문으로 잔액 소진을 못 가른다 | 그래도 「키 오류」로 계정을 빼고 메일 — 사용자에게는 같은 결과(다음 계정). 메일 문구만 덜 정확 |
| 포스터·카드뉴스 화면을 닫아 「끝남」이 안 적힌 요청이 30분간 칸을 쥔다 | 한도를 실제보다 조금 크게 잡게 될 수 있다 — 진행 중 수가 화면에 보인다. S7 재측정에서 본다 |
| 번호 붙이기가 세 번 다 실패(DB 일시 장애) | 같은 프로세스는 메모리로 찾는다. 재시작이 겹치면 그 요청은 `FAL_KEY` 로 묻다가 실패한다 — 서버 기록 `[fal-pool] 요청 번호를 계정에 묶지 못했습니다` |
| 동기 → 대기열 전환으로 장당 지연이 는다 | 1초 폴링 + 제출 왕복. S3a 시험 서버 Task 에서 전후 p50 을 잰다(기준: +3초 이내) |
| 상세페이지 참고 그림이 data URL 로 대기열 몸통에 실린다(지금 동기와 같다) | 몸통 크기는 지금과 같다. 대기열이 거절하면(413 등) 시험 서버에서 드러난다 — 그때 카드뉴스처럼 먼저 올리고 주소를 싣는다(S4 계획에 이미 있음) |
| 열쇠 분실 | 키를 다시 넣으면 된다(돈 안 듦). 사본 보관은 사용자 선택 |
| 여러 fal 계정 사용이 fal 약관에 걸린다 | 여러 계정을 **켜기 전** fal 약관·답변 확인(본 설계 §3.3·§7). 코드는 계정 하나로도 같다 |

## 8. 사용자가 정할 것

1. 여러 fal 계정을 실제로 켤지 — fal 약관 확인 뒤(본 설계 §7). 확인 전에는 계정 **하나**(지금 `FAL_KEY`)만 등록해도 S3b 의 이점(관리자 화면·
   상태·메일)은 얻는다
2. 서버 열쇠 사본을 비밀번호 관리자에 둘지(선택)
3. 각 계정의 동시 한도 — 영상 서비스와 같은 계정을 쓰는 동안은 20 에서 그 몫을 뺀 값(예 12)을 권한다
