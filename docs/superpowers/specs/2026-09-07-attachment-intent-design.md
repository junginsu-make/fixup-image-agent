# 첨부 그림을 어떻게 쓸지 사용자가 직접 말하게 한다

작성 2026-09-07 · 합의: 사용자 · 기록: Claude

> **이 문서는 사용자와 합의한 내용이다. 구현하는 쪽이 임의로 바꾸지 않는다.**
> 바꿔야 할 이유가 생기면 먼저 사용자에게 말하고, 합의한 뒤에 이 문서를 고친다.
> 「안 정함」으로 남긴 것을 구현 단계에서 혼자 정하지 않는다.

---

## 1. 무엇이 문제인가

이미지 만들기에서 사진 두 장을 넣고 **「1번 사진의 사람들을 2번 그림 느낌으로」**를
시키려 했는데, 지금 옵션으로는 표현할 방법이 없었다.

첨부 그림 한 장에서 가져올 수 있는 것은 넷이다.

| | 뜻 |
|---|---|
| 누구인지 / 무엇인지 | 이 얼굴, 이 제품이 그대로 나오는 것 |
| 어떻게 놓였는지 | 몇 명이 어디에 어떤 자세로 |
| 그림 느낌 | 사진 / 만화 / 3D |
| 색과 글자 모양 | 어디에 무슨 색, 글씨체 |

지금 역할 옵션은 이것을 **묶음으로만** 고르게 한다.

```
인물 그대로 지키기 = 누구인지 + 그림 느낌     ← 그림 느낌까지 고정돼 만화로 못 바꾼다
따라 만들기        = 놓임 + 그림 느낌 + 색    ← 누구인지를 명시적으로 버린다
```

원하는 조합은 **누구인지(1번) + 그림 느낌(2번)** 인데, 어느 옵션도 그것이 아니다.

### 실제 프롬프트가 그렇게 되어 있다

`packages/shared/src/image-look.ts` · `preserveDirective("preserve-person")`
> 이 사람을 정확히 재현하라. … 미화하지도, 날씬하게도, 나이를 바꾸지도,
> **화풍을 바꾸지도(restyle) 마라.**

`packages/poster-core/src/prompt.ts` · 따라 만들기
> 디자인 언어만 흉내 내라. **그 밖의 것은 복사하지 마라 — 제품도, 사람도,**
> 아이콘도, 글자 내용도.

### 우선순위는 이미 있지만 모순이 함께 간다

`priorityLine()` 이 이미 이렇게 보낸다.

```
Priority when instructions conflict:
  USER INSTRUCTION > PRESERVED SUBJECT > REFERENCE image > scene description
```

**사용자 지시가 최우선인 것은 이미 구현되어 있다.** 문제는 그 옆에 반대되는 말이
그대로 남아 함께 간다는 것이다.

```
USER INSTRUCTION: 1번 사람들을 2번 느낌으로       ← 최우선
Image 1 is a PRESERVED PERSON. …화풍을 바꾸지 마라…   ← 반대
Image 2 is a POSTER REFERENCE. …사람을 복사하지 마라… ← 반대
```

서로 반대되는 말 셋을 함께 보내고 「싸우면 위엣것」이라고 덧붙이는 꼴이다.

## 2. 합의한 것

### 2-1. 이미지 얘기는 이미지를 첨부하는 곳(01)에서 쓴다

첨부한 그림을 어떻게 쓸지는 **그림이 눈앞에 있을 때** 쓴다. 01 레퍼런스 화면에
자유 입력 칸을 둔다.

03 지시에 이미 「추가 지시 · 선택」 칸이 있다. 성격을 이렇게 가른다.

| | 무엇을 쓰는 곳 | 예 |
|---|---|---|
| **01 (새로 만듦)** | 첨부한 그림들을 **어떻게 쓸지** | 1번 사람들을 2번 느낌으로 |
| **03 (이미 있음)** | 결과물이 **어때야 하는지** | 배경은 밤, 창밖에 네온 |

### 2-2. 번호를 화면·프롬프트·기획 AI 셋이 같이 쓴다

카드 **왼쪽 위**에 숫자 아이콘을 찍는다. 왼쪽부터 ①②③.

프롬프트는 **이미 번호를 쓰고 있다**.

```
Follow the instruction for each attached image separately.
Image numbers match attachment order.
Image 1 is a PRESERVED PERSON…
```

화면이 그 번호를 안 보여 줄 뿐이다. 셋이 같은 번호를 쓰게 맞춘다.

- 화면 카드 왼쪽 위 아이콘
- 최종 이미지 프롬프트의 `Image N`
- 기획 AI 에게 넘기는 목록의 번호

#### **번호가 지금 어긋나 있다** (2026-09-07 설계 검토에서 발견)

번호를 화면에 찍는 것만으로는 안 된다. **지금 화면 순서와 프롬프트 번호가
서로 다르다.**

그림이 서버로 **세 갈래로 나뉘어** 간다.

```
referenceIds  ← 따라 만들기
preservedIds  ← 지키기
personIds     ← 그중 사람인 것
```

그리고 프롬프트를 만들 때 따라 만들기를 **먼저**, 지키기를 **나중에** 붙인다
(`packages/poster-core/src/generate.ts` · `buildPosterJob`).

```ts
const images = [
  ...job.referenceUrls.map(...),   // 먼저
  ...job.preservedUrls.map(...),   // 나중
];
```

실제로 어긋나는 예 — 지금 화면 상태 그대로다.

| 화면 | 역할 | 프롬프트 번호 |
|---|---|---|
| 왼쪽 (단체 사진) | 인물 지키기 | **Image 2** |
| 오른쪽 (만화) | 따라 만들기 | **Image 1** |

**정확히 반대다.** 「①번 사람들을 ②번 느낌으로」라고 쓰면 모델은 반대로 알아듣는다.

그러니 **그림을 화면 순서대로 넘기도록 함께 고쳐야 한다.** 번호를 찍는 일과
한 몸이다.

#### 「화면 순서」는 고른 순서다 (2026-09-07 결정)

구현하다 알게 된 것: 지금 화면에 그려지는 차례는 **라이브러리 목록 순서**다.

```ts
const picked = references.filter((r) => (roles[r.id] ?? "none") !== "none");
```

`references` 는 최신순이라, 먼저 고른 것이 뒤에 놓일 수 있다.

**사용자 결정: 고른 순서를 번호로 쓴다.** 먼저 고른 것이 ① 이다. 그래야
「①번 사람들을 ②번 느낌으로」가 생각한 대로 동작한다.

→ 고른 차례를 기억하는 상태가 필요하다.

#### 옛 작업은 전과 똑같이 나온다

옛 작업은 `poster_projects.data` (jsonb) 안에 두 목록으로 저장돼 있고,
다시 만들 때 그것을 그대로 읽는다.

```ts
const references = await stores.references.byIds(project.data.referenceIds);
const preserved  = await stores.references.byIds(project.data.preservedIds ?? []);
```

**화면 순서가 애초에 저장돼 있지 않다.** 사용자가 어떤 순서로 넣었는지 기록이
없다. 그러니 옛 작업을 다시 만들 때는 지금처럼 두 목록을 이어 붙일 수밖에 없고,
**결과가 지금과 같다.**

> 2026-09-07 검토 초판에서는 「옛 작업이 달라진다」고 적었으나, 다시 재 보니
> 순서 정보 자체가 없어 달라질 것이 없다. 사실에 맞게 고친다.

옛 작업을 어떻게 다룰지는 4-5 에서 정한다.

### 2-3. 첨부 카드를 작게 만든다

지금 `aspect-[2/3]` 이라 세로가 가로의 1.5배다. 4열 격자에서 화면이 넓으면
한 장이 화면을 다 먹는다. 넉 장을 넣으면 스크롤이 길어진다.

그림을 알아볼 만큼만 남기고 세로를 줄인다. 줄인 자리에 2-1 의 입력 칸이 들어간다.

### 2-4. 드롭다운은 남긴다. 자유 입력이 그 위에 선다

**둘 다 둔다. 역할이 다르다.**

- 드롭다운 — 자주 쓰는 것을 빠르게. 검증된 문구(`preserveDirective` 여섯 문장)를 넣는다
- 자유 입력 — 드문 것을 가능하게. 드롭다운으로 못 만드는 조합을 연다

드롭다운만 두면 지금 문제가 그대로다. 자유 입력만 두면 매번 뭐라고 쓸지 사용자가
고민하게 되고, 실측으로 쌓은 문구가 안 쓰여 결과가 들쭉날쭉해진다.

**사용자가 쓴 말이 드롭다운보다 우선한다.** 우선순위 줄이 이미 그렇게 되어 있다.

### 2-5. 사용자가 그림 얘기를 쓰면 반대되는 고정 문구를 뺀다

이것이 이 작업의 핵심이다. 나머지는 이것이 실제로 듣게 만드는 준비다.

01에 무언가 쓰면, 그 그림에 붙던 고정 문구 중 **사용자 지시와 반대되는 것을 뺀다.**

- 「2번 느낌으로」라고 썼으면 Image 1 의 「화풍을 바꾸지 마라」를 뺀다
- 「1번 사람들을」이라고 썼으면 Image 2 의 「사람을 복사하지 마라」를 뺀다

**무엇을 어떤 기준으로 뺄지는 아직 안 정했다.** → 4절

### 2-6. 최종 프롬프트를 LLM 이 하나로 합친다

01의 이미지 반영 요청과 03의 지시를 **최종적으로 LLM 에게 보내 하나의 최적화된
이미지 프롬프트로 만든다.**

지금은 이렇다.

```
01 역할(드롭다운)  ─┐
03 한 줄 지시      ─┼→ claude-sonnet-5 → 기획 칸 12개 → 사람이 고침 ─┐
03 추가 지시       ─┘   (references 는 제목만 넘어간다)               │
                                                                     ▼
                                            코드가 문자열로 조립 → fal
```

바꿀 것 둘.

1. 기획 AI 에게 **번호 · 역할 · 01 지시**를 함께 넘긴다.
   지금은 `references: Array<{ title, grammar }>` 로 **제목만** 간다.
   그래서 04 기획 확인에서 AI 가 채우는 칸이 첨부한 그림과 겉돈다.
2. 최종 이미지 프롬프트를 **LLM 이 하나로 합친다.**

**2번을 어디까지 LLM 에게 맡길지는 아직 안 정했다.** → 4절

## 3. 적용 범위와 순서

레퍼런스를 쓰는 **모든 섹션**에 적용한다. 다만 한꺼번에 하지 않는다.

```
1단계  이미지 만들기 (/poster)     ← 여기부터
2단계  1단계가 실제로 되는지 확인
3단계  카드뉴스 · 상세페이지 · 리디자인 · 캐릭터 만들기
```

**1단계가 제대로 작동하는 것을 보고 나서 확산한다.** 네 곳을 함께 고치면 무언가
어긋났을 때 어디서 어긋났는지 알 수 없다.

### 확산이 쉬운 이유

역할 어휘가 **이미 공용**이다 — `packages/shared/src/attachment-role.ts`.

```ts
export type AttachmentRole =
  | "style"             // 따라 만들기
  | "preserve_product"  // 제품 그대로 지키기
  | "preserve_person"   // 인물 그대로 지키기
  | "place_as_is";      // 원본 그대로 넣기
```

네 도구가 각자 어휘를 쓰다가 하나로 모은 것이다. 지시 문구도
`packages/shared/src/image-look.ts` 가 공용으로 갖고 있다.

**그러니 새로 만드는 것도 `@fixup/shared` 에 둔다.** 도구마다 따로 만들면 다시
갈린다.

## 4-1 결정 (2026-09-08) — A안: 부딪히는 문구를 통째로 뺀다

**사용자가 실제로 한 번 돌려 보고 정했다.** 「안 정한 것」 넷 중 4-1 이 닫혔다.

첨부 두 장(사진 + 만화 그림)을 다 「따라 만들기」로 고르고 「1번 사진의 사람들을
2번 그림 느낌으로」라고 적었다. 결과는 구도와 그림 느낌은 왔는데 **사람이 새로
만들어져 나왔다.**

원인은 프롬프트에 있었다. 「따라 만들기」의 고정 문구가 **두 장 모두에 대해**
`Do NOT copy anything else from it — not its people` 을 보내고 있었다. 우선순위
줄(`USER INSTRUCTION > …`)이 이미 있었지만 **한 줄로는 못 이겼다** — 반대편이
여섯 문장이고 전부 구체적이기 때문이다.

**결정: 첨부 지시를 적었으면 역할 고정 문구를 통째로 뺀다.**

- 번호와 역할 이름은 남긴다. 빼면 「1번」이 가리킬 것이 없어져 이 기능이 무너진다
- 왜 규칙이 없는지 모델에게 말해 준다. 안 말하면 자기가 아는 기본값을 채운다
- **위험을 알고 고른 것이다** — 「얼굴 특징을 하나하나 맞춰라」도 함께 사라져
  얼굴이 딴사람이 될 수 있다. 그때는 사용자가 그 말을 직접 적으면 된다. 이제
  그 한 줄이 프롬프트에서 가장 센 말이다

구현: `packages/poster-core/src/prompt.ts` · `attachmentLines()`

**4-3(새 역할 옵션)은 아직 열려 있다.** A안으로 안 되는 경우가 나오면 그때 본다.

## 4-1-b 함께 확인된 것 (2026-09-08) — 안 시킨 글자가 나왔다

같은 실측에서 첨부 두 장 어디에도 글자가 없고 사용자도 요구하지 않았는데
「BEST DAY EVER!」가 크게 박혀 나왔다.

**글자 칸이 전부 비면 프롬프트에서 글자 이야기가 통째로 사라지고 있었다** —
「넣지 마라」도 함께. 그 사이 `designerPersona()` 는 「confident typography」를
요구하고 첨부는 `POSTER REFERENCE` 라 불린다. 막는 말이 없으니 모델이 글자를
만든다.

빈 칸일 때 「글자 없이 그려라」를 낱낱이 보낸다. `designerPersona()` 는 안
고친다 — 다섯 도구가 함께 쓰고 카드뉴스·상세페이지는 글자가 있어야 한다.

## 4. 아직 안 정한 것

**여기 있는 것을 구현 단계에서 혼자 정하지 않는다.**

### 4-1. 반대되는 문구를 무엇을 기준으로 뺄까 (2-5)

세 가지 길이 있다. 정하지 않았다.

| | 방법 | 걱정 |
|---|---|---|
| A | 01에 뭐라도 쓰면 해당 그림의 고정 문구를 통째로 뺀다 | 「왼쪽에 놓아 줘」만 써도 얼굴 지키기가 풀린다 |
| B | LLM 이 읽고 판단해서 뺀다 | 판단이 매번 다를 수 있다 |
| C | 문구를 조각으로 나눠 두고 필요한 것만 뺀다 | 만들 것이 많다 |

### 4-2. 최종 프롬프트를 LLM 이 어디까지 만들까 (2-6)

| | 방법 | 걱정 |
|---|---|---|
| A | 지금처럼 코드가 조립하고, LLM 은 기획 칸만 채운다 | 01 지시와 고정 문구의 모순이 남는다 |
| B | LLM 이 전체를 다시 쓴다 | 실측으로 쌓은 문구가 LLM 손에서 흐려질 수 있다 |
| C | 고정 문구는 코드가 넣고, **모순되는 자리만** LLM 이 정리한다 | 경계를 정해야 한다 |

### 4-3. 「지키되 그림 느낌만 바꾸기」를 옵션으로 만들까

**실측이 먼저 필요하다.** 얼굴을 그대로 두라는 말과 만화로 바꾸라는 말은 서로
반대라, 실제로 fal 에 돌려서 얼굴이 알아볼 만하게 남는지 재야 값이 있는지 안다.

2-1 의 자유 입력이 생기면 옵션 없이도 한 줄로 시도할 수 있다. **그게 곧 실측이 된다.**
그 결과를 보고 정한다.

### 4-4. 「인물은 한 명만」 제약을 어떻게 할까

지금 코드는 **개수만 센다.**

```ts
images.filter(i => i.kind === "preserved" && i.subject === "person").length > 1
  → "한 명만 그려라, 첫 번째를 고르고 얼굴을 섞지 마라"
```

그래서 이 둘이 똑같이 처리된다.

| 넣은 것 | 사용자 뜻 | 지금 결과 |
|---|---|---|
| 홍길동 정면·좌·우·뒤 | 한 명을 여러 각도로 | 첫 장만 씀 |
| 홍길동·김철수·이영희·박민수 | 네 명이 다 나오게 | 첫 장만 씀 |

앞은 막는 것이 맞다 — 정체성 참조가 여러 장이면 모델이 절충해 제3의 인물을
만든다(2026-07-30 실측). **뒤는 막을 이유가 없다.** 서로 다른 네 사람을 각각
지키는 것은 최신 모델에서 되는 일이고, 우리가 안 재 봤을 뿐이다.

가릴 정보는 이미 있다. 캐릭터 각도는 제목이 `이름 (캐릭터) · 정면` 이라
같은 사람인지 코드가 알 수 있다(`characterReferenceTitle`). 안 보고 있을 뿐이다.

**이번 1단계에서는 안 건드린다.** 2-1 의 자유 입력이 생기면 「1~4번은 같은 사람의
여러 각도다」라고 직접 쓸 수 있으므로, 우선 그것으로 되는지 보고 판단한다.

### 4-5. 옛 작업의 그림 순서를 어떻게 할까 (2-2) — 정해짐

**사용자 결정 (2026-09-07): 코드 길을 하나로 둔다.**

| | 방법 |
|---|---|
| **A (선택)** | 화면 순서가 담긴 목록 하나를 받아 처리한다. 옛 작업은 **읽을 때** 두 목록을 이어 붙여 그 목록을 만들어 준다 |
| B | 새 칸이 있는 작업과 없는 작업을 갈라서 다르게 처리한다 |

B 는 규칙이 둘이 되어 나중에 「왜 이 작업만 다르지」가 생기고, 새 칸이 있는지로
갈라야 해서 코드가 늘어난다.

**A 로 잃는 것이 없다.** 옛 작업에는 화면 순서가 저장돼 있지 않으므로 어느 쪽을
골라도 두 목록을 이어 붙이는 것 말고 방법이 없다 — 결과가 지금과 같다.

→ 0번은 결정에 안 걸린다. 1~4번과 함께 만든다.

### 사용자 결정 (2026-09-07)

**1~4번만 먼저 만들고, 사용자가 직접 돌려 본 뒤에 5~6번과 4절을 정한다.**

이유: 프롬프트에 이미 「싸우면 사용자 말이 이긴다」(`priorityLine`)가 들어 있는데,
**그것이 실제로 얼마나 먹히는지 재 본 적이 없다.** 1~4번이 있으면 그것을 잴 수 있다.

- 우선순위만으로 되면 → 고정 문구를 건드릴 필요가 없다. 4-1 이 사라진다
- 안 되면 → **어떻게 안 되는지** 보고 4-1 을 정한다. 상상으로 고르는 것보다 정확하다

**고정 문구(잔소리)는 이번에 안 건드린다.**
