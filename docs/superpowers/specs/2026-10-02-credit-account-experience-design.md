# 크레딧 잔액 표시·내 구독·구매 문의 개선 설계

상태: 구현 및 로컬 검증 완료. 설계 기준: `origin/master`의 `1dee226b5882fb6a2131dcbffd91b51980778090`.
설계 위치: `.worktrees/credit-account-design`, 브랜치 `design/credit-account-experience`.
구현 위치: `.worktrees/credit-account-fixes`, 브랜치 `fix/credit-account-experience`.

## 1. 목적과 범위

사용자가 요청한 세 가지 개선만 다룬다.

1. 생성·지급·새로고침 후 상단과 계정 화면의 크레딧이 같은 서버 잔액을 표시한다.
2. 계정 화면에서 자신의 구독 플랜, 상태, 기본 월 제공량과 이번 달 실제 지급 내용을 확인한다.
3. 크레딧 부족 시 원인을 안내하고 크레딧 구매 또는 월 구독 문의를 접수할 수 있다.

관리자가 지급한다는 기존 정책을 유지한다. 자동 결제, PG, 정기 자동 청구, 새로운 가격 정책, fal 배분 변경, 장부 계산·정산 함수 변경은 범위 밖이다. 관리자 잔액·플랜·지급 화면과 기존 문의함을 그대로 사용한다. 새 테이블이나 SQL 마이그레이션은 이 설계에 필요하지 않다.

### 확인한 근거

- `app/_components/studio-actions.tsx:23`: `usage`를 최초 `useState`에만 넣는다. 새 props를 받아도 state는 갱신되지 않는다. 실제 React 컴포넌트에서 서버 props를 0→100으로 바꿨지만 상단은 0으로 남는 것을 재현했다.
- `app/_components/credit-policy-provider.tsx`: 별도 잔액 state와 갱신 이벤트를 이미 보유한다. 상단과 상태가 이중화되어 있다.
- 상세페이지·리디자인·광고에는 `studio-usage-updated` 전달 경로가 있지만, 포스터·SNS·Easy 및 화면 밖 작업 완료까지 일관되게 연결되어 있지 않다.
- `app/settings/page.tsx`: 사용량·지급 이력은 읽지만 `user_subscriptions`의 플랜 정보를 읽지 않는다.
- `lib/membership/api.ts:84,184`, `app/_components/credit-wallet.tsx:9`: 부족 안내만 있고 구매·구독 문의 동작이 없다.
- `lib/easy/relay.ts`와 Easy API의 catch: 중간 단계 실패를 전달할 때 오류 `code`와 `usage`가 빠진다. 공통 부족 안내를 붙이려면 이 전달 경로도 포함해야 한다.
- `app/api/cs/inquiry/route.ts`: AI/크레딧 예약 없이 로그인 회원의 문의를 접수한다. `question`, 선택적인 `sessionId`, `page`만 받으며 기존 문의함·메일 알림·중복 확인·빈도 제한을 재사용할 수 있다.

직전 리뷰에서 관련 DB 테스트 86개, 앱 테스트 70개가 통과했다. 추가 임시 DB 대조에서 사용자/관리자 잔액이 지급 125 → 확보 후 122(처리 중 3) → 일부 성공 후 123으로 일치했고 중복 정산·동일 결제 확인은 잔액을 바꾸지 않았다. 이는 기존 코드의 로컬 검증이며 본 설계 구현의 검증 결과 또는 운영 DB 실사 결과가 아니다.

## 2. 화면 계약

### 2.1 상단과 내 크레딧

두 위치 모두 하나의 클라이언트 상태를 읽는다. 클라이언트에서 지급·차감량을 더하거나 빼서 잔액을 추정하지 않는다. `remaining`은 서버 장부의 사용 가능 크레딧이며, `reserved`는 이미 확보되어 추가 사용이 불가능한 양이다.

- 생성 접수/완료, 명시적인 실패/중지, 정산 결과 변경 시 서버 잔액을 다시 조회한다.
- 관리자가 지급한 뒤 회원이 새로고침하면 상단과 계정 카드가 함께 바뀐다.
- 화면이 보이는 동안 60초 간격으로 다시 확인한다. 다른 탭에서 돌아오면 즉시 확인한다. 운영자 지급·회수와 시간에 따른 만료를 반영하기 위한 간격이며 실시간 푸시를 약속하지 않는다.
- 새로고침 실패 시 마지막 확인값에 `잔액 확인 지연`을 표시한다. 최초 조회가 실패했다면 `확인하지 못했습니다`를 표시하며 0이나 무제한으로 대체하지 않는다.
- 만료일을 브라우저 시간으로 계산해 잔액에서 빼지 않는다. 서버에서 다시 확인한다.
- 무제한 계정 표시는 유지하고 구매 유도는 숨긴다. legacy 정책의 기존 단위 표기도 유지한다.

### 2.2 내 구독 카드

`/settings`의 내 크레딧 가까이에 배치한다. 다음은 예시이며 새로운 판매 가격이나 플랜을 정하는 것이 아니다.

```text
내 구독
플랜: 베이직                 상태: 이용 중
플랜 기본 제공량: 월 100크레딧
이번 달 결제 확인: 완료
이번 달 확인된 지급량: 120크레딧
해당 기간: 10월 2일 ~ 11월 1일 00:00 (한국시간)
구독분 사용 가능: 85크레딧

[월 구독 문의]
```

기본 제공량 100과 실제 확인된 지급량 120은 별개다. 관리자가 조정 지급할 수 있으므로 현재 플랜 기본값으로 과거 지급량을 계산하지 않는다.

| 상태 | 표시 |
|---|---|
| 구독 없음 | `이용 중인 구독이 없습니다` + 월 구독 문의 |
| active, 해당 월 결제 확인 없음 | `플랜은 배정되어 있습니다. 이번 달 결제 확인 후 구독 크레딧이 지급됩니다` |
| active, 해당 월 결제 확인 있음 | 해당 기간의 확정 지급량·확인 금액·기간과 서버 잔액 표시 |
| canceled / suspended | `해지됨` / `중단됨`, 남은 지급분은 장부 잔액·만료일대로 표시 |
| 플랜 판매 중지 | 이미 배정된 플랜의 이름과 내역은 계속 표시 |
| 구독 조회 실패 | `구독 정보를 확인하지 못했습니다` + 재시도, 구독 없음으로 대체 금지 |

해지와 이미 결제 확인된 기간은 별개다. 이미 지급되었거나 미리 확인된 기간의 크레딧을 이 UI에서 회수하지 않는다. 다음 달 자동 결제일/갱신 예정일을 만들어 표시하지 않는다.

### 2.3 부족 안내와 문의

공통 안내 영역은 상단 잔액 가까운 셸 내부에 한 번만 둔다. 계정 화면에는 같은 동작을 가진 안내/문의 영역을 둔다. 화면의 기존 오류 표시를 깨뜨리지 않되 동일 구매 안내를 토스트·팝업 등으로 중복 노출하지 않는다. 자동 팝업은 사용하지 않는다.

| 원인 | 안내 및 동작 |
|---|---|
| `credits_required` | `사용 가능한 크레딧이 없습니다. 크레딧 구매 또는 월 구독을 문의해 주세요` |
| 개인 `quota_exceeded` | `이번 작업에 필요한 크레딧이 부족합니다. 사용 가능 N크레딧입니다` |
| 필요한 양을 서버가 확정해서 제공한 경우 | 사용 가능·필요·부족량 표시. 서버 수치가 없으면 필요량은 생략 |
| 처리 중 확보 때문에 사용 가능 0 | 처리 중 크레딧과 작업 완료 후 확인 안내를 함께 표시. 구매를 유일한 해결책으로 표현하지 않음 |
| 팀 한도 / 동시 요청 한도 / 사용량 제한 / 운영 중지 / fal 계정 오류 | 각각 기존 원인 안내. 개인 크레딧 구매로 해결된다고 표시하지 않음 |
| 잔액 조회 실패 | 조회 실패 안내. 구매 필요 여부를 단정하지 않음 |

부족 안내에는 `[크레딧 구매 문의]`와 `[월 구독 문의]`를 둔다. 계정 화면에서는 잔액이 남아 있어도 두 문의 버튼을 이용할 수 있다.

버튼을 누르면 문의 양식을 열고 유형별 기본 문장을 채운다. 사용자가 내용을 확인·수정한 후 `[문의 보내기]`를 눌러 접수한다. 문의만으로 크레딧을 지급하거나 구매·구독을 확정하지 않는다. `담당자가 확인 후 구매·구독 및 지급 방법을 안내합니다`라고 표시한다.

## 3. 서버 조회 설계

### 3.1 `GET /api/account/summary` 추가

`authenticateApiMember()`로 본인을 확인한다. URL/body에서 대상 회원 ID를 받지 않는다. 승인 대기·정지·탈퇴·가입 미완료는 기존 인증 규칙대로 거절한다. 잔액이 0이어도 조회할 수 있다. 사용량 예약과 외부 AI 호출은 없다.

`Cache-Control: private, no-store`와 동적 처리를 사용한다. 서버 전용 접근으로 기존 `getUsageSummary(userId)` 및 아래 테이블을 조회한다. 관리 키·내부 메모·지급자의 ID를 브라우저로 전달하지 않는다.

```ts
type AccountSummary = {
  usage: UsageSummary;
  subscription:
    | { state: "none" }
    | { state: "unavailable" }
    | {
        state: "present";
        status: "active" | "canceled" | "suspended";
        plan: { id: string; name: string; monthlyUnits: number; priceKrw: number };
        startedAt: string;
        cancelAt: string | null;
        currentPeriod: null | {
          period: string;
          startsAt: string;
          expiresAt: string;
          grantedUnits: number;
          paidKrw: number;
        };
      };
  fetchedAt: string; // 마지막 확인 시각. 응답 순서를 판정하는 DB 버전이 아니다.
};
```

`fetchedAt`은 마지막 확인 시각의 표시용이며 DB 버전/응답 우선순위로 사용하지 않는다.

- `usage`: 기존 `credit_summary`를 통해 계산한다. 이 RPC가 결제 확인된 현재 기간의 지급분을 생성하는 기존 동작은 유지한다. HTTP 조회라고 해서 완전한 SQL read-only라고 주장하지 않는다.
- `user_subscriptions`: 본인 행, 구독 상태와 배정된 플랜.
- `subscription_plans`: 배정된 ID를 조회한다. `active=true`로 한정하지 않는다.
- `subscription_periods`: 본인과 `usage.periodStart`에 해당하는 기간. 한국시간 월 경계를 브라우저에서 만들지 않는다. 실제 지급량과 결제 확인 금액의 근거다.
- 지급된 크레딧 잔액은 `usage.subscription`이 정본이다. `currentPeriod.grantedUnits`에서 이번 달 전체 사용량을 빼지 않는다. 구매/보너스와 혼합 소비되기 때문이다.
- 플랜 읽기 중 오류가 나면 잔액은 유지하고 구독만 `unavailable`로 반환한다. 잔액 읽기 자체가 실패하면 오류 응답으로 처리한다.
- 서버 렌더링과 API는 같은 서비스 함수를 사용한다. 구성 조회가 서로 다른 시점일 수 있으므로 전체 결제/구독의 원자적 스냅샷이라고 주장하지 않는다. 금전 계산은 항상 단일 장부 요약에 의존한다.

현재 화면의 사용 이력·지급 이력 읽기는 보존한다. 계정 화면의 수동 새로고침은 이력도 다시 읽도록 기존 `router.refresh()`를 함께 사용한다. 주기적 조회는 잔액·구독 카드에 한정하며 과거 이력 전체를 반복 조회하지 않는다.

## 4. 잔액 상태와 갱신

### 4.1 기존 Provider 확장

`CreditPolicyProvider`를 확장해 `usage`, 구독 조회 결과, 갱신 상태, `refreshAccountSummary()`를 소유한다. 기존 `useCreditPolicy()`와 `useCreditUnit()` 인터페이스는 유지한다.

- `StudioActions`의 자체 `currentUsage`와 이벤트 리스너를 제거하고 공통 상태를 읽는다.
- `CreditWallet`을 공통 상태를 읽는 클라이언트 경계로 바꾼다. 새 구독 카드도 같은 상태를 읽는다.
- `CreditRefresh`는 공통 새로고침과 계정 이력 재조회에 연결한다. 마지막 확인값이 갱신된 뒤 대기 상태를 종료한다.
- 로그인한 회원 ID를 Provider의 범위로 삼는다. 회원이 바뀌면 이전 state·진행 중 응답·안내·탭 채널을 폐기한다.

### 4.2 늦은 응답이 잔액을 되돌리지 않는 규칙

기존 생성 응답의 `usage` 값은 응답 순서가 뒤집힐 수 있다. 이제 갱신 이벤트는 잔액 덮어쓰기 명령이 아니라 서버 재조회 신호로 처리한다.

1. 서버 렌더 초기값은 첫 마운트에 사용한다. 이후 서버 props 변경은 재조회 신호가 된다. 늦게 도착한 props로 현재 값을 직접 덮어쓰지 않는다.
2. 요약 요청은 Provider당 동시에 한 개만 보낸다. 재조회 원인마다 클라이언트 세대 번호를 증가시킨다.
3. 요청 중 새로운 변경 신호가 오면 결과는 오래된 후보로 취급하고 완료 후 한 번 더 조회한다. 마지막 세대에 대응하는 응답만 확정한다.
4. 일반 이벤트는 1초 단위로 합치되 마지막 갱신을 누락하지 않는다. 수동 새로고침은 즉시 실행 또는 진행 중 요청 뒤에 예약한다.
5. 숨겨진 탭의 주기 조회를 중지한다. 다시 보이면 즉시 확인하고, 갱신 실패의 자동 재시도는 60초 간격을 하한으로 한다. 401/403이면 주기 조회를 중단하고 로그인/이용 상태를 안내한다.
6. 브라우저 탭 간에는 회원별 `BroadcastChannel`로 변경 신호만 공유한다. 잔액·이메일·구독 정보를 localStorage에 저장하지 않는다. 지원하지 않는 환경은 화면 복귀/주기/수동 조회로 동작한다. 수신한 신호를 재전송하지 않아 반복 루프를 막는다.

API의 확인 시각만 비교하거나 브라우저에서 크레딧을 낙관적으로 차감하지 않는다. 세대 번호는 클라이언트 요청 순서 제어용이며 DB 트랜잭션 버전이 아니다.

| Easy 이미지·카드뉴스 | `easy-client.tsx`, `use-cardnews.ts`, `cardnews-request.ts`의 접수/완료/실패 |
| 다른 화면에서 작업 완료 | `RunningJobsProvider`의 완료·중지 처리 |
| 관리자의 본인 지급/회수 | 관리자 액션 성공 후 동일 탭 갱신 신호. 타인 지급은 대상 회원 브라우저의 복귀/수동/60초 확인으로 반영 |

관찰 대상은 잔액이 바뀔 수 있는 경계다. 모든 상태 폴링 응답마다 요약 요청을 추가하지 않는다. 기획 완료 등 변경 없는 응답도 중복 신호를 합친다. 기존 `billableFetch`의 멱등키·메서드·반환 Response 계약은 보존한다. 이미 JSON을 파싱하는 어댑터에서 관찰하며 전역 fetch 교체나 스트림 본문 선소비는 하지 않는다.

## 5. 크레딧 부족 전달과 문의 구현

### 5.1 오류 식별

공통 클라이언트 함수가 파싱된 응답의 `code`를 검사한다. 한국어 문구, HTTP 403/429만으로 크레딧 부족을 판정하지 않는다. HTTP 상태 코드는 이번 범위에서 변경하지 않는다.

- `credits_required`, 개인 `quota_exceeded`만 구매 안내 대상으로 삼는다.
- `quota_exceeded`도 `retryable: false`로 명시해 잔액 부족으로 거절된 요청을 자동 재전송하지 않게 한다. 단순 새로고침과 사용자 의도의 새 생성 요청은 가능하다.
- Easy의 `EasyStepError`에 선택적 업무 코드와 검증된 usage를 보존하고 두 바깥 API로 전달한다. 확인된 코드 목록만 사용하고 원시 내부 오류를 노출하지 않는다.
- 부족 안내는 자동 생성 재시도를 하지 않는다. 지급 후 다시 실행하려면 사용자가 생성 버튼을 눌러야 한다.
- 갱신 후에도 남은 잔액이 필요한 양보다 적으면 안내를 유지한다. 필요한 양을 모르는 경우 조회 성공만으로 충분하다고 선언하지 않고 재시도를 안내한다. 사용자가 닫을 수 있다.
- 무료 AI 작업의 `credits_required`는 작업 가격이 0이라는 이유로 통과시키지 않는다. 기존 서버의 사용 자격 정책을 유지한다.

### 5.2 기존 문의 접수 재사용

양식은 문의 유형(크레딧 구매/월 구독)과 편집 가능한 내용만 받는다. 기존 `POST /api/cs/inquiry`에 `[크레딧 구매 문의]` 또는 `[월 구독 문의]` 접두어를 붙인 `question`, 현재 페이지 `page`를 보낸다. AI 상담 sessionId는 보내지 않는다. 사용자 ID와 이메일은 기존 서버 인증에서 결정한다.

- 화면에 `CS_EMAIL`과 메일 링크도 표시한다. 이메일 앱을 열기 어려운 사용자는 서비스 내 양식을 이용한다.
- AI 상담 횟수 소진·크레딧 0·AI 일시 중지에서도 활성 회원은 문의를 접수할 수 있다.
- 기존 관리자 문의함(`/admin/system`)과 메일 알림을 사용한다. 새 문의함이나 지급 자동화는 만들지 않는다.
- `saved=true, mailed=false`는 접수 성공으로 안내한다. 메일 실패가 문의 저장을 취소하지 않는다.
- `duplicate=true`는 이미 접수됨으로 안내하고 새 결제나 지급으로 취급하지 않는다.
- 저장 실패/빈도 제한은 실제 응답 메시지를 보여주고 입력을 보존한다. 성공으로 표시하지 않는다.
- 문의 내용의 희망 크레딧은 참고 자료다. 서버 장부 수치·결제 확인·지급 명령으로 신뢰하지 않는다.

## 7. 재발 방지 검증 기준

소스 문자열 존재 여부만 검사하지 않고 실제 React 상태 전이와 API 응답을 검증한다.

| 검증 | 통과 조건 |
|---|---|
| 상단 0→100 지급 | 서버 재조회 후 상단·계정 카드 모두 100 |
| 생성 확보/정산 | 125→122(처리 중3)→123이 두 위치에서 동일 |

## 8. 구현 순서와 완료 조건

1. 본인 요약 조회·공통 잔액 상태: 0→100 재현부터 고치고 응답 역전·조회 실패·계정 전환을 검증한다.
2. 생성 경로 연결: 포스터/SNS/Easy/화면 밖 작업을 포함해 상태 갱신을 연결한다.
3. 내 구독 카드: 기존 테이블로 실제 플랜과 해당 월 확인 정보를 표시한다.
4. 부족 안내·문의: 업무 오류 코드 보존, 공통 안내, 기존 문의 API 연결을 구현한다.
5. 전체 연결 검증과 코드 리뷰: 기존 장부 불변, 사용자/관리자 수치 일치, 문의함 접수와 실패 처리를 확인한다.

각 단계는 관련 테스트가 통과한 뒤 다음 단계로 진행한다. 설계 단계에서는 앱 코드·SQL·운영 환경을 변경하지 않는다.

운영 적용 때는 최종 코드의 CI와 릴리스 빌드를 확인하고 일반 테스트 회원으로 상단/계정 잔액 일치, 실제 플랜 표시, 문의 접수를 검증한다. 메일/문의의 운영 검증은 의도한 테스트 접수 한 건으로 구분한다. 테스트를 위한 실제 회원 지급·회수는 하지 않는다. 로컬 통과와 운영 기능 확인은 별도로 보고한다.

완료란 세 화면 흐름이 위 검증을 충족한다는 뜻이다. 클라이언트에 예전 숫자가 남는 문제를 해결하며, 서버 장부의 모든 장애나 항상 즉각적인 다른 기기 동기화를 보장한다는 뜻은 아니다.
