## 0. 사용자 결정 (2026-09-30)

1. **상세페이지는 안내로 끝낸다.** 「쉽게」에서 상세페이지를 달라고 하면 만들지 않고
   상세페이지 기능으로 보낸다.
2. **카드뉴스는 「쉽게」에서 끝까지 만든다.** 기존 카드뉴스의 옵션과 기능이
   **전부** 채팅에서 돌아야 한다 — 레퍼런스 디자인 따라가기, 긴 글, 주제만 주고
   정보 수집 맡기.
3. **붙인 사진은 무조건 분위기 참고가 아니다.** 사용자는 사진을 붙이고 그 사진을
   어떻게 해 달라고 말한다. **그 말을 따른다.** 제품을 가리키면 제품을 지킨다.
   여러 장이면 장마다 다를 수 있다(이건 분위기, 저건 유지). 정확한 말이 필요하면
   **AI 가 사용자에게 묻는다.** 사용자의 말은 이미지 모델까지 그대로 가고, LLM 은
   그 뜻을 정확히 읽어 반영한다.
4. **사진 없이 카드뉴스를 달라고 하면** 채팅이 따라 만들 카드뉴스를 요청한다.
   `[라이브러리에서 고르기] [저장한 레퍼런스 세트]` 단추를 함께 낸다.
5. **A안**(§2-2) — AI 가 말과 사진을 함께 보고 사진마다 역할을 정한다.
6. **새 가지에서 한다.** 다른 터미널이 크게 작업 중이라 `feat/easy-cardnews` 에서
   하고 나중에 합친다.

> **「되묻지 않는다」와의 관계.** 2026-09-17 설계는 되묻기를 버렸다. 3번은 그것을
> **사진 역할에 한해** 되살린다. 모르는 채로 만들면 값이 나가고 제품이 다시
> 그려진다 — 묻는 것은 값이 0 이다. 비율·그림체를 한 번 묻던 방식(2026-09-21)과
> 같은 원칙이다: **묻되 막지 않는다**가 아니라, 여기서는 **모르면 묻고, 알면 안
> 묻는다.**

## 2. 1단계 — 사진 역할과 상세페이지 안내

### 2-1. 지금 무엇이 틀렸나

| 무엇 | 어디 |
|---|---|
| 붙인 사진을 **전부 `referenceIds`(따라 만들기)**로 보낸다 | `app/easy/easy-client.tsx:300` |
| 번호 순서를 「따라 만들기 먼저, 지킬 것 나중」으로 다시 짠다. 사용자가 붙인 순서가 사라진다 | `app/api/easy/generate/route.ts:219` |
| 붙인 수에 `personIds` 를 한 번 더 더한다. 인물이 `preservedIds` 에도 있으면 두 번 센다 | `route.ts:136` |
| `restyledIds` · `attachmentIntent` 를 안 넘긴다 | `route.ts:210-220` |

**이미지 만들기 쪽은 이미 다 받을 줄 안다.** 역할 네 가지(`@fixup/shared` 의
`AttachmentRole`), 역할마다 다듬어진 문구(`poster-core/src/prompt.ts` 의
`attachmentLines`), 사용자 말이 고정 문구를 이기는 규칙(같은 파일, `hasAttachmentIntent`),
사진마다 무엇이 찍혔는지 읽는 기계(`readAttachments`)가 있다.
**빠진 것은 하나다 — 말과 사진을 보고 역할을 정하는 자리.**

### 2-2. 방법 — A안

| | 방법 | 버린 까닭 |
|---|---|---|
| **A** | 사진마다 무엇이 찍혔는지 읽고, 그 설명과 사용자 말로 역할을 정한다 | — |
| B | 말만 보고 정한다 | 「제품은 살려」라고만 하면 어느 사진이 제품인지 모른다. 거의 매번 되묻게 된다 |
| C | 역할 없이 말만 넘긴다 | 역할이 없으면 전부 「따라 만들기」가 되고, 그 문구가 「사람·제품은 베끼지 마라」를 붙인다. **지금 문제가 그대로다** |

A안의 사진 읽기는 **그림을 만들 턴에만** 돈다(§2-3).

### 2-3. 한 턴의 흐름

```
사용자가 보낸다 — 말 + 붙인 사진(붙인 순서대로)
                  + [물음에 답해 다시 보낼 때] 사진마다 고른 역할
  │
  ├─ ⓪ 사진 확인 — 붙인 것이 있을 때만. 값 0
  │     세션 회원 기준으로 조회해 **요청한 사진 전부**가 나와야 한다
  │     하나라도 안 나오면 멈춘다. 아무것도 안 남긴다
  │
  ├─ ⓑ1 말인가 주문인가 — 글 모델 한 번. 지금 판단에 detail_page 하나를 더한다
  │     원하는 것   talk · image · detail_page
  │     사진은 안 본다. 몇 장 붙었는지만 안다 (지금과 같다)
  │
  ├─ talk        → 답을 남기고 끝. 사진을 안 읽는다 (지금과 같다)
  ├─ detail_page → 안내 줄을 남기고 끝. 사진을 안 읽는다 (§2-7)
  ├─ image, 사진 없음 → 지금 그대로 (비율·그림체 물음 → 세 라우트)
  └─ image, 사진 있음
        ├─ ⓒ 장수 확인 — 실제로 쓸 모델의 상한을 넘으면 멈춘다. 값 0 (§2-6)
        ├─ ⓐ 사진 읽기 — **단추로 고르지 않은 사진만**, 한 장씩 따로 · 동시에(`readAttachments`)
        ├─ ⓑ2 역할 판단 — 글 모델 한 번. 말 + 읽은 설명
        │     사진마다   style · preserve_product · preserve_person ·
        │               preserve_person_restyled · unclear
        │               + said (말이 이 사진의 쓰임을 말했나)
        │     말 전체    같은 사진의 쓰임이 말 안에서 엇갈리나
        ├─ ⓓ 합치기 — 코드. 고른 것 > 말 > 지난 역할 > 판단 > 모름 (§2-4)
        ├─ unclear 가 있다          → 묻고 끝, 아무것도 안 남긴다 (§2-5)
        ├─ 인물 역할 사진이 둘 이상 → 묻고 끝 (§2-5)
        └─ 역할대로 칸을 채워 기존 세 라우트를 부른다 (§2-6)
```

**⓪을 가장 먼저 한다.** 붙인 사진 id 는 화면이 보낸 값이다. 서버에는 「이번에
붙인 사진」의 기록이 따로 없으므로, 요청 안의 두 목록(붙인 것·고른 것)을 서로
견주는 것은 검사가 아니다 — 남의 id 를 두 목록에 똑같이 넣으면 통과한다.
- 이미지 만들기와 **같은 함수로** 조회한다(`posterReferencesByIds` —
  세션 회원·권한·팀 기준, `lib/poster/references.ts:50`)
- 그 함수는 볼 수 없는 id 를 **오류 없이 뺀다**(`reference-images.ts:248`).
  그대로 두면 사진이 빠진 채 만들어지거나, 뒤 사진 번호가 당겨져 말 속의
  「2번」이 다른 사진을 가리킨다. 그래서 **요청한 서로 다른 id 가 전부
  나왔는지** 센다. 모자라면 「붙인 사진 중 쓸 수 없는 것이 있습니다」로 멈춘다 —
  unclear 로 묻지 않고, 조용히 빼지도 않는다
- 같은 id 가 두 번 오면 처음 자리 하나만 남긴다. 번호는 그 차례다
- 만들기 직전에 라이브러리에서 지워지는 경우는 지금의 이미지 만들기와 같다 — 범위 밖

**판단을 둘로 나눈다(ⓑ1 · ⓑ2).** 한 번에 판단하려면 모든 턴이 사진부터 읽어야
하는데, 읽기가 필요한 것은 그림을 만들 턴뿐이다.
- 읽기는 한 장씩 **차례로** 돈다(`read-attachment.ts:183`). 한 번에 판단하면
  사진 다섯 장을 붙인 채 「안녕하세요」라고 해도 답이 다섯 번 읽기를 기다린다
- 붙인 사진은 **보낸 뒤에도 입력창에 남는다** — 비우는 곳이 ✕ 단추 하나다
  (`easy-client.tsx:523`). 한 번에 판단하면 사진을 붙인 채 나누는 말 턴마다
  사진값이 다시 나간다
- 대신 그림 턴은 글 모델이 한 번 는다. 그 턴은 기획과 그림이 뒤따르는 턴이라
  몫이 작다

ⓑ1 은 지금 쓰는 판단(`app/easy/chat.ts`)을 넓힌다 — 원하는 것에 `detail_page`
를 더할 뿐, 사진 역할은 정하지 않는다. ⓑ2 는 새 판단이다. 둘을 따로 잰다(§2-11).

**ⓐ를 ⓑ2 앞에 둔다.** 판단이 「제품 사진은 살려」의 「제품 사진」이 몇 번인지
알아야 하기 때문이다. 읽기는 **이미지 만들기 기획이 쓰는 그 기계**를 쓴다 —
새로 만들면 두 벌이 되고 하나는 곧 낡는다.

**사진을 판단 모델에 직접 넣지 않는다.** 한 번에 여러 장을 주면 모델이 사람과
연출을 뒤섞는다(`read-attachment.ts:168`, 옛 `readPeople` 이 같은 판단을 했다).
한 장씩 읽은 설명을 번호와 함께 준다. **id 는 주지 않는다** — 번호만 주고,
번호를 id 로 바꾸는 것은 코드가 한다. 모르는 번호·모르는 역할이 오면 버린다.

**코드가 묻게 하는 두 경우**(`photo-turn.ts`). 말이 쓰임을 말하지 않았고 단추로
고르지도 않았는데 아래면, 판단이 무엇을 주든 unclear 다. 프롬프트도 그렇게 시키지만
그 문장에만 기대지 않는다(2026-09-30 독립 리뷰 · 사용자 사진 실측).
- 읽지 못한 사진
- 사람이 있고 글자가 없는 사진 · 그림(읽기가 주는 `people` · `hasText` 로 가른다) —
  사용자 사진으로 재 보니 가족 일러스트가 세 번 중 두 번 분위기로 갔다. 다만
  `hasText` 는 작은 글씨 하나에도 참이라, 배경에 간판이 있는 사진은 여기 안 걸리고
  판단을 따른다(알려진 한계)

지난 역할이 있으면 그것이 판단보다 앞서므로 이 가드와 부딪히지 않는다.

**읽기가 실패한 사진**은 설명 없이 ⓑ2 에 간다. 말이 그 사진의 쓰임을 말했으면
그대로, 아니면 unclear 다. **분위기 참고로 떨어지지 않는다** — 그것이 가장
비싼 실수다(§2-11). 주소 서명이 비어 읽을 수 없는 사진도 같다(생성은 주소가
아니라 저장 경로로 올리므로 만들 수는 있다, `generate/route.ts:123`).

### 2-4. 역할을 정하는 규칙

**사용자 말이 먼저다.** 말이 사진을 가리키고 쓰임을 말하면 그대로 따른다.

| 사용자 말 | 사진 | 역할 |
|---|---|---|
| 쓰임을 말했다 — 「1번 제품은 그대로」 · 「이 느낌으로」 · 「1번 사람들을 2번 그림체로」 | 무엇이든 | **말대로** |
| 가리키지만 쓰임이 모호하다 — 「이걸로」 · 「이거 참고해서」 | 한 갈래로만 읽힌다 (제품만 찍힌 사진, 글자와 디자인이 있는 포스터) | 그 갈래 — 제품 사진이면 **제품 유지**, 디자인이면 **분위기 참고** |
| 가리키지만 쓰임이 모호하다 | 두 갈래로 읽힌다 (인물 사진 — 사람을 살릴지 느낌만 볼지) | **unclear** |
| 사진 이야기가 없다 — 「카페 포스터 만들어줘」 | 디자인 참고물(포스터 · 광고 · 카드뉴스) | 분위기 참고 |
| 사진 이야기가 없다 | 제품 · 인물 사진 | **unclear** |

**애매하면 묻는 쪽으로 기운다.** 묻는 값은 0 이고, 틀리게 만들면 값이 나가고
제품이 다시 그려진다. 반대로 **말에 이미 있는 것을 또 묻지 않는다** — 안 들은
것이 된다.

위 표에서 「말대로」인 사진은 ⓑ2 가 `said` 를 참으로 준다 — 말이 그 사진의
쓰임을 말했다는 뜻이다. 나머지(사진을 보고 한 판단, unclear)는 거짓이다.

**최종 역할은 이 차례로 정한다 — 고른 것 > 말 > 지난 역할 > 판단 > 모름.**

| 차례 | 무엇 | 어디서 |
|---|---|---|
| 1 | 물음에서 단추로 고른 역할 | 화면 → 서버가 검사한다(§2-5) |
| 2 | 말이 가리킨 쓰임 (`said` 참) | ⓑ2 |
| 3 | **지난 역할** — 이 대화에서 같은 사진으로 이미지를 만들 때 정해진 역할 | 화면이 들고 있다가 보낸다 → 서버가 검사한다 |
| 4 | 말이 모호할 때 사진을 보고 한 판단 | ⓑ2 |
| 5 | 아무것도 없으면 unclear → 묻는다 | 코드 |

`ask.ts` 의 「고른 것이 가장 세다」와 같은 차례다. 합치는 것은 코드가 한다 —
판단 모델에는 고른 것도 지난 역할도 안 준다. 줘 버리면 말이 무엇을 말했는지
(`said`)를 그것과 떼어 알 수 없다.

**지난 역할(2026-09-30 독립 리뷰 · 사용자 결정).** 붙인 사진은 보낸 뒤에도
입력창에 남는다. 그 사진으로 한 장을 만든 뒤 「좀 더 밝게」처럼 사진 이야기 없이
이어 말하면, 지난 역할이 없을 때는 방금 답한 물음이 **또 뜬다** — 들은 것을 안
들은 것이 된다.
- 그림 턴이 끝나면 서버가 사진마다 최종 역할을 돌려주고, 화면이 사진 id 별로 들고
  있다가 다음 그림 턴에 함께 보낸다. 대화 표에는 안 남는다(마이그레이션 없음) —
  새로고침하면 붙인 사진도 사라지므로 들고 있을 까닭도 같이 사라진다
- 서버는 고른 값과 같은 검사를 한다(⓪ 목록 안의 id · 네 역할 · id 마다 하나)
- **말이 이긴다.** 「이번엔 1번은 느낌만」처럼 말이 그 사진의 쓰임을 말하면 지난
  역할을 덮는다. 단추로 고른 것은 늘 이긴다
- 지난 역할이 있는 사진도 **읽는다**(ⓐ). 처음에는 안 읽었는데 두 번째 독립 리뷰가
  짚었다 — 설명이 없으면 사진이 둘 이상일 때 「제품 그대로 크게」가 어느 사진인지
  판단이 못 가려, 바로잡으려는 말이 무시되거나 엉뚱한 사진이 뒤집힌다
- 이어 만드는 턴이면 ⓑ2 에 **그 사실만** 알린다(지난 역할 자체는 안 준다). 「이
  느낌으로 더 밝게」의 「이 느낌」은 방금 만든 결과를 가리킬 수 있으므로, 번호나
  생김새로 분명히 가리킬 때만 said 로 친다. 실측(§2-11)은 이어 만들기를 **최종
  역할**로 잰다

**말은 떼어 오지 않는다.** 전에는 판단이 말 가운데 사진에 관한 부분을 떼어 오게
하고, 그것이 원문 안에 있는지만 봤다. 원문 안에 있다고 뜻이 지켜지는 것은
아니다 — 「제품을 바꿔 그리지 마」에서 「제품을 바꿔」만 떼어도 원문 안에 있고,
떨어진 지시 둘 중 하나만 떼어도 나머지가 빠진다. 이 말은 그림 모델에서 역할
문구를 **이기는** 자리로 간다(§2-6). 뒤집히거나 잘린 말이 가장 센 말이 된다.
그래서 **이번 요청의 말 전체**(처음 말 + 말로 한 답)를 그대로 쓴다. 떼어 오는
일이 없으면 잘못 뗄 일도 없다. 보낼지 말지만 코드가 정한다(§2-6).

### 2-5. 묻는 모양

```
  ─────────────────────────────────────
  카페 오픈 포스터 만들어줘               ← 사용자 (사진 2장)
  ─────────────────────────────────────
  사진을 어떻게 쓸지 알려 주세요.

   [①사진]  [분위기만 참고] [제품 그대로] [인물 그대로]
   [②사진]  [분위기만 참고] [제품 그대로] [인물 그대로]

   말로 답하셔도 됩니다 — 「1번은 우리 원두 봉투야」
                                      [이걸로 만들기]
  ─────────────────────────────────────
```

- **물음은 코드가 짓는다.** 판단 모델은 어느 사진이 unclear 인지만 말한다.
  같은 상황에 같은 물음이 나와야 사용자가 배운다.
- 분명한 사진은 물음에 **이미 고른 채로** 보인다. 틀렸으면 거기서 바꾼다.
- 「인물은 그대로 두고 그림체만 바꾸기」는 **새 단추로 내지 않는다.** 말로
  받는다 — 단추가 넷이면 읽고 고르는 데 오래 걸리고, 이 역할은 「애니풍으로」처럼
  말에 이미 들어 있을 때가 대부분이다.
- **다만 판단이 그 역할로 정한 사진은, 그 줄에만 「인물 그대로 · 그림체만」이
  고른 채로 보인다.** 담을 자리가 없으면 다시 보낼 때 「인물 그대로」로 바뀌는데,
  그 문구는 그림체 바꾸기를 **금지**한다(`prompt.ts:158` 이 가르는 까닭). 사용자가
  한 말의 반대가 된다.
  - 다른 줄에 답해도 이 줄은 그대로 간다 — 줄마다 따로 들고 있다
  - 이 줄에서 다른 단추를 누르면 그것으로 바뀐다. 표시는 남아 있어 되돌릴 수 있다
  - 다른 줄에는 이 표시가 없다
- **말로 답하면** 처음 말과 답을 **함께** 다시 판단한다. 묻는 동안은 대화 표에
  아무것도 안 남기므로(지금 비율·그림체 물음과 같다), 답만 보내면 처음 말이 사라진다.
  이때 「말 전체」(§2-4)는 처음 말과 답을 이은 것이다.
- **다시 보낼 때도 ⓑ1·ⓑ2 를 다시 돈다.** 고른 역할이 판단보다 세다(§2-4).
  **단추로 고른 사진은 읽지 않는다**(ⓐ). 모두 골랐으면 ⓐ 는 통째로 건너뛰고 ⓑ2 는
  말만 본다 — 역할은 이미 정해졌지만, 말과 고른 것이 부딪히는지는 알아야 한다(§2-6).
- 고른 값은 **서버가 다시 확인한다.**
  - ⓪에서 확인한 사진의 id 인가 — 그 밖의 id 는 버린다
  - 네 역할(`style` · `preserve_product` · `preserve_person` ·
    `preserve_person_restyled`) 가운데 하나인가
  - 같은 id 가 한 번만 왔나 — 두 번 오면 둘 다 버린다

  어긋난 줄은 고른 것이 없는 것으로 치고, 그 사진은 판단대로 간다. 판단도 없으면
  unclear 다.
- **인물 역할인 사진이 둘 이상이면** 한 장만 된다고 말하고 같은 물음 모양으로
  다시 묻는다. 둘이면 얼굴이 섞인다. 인물 역할(「인물 그대로」·「인물 그대로 ·
  그림체만」)은 한 줄에서만 고를 수 있고, 서버도 같은 셈으로 다시 센다.
- **세는 단위는 사람이 아니라 장이다.** 단체 사진 한 장은 1이다.
  - 이미지 만들기가 같은 단위로 센다. 최종 프롬프트의 「인물이 여럿이면 첫
    사람만」은 인물 역할인 **장**을 센다(`prompt.ts:222`). 단체 사진 한 장을 그대로
    지키는 것은 이미 되는 일이다(「사진 다섯 명을 만화로」, `attachment-role.ts:34`)
  - 사진 속 사람 수는 읽어야 안다. 읽기를 건너뛰거나 실패한 사진은 모른다. 장은
    언제나 안다
  - **캐릭터 예외(같은 캐릭터의 여러 각도는 한 명)는 「쉽게」에 없다.** 「쉽게」의
    첨부에는 캐릭터 표시가 없고(`easy-client.tsx:59`), 이미지 만들기 화면도 그
    표시를 제목을 맞춰 짐작한다(`reference-picker.tsx:239`). 최종 프롬프트는 그
    예외를 모른다(위 `prompt.ts:222`)
  - 셈은 `@fixup/shared` 의 `countPreservedPeople` 를 그대로 쓴다. 캐릭터 표시 없이
    넘기면 장마다 1로 센다
- 비율·그림체 물음은 **사진이 없을 때만** 나온다(지금 그대로). 두 물음이 한 턴에
  겹치지 않는다.

### 2-6. 이미지 만들기로 넘기는 것

| 판단 | 칸 |
|---|---|
| style | `referenceIds` |
| preserve_product | `preservedIds` |
| preserve_person | `preservedIds` + `personIds` |
| preserve_person_restyled | `preservedIds` + `personIds` + `restyledIds` |
| 말 전체 (조건부, 아래) | `attachmentIntent` |
| 붙인 순서 | `attachmentOrder` — **사용자가 붙인 순서 그대로** |

- **세 목록은 포함 관계를 지킨다 — `restyledIds ⊆ personIds ⊆ preservedIds`.**
  「쉽게」가 보장한다. 까닭은 주소와 셈이다.
  - 이미지 만들기는 올릴 그림을 `referenceIds`·`preservedIds` 에서만 찾는다
    (`generate/route.ts:116-126`). `personIds` 에만 있으면 주소가 없어 첨부가
    **통째로 빠진다**(`attachment-restore.ts:57`)
  - 차례(`attachmentOrder`)에 넣으면 차례 검사가 「첨부와 차례가 어긋난다」로
    거절한다(`schemas.ts:218-231`)
  - 옛 경로(`orderFromLegacyLists`)와 장수 셈(`generate.ts:137`)도 두 목록만 센다
  - 전에 적은 「빠지면 조용히 따라 만들기가 된다」는 **틀렸다.** 차례가 있으면
    역할은 `personIds` 만으로도 되살아난다(`attachment-restore.ts:31`). 틀리는
    모양은 「따라 만들기」가 아니라 「빠짐」이나 「거절」이다
- 붙인 수는 **서로 다른 사진 수**로 센다. 값 셈(`easyCost`)이 같은 수를 쓴다.
- **장수는 기획 전에 본다(ⓒ).** 이미지 만들기는 모델 상한을 **그림을 만들기
  직전**에 본다(`generate.ts:137`). 「쉽게」는 그 전에 기획을 돌려 값을 확정한다
  (`plan/route.ts:193`). 크레딧 계정으로 전환하지 않은 회원(cost-v1)은 기획값이
  빠지고(`credit_reserve_dispatch` → `reserve_generation_cost_v1`), 그다음에 그림이
  거절된다. 경제형(`nano-banana`)은 7장까지다(`models.ts:218`).
  - ⓒ은 **생성 라우트와 같은 모델 고르기**로 실제로 쓸 모델을 정한다 —
    `chooseModelForRatio(비율, 고른 모델, IMAGE_MODELS)`(`generate/route.ts:138`).
    비율 때문에 모델이 바뀌면 상한도 바뀐다. 고른 모델로 보면 틀린다
  - 서로 다른 사진 수가 그 모델의 `maxReferenceImages` 를 넘으면 멈추고, 모델
    이름과 상한을 말한다(「경제형은 7장까지입니다 — 지금 8장」)
  - 멈추면 프로젝트·기획·생성 라우트를 **아예 안 부르고 사진도 안 읽는다.**
    예약이 없으니 두 정책(cost-v1 · image-v2) 모두 값이 0 이다
  - 그 밖에 생성 단계에서 늦게 거절되는 것(이번 달 한도 등)은 지금의 이미지
    만들기와 같다 — 이 단계 범위 밖
- **`attachmentIntent` 는 말과 최종 역할이 맞을 때만 보낸다.**
  이 말이 있으면 이미지 만들기는 「사용자 말이 부딪히는 규칙을 이긴다」를
  붙이고(`prompt.ts:203`), 말을 프롬프트 맨 앞과 맨 뒤에 둔다(`prompt.ts:362`).
  말과 역할이 어긋난 채 보내면 **말이 이긴다.** 처음에 「1번 제품은 그대로」라고
  쓰고 물음에서 1번을 「분위기만 참고」로 바꾸면, 프롬프트는 「이 그림의 제품을
  베끼지 마라」와 그것을 이기는 「1번 제품은 그대로」를 함께 받는다.

  보내는 조건 — **셋 다** 맞아야 한다.
  1. 말이 사진의 쓰임을 말했다 — `said` 인 사진이 하나 이상. 사진 이야기가 없는
     말은 지금처럼 안 보낸다
  2. 고른 것이 말을 뒤집지 않았다 — `said` 인 사진마다 최종 역할이 말의 역할과 같다
  3. 말 안에서 같은 사진의 쓰임이 엇갈리지 않았다 — ⓑ2 가 알린다(「1번은
     그대로 해줘. 아 아니다, 느낌만」)

  하나라도 아니면 **역할 문구만** 간다. 말은 지금처럼 기획(`instruction`)으로만
  가고, 기획은 사진마다 최종 역할 이름을 함께 본다(`planReferences` 의
  `roleLabel`). 기획이 채운 칸은 역할 문구를 이기는 자리가 아니다 —
  「사용자 지시」로 가지 않는다.
- 보낼 때는 안 부딪히는 규칙이 그대로 산다(「부딪히는 것만 이긴다」). 제품
  유지 문구는 사용자가 반대로 말하지 않는 한 산다.
- 이 규칙은 **최종 프롬프트로 잰다.** 「쉽게」가 만든 칸을 `buildPosterPrompt`
  에 그대로 넣어, 부딪히는 경우에는 「첨부한 그림에 대해」가 없고 그 사진이
  `POSTER REFERENCE` 인지, 맞는 경우에는 둘 다 있는지 본다(§2-11). 칸 나누기만
  재면 이 사고를 못 잡는다.

### 2-7. 상세페이지 안내

- 판단이 `detail_page` 면 **만들지 않는다.** 내 말과 안내 한 줄을 남긴다.
- 안내 문구는 **코드가 정한 한 문장**이다. 모델이 짓게 두면 매번 다른 길을 알려 준다.
- 안내 줄 밑에 `[상세페이지 만들기 열기]` 단추를 단다(`/create`). 다시 열어도
  단추가 보이게, 화면은 **그 문구와 똑같은 줄**에만 단추를 단다 — 표를 바꾸지 않는다.
- 값은 판단(ⓑ1) 한 번뿐이다. **제품 사진을 붙여도 읽지 않는다** — ⓑ1 이
  상세페이지로 가르면 ⓐ까지 가지 않는다(§2-3). 회원 크레딧은 안 빠진다.

### 2-8. 판단 결과를 보여 준다

- 결과 밑 「만든 조건」에 `①제품 유지 · ②분위기 참고` 를 적는다.
- **다시 열어도 보인다.** 역할은 이미지 만들기 작업에 이미 저장된다(`referenceIds`
  · `preservedIds` · `personIds` · `restyledIds` · `attachmentOrder`). 거기서 읽는다 —
  대화 표에 베끼면 어긋난다(`_components/load.ts` 가 모델·비율을 읽는 방식과 같다).

### 2-9. 값

- 회원이 보는 값은 **그대로다.** 판단은 지금도 크레딧을 잡지 않는 자리이고, 사진
  읽기와 역할 판단도 그 자리에 붙는다.
- **운영비는 그림 턴에만 는다.** 말 턴과 상세페이지 안내 턴은 지금과 같다(판단 한
  번). 그림 턴은 역할 판단 한 번과, 단추로 안 고른 사진 수만큼의 읽기가 더해진다.
  기획이 같은 사진을 한 번 더 읽는다 — 기획 라우트는 안 바꾸므로 넘겨줄 길이 없다.
- 한 턴에 읽는 장수는 ⓒ가 모델 상한 이하로 막는다(7~16장).
- `llmCostUsd({ visionReads: 1 })` 는 **어림**이다(`credit.ts:58` — 한 장 $0.007
  로 박아 둔 값). 실측(§2-11)은 계량기(`withLlmMeter`)로 실제 값을 잰다.
  두 판단과 읽기는 이미 토큰을 계량기에 적는다(판단은 공용 어댑터가 —
  `lib/llm/structured.ts:79,111`, 읽기는 `lib/poster/providers.ts:142`). 빠진 것은
  **계량기로 감싸는 자리**다 — 「쉽게」 라우트가 `withLlmMeter` 밖에서 부른다.
- **담아 두지 않는다.** 읽기가 그림 턴에만 돌므로, 같은 사진을 다시 읽는 것은
  같은 사진으로 그림을 또 만들 때뿐이다. 실측에서 기다림이나 값이 크다고 나오면
  그때 붙인다.
- **장부 기록과 시간당 한도 — B 로 정했다**(2026-09-30 사용자 승인).
  지금 「쉽게」의 판단은 장부에 안 적히고 한도도 없다 — 예약 없이 부르고
  (`api/easy/generate/route.ts:149`), 계량기 밖이라 값도 버려진다(`meter.ts:41`).
  이 단계가 그 자리에 읽기를 더한다. CS 도우미처럼 장부에 실으려면(`cs/ask/route.ts:70`
  — 크레딧 0 예약 + 계량 + 확정, 시간당 60번) **새 작업 종류**가 필요하고, 그것은
  `reserve_generation` 전체를 다시 쓰는 마이그레이션이다(선례
  `202609280001_cs_ask_operation.sql`, 304줄).
  - **A.** 이 단계에 넣는다. 정확하다. 다만 다른 터미널이 크레딧 장부를 고치는
    중이라, 같은 함수를 두 가지(branch)가 각자 다시 쓰게 된다 — 나중에 돌린 쪽이
    앞의 것을 덮는다
  - **B. (권장)** 이 단계는 마이그레이션 없이 간다. 읽기를 그림 턴 · 안 고른 사진 ·
    모델 상한으로 줄이고, ⓑ1 · ⓐ · ⓑ2 를 계량기로 감싸 실제 값을 서버 기록(journalctl)에
    한 줄 남긴다. 장부·한도는 크레딧 작업이 master 에 들어간 뒤 작은 후속으로 한다

  아래 §2-10 은 B 를 기준으로 적었다. 후속(장부·한도)은 이 문서의 범위 밖이다.

  제품이 다시 그려진다. 설명 없이 간 사진도 같다
- 말에 쓰임이 있는데 되묻는 것 0건
- 정정을 엇갈림으로 못 알아본 것 0건 — 알아보지 못하면 뒤집힌 말이 그림 모델까지 간다
- 나머지는 표와 맞는다. 어긋나면 프롬프트를 고치고 다시 잰다

**시험으로 잠근다**

- ⓪ 사진 확인 — 하나라도 안 나오면 멈추고, 판단·읽기·라우트를 하나도 안
  부르고, 아무것도 안 남기는지. 같은 id 는 한 번만, 차례는 처음 자리
- 고른 값 검사 — 네 역할만, id 마다 하나, ⓪ 목록 밖의 id 는 버리는지
- 판단 응답 읽기 — 모르는 번호·모르는 역할은 버리고 unclear 로
- 합치기 — 고른 것 > 말 > 판단 > unclear. 설명 없이 간 사진이 분위기 참고로
  안 떨어지는지
- 칸 나누기 — `restyledIds ⊆ personIds ⊆ preservedIds`, 차례 = 붙인 순서, 결과가
  `PosterProjectInputSchema` 를 통과하는지
- 말 보내기 — 세 조건을 하나씩. 그리고 **최종 프롬프트**: 칸을 `buildPosterPrompt`
  에 넣어, 부딪히는 경우에는 「첨부한 그림에 대해」가 없고 그 사진이
  `POSTER REFERENCE` 인지, 맞는 경우에는 둘 다 있는지
- 인물 장 수 — 단체 사진 한 장은 1, 인물 역할 둘이면 묻는지
- 장수 상한 — 실제로 쓸 모델 기준(비율 때문에 모델이 바뀌는 경우 포함). 넘으면
  읽기 · 프로젝트 · 기획을 하나도 안 부르는지
- 라우트 — talk · detail_page 에서 사진을 안 읽는지, 물을 때 아무것도 안
  남기는지, detail_page 에서 값이 안 나가는지, 역할이 이미지 만들기 칸까지 가는지
- 화면 — 「그림체만」 줄이 다시 보낼 때 그대로 가는지, 다른 줄에 답해도 남는지,
  다른 단추를 누르면 바뀌는지
- 뮤테이션 — 규칙 하나씩 무력화해 시험이 잡는지 본다
- 독립 리뷰 — 다른 에이전트가 따로 본다

**정한 것**

- 사진 없이 요청하면 따라 만들 카드뉴스를 요청한다(§0-4)
- 사진 역할은 1단계의 판단을 넓혀 쓴다 — 카드뉴스 쪽 갈래(원본 그대로 한 장 ·
  마지막 장 · 표지/속지/엔딩 자리)를 더한다
- 원고를 보여 주고 「이대로 만들기 · 약 N크레딧」으로 확인받은 뒤 그림을 만든다
- 기사 주소는 카드뉴스가 켜질 때 같이 켜진다. 「쉽게」가 따로 켜지 않는다

**2단계 설계에서 정할 것**: 카드뉴스와 이미지 한 장을 어떻게 가르나(09-19 §12 의
실측) · 옵션을 어느 때 버튼으로 내나 · 결과 칸이 여러 장을 어떻게 받나 · 대화 표에
원고 줄을 어떻게 남기나(마이그레이션) · 화면을 떠나도 계속 만들어지게(셸의
`RunningJobsProvider`).
