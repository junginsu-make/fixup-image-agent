# 스타일 레퍼런스 RAG (프로젝트 H)

작성일: 2026-07-27

## 되는 것을 먼저 확인했다

설계 전에 가장 위험한 가정부터 쟀다. **스타일 레퍼런스 한 장이 결과를 바꾸는가.**

같은 프롬프트로 두 장을 만들고 한쪽에만 레퍼런스(짙은 네이비 + 머스터드 옐로,
굵은 압축 서체)를 넣었다.

| | 레퍼런스 없이 | 레퍼런스와 함께 |
|---|---|---|
| 색 | 크림·따뜻한 갈색 | 네이비 + 머스터드 옐로 |
| 서체 | 가는 명조 | 굵은 압축 산세리프 |
| 그 외 | — | 레퍼런스의 노란 가로 규칙선까지 옮겨왔고, 제품 라벨도 같은 색으로 다시 디자인됐다 |

**효과는 확실하고, 예상보다 세다.** 텍스트로 정한 designSystem 보다 힘이 세다.

## 그래서 위험한 것

이 강도가 그대로 문제가 된다. 레퍼런스가 디자인을 지배하므로, 같은 레퍼런스를
계속 쓰면 **모든 페이지가 서로 닮는다** — "템플릿 같다"는 결과다.

사용자는 반영 강도를 **디자인 전체**로 정했다. 통일감을 택한 것이다.
그렇다면 템플릿화를 막는 책임은 **레퍼런스를 여러 종 갖추고 주제에 맞게 고르는 쪽**에
있다. 레퍼런스가 한 종뿐이면 이 기능은 해가 된다.

## 설계

### 1. 페이지당 한 장만 쓴다

섹션마다 다른 레퍼런스를 뽑으면 안 된다. 우리가 designSystem 으로 어렵게 맞춰 놓은
섹션 간 통일이 그대로 깨진다. **레퍼런스는 시나리오 단계에서 한 번 고르고,
그 페이지의 모든 섹션이 같은 것을 쓴다.**

### 2. 이미지가 아니라 설명을 검색한다

브리프(텍스트)로 레퍼런스(이미지)를 찾아야 한다. 이미지 임베딩을 따로 두지 않고,
**Gemini 로 이미지를 읽어 디자인 특성을 한국어로 서술**한 뒤 그 텍스트를 임베딩한다.

이유는 두 가지다. 기존 저장소(1536차원 텍스트 임베딩)를 그대로 쓸 수 있고,
찾으려는 것이 "무엇이 찍혔는가"가 아니라 **"어떤 인상을 주는 디자인인가"**라
어차피 언어로 표현하는 편이 정확하다.

서술에 담을 것: 팔레트 / 서체 성격 / 구성 / 분위기 / 어울리는 상품군.

### 3. 자동 추천하되 반드시 보여주고 바꿀 수 있게 한다

프로젝트 G 에서 배운 것이 있다. **레퍼런스가 몇 장뿐일 때 검색 순위는 못 믿는다.**
그러니 자동으로 고르되 화면에 무엇을 골랐는지 유사도와 함께 보여주고,
바꾸거나 끄게 한다. 몰래 적용하지 않는다.

유사도 하한 미달이면 아무것도 고르지 않는다. 어울리지 않는 레퍼런스를 강제로
씌우면 없느니만 못하다 — 강도가 "디자인 전체"라 더욱 그렇다.

### 4. 세 갈래로 채운다

사용자가 셋 다 고른 대로 전부 지원한다.

- **직접 업로드** — 잘 만든 상세페이지 스크린샷 등. 품질이 가장 좋다
- **스타일 견본** — 서로 다른 디자인 방향 8~12종을 생성해 초기 라이브러리로 넣는다.
  즉시 쓸 수 있고, 무엇보다 **여러 종을 갖춰 템플릿화를 막는다**
- **생성 결과 재사용** — 마음에 든 결과를 레퍼런스로 저장한다

### 5. pdp-core 는 DB 를 모른다

프로젝트 G 와 같은 구조다. 순수 로직(분석 프롬프트, 선택 규칙)은 pdp-core,
DB 는 redesign-core, 둘을 잇는 것은 라우트. pdp-core 테스트가 DB 없이 돈다.

## 저장

```sql
CREATE TABLE style_references (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name         text NOT NULL,
  source       text NOT NULL,        -- upload | specimen | generated
  image_base64 text NOT NULL,
  mime_type    text NOT NULL,
  description  text NOT NULL,        -- 검색 대상
  embedding    vector(1536) NOT NULL,
  content_hash text NOT NULL UNIQUE,
  created_at   timestamptz NOT NULL DEFAULT now()
);
```

이미지를 Postgres 에 base64 로 둔다. 1024px JPEG 한 장이 약 150KB, base64 로 200KB다.
100장이면 20MB로 Neon 이 감당한다. S3 를 붙이는 것은 수요가 확인된 뒤에 한다.

## 흐름

```
[등록]  이미지 → Gemini 분석(디자인 특성 서술) → 임베딩 → 저장

[사용]  브리프 → 임베딩 → 유사도 검색 → 상위 1장(하한 미달이면 없음)
           ↓
        시나리오 화면에 표시 (바꾸기 / 끄기 가능)
           ↓
        확정된 1장을 그 페이지 모든 섹션 생성에 참조로 전달
```

## 하지 않는 것

- **섹션마다 다른 레퍼런스** — 통일이 깨진다
- **레퍼런스로 이미지 재생성 루프** — 비용이 뛴다. 강도 조절은 사용자가 끄는 것으로 충분
- **사용자별 레퍼런스 분리** — 지금은 공용 하나. 수요 확인 후
- **S3 등 외부 저장소** — 100장 수준까지는 필요 없다

## 단계

| 단계 | 내용 | 검증 |
|---|---|---|
| H1 | 저장소 + 이미지 분석 + 등록 | 실제 이미지를 넣고 서술·검색이 되는지 |
| H2 | 스타일 견본 8~12종 생성·시딩 | 서로 충분히 다른지 눈으로 확인 |
| H3 | 검색 + 생성 연결 (페이지당 1장) | 레퍼런스 유무로 결과가 달라지는지 |
| H4 | UI — 추천 표시·교체·끄기·업로드·결과 저장 | 브라우저로 끝까지 |
