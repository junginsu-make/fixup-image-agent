# 글기반 상세페이지 — 표현 강도·빈칸 처리 손잡이와 근거 추적 설계

- 작성일: 2026-07-29 (Codex 리뷰 반영 개정)
- 대상: `/create` 의 **글로 시작하는 경로**(무형 상품). 사진으로 시작하는 경로는 건드리지 않는다.
- 상태: 설계 승인 대기

> **개정 이력**
> 초안은 세 가지를 잘못 짚었다. Codex 리뷰가 지적했고 코드로 확인했다.
> ① "서버 게이트는 우회 불가" — 거짓. 서버는 클라이언트가 보낸 구성안을 받는다(§6-4)
> ② "기존 심사 루프 재사용은 공짜" — 거짓. 심사자가 원문을 못 보는 것은 의도적 설계다(§6-1)
> ③ 문구를 고치면 근거가 낡는 것을 감지할 구조가 없었다(§3-1)

## 1. 왜 하는가

무형 상품(강의·코칭·구독·소프트웨어)은 보여 줄 실물이 없어, 상세페이지가 **글로만 이루어진다.**
사용자가 넣은 짧은 텍스트 하나에서 6~8개 섹션의 카피를 지어내야 한다.

**문제 1 — 원문에 없는 사실이 섞여도 아무도 모른다.**
브리프 단계에는 추정을 적어 두는 `assumptions` 가 있다(`pdp.text-plan.ts:83`).
섹션 카피 단계에는 원문과 대조하는 장치가 없다.
`pdp.sales-principles.ts:190` 은 **"근거 없는 숫자 — 신뢰를 통째로 잃는다. 법적 문제도 된다"**
라고 못 박고 있으나, 지키는지 확인하는 코드가 없다.

**문제 2 — 사용자가 톤을 조절할 수 없다.**
담백하게 쓸지 세게 후킹할지는 판매자마다 다른데 지금은 고정이다.

### 하지 않는 것

- HTML 렌더 출력 경로 — 별개 작업
- 사진으로 시작하는 경로(`analyze`)의 카피
- 구성안의 서버 저장(§6-4에서 이유를 밝힌다)

## 2. 손잡이 정의

두 값 모두 `TextPlanRequest` 에 실려 오고, 없으면 기본값을 쓴다. **기존 호출을 깨지 않는다.**

**어디에 두는가:** 상태는 `TextModeFlow` 가 소유하고 **입력 화면(`TextBriefInput`)에 노출**한다.
구성안 요청은 시나리오 화면에 닿기 전 `handlePlan()` 에서 나가므로(`TextModeFlow.tsx:83`),
시나리오 화면에만 두면 첫 생성에 아무 영향이 없다.

동시에 시나리오 화면에 **「설정 바꿔 다시 만들기」**를 둔다. 손잡이를 돌려 결과가 어떻게
달라지는지 보는 것이 이 기능의 핵심 경험이고, **구성안 생성은 크레딧을 쓰지 않는다**
(`plan-from-text/route.ts:20` — *"이미지를 만들지 않는 단계라 크레딧은 소모하지 않는다"*,
`reserveAiUsage(req, "pdp_analyze", 0)`). 시간당 횟수 제한만 걸린다.
재생성하면 구성안이 통째로 새것이 되므로 **기존 근거와 확인은 전부 버린다.**

### 2-1. 표현 강도 `copyIntensity`

사실은 건드리지 않고 **문장의 세기만** 바꾼다.

| 값 | 뜻 |
|---|---|
| `plain` | 담백. 사실 나열에 가깝게. 감탄·도발 없음 |
| `normal` (기본) | 지금 수준 |
| `strong` | 불편을 크게 부각. 대비를 세우고 단정형을 쓴다 |
| `max` | 도발적 질문·강한 단정·짧은 문장. 첫 3초를 우선한다 |

**의도한 성질: 강도를 올려도 사실 주장이 새로 생기지 않는다.**
이것은 프롬프트로 유도하는 목표이지 코드가 강제하는 불변식이 아니다.
모델은 확률적이라 두 번 생성한 결과의 사실 집합이 정확히 같기를 요구할 수 없다.
그래서 **완료 기준이 아니라 관찰 지표**로 둔다(§7).

### 2-2. 빈칸 처리 `gapPolicy`

원문에 근거가 없는 사실이 필요할 때.

| 값 | 동작 |
|---|---|
| `omit` | 그 문장을 쓰지 않는다 |
| `ask` (기본) | 자리를 비우고 `ask` 딱지를 단다. `note` 에 "실제 수강생 수" 처럼 무엇이 필요한지 적는다 |
| `sample` | 그럴듯한 값을 채운다. 반드시 `sample` 딱지가 붙는다 |

`sample` 은 빈 화면 앞에서 막히는 사용자를 위한 것이다. **채운 값은 끝까지 미검증이다.**
확인 화면(§5)을 지나기 전에는 이미지 생성으로 넘어갈 수 없다.

## 3. 핵심 장치 — 문장마다 근거를 단다

모델에게 "지어내지 마라"고 지시하는 대신 **"이 문장의 근거가 무엇인지 같이 적어라"**고 시킨다.

### 3-1. 근거 딱지

문장을 **문자열 경로가 아니라 타입 있는 목표**로 가리킨다. 문자열 경로(`"S3.bullets[1]"`)는
오타에 약하고, 섹션 안에 저장되므로 섹션 id 는 애초에 중복이다.

```ts
export type CopyTarget =
  | { slot: "headline" | "subheadline" | "trust_or_objection_line" | "CTA" }
  | { slot: "bullet"; index: number }
  /**
   * 이미지 장면 지시도 주장을 만든다(§4-2). 사용자가 화면에서 고치는 것은
   * 한국어 쪽뿐이고, prompt_en 은 여기서 파생되므로 근거 대상은 prompt_ko 하나다.
   */
  | { slot: "prompt_ko" };

export type EvidenceKind = "quoted" | "rhetoric" | "sample" | "user" | "ask";

export interface CopyEvidence {
  target: CopyTarget;
  /**
   * 딱지를 붙일 당시의 **정확한 문구**. 사용자가 문장을 고치면 이 값과 어긋나고,
   * 그 순간 이 근거는 낡은 것으로 판정된다(§3-4). 확인도 함께 무효가 된다.
   */
  value: string;
  kind: EvidenceKind;
  /** kind=quoted 일 때만: 사용자 원문에서 그대로 따온 근거 문장 */
  quote?: string;
  /** kind=sample 일 때만: 무엇을 채웠는지 한국어 한 줄 */
  note?: string;
  /** kind=sample 을 사용자가 확인한 시각(ISO). 화면에서만 찍힌다(§3-3) */
  acknowledgedAt?: string;
}
```

| 딱지 | 뜻 | 확인 필요 |
|---|---|---|
| `quoted` | 사용자 원문에 근거가 있다 | 아니오 |
| `rhetoric` | 사실 주장이 아니다 (감정·질문·비유) | 아니오 |
| `user` | 확인 화면에서 사용자가 직접 써 넣었다. **검증됐다는 뜻이 아니다** | 아니오 |
| `sample` | 우리가 채운 값. 사실이 아니다 | **예** |
| `ask` | 근거가 없어 비워 둔 자리. `note` 에 무엇이 필요한지 적는다 | **예** |

`ask` 를 딱지로 둔다. 자리표시자를 본문 정규식(`{{...}}`)으로 찾으면 "무엇이 필요한지"를
안정적으로 담을 곳이 없고, 강등·수정·삭제·수집이 서로 다른 경로를 타게 된다.
딱지로 두면 넷이 같은 구조를 쓴다.

**한 target 에 여러 성격이 섞이면 가장 위험한 것을 쓴다.**
`sample` > `ask` > `quoted` > `rhetoric`.
예: 서브헤드라인에 인용된 사실과 우리가 채운 수치가 함께 있으면 그 target 은 `sample` 이다.
근거는 target 당 **하나**만 둔다 — 여럿을 허용하면 화면·게이트·수정이 전부 복잡해진다.

### 3-2. 어디에 담기는가

```ts
export interface SectionBlueprint {
  // ... 기존 필드 전부 유지
  evidence?: CopyEvidence[];
}
```

집계는 저장하지 않는다. 순수 함수로 그때그때 계산한다.

```ts
/** 화면과 서버가 같은 함수를 쓴다. */
export function collectUnverified(blueprint: LandingPageBlueprint): UnverifiedItem[];

/** 근거 하나가 지금도 유효한가. value 대조 + target 존재 확인. */
export function validateEvidenceBinding(section: SectionBlueprint, ev: CopyEvidence): BindingState;

/** target 으로 읽고 쓴다. 화면·서버·테스트가 전부 이 둘만 쓴다. */
export function readCopyTarget(section: SectionBlueprint, target: CopyTarget): string | undefined;
export function writeCopyTarget(section: SectionBlueprint, target: CopyTarget, value: string): SectionBlueprint;

/** 불릿을 지우거나 끼워 넣을 때 인덱스와 근거를 함께 재배열한다. */
export function spliceBullet(section: SectionBlueprint, index: number, insert?: string): SectionBlueprint;
```

### 3-3. 모델이 만들 수 없는 것 (정규화에서 잘라낸다)

모델 응답을 그대로 믿지 않는다. `normalizeTextBlueprint` 가 아래를 **버린다.**

- `kind: "user"` — 사용자만 만들 수 있다. 모델이 적으면 `sample` 로 강등한다
- `acknowledgedAt` — 확인 화면에서만 찍힌다. 모델이 적으면 지운다
- 존재하지 않는 `target` — 구조 검증 실패로 본다(§3-5)
- 같은 `target` 에 근거가 둘 이상 — 구조 검증 실패로 본다
- `kind: "ask"` 인데 `note` 가 비었다 — 무엇이 필요한지 모르면 사용자가 채울 수 없다

**막지 못하는 것:** 모델이 사실 주장을 `rhetoric` 으로 표시하는 위장.
`rhetoric` 도 유효한 근거라서 "누락"으로 잡히지 않고, 그것이 진짜 수사인지 판단하려면
의미를 읽어야 한다 — 이번 범위 밖이다(§8).

**보조 방어 하나만 둔다.** `rhetoric` 으로 표시된 문구에 **숫자·기간·비율·가격·금지 키워드**가
들어 있으면 구조 검증 실패로 본다. 위장의 전부는 아니지만 가장 위험한 형태는 잡힌다.

### 3-4. 문구가 바뀌면 근거는 낡는다

`ScenarioEditor.tsx:260` 의 `patchSection` 은 `Partial<SectionBlueprint>` 를 단순 병합한다.
그래서 사용자가 헤드라인을 전혀 다른 주장으로 바꿔도 옛 근거가 그대로 남는다.

**판정은 저장이 아니라 계산으로 한다.** `validateEvidenceBinding` 이 매번 `evidence.value` 와
현재 필드값을 대조한다.

| 상태 | 뜻 | 처리 |
|---|---|---|
| `fresh` | `value` 가 현재 문구와 같다 | 그대로 |
| `stale` | 문구가 바뀌었다 | 근거·확인 모두 무효. **미확인으로 되돌린다** |
| `dangling` | `target` 이 없다(불릿 삭제 등) | 근거를 버린다 |

사용자가 확인 화면에서 고친 값은 `writeCopyTarget` 과 함께 근거를 `{ kind: "user", value: 새 문구 }`
로 다시 쓴다. 그래서 고친 직후에는 항상 `fresh` 다.

### 3-5. 구조 검증 실패 시 (fail-closed, 단 결과는 돌려준다)

근거 구조가 어긋나면 **재생성을 요청한다.** 기존 심사 재생성 루프와 같은 예산을 쓴다.
재시도를 소진하면 실패 종류마다 다르게 처리한다 — 한 가지로 뭉뚱그리면
"알 수 없는 target" 때문에 멀쩡한 문구가 지워진다.

**문구를 지우는 것은 마지막 수단이다.** 구조 실패의 대부분은 모델이 *딱지를* 잘못 단
것이지 문장이 나쁜 것이 아니다. 특히 **입력이 짧으면 인용할 원문이 없어** 모델이 자기가
쓴 문장에 `quoted` 를 달고, `bad_quote` 가 무더기로 난다.

> **실측 (2026-07-29):** `"요가 강의 팝니다"` 한 줄 입력 + `gapPolicy: "sample"` 로
> 돌렸더니 구조 실패 5건이 전부 `bad_quote` 였고, 강등이 그 문구들을 지워
> **헤드라인·서브헤드라인 10칸 중 9칸이 비었다.** 모델이 쓴 카피 자체는 멀쩡했다
> ("퇴근 후 어깨가 돌처럼 굳어있나요?"). 이 기능이 도우려던 사용자가 빈 페이지를 받았다.

그래서 **빈칸 처리 정책을 따른다.** 원문에 없는 문장은 곧 우리가 지어낸 값이고,
그것은 지울 대상이 아니라 **표시할 대상**이다.

| 실패 종류 | `gapPolicy: "sample"` | `ask` · `omit` |
|---|---|---|
| 잘못된 인용 · 근거 누락 · 중복 · 숫자 든 `rhetoric` | **문구를 살리고 `sample` 로 표시** | `ask` 로 강등 (문구 비움 + `note`) |
| 금지 분류 적발 | **정책과 무관하게 `ask` 로 강등** — 표시로 해결되지 않는다 | 〃 |
| 원래 비어 있던 자리 | `ask` 그대로 | 〃 |
| 존재하지 않는 target 을 가리키는 근거 | 그 **근거 항목만 버린다.** 실제 필드는 건드리지 않는다 | 〃 |

> **수정 후 재실측:** 같은 입력에서 **빈칸 0개**, "예시" 표시 2건(둘 다 원문에 없는
> "20분"). 나머지 카피는 살아남았다.

**알 수 없는 target 을 임의의 실제 필드로 옮겨 강등하지 않는다.** 어디를 고쳐야 하는지
사용자가 알 수 없게 된다.

> 구성안 자체를 실패시키지 않는 이유: `pdp.text-plan.ts:585` 는 *"심사 때문에 생성 자체가
> 죽으면 손해가 더 크다"*, `:601` 은 *"함수가 상한에 걸려 죽으면 사용자는 몇 분을 기다리고도
> 아무것도 못 받는다"* 고 적고 있다. 이 원칙을 깨지 않는다.
> 강등된 자리는 비어 있어 눈에 띄고, 게이트가 막으므로 조용히 새지 않는다.

### 3-6. 사실 주장과 수사의 경계

**사실 주장 (근거 필요)** — 숫자·기간·비율·순위·인증·수상·보장·기능 유무·가격·후기 인용
**수사 (근거 불필요)** — 감정 묘사, 질문, 비유, 호칭, 사실을 함의하지 않는 권유

경계가 애매하면 **사실 주장으로 분류한다.**

## 4. 금지 분류 — 예시로 채우지 않는 것

### 4-1. 목록과 적발 후 동작

`gapPolicy: "sample"` 이어도 아래는 채우지 않는다.

| 분류 | 예 |
|---|---|
| 수익·성과 보장 | "월 500만 원", "3개월이면 퇴사", "확정 수익" |
| 의학적·신체적 효능 | "아토피 개선", "체지방 감소", "탈모 완화" |
| 인증·수상·순위 | "국내 1위", "식약처 인증", "특허 출원" |

**적발되면:** 재생성 → 재시도 소진 시 해당 자리를 **`ask` 로 강등**(문구를 비우고 `note` 를 남긴다).
근거만 조용히 버리고 문구를 남기는 동작은 금지한다.

구현은 `pdp.claim-policy.ts` 한 곳. 프롬프트 규칙 + 생성 후 키워드 스캔 **두 겹**.

**이 목록은 완전하지 않다.** 표시광고법은 세 분류에 한정하지 않고 소비자를 오인시킬 우려가 있는
거짓·과장 광고 전반을 금지한다(제3조). 이 목록은 **위험이 특히 큰 것을 걸러내는 그물**이지
"나머지는 안전하다"는 보증이 아니다.

### 4-2. 이미지 장면 지시도 검사한다

카피가 깨끗해도 장면이 같은 주장을 할 수 있다. `pdp.image-prompt.ts:95` 는 full-image 모드에서
headline·subheadline·bullets 를 이미지에 직접 굽고, 장면은 `prompt_en` 이 만든다.
"급증하는 매출 대시보드", "전후 비교 사진" 같은 지시가 그 예다.

**근거 대상은 `prompt_ko` 하나다. `prompt_en` 은 파생 필드로 다룬다.**

이유는 `prompt_en` 이 확인 화면 **이후에** 바뀌기 때문이다.
`TextModeFlow.tsx:152` 의 `handleApprove` 가 `mergeArtDirection()` 을 부르고,
그 함수는 `prompt_ko` 가 바뀌었으면 `prompt_en` 을 `기존 + 마커 + 한국어` 로 다시 쓴다
(`pdp.text-plan.ts:378~383`). `prompt_en` 을 근거 대상으로 두면 확인 시점에 `fresh` 였던
근거가 이미지 API 에 닿을 때 `stale` 이 되어 **정상 요청이 막힌다.**
사용자가 화면에서 고치는 것도 한국어 쪽뿐이다.

대신 **`mergeArtDirection()` 이후에 금지 스캐너를 반드시 한 번 더 돌린다.**
파생 결과에 금지 문구가 섞여 들어가는 경로를 그대로 두면 §4-1이 무의미해진다.
이 검사는 이미지 API 게이트와 같은 자리에서 수행한다(§6-3).

### 6-4. 게이트의 한계를 정직하게 적는다

**서버는 클라이언트가 보낸 구성안을 받는다**(`batch/route.ts:33`). 구성안을 서버에 저장하지
않으므로, API 를 직접 호출해 `evidence` 를 지우거나 `acknowledgedAt` 을 위조하면 통과한다.

**이것은 우회 불가능한 게이트가 아니다. "클라이언트 상태의 서버 재검사"다.**

그렇게 두는 이유: 우회할 수 있는 사람은 **로그인한 판매자 본인**이고, 그 사람이 곧 게시하고
책임지는 당사자다. 이 게이트가 막아야 하는 것은 악의적 우회가 아니라 **사고**다 —
UI 버그, 예시를 못 보고 지나침, 초안 저장·복원 중 유실.
서명·서버 상태를 도입하면 그 사고를 막는 효과는 같고 비용만 는다.

구버전 데이터 판정은 **`evidence` 가 없다는 사실이 아니라 스키마 버전으로** 한다.
안전 필드의 부재를 통과 사유로 삼으면, 필드를 지우는 것이 곧 우회가 된다.

```ts
export interface SectionBlueprint {
  /** 근거 스키마 버전. 이 값이 있으면 evidence 가 있어야 한다. 없으면 구버전. */
  evidenceVersion?: 1;
  evidence?: CopyEvidence[];
}
```

**버전은 섹션마다 둔다.** 단건 이미지 API 는 섹션 하나만 받으므로(`images/route.ts` 의
`body.section`), 구성안 단위 버전으로는 판정할 수 없다.

이 장치가 막는 것과 못 막는 것을 분명히 한다.

| 시도 | 결과 |
|---|---|
| `evidence` 만 지우고 보냄 | **거절** — 수치를 말하는 자리에 근거가 없다 |
| 수치가 없는 카피에서 `evidence` 를 지움 | 통과. 숨길 미확인 값이 애초에 없다 |
| `evidenceVersion` 까지 함께 지움 | 통과. 구버전으로 보인다. **막지 않는다** |
| `acknowledgedAt` 에 아무 시각이나 넣음 | 통과. 서명이 없으므로 **진위를 알 수 없다** |

### 게이트를 붙이지 않는 라우트 — `/api/pdp/key-visual`

이미지를 만드는 라우트인데 게이트가 없다. 빠뜨린 것이 아니라 **필요가 없어서**다.

`buildKeyVisualPrompt`(`pdp.text-plan.ts:204~212`)는 브리프와 `style_guide` 만 읽는다.
headline·subheadline·bullets·prompt_ko 를 쓰지 않으므로, 미확인 예시 값이 대표 이미지로
구워질 경로가 없다. 대표 이미지는 색·조명·질감을 묶는 용도이고 글자를 넣지 않는다.

**이 전제가 깨지면 게이트를 붙여야 한다** — 키비주얼 프롬프트가 섹션 카피를 읽기 시작하면
그때는 다른 이야기다.

**판정은 "근거 배열이 비었는가"가 아니라 "사실 표지가 있는 자리에 근거가 있는가"로 한다.**
배열이 비었는지로 보면 숫자가 하나도 없는 카피, 사용자가 방금 추가한 빈 섹션,
확인 화면에서 마지막 문장을 「빼기」한 섹션까지 전부 막힌다 — 정상 사용을 막는 쪽이
우회를 막는 것보다 훨씬 자주 아프다. 장면 지시(`prompt_ko`)는 판매 주장이 아니므로
이 판정에서 제외한다(금지 표현 검사는 그대로 받는다).

뒤 두 줄이 이 신뢰 모델의 한계다. 서버에 구성안을 저장하지 않기로 한 결과이며,
§6-4 첫머리의 이유로 감수한다.

## 8. 이번에 하지 않는 것

**의미 대조 감사 호출.** 코드로 못 잡는 위장이 둘 있다.

1. **인용 오용** — `quote` 가 원문에 실재하지만 그 주장을 뒷받침하지는 않는 경우.
   원문 한 문장을 아무 데나 붙여 놓으면 통과한다
2. **`rhetoric` 오분류** — 사실 주장을 수사로 표시하는 경우.
   숫자·금지어가 든 것은 보조 방어로 잡지만(§3-3), 숫자 없는 사실 주장은 통과한다.
   예: "업계에서 유일하게 이 방식을 씁니다"

둘 다 판단하려면 의미를 읽어야 하고, 원문·문구·근거를 함께 주는 별도 호출이 필요하다.
지금은 **구조 검증 + 인용 실재 대조 + 보조 방어**까지만 한다. 위장이 실제로 관측되면 켠다.

> 켤 때는 그 호출 비용을 반드시 계상한다.
> 2026-07-28 에 재시도·검증 호출 비용이 장부에서 빠지던 문제를 겪었다.

## 9. 위험과 대응

| 위험 | 대응 |
|---|---|
