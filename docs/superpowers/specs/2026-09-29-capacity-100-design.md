## 2. 지금 상태 — 측정 근거

### 2.1 측정 환경

운영과 같은 급의 시험 서버 A(t3.micro, 911MB, 스왑 2GB, 같은 systemd 유닛·
`NODE_OPTIONS=--max-old-space-size=512`·Caddy)에 운영 master 빌드를 올렸다. 도우미
서버 B(t3.large)에 시험용 Supabase 스택, **가짜 AI**(같은 모양·같은 크기 응답, 이미지
45초·글 3초), k6 를 두었다. 운영 코드는 그대로이고 A 의 `/etc/hosts` 만 돌렸다.

운영과 다른 점: 시험 DB 는 같은 망(왕복 <1ms, 운영 약 0.2초)이고 운영(MICRO)보다
크다. 가짜 AI 는 늘 성공한다. k6 는 자바스크립트를 실행하지 않아 실제 브라우저의
미리 불러오기(prefetch)·폴링 호출이 빠져 있다(§3.0 에서 보탠다).

### 2.2 강제 종료 시점

| 상황 | 버틴 최대치 | 멈춘 지점 | 직전 모습 |
|---|---|---|---|
| 로그인 전 화면 | 160명 3분(보통 4.4초) | **200명 약 4분 만에 종료(2/2회)** | 처리량이 초당 32~40건에서 고정 → 대기 누적 → 여유 램 22MB |

| 섞임: 로그인 50 화면 + 상세 3 | 종료 없음 | — | 화면 보통 6초·느린 쪽 17초 |
| 로그인 후 화면만 | 100명 종료 없음 | — | 10명 0.3초 · 25명 1.6초 · 50명 5.5초. A CPU 10~20%, **시험 DB CPU 120%** |

상세페이지는 **한 건만으로** 여유 램이 35MB 까지 떨어진다(서비스 전체 메모리 128→666MB,
힙 몫은 따로 재지 않았다).

### 2.3 멈추는 방식 — 두 가지 원인

- **메모리**: `--max-old-space-size=512` 를 넘으면 `FATAL ERROR: Reached heap limit …` 로
  프로세스가 죽고(`status=6/ABRT`) systemd 가 5초 뒤 다시 띄운다(`Restart=always`,
  `RestartSec=5`). 상세페이지·섞임이 이 경로다.
- **처리량**: 로그인 전 화면은 CPU 한 코어(Node 한 프로세스)가 초당 32~40건에서
  막히고, 밀린 요청이 쌓여 결국 메모리로 죽는다. 램만 늘리면 죽지 않는 대신 느려진다.

죽는 동안: 약 10초 모두 502 · 생성 중 결과 유실(fal 비용은 나감) · 그 사람의 예약이
묶여 동시 1건 규칙에 최대 10분 막히고(`202609280001_cs_ask_operation.sql:264`),
잡아 둔 크레딧(`credit_holds`)은 풀리지 않으며, `started` 로 죽은 건은 관리자 「정산
확인」(`needs_review` 만 봄, `202609220001:512`)에도 **보이지 않는다.** 알림 없음.

**재시작은 사고 때만이 아니다** — 배포할 때마다 `systemctl restart` 가 돌고
(`deploy-release.sh:61`) 30초 뒤 강제로 끈다(`TimeoutStopSec=30`).

## 3. 설계

단계마다 **시험 먼저 → 구현 → 독립 리뷰 → 뮤테이션 확인 → 배포 → 운영 확인**.

### 3.0 기준선 — 운영과 비슷한 조건으로 다시 잰다

- 시험 DB 컨테이너를 MICRO 에 가깝게(메모리 1GB, CPU 제한), A→B DB 구간에 왕복 약
  0.2초 지연
- 시나리오: 로그인 25·50·100, 섞임 50+3, 로그인 전 200
- **실제 브라우저로 화면 한 번 여는 동안의 총 호출 수**를 잰다(Playwright 몇 개) —
  사이드바 prefetch·진행 중 작업 폴링 포함
- **가짜 AI 보강**: fal 대기열 API(submit·status·result·cancel), **키별 동시 한도**, 401·403(잠김)·429 를
  흉내 낸다 — §3.9 기준을 재려면 필요하다
- **CORS 확인**: `curl -I -H "Origin: <사이트 주소>" <Supabase 서명 주소>` 로 `Access-Control-Allow-Origin` 이
  오는지(§3.4 화면이 결과를 받아 오는 길)
- 한계: MICRO 는 ARM 공유 코어라 똑같이 흉내 낼 수 없다 — 「비슷한 쪽」으로 보고한다

### 3.1 서버 (설정)

1. **t3.medium** — 운영 AWS 계정에서 사용자가 콘솔로(중지 → 유형 변경 → 시작, 탄력적 IP
   유지, 약 5분). 이 컴퓨터의 AWS 권한은 다른 계정이다
2. **메모리 상한은 RSS 로 정한다** — V8 힙 상한(`--max-old-space-size`)은 힙만 묶고 Buffer·
   sharp/libvips 는 밖에 있다. 시험 서버 A 를 t3.medium 으로 바꿔 heap·external·rss 최고치를
   잰 뒤 정한다(시작값 힙 2GB 쪽). systemd 에 `MemoryHigh`/`MemoryMax` 를 두어 커널이
   서버 전체를 죽이기 전에 이 서비스만 다시 뜨게 한다. `NODE_OPTIONS` 를 `app.env.example`
   에 적는다(지금은 운영 파일에만 있다)
3. **정적 파일은 Caddy 가 직접** — `/_next/static/*` 을 릴리스 폴더에서 Caddy 가 내준다.
   Node 한 코어가 막히는 로그인 전 화면 부담을 덜고 추가 비용이 없다. (Cloudflare 는
   도메인 작업 ④)
4. **재시작 틈** — Caddy `lb_try_duration 20s`: 몇 초 재시작 동안 502 대신 기다린다
5. **감시** — 서버 안 systemd 타이머가 1분마다 `curl --max-time 5 /api/health/ready`·재시작
   횟수·메모리·커널 OOM(`status=9`)·CPU 크레딧을 보고, 이상이 있으면 관리자에게 메일.
   같은 사건은 한 번만. **메일 계정은 가입 메일과 분리하거나 발송 수를 제한한다**(§3.7)
6. **t3 CPU 크레딧** — 크레딧 방식(unlimited/standard)을 확인하고 `CPUCreditBalance` 를 감시한다
7. **새 서버 설치 고침** — `install-host.sh` 첫 실행 시 Caddy 로그 폴더 권한으로 Caddy 가
   안 뜨는 문제(2026-09-28 발견)
8. **반영 절차를 따로 적는다** — `deploy-release.sh` 는 Caddy 설정·타이머를 건드리지 않는다
   (`install-host.sh` 만). 올리는 절차와 되돌리는 절차를 `docs/DEPLOY.md` 에 추가한다

### 3.2 로그인 확인을 서버가 직접 (코드, 단독 배포)

- `auth.getUser()`(Supabase 왕복) → `auth.getClaims()`(토큰 서명을 직접 확인). 이 저장소의
  supabase-js 2.110.8·ssr 0.7.0 에 있다. 운영은 ES256 비대칭 키를 쓴다
  (`/auth/v1/.well-known/jwks.json`)
- **확인할 것**: 운영의 실제 토큰 머리가 `alg=ES256` 이고 `kid` 가 목록과 맞는지. 아니면
  조용히 `getUser` 로 돌아간다(`GoTrueClient.js:5253-5270`) — 돌아간 횟수를 로그로 센다
- 한 요청 안에서 두 번 인증하는 곳(`readPdpRequest` → `reserveAiUsage`)은 **인증 결과를
  넘겨준다**(React `cache` 는 라우트에서 안 된다)
- 관리자 판정은 계속 `profiles.role`(토큰의 `role` 은 DB 역할이다). 정지·탈퇴 회원은
  profiles 확인에서 그대로 막힌다. 24시간 세션 규칙은 그대로
- 맞바꾸는 점: 로그아웃한 토큰이 만료(최대 1시간)까지 유효하다
- **줄 세우기·작업 폴링보다 먼저 배포한다** — 폴링이 늘기 전에 호출당 비용을 줄인다

### 3.3 fal 계정 풀과 동기 호출 없애기 (코드)

**먼저 동기 호출을 없앤다.** 한도를 넘었을 때 **즉시 429 로 실패**하는 것은 `fal.run` 동기
경로뿐이다(`lib/pdp/fal.ts:41`, `lib/redesign/image-generator.ts:125`). 대기열 요청은 한도를
넘어도 fal 쪽에서 기다린다. 그래서 남은 동기 호출을 **요청 안에서 대기열에 제출하고 상태를
확인하는 방식**으로 바꾸고, fal 쪽 대기 상한(`startTimeout`, `@fal-ai/client` `queue.d.ts:63-70`)을
건다. 429 가 사라지고, 칸을 정확히 세지 않아도 된다 — 포스터·카드뉴스는 화면이 물을 때만
결과를 가지러 가고(`lib/running-jobs.ts:6-12`) fal 계정을 영상 서비스와 함께 써서, 서버 안에서
정확히 셀 수도 없다.

**표** `fal_accounts`: 이름, 암호화한 키, 끝 4자리, 동시 한도(관리자 입력 — **부드러운 상한**,
공정 분배와 대기 표시에만), 켜짐/꺼짐, 상태(`ok`·`locked`·`invalid`·`rate_limited`·
`decrypt_failed`), 마지막 오류와 시각, 만든·바꾼 사람. 변경 기록 표 따로.

- **어느 계정으로 보냈는지는 요청(시도)마다 기록한다.** fal 요청 번호는 계정마다 따로라 상태·
  결과·취소를 보낸 계정의 키로 해야 한다. 기록이 없는 옛 요청(카드뉴스·포스터 기록에는 계정
  칸이 없다, `lib/sns/queued-flow.ts:194-205`)은 `FAL_KEY` 로 본다
- **계정 끄기** = 새 제출만 멈춘다. 진행 중 요청이 참조하는 계정은 지울 수 없다
- **한도 입력값은 천장**으로만 쓴다. 우리 요청이 fal `IN_QUEUE` 에 머무는 것이 보이면 자동으로
  낮추고 관리자 화면에 표시한다. 입력 범위 1~200
- **처음 계정**은 지금의 `FAL_KEY`. 표가 비면 `FAL_KEY` 로 돌아간다. **표에 행이 있는데 복호 열쇠가
  없으면 조용히 돌아가지 않고 알린다**
- **여러 계정을 실제로 켜기 전 fal 약관 확인**(사용자·fal 답변)

**암호화**: AES-256-GCM. 열쇠는 32바이트 무작위 값을 base64 로 `app.env` 의
`FAL_KEY_ENCRYPTION_SECRET` 에 두고 기동할 때 길이를 검사한다. 기록마다 12바이트 무작위 IV 와
인증 태그를 저장하고, **추가 인증 데이터에 계정 id** 를 넣어 암호문을 다른 행으로 옮겨 붙이지
못하게 한다. `key_version` 칸과 재암호화 스크립트를 둔다. DB 를 다른 제품과 함께 쓰므로 암호화가
사실상 유일한 방어다 — RLS 를 켜고 anon·authenticated 권한을 회수한다(`202609180001_pdp_jobs.sql:127-133`
과 같은 방식). **열쇠를 잃으면 모든 키를 다시 입력해야 한다** — 열쇠 보관처를 `DEPLOY.md` 에 적는다.

**관리자 화면**(`/admin` 시스템 탭): **관리자 두 명 모두**(`profiles.role='admin'`, 사용자 결정).
등록(붙여 넣기 → 저장 즉시 원문 폐기), 끝 4자리, 켜기/끄기, 한도 수정, 「확인」, 최근 오류, 변경
기록. 「확인」은 이미지를 만들지 않는 무료 요청이라 **잔액 소진 잠김은 드러나지 않는다**(실제
생성에서만 드러남) — 화면에 그 한계를 적는다.

### 3.4 이미지 작업 접수 — 상세페이지부터 (코드, 가장 큼)

이미 있는 작업 표 `pdp_generation_jobs`·**`pdp_generation_items`**(`202609180001_pdp_jobs.sql`)
위에 세운다. 이 표에는 상태 단계, 장별 fal 요청 번호(`provider_request_id`), 작업을 맡은 표시
(`lease_owner`·`lease_until`, 기본 120초)가 이미 있다.

**작업 한 건 = 상세페이지 한 벌(섹션 최대 10개,** `pdp.section-plan.ts:40`**).** 모델별 묶음
나누기(gpt-image-2 는 3장씩, `PdpEditor.tsx:1821`)와 칸 나누기는 배치기가 한다.

**표에 더하는 것**

| 칸·값 | 뜻 |
|---|---|
| `mode text not null default 'sync' check (mode in ('sync','queued'))` | **옛 동기 작업과 새 작업을 가른다.** 기존 행은 자동으로 `sync`. 배치기는 `queued` 만 집는다 |
| 상태 `queued`(validated → queued → reserved) | 접수됐고 차례를 기다린다 |
| 끝 상태 `cancelled` | 취소, **완성 0장일 때만**. 완성 장이 있으면 `partial` + 취소 표시 |
| `cancel_requested_at` | 취소는 단계가 아니라 **표시** — 전이표(`state.ts:89-103`)와 부딪히지 않게 |
| `request jsonb` | 요청 몸통(그림 제외) — 스타일 참고·조각·라이브러리 맞춤 값 등, 몇 분 뒤·재시작 뒤 같은 그림을 만들 재료 |
| `input_paths jsonb` | 상품·인물 사진 등을 둔 저장소 경로. **인물 사진은 작업이 끝나면 지운다** |
| `library_state` | 라이브러리 등록 단계 — DB 에 남아 재시작에도 이어진다 |
| 항목(시도)별 fal 계정 id | §3.3 |
| 부분 고유 색인 `unique(user_id) where mode='queued' and generation not in (끝 상태들)` | **한 사람 대기+진행 1건**을 표가 강제 |

끝 상태 목록을 고칠 곳(한곳에 모아 적는다): check 제약, 부분 색인(`202609180001:78-80`),
`claimNext` 필터(`supabase-repository.ts:289`), `TERMINAL`(`state.ts:154`), `outcomeOf`,
`mergeDocumentJobs`, 로컬 저장소, `migration-contract.test.ts`.

**배치기 배포 전 1회 정리**: 1시간 넘게 끝나지 않은 `sync` 행(프로세스가 죽어 `submitted`·
`lease_until null` 로 남은 것)을 items 기준으로 `partial`/`failed` 로 닫는다. 되돌리기 SQL 포함.

**흐름**

1. **접수** `POST` — 인증(§3.2) → 입력 검사(**초안 문서 id 필수** — 없으면 라이브러리 등록과 되찾기가
   안 된다, `library-sync-request.ts:26-27`) → 입력 이미지를 저장소에 두고 경로만(이미 초안 자산에
   있는 사진이면 경로만 받는다) → **크레딧 예약**(사용자 결정: 접수 때. 서버용 예약 함수 —
   `reserveAiUsage` 는 요청 쿠키에 묶여 있어 배치기에서 못 쓴다, `api.ts:66-84`. 예약 이름
   **`pdp:job`**, 요청 id = 작업의 `reservation_request_id`) → `queued` 저장 → 작업 번호. 크레딧 부족·
   이미 진행 중이면 **바로** 알린다. 같은 누름은 멱등키로 한 번만, 제약 이름으로 오류를 갈라
   「이미 진행 중(작업 번호)」을 돌려준다(`supabase-repository.ts:160-184`)
2. **배치기**(웹과 **다른 프로세스**, 별도 systemd 유닛 — 배치기가 메모리로 죽어도 사이트는 산다.
   §2.2 의 주된 원인이 상세페이지 메모리였다) — 오래된 순으로 `mode='queued'` 를 집어 lease 를 잡고
   `credit_mark_started`. 예약의 만료가 생성 도중 지나지 않도록 lease 갱신 때 함께 늘린다
3. **생성** — 품질검사 재시도 반복을 **배치기 단계로 꺼낸다**(지금은 함수 안 지역 변수,
   `pdp.service.ts:771-1041`). 시도마다 items 한 줄에 순서대로: 보내기 **전** 의도(계정·시각) →
   fal 요청 번호 → 결과 경로 → qa(교정 지시 포함). 번호 없는 의도 줄은 `uncertain` — **그 섹션만
   한 번 다시 보내고 원가는 회사 부담으로 기록**. fal 참조 이미지는 먼저 올리고 주소를 싣는다
   (카드뉴스 방식, `lib/sns/providers.ts:287-288`). 429·일시 오류는 기다렸다 다시, 계정 잠김·키
   무효는 그 계정을 빼고 다른 계정으로 + 관리자 알림
4. **후처리 동시 수는 fal 칸과 따로 묶는다**(시작 2~4) — 결과 내려받기·저장·품질검사·라이브러리
   인코딩이 서버 메모리를 쓴다. fal 칸이 늘어도 후처리가 한꺼번에 몰리지 않게. 라이브러리 줄은
   경로만 쥐고 차례가 오면 저장소에서 읽는다
5. **결과** — 원본 화질 그대로 저장소 → 품질검사 → 라이브러리 등록(지금의 서버 등록 경로) →
   진행 중이던 장이 모두 끝나면 **완성된 장만 한 번에 확정 차감**
6. **조회** `GET` — 상태, `ahead`(이 작업보다 먼저 접수돼 아직 시작 안 한 `queued` 수, 부분 색인으로
   센다), 장별 진행. 결과 서명 주소는 **작업이 끝났을 때만** 만든다(`app/api/pdp/jobs/view.ts:16`).
   화면 폴링 간격 5~10초, 사이드바는 진행 중 작업이 있을 때만 부른다
7. **취소** `POST …/cancel` — `cancel_requested_at` 기록. 대기 중이면 곧바로 `cancelled`·예약 전부
   풀기(차감 0). 만드는 중이면 아직 안 보낸 장은 보내지 않고, fal 대기열에 있는 장은 취소 요청,
   **이미 만들고 있던 장은 완성되면 라이브러리에 두고 그만큼 차감**(사용자 결정). 정산은 그 장들이
   모두 끝난 뒤 한 번. 화면 문구: 「이미 만들고 있던 k장은 완성되면 저장되고 그만큼 차감됩니다」
8. **대기 10분 초과** — 자동 `cancelled`, 예약 풀기, 「지금 사용자가 많습니다」
9. **종료 신호(SIGTERM)** — 새 제출을 멈추고 lease 를 반납한다(지금 웹에는 처리가 없다). 반납하지
   않으면 배포마다 작업이 최대 2분(lease 120초) 멈춘다. `MemoryMax` 초과는 SIGKILL 이라 정리 기회가
   없다 — 그때는 lease 만료 뒤 다른 차례에 이어받는다
10. **fal 결과 보존** — 제출할 때 보존 기간을 명시하고(`x-fal-object-lifecycle-preference`), 이어받기
   가능한 시간 창을 넘은 장은 실패·차감 0·원가 기록(`lib/fal/failure.ts:95-110` 의 410 처리 재사용)

**화면이 들고 있던 책임**(옮길 때 빠뜨리지 않는다)

1. 결과는 **data URL 로 바꿔 넣는다** — 지문 계산이 data URL 이 아니면 null(`library-server-sync.ts:90-92`),
   서명 주소는 1시간이면 죽는다. 이미 있는 `bakeRecoveredImages`(`job-recovery.ts:113`) 재사용.
   캔버스에 주소를 직접 넣지 않으므로 캔버스 오염은 없고, 브라우저 `fetch` 의 CORS 만 확인한다(S0)
2. 문구 자국 `imageStampOf(보낸 섹션)`(`PdpEditor.tsx:1943`) — 작업의 `request` 스냅숏으로 계산
3. 생성 중 편집 잠금(`PdpEditor.tsx:1808`, `:1989·2015·2044`) — 몇 분 걸리는 접수 방식에서는 **결과를
   섹션 id 로 붙이고 편집은 허용**, 삭제된 섹션의 결과는 라이브러리에만 둔다. 다시 열 때 진행 중
   표시를 되살린다
4. 저장 안 한 초안 — 접수 조건에 초안 문서 id 필수
5. 실패·취소 뒤 「다시 만들기」는 **새 멱등키**(`claim.ts:67-76`)
6. 품질 경고 — 작업 items 의 qa 에서 읽는다
7. **한 장 다시 만들기(`pdp:image`)·대표 이미지(`pdp:key-visual`)** — S3 에서 대기열 제출로 바꿔
   429 가 사라지고, 이후 같은 작업 접수로 옮긴다
8. 잔액 표시 갱신 — 조회 응답에 잔액을 싣는다

**나머지 무거운 동기 경로**(리디자인 2, 캐릭터 2): S3 에서 대기열 제출로 바꾸고, 서버 전체 동시
수 상한만 둔다(대기 없이 자리가 없으면 곧바로 「잠시 후 다시」). 작업 접수 이전은 다음 단계.

**스위치**: `PDP_JOBS_MODE=queued|sync` 는 **접수 방식만** 바꾼다. 배치기는 늘 남은 `queued` 작업을
끝낸다. 기존 `PDP_JOBS_ENABLED`(`lib/pdp/jobs/flags.ts:17-21`, 기록기 켜기)는 그대로 켜 둔다.

### 3.5 사고 뒤처리 — 남은 동기 경로 (코드, S1 직후)

S1~S4 동안에도 배포(곧 재시작)가 여러 번 있다 — 그래서 앞당긴다. 작업 접수로 옮긴 경로는
재시작해도 이어지므로 대상이 아니다.

- **허용 목록 — 와일드카드 없이**: `credit_quote->>'resource' in ('pdp:batch','pdp:image',
  'pdp:key-visual','redesign:generate','redesign:edit','character:candidates','character:angles',
  'character:view')`, `pricing_policy='image-v2'`, `status='reserved'`, `credit_jobs` 연결 없음, **그리고
  `not exists (select 1 from pdp_generation_jobs j where j.reservation_request_id = e.request_id and
  j.mode = 'queued')`**. 배치기의 `pdp:job` 은 목록에 없다. **`sns:*`·`poster:*` 는 절대 건드리지
  않는다**
- 단계별: `phase='reserved'` → 차감 없이 푼다. `phase='started'` → `needs_review` 로 옮겨 관리자
  「정산 확인」에 보이게(`2026-09-22-credit-subscription-design.md:717`)
- 닫을 때 `error_code='process_restart'`, `cost_state='unknown'`
- 고르는 기준: 예약에 **서버 표식(boot id)** — 시각 비교보다 튼튼하고 공유 DB 의 다른 제품 예약을
  고르지 않는다. 함수 인자를 바꾸면 42725 재발 위험 — 옛 판 삭제·이름 유일성 검사를 함께
- 시작 훅은 nodejs 에서만(`instrumentation.ts` 는 아직 없다), 기다리지 않고, 실패해도 기동은 계속
- **시험: 배치기 예약(`pdp:job`)과 `sns`·`poster` 예약은 뒤처리 대상이 아니다**

2. **`credit_summary`** — 「이번 달 납부 기간은 있는데 지급 행이 없을 때」만 잠그고 지급한다.
   나머지는 잠금 없이 조회(`wallet_state` 는 한 문장이라 값이 섞이지 않는다). 운영 함수 정의를

3. **팀 조회 생략은 메뉴에만**(`studio-layout.tsx:37`). 읽기 범위를 정하는 `teamIdOf` 는 그대로 —

4. **사이드바 미리 불러오기(prefetch) 끄기** 후보 — §3.0 의 브라우저 측정으로 효과를 보고 정한다
5. 목표: 로그인 후 화면 하나당 **profiles 2 + 잔액 1** 안팎

### 3.7 가입·메일 한도 (확인 + 설정)

요구 원문이 「회원가입 과정부터」다.

- Supabase 대시보드 Auth › Rate Limits: **메일 발송 한도**(custom SMTP 기본 시간당 약 30통으로
  알려짐), IP 당 가입·로그인 한도, 토큰 갱신 한도 — 확인 후 필요한 만큼 올린다
- SMTP 제공자 자체 하루·시간 한도 — 부족하면 트랜잭션 메일 서비스로 바꾼다(사용자 결정)
- 서버 쪽 토큰 갱신은 EC2 한 IP 에서 나간다 — 한꺼번에 로그인한 사람들이 1시간 뒤 한꺼번에 갱신
- 감시 메일은 가입 메일 몫을 먹지 않게 분리하거나 제한(§3.1-5)

### 3.8 외부 AI

- **Anthropic**: Scale 등급으로 넉넉하다. 콘솔 Billing 에서 **직접 정해 둔 월 지출 한도**와 알림
  이메일만 확인한다
- **fal**: ① 한도 상향 요청(목표 200칸, 문안 작성함) ② 계정 풀(§3.3). 필요한 칸 =
  「동시 상세페이지 수 × 섹션 수(최대 10) + 포스터·카드뉴스 동시 수 + 품질검사 재생성 여유 + 영상
  서비스 몫(같은 계정을 쓰는 동안)」. 이 서비스 전용
  계정으로 분리하면 영상 작업이 칸을 뺏지 않는다. 잔액·자동 충전은 운영 준비 목록에
- **Google·OpenAI 직접 호출**(리디자인)의 한도도 확인 목록에 넣는다
- 계정 단위 장애(잔액 소진·키 무효) 알림은 §3.3 풀 상태 + AI 비용 보안(③)

|---|---|
| 로그인 100명 화면 + 동시 생성 10건 | **재시작 0회**, 생성은 접수·대기·완료 |
| 로그인 후 화면 | 보통 2초 · 느린 쪽 5초 이내 |
| 로그인 전 화면 200명 3분 | 재시작 0회, 보통 3초 이내 |
| 생성 | 실패·라이브러리 누락 0(가짜 AI 기준), 10분 넘은 대기는 차감 없이 취소 |
| 만드는 중 서버 재시작 | 작업이 이어서 완성, 이중 차감 0, **fal 제출 수 = 장 수 + 재시도 수**(이중 원가 0) |
| 재시작 뒤처리 | 배치기 예약(`pdp:job`)·`sns`·`poster` 예약은 건드리지 않음 |
| 취소 | 대기 중 차감 0, 만드는 중: 취소 뒤 도착한 장 포함 **완성 장만** 저장·차감 |
| fal 계정 하나 막힘(가짜 AI 로 403 흉내) | 다른 계정으로 계속, 관리자 메일 |
| 가입 | 한 시간에 100명 가입 → 확인 메일 전부 도착(설정 확인 + 시험 계정 발송) |
| 실제 브라우저 | 5·10·15분 대기에서도 상태 표시가 이어짐 |

기준에 못 미치면 원인(서버/DB/외부)을 가려 보고하고, DB 라면 **Supabase 컴퓨트 올리기**를
제안한다.

## 5. 하지 않는 것

- 웹 프로세스 여러 개 — CPU 가 한계로 드러나면 그때. (배치기는 처음부터 웹과 다른 프로세스 하나)

- Supabase 지역 이전 — 호출 수를 줄이는 쪽이 효과가 크다
- 결제, AI 비용 보안(③)

## 6. 위험과 되돌리기

| 위험 | 대비 |
|---|---|
| 작업 접수 전환이 상세페이지 전체에 영향 | 스위치로 옛 동기 방식으로 되돌린다(`PDP_JOBS_MODE`). 옛 방식은 한동안 남긴다 |
| 배치기 결함으로 작업이 멈춤 | 작업마다 `lease_until` — 멈춘 작업은 다시 잡힌다. 관리자 목록에서 보이고 강제 취소 가능. 감시가 「대기만 쌓이고 진행 0」을 알린다 |
| 키 유출 | 암호화 저장(AAD=계정 id), 원문은 서버 안에서만, 관리자만, 변경 기록, RLS·권한 회수. 열쇠는 `app.env`(root 0640), 보관처는 `DEPLOY.md` |
| 메모리 상한 오설정 | 시험 서버에서 먼저, `app.env` 한 줄로 되돌림, `MemoryMax` 로 서버 전체는 보호 |
| 로그인 확인 변경 | 단독 배포, 되돌리기는 이전 릴리스 |
| 잔액 조회 잠금 제거 | 표시 전용, 지급이 필요할 때만 잠근다, DB 에서 먼저 시험 |
| 재시작 뒤처리가 남의 예약을 고름 | 와일드카드 없는 허용 목록 + `mode='queued'` 작업 제외 + 서버 표식 + `pdp:job`·`sns`·`poster` 제외를 시험으로 고정 |
| 배치기가 옛 동기 작업을 집음 | `mode` 칸(기존 행 `sync`), 배치기는 `queued` 만, 배포 전 1회 정리 SQL, 시험 |
| 제출 불확실(보내고 번호를 적기 전 죽음) | 보내기 전 의도 기록 → `uncertain` → 그 섹션만 한 번 다시(원가 회사 부담) |
| 배포 자체가 재시작 | 작업 접수로 옮긴 경로는 이어진다. 남은 동기 경로를 위해 배포 전 「진행 중 생성 수」 확인을 `DEPLOY.md` 에 |

## 7. 결정이 필요한 것 (진행 중에 묻는다)

- Supabase 컴퓨트 올리기(§3.9 결과)
- 여러 fal 계정을 실제로 켤지(fal 약관·답변)
- 이 서비스 전용 fal 계정으로 분리할지
- 메일 한도가 모자랄 때 SMTP 바꾸기(§3.7)
- Supabase 요금제의 Storage 용량·전송량(egress) 한도 — Billing 에서 확인. 결과 보기는 대부분
  서명 주소(Storage egress)이고 포스터 원본은 EC2 를 거친다(`lib/poster/supabase-store-core.ts:48`)
