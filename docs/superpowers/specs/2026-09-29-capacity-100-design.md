## 2. 지금 상태 — 측정 근거

### 2.1 측정 환경

운영과 같은 급의 시험 서버 A(t3.micro, 911MB, 스왑 2GB, 같은 systemd 유닛·
`NODE_OPTIONS=--max-old-space-size=512`·Caddy)에 운영 master 빌드를 올렸다. 도우미
서버 B(t3.large)에 시험용 Supabase 스택, **가짜 AI**(같은 모양·같은 크기 응답, 이미지
45초·글 3초), k6 를 두었다. 운영 코드는 그대로이고 A 의 `/etc/hosts` 만 돌렸다.

운영과 다른 점: 시험 DB 는 같은 망(왕복 <1ms, 운영 약 0.2초)이고 운영(MICRO)보다
크다. 가짜 AI 는 늘 성공한다. k6 는 자바스크립트를 실행하지 않아 실제 브라우저의
미리 불러오기(prefetch)·폴링 호출이 빠져 있다(§3.0 에서 보탠다).

### 2.2 강제 종료 시점

| 상황 | 버틴 최대치 | 멈춘 지점 | 직전 모습 |
|---|---|---|---|
| 로그인 전 화면 | 160명 3분(보통 4.4초) | **200명 약 4분 만에 종료(2/2회)** | 처리량이 초당 32~40건에서 고정 → 대기 누적 → 여유 램 22MB |
| 상세페이지 6장 묶음 동시 | 6명 전부 성공(약 2분) | **10명 종료** | 8명: 502 1건, `library sync queue is full` 로 결과가 라이브러리에 안 들어감, 스왑 1.8/2GB |
| 섞임: 로그인 50 화면 + 상세 3 | 종료 없음 | — | 화면 보통 6초·느린 쪽 17초 |
| 로그인 후 화면만 | 100명 종료 없음 | — | 10명 0.3초 · 25명 1.6초 · 50명 5.5초. A CPU 10~20%, **시험 DB CPU 120%** |

상세페이지는 **한 건만으로** 여유 램이 35MB 까지 떨어진다(서비스 전체 메모리 128→666MB,
힙 몫은 따로 재지 않았다).

### 2.3 멈추는 방식 — 두 가지 원인

- **메모리**: `--max-old-space-size=512` 를 넘으면 `FATAL ERROR: Reached heap limit …` 로
  프로세스가 죽고(`status=6/ABRT`) systemd 가 5초 뒤 다시 띄운다(`Restart=always`,
  `RestartSec=5`). 상세페이지·섞임이 이 경로다.
- **처리량**: 로그인 전 화면은 CPU 한 코어(Node 한 프로세스)가 초당 32~40건에서
  막히고, 밀린 요청이 쌓여 결국 메모리로 죽는다. 램만 늘리면 죽지 않는 대신 느려진다.

죽는 동안: 약 10초 모두 502 · 생성 중 결과 유실(fal 비용은 나감) · 그 사람의 예약이
묶여 동시 1건 규칙에 최대 10분 막히고(`202609280001_cs_ask_operation.sql:264`),
잡아 둔 크레딧(`credit_holds`)은 풀리지 않으며, `started` 로 죽은 건은 관리자 「정산
확인」(`needs_review` 만 봄, `202609220001:512`)에도 **보이지 않는다.** 알림 없음.

**재시작은 사고 때만이 아니다** — 배포할 때마다 `systemctl restart` 가 돌고
(`deploy-release.sh:61`) 30초 뒤 강제로 끈다(`TimeoutStopSec=30`).

## 3. 설계

단계마다 **시험 먼저 → 구현 → 독립 리뷰 → 뮤테이션 확인 → 배포 → 운영 확인**.

### 3.0 기준선 — 운영과 비슷한 조건으로 다시 잰다

- 시험 DB 컨테이너를 MICRO 에 가깝게(메모리 1GB, CPU 제한), A→B DB 구간에 왕복 약
  0.2초 지연
- 시나리오: 로그인 25·50·100, 섞임 50+3, 로그인 전 200
- **실제 브라우저로 화면 한 번 여는 동안의 총 호출 수**를 잰다(Playwright 몇 개) —
  사이드바 prefetch·진행 중 작업 폴링 포함
- 한계: MICRO 는 ARM 공유 코어라 똑같이 흉내 낼 수 없다 — 「비슷한 쪽」으로 보고한다

### 3.1 서버 (설정)

1. **t3.medium** — 운영 AWS 계정에서 사용자가 콘솔로(중지 → 유형 변경 → 시작, 탄력적 IP
   유지, 약 5분). 이 컴퓨터의 AWS 권한은 다른 계정이다
2. **메모리 상한은 RSS 로 정한다** — V8 힙 상한(`--max-old-space-size`)은 힙만 묶고 Buffer·
   sharp/libvips 는 밖에 있다. 시험 서버 A 를 t3.medium 으로 바꿔 heap·external·rss 최고치를
   잰 뒤 정한다(시작값 힙 2GB 쪽). systemd 에 `MemoryHigh`/`MemoryMax` 를 두어 커널이
   서버 전체를 죽이기 전에 이 서비스만 다시 뜨게 한다. `NODE_OPTIONS` 를 `app.env.example`
   에 적는다(지금은 운영 파일에만 있다)
3. **정적 파일은 Caddy 가 직접** — `/_next/static/*` 을 릴리스 폴더에서 Caddy 가 내준다.
   Node 한 코어가 막히는 로그인 전 화면 부담을 덜고 추가 비용이 없다. (Cloudflare 는
   도메인 작업 ④)
4. **재시작 틈** — Caddy `lb_try_duration 20s`: 몇 초 재시작 동안 502 대신 기다린다
5. **감시** — 서버 안 systemd 타이머가 1분마다 `curl --max-time 5 /api/health/ready`·재시작
   횟수·메모리·커널 OOM(`status=9`)·CPU 크레딧을 보고, 이상이 있으면 관리자에게 메일.
   같은 사건은 한 번만. **메일 계정은 가입 메일과 분리하거나 발송 수를 제한한다**(§3.7)
6. **t3 CPU 크레딧** — 크레딧 방식(unlimited/standard)을 확인하고 `CPUCreditBalance` 를 감시한다
7. **새 서버 설치 고침** — `install-host.sh` 첫 실행 시 Caddy 로그 폴더 권한으로 Caddy 가
   안 뜨는 문제(2026-09-28 발견)
8. **반영 절차를 따로 적는다** — `deploy-release.sh` 는 Caddy 설정·타이머를 건드리지 않는다
   (`install-host.sh` 만). 올리는 절차와 되돌리는 절차를 `docs/DEPLOY.md` 에 추가한다

### 3.2 로그인 확인을 서버가 직접 (코드, 단독 배포)

- `auth.getUser()`(Supabase 왕복) → `auth.getClaims()`(토큰 서명을 직접 확인). 이 저장소의
  supabase-js 2.110.8·ssr 0.7.0 에 있다. 운영은 ES256 비대칭 키를 쓴다
  (`/auth/v1/.well-known/jwks.json`)
- **확인할 것**: 운영의 실제 토큰 머리가 `alg=ES256` 이고 `kid` 가 목록과 맞는지. 아니면
  조용히 `getUser` 로 돌아간다(`GoTrueClient.js:5253-5270`) — 돌아간 횟수를 로그로 센다
- 한 요청 안에서 두 번 인증하는 곳(`readPdpRequest` → `reserveAiUsage`)은 **인증 결과를
  넘겨준다**(React `cache` 는 라우트에서 안 된다)
- 관리자 판정은 계속 `profiles.role`(토큰의 `role` 은 DB 역할이다). 정지·탈퇴 회원은
  profiles 확인에서 그대로 막힌다. 24시간 세션 규칙은 그대로
- 맞바꾸는 점: 로그아웃한 토큰이 만료(최대 1시간)까지 유효하다
- **줄 세우기·작업 폴링보다 먼저 배포한다** — 폴링이 늘기 전에 호출당 비용을 줄인다

### 3.3 fal 계정 풀 — 관리자가 관리 (코드)

**표** `fal_accounts`: 이름, **암호화한 키**, 끝 4자리, 동시 한도(관리자가 입력),
켜짐/꺼짐, 상태(`ok`·`locked`·`invalid`·`rate_limited`), 마지막 오류와 시각, 만든·바꾼 사람.
변경 기록 표 따로.

- **암호화**: AES-256-GCM, 열쇠는 서버 `app.env` 의 `FAL_KEY_ENCRYPTION_SECRET` 에만 둔다.
  DB 가 새도 키는 안 샌다. 키는 서버 안에서만 풀고, 화면·로그·오류 문구에 원문을 싣지
  않는다. 표는 서비스 권한만 읽는다(회원 역할 권한 없음)
- **관리자 화면**(`/admin` 시스템 탭): 등록(키 붙여 넣기 → 저장 즉시 원문 폐기), 끝 4자리
  표시, 켜기/끄기, 동시 한도 수정, 「확인」(이미지를 만들지 않는 무료 요청으로 키가
  살아 있는지), 최근 오류. **최고 관리자만**
- **처음 계정**은 지금의 `FAL_KEY` 를 그대로 등록해 쓴다(이전 경로). 표가 비면 `FAL_KEY`
  로 돌아간다
- **여러 계정을 실제로 켜기 전 fal 약관 확인**(사용자·fal 답변) — 기능은 만들어 두고 쓸지는
  그때 정한다
- 포스터·카드뉴스도 제출할 때 풀에서 계정을 고르고, 진행 중 건수로 칸을 센다(§3.4 배치기와
  같은 셈). 그래야 동기 경로와 서로 칸을 뺏지 않는다

### 3.4 이미지 작업 접수 — 상세페이지부터 (코드, 가장 큼)

이미 있는 **작업 표** `pdp_generation_jobs`·`pdp_generation_artifacts`
(`202609180001_pdp_jobs.sql`) 위에 세운다. 이 표는 상태 단계(validated → reserved →
submitting → submitted → generating → result_available → persisted → completed / partial /
failed / review_required), 장별 fal 작업 번호(`provider_request_id`), 작업을 맡은 서버 표시
(`lease_owner`·`lease_until`)를 이미 갖고 있다.

**더하는 것**: 상태 `queued`·`cancel_requested`·`cancelled`, 사용한 fal 계정, 입력(상품
사진 등)을 둔 저장소 경로, 앞선 대기 수 계산용 접수 시각.

**흐름**

1. **접수** `POST` — 인증(§3.2) → 입력 검사 → **잠금 없는 사전 확인**(잔액, 이미 진행·대기
   중인 작업) → 입력 이미지를 **저장소에 올리고 경로만** 작업 표에 → `queued` 로 저장 →
   작업 번호를 돌려준다. 같은 요청은 멱등키로 한 번만. 한 사람당 대기+진행 1건
2. **배치기**(서버 안 반복 작업, 프로세스 하나) — 오래된 순으로 `queued` 를 집어, fal 풀에서
   빈 칸을 찾아 **장 수만큼 칸을 잡는다**(상세페이지 한 건 = 최대 6칸, 빈 칸이 모자라면 가능한
   만큼씩 나눠 보낸다). 그때 **크레딧을 예약**한다(실패하면 차감 없이 실패로 닫음)
3. **생성** — fal **대기열 API**(submit → status → result)로 보낸다. 작업 번호를 장별로 적어
   두므로 **서버가 재시작돼도 결과를 다시 받아 온다.** 429·일시 오류는 기다렸다 다시, 계정
   잠김·키 무효는 그 계정을 풀에서 빼고 다른 계정으로, 관리자에게 알림
4. **결과** — 완성된 장은 곧바로 저장소에 두고(원본 화질 그대로), 품질검사, 라이브러리 등록
   (지금의 서버 등록 경로 재사용), **완성된 장만 확정 차감**
5. **조회** `GET` — 상태, 앞선 대기 수(`ahead` = 이 작업보다 먼저 접수돼 아직 시작 안 한 수),
   장별 진행, 결과 주소. 가볍게(§3.2 인증만, profiles 없이)
6. **취소** `POST …/cancel` — 대기 중: 바로 `cancelled`, 차감 0. 만드는 중: 아직 안 보낸 장은
   안 보내고, fal 대기열에 있는 장은 취소 요청, **이미 완성된 장은 저장·차감**(사용자 결정)
7. **대기 10분 초과** — 자동 `cancelled`, 차감 0, 「지금 사용자가 많습니다」

**화면**: 상세페이지 만들기는 접수 뒤 작업 번호로 조회만 한다. 「접수됨(앞에 N명)」→
「만드는 중(6장 중 k장)」→ 「완료」/「일부 실패」/「실패」/「취소됨」. 사이드바 「만드는 중」은
서버 작업 목록을 읽는다 — 다른 기기에서도 보인다. 결과는 **저장소 주소**로 받는다(편집기
`PdpEditor` 가 그 주소를 캔버스에 그릴 수 있는지 — 교차 출처 — 를 먼저 확인).

**변수별 처리**

| 상황 | 처리 |
|---|---|
| 창 닫기·화면 이동·휴대폰 잠금·네트워크 끊김 | 작업은 계속. 다시 열면 상태 그대로, 결과는 라이브러리 |
| 버튼 여러 번·여러 탭 | 멱등키로 한 번만, 한 사람 1건 |
| 서버 재시작·배포 | 배치기가 켜질 때 `lease_until` 이 지난 작업을 다시 잡아 fal 작업 번호로 이어서 |
| fal 한 계정 막힘 | 다른 계정으로. 전부 막히면 그 장만 실패·차감 없음·관리자 알림 |
| 일부 실패 | 성공한 장만 차감·저장, 실패 장은 「다시 만들기」 |
| 크레딧 부족 | 접수 때 바로 거절(기다린 뒤가 아님) |
| 관리자 | 전체 작업 목록·상태·강제 취소 |

**메모리**: 입력은 저장소에, 결과도 저장소에 두고 응답은 주소만 — 지금의 base64 6장 응답
(40~50MB)과 라이브러리 대기열이 이미지를 쥐는 문제(`library-sync.ts:279-284`)가 함께 사라진다.
품질검사에 싣는 사본 크기는 측정 뒤 정한다(결과 화질과 무관).

**나머지 무거운 동기 경로**(리디자인 2, 캐릭터 2): 같은 작업 접수로 옮기는 것은 다음 단계.
그 전까지는 서버 전체 동시 수 상한만 둔다(render-gate 처럼 **대기 없이** 자리가 없으면 곧바로
「잠시 후 다시」, fal 호출은 풀의 칸을 잡고).

### 3.5 사고 뒤처리 — 남은 동기 경로 (코드)

작업 접수로 옮긴 경로는 재시작해도 이어지므로 해당이 없다. 옮기기 전의 동기 경로만:

- **허용 목록만**: `pricing_policy='image-v2' and status='reserved' and credit_quote->>'resource'
  in ('pdp:…','redesign:generate','redesign:edit','character:…')` 이고 `credit_jobs` 연결이 없는 것.
  **`sns:*`·`poster:*` 는 절대 건드리지 않는다**(재시작 뒤에도 이어지는 설계다)
- 단계별: `phase='reserved'`(제공사 안 부름) → 차감 없이 푼다. `phase='started'` → 장부 설계대로
  **`needs_review` 로 옮겨 관리자 「정산 확인」에 보이게** 한다(`2026-09-22-credit-subscription-design.md:717`)
- 닫을 때 `error_code='process_restart'`, `cost_state='unknown'`
- 고르는 기준: 예약에 **서버 표식(boot id)** 을 남긴다 — 시각 비교보다 튼튼하고 공유 DB 의
  다른 제품 예약을 고르지 않는다. 함수 인자를 바꾸면 42725(같은 이름 함수가 둘) 재발 위험 —
  옛 판 삭제·이름 유일성 검사를 함께
- 시작 훅은 nodejs 에서만, 기다리지 않고, 실패해도 기동은 계속

### 3.6 데이터베이스 부담 줄이기 (코드)

1. §3.2 로 `auth/v1/user` 왕복이 빠진다
2. **`credit_summary`** — 「이번 달 납부 기간은 있는데 지급 행이 없을 때」만 잠그고 지급한다.
   나머지는 잠금 없이 조회(`wallet_state` 는 한 문장이라 값이 섞이지 않는다). 운영 함수 정의를
   먼저 확인하고, 상세페이지 제품이 이 함수를 부르는지도 확인한다
3. **팀 조회 생략은 메뉴에만**(`studio-layout.tsx:37`). 읽기 범위를 정하는 `teamIdOf` 는 그대로 —
   운영에 팀 소속이 1행 있다
4. **사이드바 미리 불러오기(prefetch) 끄기** 후보 — §3.0 의 브라우저 측정으로 효과를 보고 정한다
5. 목표: 로그인 후 화면 하나당 **profiles 2 + 잔액 1** 안팎

### 3.7 가입·메일 한도 (확인 + 설정)

요구 원문이 「회원가입 과정부터」다.

- Supabase 대시보드 Auth › Rate Limits: **메일 발송 한도**(custom SMTP 기본 시간당 약 30통으로
  알려짐), IP 당 가입·로그인 한도, 토큰 갱신 한도 — 확인 후 필요한 만큼 올린다
- SMTP 제공자 자체 하루·시간 한도 — 부족하면 트랜잭션 메일 서비스로 바꾼다(사용자 결정)
- 서버 쪽 토큰 갱신은 EC2 한 IP 에서 나간다 — 한꺼번에 로그인한 사람들이 1시간 뒤 한꺼번에 갱신
- 감시 메일은 가입 메일 몫을 먹지 않게 분리하거나 제한(§3.1-5)

### 3.8 외부 AI

- **Anthropic**: Scale 등급으로 넉넉하다. 콘솔 Billing 에서 **직접 정해 둔 월 지출 한도**와 알림
  이메일만 확인한다
- **fal**: ① 한도 상향 요청(목표 200칸, 문안 작성함) ② 계정 풀(§3.3). 필요한 칸 =
  「동시 상세페이지 수 × 6 + 포스터·카드뉴스 동시 수 + 품질검사 재생성 여유」. 이 서비스 전용
  계정으로 분리하면 영상 작업이 칸을 뺏지 않는다. 잔액·자동 충전은 운영 준비 목록에
- **Google·OpenAI 직접 호출**(리디자인)의 한도도 확인 목록에 넣는다
- 계정 단위 장애(잔액 소진·키 무효) 알림은 §3.3 풀 상태 + AI 비용 보안(③)

### 3.9 재측정과 성공 기준

§3.0 과 같은 조건으로 전후를 잰다.

| 기준 | 값 |
|---|---|
| 로그인 100명 화면 + 동시 생성 10건 | **재시작 0회**, 생성은 접수·대기·완료 |
| 로그인 후 화면 | 보통 2초 · 느린 쪽 5초 이내 |
| 로그인 전 화면 200명 3분 | 재시작 0회, 보통 3초 이내 |
| 생성 | 실패·라이브러리 누락 0(가짜 AI 기준), 10분 넘은 대기는 차감 없이 취소 |
| 만드는 중 서버 재시작 | 작업이 이어서 완성, 이중 차감 0 |
| 취소 | 대기 중 차감 0, 만드는 중 완성 장만 차감 |
| fal 계정 하나 막힘(가짜 AI 로 403 흉내) | 다른 계정으로 계속, 관리자 메일 |
| 가입 | 한 시간에 100명 가입 → 확인 메일 전부 도착(설정 확인 + 시험 계정 발송) |
| 실제 브라우저 | 5·10·15분 대기에서도 상태 표시가 이어짐 |

기준에 못 미치면 원인(서버/DB/외부)을 가려 보고하고, DB 라면 **Supabase 컴퓨트 올리기**를
제안한다.

## 5. 하지 않는 것

- 프로세스 여러 개 — 배치기·자리 셈이 프로세스 하나를 전제한다. CPU 가 한계로 드러나면 그때

- Supabase 지역 이전 — 호출 수를 줄이는 쪽이 효과가 크다
- 결제, AI 비용 보안(③)

## 6. 위험과 되돌리기

| 위험 | 대비 |
|---|---|
| 작업 접수 전환이 상세페이지 전체에 영향 | 스위치로 옛 동기 방식으로 되돌린다(`PDP_JOBS_MODE`). 옛 방식은 한동안 남긴다 |
| 배치기 결함으로 작업이 멈춤 | 작업마다 `lease_until` — 멈춘 작업은 다시 잡힌다. 관리자 목록에서 보이고 강제 취소 가능. 감시가 「대기만 쌓이고 진행 0」을 알린다 |
| 키 유출 | 암호화 저장, 원문은 서버 안에서만, 최고 관리자만, 변경 기록. 열쇠는 `app.env`(root 0640) |
| 메모리 상한 오설정 | 시험 서버에서 먼저, `app.env` 한 줄로 되돌림, `MemoryMax` 로 서버 전체는 보호 |
| 로그인 확인 변경 | 단독 배포, 되돌리기는 이전 릴리스 |
| 잔액 조회 잠금 제거 | 표시 전용, 지급이 필요할 때만 잠근다, DB 에서 먼저 시험 |
| 재시작 뒤처리가 남의 예약을 고름 | 허용 목록 + 서버 표식 + `sns`·`poster` 제외를 시험으로 고정 |
| 배포 자체가 재시작 | 작업 접수로 옮긴 경로는 이어진다. 남은 동기 경로를 위해 배포 전 「진행 중 생성 수」 확인을 `DEPLOY.md` 에 |

## 7. 결정이 필요한 것 (진행 중에 묻는다)

- Supabase 컴퓨트 올리기(§3.9 결과)
- 여러 fal 계정을 실제로 켤지(fal 약관·답변)
- 이 서비스 전용 fal 계정으로 분리할지
- 메일 한도가 모자랄 때 SMTP 바꾸기(§3.7)
- Supabase 요금제의 Storage 용량·전송량(egress) 한도 — Billing 에서 확인. 결과 보기는 대부분
  서명 주소(Storage egress)이고 포스터 원본은 EC2 를 거친다(`lib/poster/supabase-store-core.ts:48`)
