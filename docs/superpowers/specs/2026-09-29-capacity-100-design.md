## 2. 지금 상태 — 측정 근거

### 2.1 측정 환경

운영과 같은 급의 시험 서버 A(t3.micro, 911MB, 스왑 2GB, 같은 systemd 유닛·
`NODE_OPTIONS=--max-old-space-size=512`·Caddy)에 운영 master 빌드를 올렸다.
도우미 서버 B(t3.large)에 시험용 Supabase 스택, **가짜 AI**(fal·Anthropic·OpenAI 와
같은 모양·같은 크기의 응답, 이미지 45초·글 3초 지연), k6 부하 발생기를 두었다.
운영 코드는 바꾸지 않고 A 의 `/etc/hosts` 만 가짜 AI 로 돌렸다.

**운영과 다른 점:** 시험 DB 는 A 와 같은 망(왕복 <1ms, 운영은 약 0.2초), 크기도
운영(MICRO)보다 크다. 가짜 AI 는 늘 성공하고 지연이 일정하다.

### 2.2 강제 종료 시점

| 상황 | 버틴 최대치 | 멈춘 지점 | 직전 모습 |
|---|---|---|---|
| 로그인 전 화면(첫 화면·가입·로그인 + 정적 파일) | 160명 3분 (보통 4.4초) | **200명 약 4분 만에 종료 (2/2회)** | 처리량이 초당 32~40건에서 고정, 대기가 쌓여 여유 램 22MB |
| 상세페이지 6장 묶음 동시 생성 | 6명 전부 성공(약 2분) | **10명 종료** | 8명: 502 1건, `library sync queue is full` 로 **결과가 라이브러리에 안 들어감**, 스왑 1.8GB/2GB |
| 섞임: 로그인 50명 화면 + 상세페이지 3명 | 종료 없음 | — | 화면 보통 6초·느린 쪽 17초 |
| 로그인 후 화면만 | 100명 종료 없음 | — | 10명 0.3초 · 25명 1.6초 · 50명 5.5초. **A 는 한가(CPU 10~20%), 시험 DB CPU 120%** |
| 포스터·카드뉴스 생성 | 20명 동시 전부 성공 | — | 여유 램 190MB 이상 |

**상세페이지는 한 건만으로 여유 램이 35MB 까지 떨어진다**(서비스 메모리 128→666MB).

### 2.3 멈추는 방식

`--max-old-space-size=512` 를 넘는 순간 `FATAL ERROR: Reached heap limit … JavaScript
heap out of memory` 로 프로세스가 스스로 죽는다(`status=6/ABRT`). systemd 가 5초 뒤
다시 띄운다(`Restart=always`, `RestartSec=5`). 그동안:

- 모두 약 10초 접속이 끊긴다(Caddy 502)
- 생성 중이던 요청은 결과를 잃는다 — fal 비용은 이미 나갔다
- 그 사람의 크레딧 예약이 묶여 **「이미 생성 중인 요청이 있습니다」(429)** 로 한동안
  새 생성을 못 한다 — 시험에서 재현(`202609220001_credit_ledger_v2.sql` 의 동시 1건 규칙)
- 알림이 없다 — 운영자는 고객 문의로 안다

### 2.4 데이터베이스

- 운영 Supabase: 프로젝트 `page.mktinsight`(상세페이지 제품과 **공유**), 컴퓨트 **MICRO**
  (2코어 공유·1GB — Supabase 안내 기준), 백업 매일(유료 요금제로 보임, Billing 미확인)
- 운영 앱 → Supabase 왕복 **약 0.2초**(0.11~0.23초, 10회). 서울 밖으로 추정
- 실제 고객 기록(Caddy 접근 로그): 목록 API 보통 0.4~0.6초·느린 쪽 0.9초
- 로그인 후 화면 하나가 부르는 것(시험에서 셈): `auth/v1/user` 2 · `profiles` 2 ·
  `team_members` 1 · `rpc/credit_summary` 1~2. 목록 API 도 `auth/v1/user` 2 · `profiles` 1 ·
  `team_members` 2
- 크레딧 함수 전부가 전역 잠금 하나(`credit_lock()` = `pg_advisory_xact_lock`)를 잡는다 —
  잔액 조회(`credit_summary`)도. 25명 시험에서 잠금 대기는 0 이었다

### 2.5 외부 AI 한도

- **Anthropic**(운영 키, `claude-sonnet-5`, 2026-09-29 응답 헤더로 확인): 분당 요청
  10,000 · 분당 입력 토큰 1,000만 · 분당 출력 토큰 200만. 100명 규모에 넉넉하다.
  월 지출 상한은 헤더에 없다 — 콘솔에서 확인
- **fal.ai**: 응답에 한도 정보를 싣지 않는다. 계정 동시 요청 한도는 문서·대시보드로
  확인해야 한다(§3.7)

## 3. 설계

단계마다 **시험 먼저 → 구현 → 독립 리뷰 → 뮤테이션 확인 → 배포 → 운영 확인**
(`staged-rollout-with-independent-review`). 단계 순서는 막는 위험이 큰 것부터다.

### 3.0 기준선 — 운영 크기로 다시 잰다

지금 숫자는 운영보다 넉넉한 DB 로 잰 것이다. 개선 효과를 말하려면 기준선이 운영과
같아야 한다.

- 시험 DB 컨테이너를 MICRO 에 가깝게 묶는다: 메모리 1GB, CPU 제한
- A→B DB 구간에 운영과 비슷한 지연(왕복 약 0.2초)을 넣는다
- 같은 시나리오(로그인 25·50·100, 섞임 50+3)를 잰다 → **개선 전 기준선**

한계: 운영 MICRO 는 ARM 공유 코어라 x86 에서 똑같이 흉내 낼 수 없다. 숫자는
「운영과 비슷한 쪽」이지 같지 않다 — 보고할 때 그렇게 적는다.

### 3.1 서버 키우기와 감시 (설정)

1. **t3.medium** 으로 바꾼다. 운영 AWS 계정에서 사용자가 콘솔로 한다(이 컴퓨터의 AWS
   권한은 다른 계정이다). 중지 → 유형 변경 → 시작, 탄력적 IP 유지, 약 5분 정지
2. 메모리 상한을 올린다. 값은 시험 서버 A 를 t3.medium 으로 바꿔 먼저 재서 정한다
   (시작값 후보 2.5GB). `app.env` 의 `NODE_OPTIONS`
3. Caddy 에 재시작 틈을 기다리는 설정(`lb_try_duration`)을 넣는다 — 몇 초 재시작 동안
   502 대신 대기
4. **감시**: 서버 안의 systemd 타이머가 1분마다 `/api/health/ready`·재시작 횟수·메모리를
   보고, 멈춤·재시작·메모리 90% 초과를 **기존 SMTP 계정**으로 관리자에게 메일한다.
   추가 비용 없음(`no-extra-billing-prefer-self-hosted`). 같은 사건은 한 번만 보낸다
5. 새 서버에 `install-host.sh` 를 처음 돌리면 Caddy 로그 폴더 권한으로 Caddy 가 안 뜨는
   문제(2026-09-28 시험에서 발견)를 함께 고친다 — 서버를 다시 만들어야 하는 날 대비

### 3.2 줄 세우기 (코드)

**무엇을 묶나** — 우리 서버의 메모리를 크게 쓰는 동기 생성만:

| 도구 | 경로 |
|---|---|
| 상세페이지 | `/api/pdp/images/batch` · `/api/pdp/images` · `/api/pdp/key-visual` |
| 리디자인 | `/api/redesign/generate` · `/api/redesign/edit-section` |
| 캐릭터 | `/api/characters`(생성) · `/api/characters/views` |

포스터·카드뉴스는 fal 큐에 맡기고 결과만 받아 와 가볍다(20명 측정). 묶지 않는다.

**어떻게** — 프로세스 하나 안의 **선착순 자리 표**(`lib/generation/slots.ts`).

- 자리 수 `GENERATION_SLOTS`(시작 4, 재측정으로 조정). 상세페이지 묶음은 한 건이
  무거우므로 가중치를 둘지 3.3 측정 뒤 정한다
- 자리가 없으면 서버 안에서 **순서대로 기다린다.** 최대 `GENERATION_QUEUE_TIMEOUT_MS`
  (10분). 넘으면 **503 + 「지금 사용자가 많습니다. 잠시 후 다시 시도해 주세요」**
- **크레딧 예약은 자리를 얻은 뒤에 한다.** 기다리는 동안 차감·묶임이 없고, 사용자당
  동시 1건 규칙에도 안 걸린다
- 끄는 스위치 `GENERATION_QUEUE=off` — 줄 세우기에 결함이 있으면 배포 없이 되돌린다
- 이미 있는 합성 자리(`lib/layout/render-gate.ts`)와 같은 모양으로 만든다

**화면** — 「앞에 N명 기다리는 중」

- `GET /api/generation/queue` → `{ ahead, active, slots }`(로그인 회원만, 개인 정보 없음)
- 해당 생성 화면은 요청이 끝나기 전까지 5초마다 이 값을 보여 준다. 기다리는 사람이
  없으면 지금처럼 「만드는 중」만

**확인할 것(구현 계획에서)**

- 기다리는 동안 요청 본문을 어디서 들고 있나. 자리보다 먼저 읽으면 기다리는 사람
  수만큼 본문(상품 사진 등)이 메모리에 쌓이고, 나중에 읽으면 Node 의 요청 수신 제한
  시간(`requestTimeout`)에 걸릴 수 있다. 본문 크기와 서버 설정을 재서 정한다
- 프로세스를 여럿 띄우게 되면 자리 표를 공유해야 한다 — 지금은 하나라서 범위 밖(§4)

### 3.3 상세페이지 메모리 (코드, 측정 먼저)

한 건이 약 500MB 를 쓴다. 어디서 쓰는지 **먼저 잰다**(시험 서버에서 힙 스냅샷·단계별
메모리). 후보:

1. 결과 6장을 base64 로 한 응답에 담는다(`app/api/pdp/images/batch/route.ts`) — 응답
   한 번에 40~50MB
2. 품질검사가 같은 그림을 글 모델 요청에 다시 싣는다(`packages/pdp-core/src/pdp.qa.ts`)
3. 라이브러리 저장 대기열이 같은 6장을 또 쥔다(`lib/pdp/jobs/library-sync.ts`, 상한이 건수 12)

큰 것부터 줄인다. **결과 이미지의 화질은 건드리지 않는다**(원본 그대로). 응답을
주소로 바꾸는 쪽을 고르면 편집기(`PdpEditor`)가 그 주소로 그림을 받아 캔버스에
그릴 수 있는지(교차 출처)를 먼저 확인한다.

### 3.4 사고 뒤처리 (코드)

1. **재시작 때 묶인 예약 풀기** — 서버가 켜질 때, 이 서버가 켜지기 전에 시작돼 끝나지
   않은 예약을 **차감 없이** 푼다. 사용자는 결과를 못 받았으므로 차감하지 않는 것이
   맞다. 회사 원가(fal)는 장부에 원가로 남는다. DB 함수 하나 + 앱 시작 훅
2. **라이브러리 저장이 넘쳐도 버리지 않는다** — 대기열이 차면 「나중에 다시」로 기록하고
   다시 저장한다. 3.3 에서 대기열이 이미지 대신 경로를 들게 되면 넘침 자체가 준다

### 3.5 데이터베이스 부담 줄이기 (코드)

1. **로그인 확인을 서버가 직접 검증한다** — `auth.getUser()`(Supabase 로 왕복) 대신
   `auth.getClaims()`(토큰 서명을 직접 확인). 운영 Supabase 는 **ES256 비대칭 키**를
   쓴다(`/auth/v1/.well-known/jwks.json`, 2026-09-29 확인). 요청마다 왕복 2번(약 0.4초)이
   빠진다
   - 맞바꾸는 점: 로그아웃한 토큰이 만료(최대 1시간)까지 유효하다. **정지 회원은 회원
     정보(`profiles.status`) 확인에서 그대로 막힌다**
2. **한 요청 안에서 한 번만** — 회원 정보·크레딧 잔액을 요청 단위로 기억해 두 번 묻지
   않는다
3. **팀 조회 생략** — 팀 기능이 꺼져 있을 때는 `team_members` 를 묻지 않는다
4. **잔액 조회는 잠금 없이** — `credit_summary` 가 전역 잠금을 잡지 않게 한다. 예약·
   확정·회수는 지금처럼 잠금 안에서 한다(돈이 움직이는 곳). 조회가 한순간 늦은 값을
   보여 줄 수는 있다 — 화면 표시용이라 받아들인다

목표: 로그인 후 화면 하나당 6~7번 → 2~3번.

### 3.6 재측정과 운영 확인

- 3.0 과 같은 조건(운영 크기 DB·지연)으로 다시 잰다
- **성공 기준**
  - 로그인 100명이 화면을 보는 중 10명이 동시에 생성 → **재시작 0회**
  - 로그인 후 화면 보통 2초·느린 쪽 5초 이내
  - 생성: 실패·라이브러리 누락 0건. 10분 넘게 기다린 요청은 차감 없이 안내
  - 로그인 전 화면 200명 3분 버팀
- 기준에 못 미치면 원인(서버/DB)을 가려 보고하고, DB 라면 **Supabase 컴퓨트 한 단계
  올리기**를 비용과 함께 제안한다(사용자 결정)

### 3.7 외부 AI 한도

- Anthropic: 분당 한도는 확인됨(§2.5). **월 지출 상한**을 콘솔에서 확인
- fal: **계정 동시 요청 한도**·잔액 소진 시 동작·자동 충전을 문서와 대시보드로 확인.
  동시 한도가 `GENERATION_SLOTS × 6`(상세페이지 한 건이 6장을 동시에 부름)보다 작으면
  자리 수를 거기에 맞추거나 한도 상향을 요청한다
- 잔액 소진·키 무효 같은 **계정 단위 장애 알림**은 AI 비용 보안(③)에서 다룬다

## 4. 하지 않는 것

- 프로세스 여러 개 띄우기 — CPU 가 한계로 드러나면 그때(자리 표 공유가 필요해진다)
- Cloudflare 앞단·정적 파일 캐시 — 도메인 연결(④)에서
- Supabase 지역 이전 — 어렵다. 호출 수를 줄이는 쪽이 효과가 크다
- 포스터·카드뉴스 줄 세우기, 결제, AI 비용 보안(③)

## 5. 위험과 되돌리기

| 위험 | 대비 |
|---|---|
| 메모리 상한을 잘못 잡아 재시작 반복 | 시험 서버를 같은 급으로 바꿔 먼저 돌린 값만 쓴다. `app.env` 한 줄이라 즉시 되돌린다 |
| 줄 세우기 결함으로 생성이 전부 막힘 | `GENERATION_QUEUE=off` 스위치. 대기·해제를 시험으로 고정(자리가 반드시 돌아오는지) |
| 로그인 확인 변경이 모든 화면에 영향 | 시험을 가장 두텁게, 단독 배포. 되돌리기는 이전 릴리스 |
| 잔액 조회에서 잠금을 빼 순간 불일치 | 표시 전용 경로만. 차감 판단은 잠금 안의 함수가 한다 |
| 재시작 때 예약 풀기가 살아 있는 요청까지 풂 | 「이 프로세스가 켜진 시각 이전에 시작된 것」만. 프로세스가 하나라는 전제를 문서와 시험에 적는다 |
