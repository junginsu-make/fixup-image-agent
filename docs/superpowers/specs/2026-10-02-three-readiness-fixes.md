# 배포 전 발견한 세 결함 개선

대상: `d4c6555e`에서 분리한 `fix/three-readiness` / `.worktrees/fix-three-readiness`.
범위는 사용자 승인한 세 건이다. 회원가입·전화번호·관리자 회원 화면은 변경하지 않는다.

## 1. fal 요청 복구와 처리 자리 정리

기존 결함은 공급자 접수 후 계정 연결 저장 실패를 성공처럼 반환하고, 재시작 뒤 기록 누락을 기존 서버 키 요청으로 간주하는 것이다. 계정 목록 읽기 실패도 빈 목록으로 취급했다. 연결되지 않은 자리에는 제공자 요청 번호가 없어 완료 시에도 30분 동안 한도를 차지했다.

정상 저장된 요청과 기존 요청의 번호는 그대로 유지한다. 저장을 확인하지 못한 경우만 `fxfal1.<payload>.<signature>` 복구 영수증을 반환한다. 공급자 요청 번호·계정 ID·원래 처리 자리 ID가 들어가며 **API 키는 포함하지 않는다**. 기존 `FAL_KEY_ENCRYPTION_SECRET`에서 용도를 분리해 파생한 키로 HMAC 서명한다. 영수증은 기존 서버 소유 작업 기록의 요청 ID 자리에 보관되므로 별도 로컬 파일이나 메모리에만 의존하지 않는다. DB 연결 RPC의 void 응답 뒤에는 실제 저장된 번호도 확인한다.

후속 조회에서는 영수증 서명을 확인하고 원래 계정으로만 조회한다. fal HTTP 호출에는 영수증을 풀어 얻은 원래 제공자 요청 번호만 보낸다. 서버 키 모드에서는 풀 영수증을 거부한다. 잘못된 영수증·키·계정 정보 조회 실패는 HTTP 상태 없는 복구 오류로 처리하여 결과 소실/환급으로 오인하지 않는다. 정상적으로 읽은 과거 DB 기록이 없는 기존 요청의 서버 키 호환은 유지한다.

원가 장부도 원래 제공자 요청 번호로 정규화해 같은 요청의 비용이 다른 ID로 두 번 기록되지 않게 한다. 동기 처리의 상태·결과·취소도 같은 규칙이다.

완료 정리는 `release(slotId)` → `finish(providerRequestId)` 순서다. 앞의 함수는 **번호가 붙지 않은 자리만 삭제**하고, 뒤의 함수는 번호가 이미 붙은 행을 완료한다. 늦은 bind가 먼저 잠금을 잡으면 뒤의 finish가 처리하고, release가 먼저면 bind가 지운 행을 되살리지 못한다. 기존 SQL 함수를 재사용하므로 **새 DB 마이그레이션은 없다**.

완료 정리 실패는 이미 받은 결과를 버리지 않고 프로세스 안에서 재시도 대기한다. 다음 제출 전에 대기한 정리 한 건을 다시 시도한다. 완료 후 DB 작업에는 요청별 5초 제한을 두고 최대 3회 시도한다. 전체 DB 장애·프로세스 종료 때도 즉시 자리가 정리된다고 보장하는 것은 아니며, 기존 30분 lease가 최종 상한으로 남는다.

배포 전에 이미 계정 연결을 잃어버린 요청의 계정을 새 코드가 자동 추측해 복원하지 않는다. 새 복구 영수증을 보관한 작업이 진행 중이면 이 형식을 모르는 이전 앱으로 되돌리지 않는다. 운영자 멈춤 기능으로 새 생성을 잠시 막고 진행 중 작업과 결과 저장을 확인한 뒤 되돌리거나, 이 복구 기능을 유지한 수정 릴리스를 사용한다. 암호화 비밀값도 진행 중 작업이 있는 동안 임의로 바꾸지 않는다.

## 2. 배포 실패 복구

배포·수동 되돌리기 모두 `release-recovery.sh`를 사용한다. 전환 전에 앱과 정적 파일의 이전 연결을 각각 기록하고, 정적 파일 활성화부터 건강 검사까지 ERR 복구를 건다. 재시작 명령 실패도 이 경로로 들어간다.

복구는 두 연결을 되돌리고, 필요한 경우 서비스를 다시 시작한 다음 liveness/readiness를 확인한다. 성공을 확인한 경우만 복구 완료를 알린다. 복구 실패는 `RECOVERY FAILED`와 실패 종료 상태로 남긴다. 이전 릴리스가 없으면 서비스 중단 및 수동 복구 필요를 보고한다. 건강 요청에는 연결·응답 시간 제한을 둔다. 서비스 마스킹 등 인프라 원인까지 이 스크립트가 자동 해결한다는 의미는 아니다.

## 3. 준비 상태와 실제 기획 제공자

기존 회원·CAPTCHA·메일·Google/FAL 설정 검사는 유지하고 공백 값을 거부한다. 현재 제공하는 상세페이지/포스터 기획과 SNS 기능의 요구에 맞춰 `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`도 generation 준비 검사에 포함한다. 준비 검사에서 유료 생성이나 외부 제공자 API를 호출하지 않는다.

포스터 제공자는 필요할 때만 SDK 클라이언트를 만든다. Anthropic 기획·첨부 읽기가 사용하지 않는 OpenAI 클라이언트 초기화 때문에 실패하지 않도록 한다. OpenAI를 사용하는 선택 경로는 기존처럼 키를 요구한다. 전체 서비스 준비 검사에서 OpenAI가 필요한 이유는 SNS 등 현재 포함된 다른 기능의 필수 조건 때문이다.

## 회귀 검증과 운영 적용

- `lib/fal/pool/__tests__/durability.test.ts`: 기록 실패 뒤 새 프로세스 복구, 키/서명 변조, DB 읽기 실패, 원래 번호로 조회·취소, 원가 ID 일치, 완료 정리 재시도.
- `scripts/tests/fal-route-recovery.test.mjs`: 임시 PostgreSQL에서 기록 실패 → 재시작 → 결과 조회 → 1회 정산, 완료 자리 반환, 응답 유실, 지연 bind 경합을 검증한다. 실제 유료 API는 호출하지 않는다.
- `scripts/tests/release-rollback.test.mjs`: 실제 스크립트의 전환 구간과 복구 함수를 실행하고 OS 명령만 모의한다. 재시작 실패·건강 검사 실패·복구 실패·수동 되돌리기를 검증한다. 실제 운영 systemd 복구 시험과 구분한다.
- readiness/포스터 초기화 시험: 필수 키 누락·공백 거절, 완전한 설정 수용, 선택 예비 키 없는 초기화, 외부 호출 없음.

위 두 스크립트는 `pnpm test:readiness-fixes`로 실행하며 PR 검사와 릴리스 생성 전 검사에 연결한다. 타입 검사·웹 회귀·Linux 빌드를 확인하고, 운영에서는 새 ops 꾸러미의 `release-recovery.sh`를 함께 사용한다. 앱만 바꾸고 옛 배포 스크립트를 계속 쓰면 롤백 수정은 적용되지 않는다.

현재는 로컬 구현·검증 단계다. 운영 서버·실제 제공자·운영 크레딧을 변경하지 않는다. 최종 실행 결과는 작업 완료 시 갱신한다.
