## 1. 목표와 완료의 의미

사용자가 입력한 사실·참조·설정으로 구성안을 만들고, 사용자가 승인한 구성안으로 이미지를 만들며, 같은 결과를 저장·편집·내보내기까지 보존한다.

```text
입력 자료와 목적
    ↓
상품 사실 + 판매 브리프 + 참조 역할
    ↓
Fable 기획 → 구성안 심사 → 사용자 수정·승인
    ↓
승인 버전과 실제 실행 모델·참조·금액 확정
    ↓
서버 작업 생성 → 섹션 생성 → 결과 보존 → 검수·정산
    ↓
전체 페이지 확인 → 편집 → 동일한 완성본 저장·다운로드
```

필수 불변 조건:

1. 화면을 옮기거나 응답을 못 받아도 만들어진 결과를 다시 찾을 수 있다.
2. 저장→읽기→화면 복원 후 사실·참조·설정·문구·이미지·레이어가 보존된다.
3. 같은 요청의 재전송은 같은 작업을 조회한다. 의도적인 재생성만 새 작업이다.
4. 생성 당시 승인 버전은 불변이다. 이후 편집이 진행 중인 생성의 입력을 바꾸지 않는다.
5. 선택 모델·실제 모델·품질·크기·차감 근거가 일치한다. 대체 실행은 기록·표시한다.
6. 제품·캐릭터의 정체성 보존 조건은 배치·분위기 지시로 해제되지 않는다.
7. 참조를 조용히 버리거나, 검사하지 못한 결과를 통과로 표시하지 않는다.
8. 최종 미리보기·완성본 저장·다운로드는 같은 합성 규칙을 사용한다.
9. 원본 조사 항목은 수정·중복·검증 후 제외 중 하나로 종결한다. 목록에서 그냥 삭제하지 않는다.
10. 코드 완료, DB 적용, 배포, 실제 생성 품질 확인, 판매 성과 확인은 각각 별도로 기록한다.

이번 작업으로 실제 구매 전환 개선을 보장하지 않는다. 상품 사실 정확성·원형 보존·사용 흐름·결과 품질을 먼저 검증한다.

## 2. 증거 수준과 원문 보정

- `재현`: 실제 함수/저장 왕복/오류 대역으로 확인한 결과. 실제 유료 생성·운영 장애 실측과 구분한다.
- `코드`: 현행 코드에서 경로를 확인한 것. 수정 전 해당 동작 시험을 먼저 만든다.
- `검증`: 발생 조건·영향이 아직 불확실하다. 재현되면 수정, 재현되지 않으면 그 근거를 남겨 종결한다.
- 이 문서의 신규 타입·테이블·환경변수·엔드포인트는 **목표 계약**이며 현재 구현돼 있다는 뜻이 아니다.
- Claude의 64건과 Codex의 13건을 더하지 않는다. 묶음 항목의 세부 지적까지 §14에 추적한다.
- 빈 심사는 현재 UI에서 숨겨진다. 한 항목만 pass일 때 전체 통과 문구가 표시되는 문제와 구분한다.
- 사진 기획은 최초 생성 뒤 심사 수정 최대 1회다. 텍스트 기획은 최대 2회다.
- ‘인증 구멍 없음’, ‘실패는 0장이므로 환불 누락 없음’은 전체 안전성 보증으로 채택하지 않는다.
- 1536px→920px은 폭 약 60%, 같은 비율의 픽셀 면적 약 36%다. ‘해상도 40%’라는 표현 대신 실제 폭·높이를 검증한다.
- 잘린 JSON의 40~60KB 처리 시간, 운영 번들 노출, 토큰 상한 초과는 검증 과제로 남긴다. 추정을 확정 장애로 쓰지 않는다.

## 3. 메인 기획 LLM: Fable

### 3.1 현재 근거와 선택

기존 [포스터 설계 D7](../2026-08-31-poster-studio-design.md)에 Anthropic 제공자와 모델 ID `claude-fable-5`가 명시돼 있다. 현행 `apps/web/lib/{pdp,poster,sns}/providers.ts`와 로컬 `ANTHROPIC_MODEL`은 `claude-sonnet-5`다. 이 체크아웃에서 Fable이 이미 실행 중이라는 사실은 확인되지 않았다.

사용자가 말한 ‘Claude Code Fable’은 우선 이 기존 **Anthropic API 모델 `claude-fable-5`**로 연결한다는 설계다. Claude Code CLI를 웹서버에서 실행하는 구현은 확인되지 않았으므로 새로 도입하지 않는다. 정확한 실행 경로에 대한 사용자 답변이 다르면 이 절을 먼저 갱신한다.

### 3.2 적용 범위와 설정 계약

`apps/web/lib/pdp/providers.ts`에서 업무 목적을 구분해 모델을 선택한다.

| 역할 | 기본 실행 정책 |
|---|---|
| 사진에서 상품 사실·구성안 작성 | Fable |
| 텍스트 판매 브리프·구성안 작성·재작성 | Fable |
| 리디자인의 분석·구성 기획 | 공통 기획 어댑터의 Fable. 이미지 모델 선택과 분리 |
| 구성안 심사·사실 확인·이미지 QA·인물 검증 | 기존 검수 제공자 설정 유지, 업무 목적을 명시해 호출 |
| 이미지 생성·전사 | 기존 해당 제공자 경로 유지. 이번 메인 기획 모델 변경과 구분 |

- 새 상세페이지 전용 설정: `PDP_PLANNING_MODEL=claude-fable-5`. 미설정 기본값도 Fable이다.
- 기존 전역 `ANTHROPIC_MODEL=claude-sonnet-5`가 상세페이지 기획 설정을 덮어쓰지 않는다.
- 포스터·SNS·레이아웃의 전역 설정과 호출은 바꾸지 않는다.
- 기존 `ANTHROPIC_API_KEY`와 구조화 응답 어댑터를 사용한다. 별도의 키 복사나 하드코딩을 하지 않는다.
- 기존 OpenAI 기획 폴백을 유지하되 실제 모델·폴백 사유를 기록한다. 응답의 운영용 메타데이터와 장부에 실제 모델을 남긴다. UI에는 ‘대체 기획 모델 사용’으로 알린다.
- Fable 모델 없음/접근 불가 같은 구성 오류를 조용한 영구 폴백으로 숨기지 않는다. 출시 전 연결 검증 실패로 다룬다.
- 런타임 과부하 등 일시 실패는 기존 폴백을 사용할 수 있다. 주/대체 모델에 같은 입력·스키마·근거 규칙을 적용한다.
- 기획 응답에 사용한 모델과 프롬프트/스키마 버전을 작업 revision에 남긴다.
- 현행 호출 이름 `pdp_brief`·`pdp_blueprint`는 기획, `pdp_review`·`pdp_qa`·`pdp_person_profile`·`pdp_person_check`는 검수/참조 분석으로 매핑한다. 새 호출은 `PdpLlmRequest.purpose`를 명시한다. 알 수 없는 이름을 우연히 기획으로 분류하지 않는다. 리디자인 분석은 명시적인 planning 목적을 가진 같은 서버 어댑터로 연결한다.
- 주 모델은 `PDP_PLANNING_MODEL` → 기본 `claude-fable-5`, 대체 기획 모델은 기존 OpenAI 환경 설정 → 기본 `gpt-5.6-sol` 순서다. 모델의 응답 스키마 검증 실패도 실제 사용 모델별로 기록한다.
- Fable의 멀티모달·구조화 출력·응답 길이 적합성은 기존 계정으로 이미지 기획/텍스트 기획 각 한 건을 실제 검증한다. 불가능하면 Sonnet으로 조용히 되돌리지 않고 이 단계의 미완료로 보고한다.

검증 `T-MODEL`: 전역 Sonnet이 존재해도 PDP 기획 호출은 Fable, 검수는 기존 모델, 포스터/SNS 호출 설정은 이전 그대로인지 확인한다. 폴백·모델 미지원·잘린 응답도 포함한다.

## 4. 작업 데이터와 단계의 단일 기준

### 4.1 목표 작업 계약

`PdpDocumentV3`를 UI·IndexedDB·서버 작업이 공유하는 직렬화 가능한 계약으로 둔다. 타입 이름은 구현 시 이 문서를 따라 정한다.

```ts
type PdpDocumentV3 = {
  schemaVersion: 3;
  id: string;
  revision: number;
  savedRevision: number;
  sourceMode: "image" | "text" | "redesign";
  offeringType: "physical" | "service" | "digital" | "other";
  objective: "purchase" | "inquiry" | "promotion";
  stage: "input" | "planning" | "outline" | "evidence" |
         "key_visual" | "generating" | "review" | "editor";
  inputs: ProductInputs;           // 사용자 원문·판매자 브리프·추가 정보
  references: ReferenceAssignment[];
  settings: PdpSettings;
  brief?: ProductBrief;
  productFacts: GroundedFact[];
  sections: PdpSection[];          // 구성안과 편집기가 같은 배열을 참조
  designSystem?: PageDesignSystem;
  planningReview?: ReviewRecord;
  keyVisual?: AssetReference;
  approved?: ApprovedRevision;
  assets: Record<string, AssetReference>;
  editor: EditorState;             // 레이어·선택은 안정된 섹션 ID로 보관
  previousRevision?: RevisionReference;
};
```

`inputs`와 참조의 원문은 생성으로 덮어쓰지 않는다. `sections`의 현재 편집본과 `approved`의 생성용 스냅샷은 버전 관계가 명시돼 있어야 한다.

필수 상세:

- `PdpSettings`: 이미지 모델, 출력 모드, 비율, 문구 강도, 정보 부족 정책, 분위기, 그림체, 기획 지시, 이미지 연출 지시를 담는다.
- `ReferenceAssignment`: asset ID, 역할(product/character/style), 사용 여부, 내용 hash, 적용 섹션, 각도, 사용자 연출 지시, 보존 조건을 담는다.
- `PdpSection`: 애플리케이션이 발급한 UUID, AI 원래 ID(참고용), 역할·목표·모든 노출 문구·장면·배치·근거·생성 자산·검수 상태를 담는다.
- AI의 `S1`은 고유 키로 신뢰하지 않는다. 중복 ID 응답은 입구에서 새 UUID로 분리한다.
- `ApprovedRevision`: 승인 revision, 대상 section ID, 모든 노출 문구와 참조 hash·장면·디자인·설정의 불변 스냅샷이다.
- `AssetReference`: 원본 픽셀 크기/MIME/hash, 로컬 blob 키 또는 서버 storage path, 저장 상태를 포함한다. 장기 base64 중복은 줄이되 기존 초안 변환 성공 전에 원본을 삭제하지 않는다.
- 기존 `result.blueprint.sections`와 `editorDraftState.sections`를 두 개의 쓰기 가능한 정본으로 유지하지 않는다. 레거시 API는 이 문서에서 파생해 보낸다.

### 4.2 수정과 승인

- 문구·장면·섹션 순서·참조·모델을 바꾸면 revision 증가 및 승인 상태 해제. 이전 생성 자산은 삭제하지 않고 ‘이전 구성의 결과’로 표시한다.
- 섹션 삭제·재분석·재생성은 직전 revision/asset을 보존하고 되돌리기를 제공한다. 과거 자산은 정책에 따라 정리하되 조작 즉시 삭제하지 않는다.
- 선택 섹션은 배열 인덱스 대신 UUID. 앞 섹션 삭제 후 같은 섹션을 계속 본다.
- 생성은 pinned revision을 사용한다. 완료 응답은 job ID + section UUID + input revision으로 연결한다. 현재 화면이 달라졌어도 원래 작업 자산으로 보존한다.
- ‘처음부터 다시’는 새 작업 ID와 기본 입력을 만든다. 다른 제품의 지시·캐릭터·분석 기준을 물려받지 않는다. 같은 작업 내 단계 이동과 새 작업 시작을 구분한다.
- 이미지/텍스트 전환은 이전 작업을 저장하고 다른 초안으로 이동한다. 내부 컴포넌트 unmount가 작업 삭제를 의미하지 않는다.
- 텍스트 모드의 stage와 text/brief/blueprint/keyVisual은 함께 저장·복원한다. 필요한 데이터가 없는 레거시 stage는 가장 가까운 유효 단계로 복구하고 알린다.
- 전체 전략 수정은 요약 수정이다. 섹션 재설계는 별도의 ‘이 전략으로 구성 다시 만들기’ 동작이며 이전 revision을 보존한다.

### 4.3 장면·신규 섹션

- `createSection`을 구성안·편집기에서 공유한다. 기본 장면과 페이지 디자인을 계승한다.
- 사용자가 편집하는 장면 지시를 정본으로 삼는다. 한국어를 바꿨는데 숨겨진 영어 기본값이 우선하는 구조를 제거한다.
- 영어 장면이 필요하면 현재 장면 revision에서 명시적으로 파생한다. 번역/병합 버전을 기록하고 stale이면 생성 전에 갱신한다. 이전 초안의 영문을 section ID만으로 합치지 않는다.
- 장면이나 필수 입력이 빈 섹션은 UI에서 원인을 보여주고 생성 전에 400으로 거부한다. 예약 이후 TypeError로 처리하지 않는다.

## 5. 저장·복원과 이전 초안 호환

### 5.1 먼저 고칠 기존 저장소

서버 작업 전환 전에도 `buildDraftInput → savePdpDraft → normalizeDraftRecord → getPdpDraft → UI` 전체 필드를 보존한다. 타입 선언이나 첫 조립 함수 시험만으로 완료하지 않는다.

- 첨부 지시·레퍼런스 원본·토글·모델·캐릭터·각도·제품 보존·모드·비교 기준·텍스트 중간 상태를 포함한다.
- 알 수 없는 레거시 옵션은 기본값으로 복구하고 변경 사실을 기록한다. 다른 작업의 현재 값을 기본값으로 쓰지 않는다.
- v2→v3 변환은 copy-on-write. 읽기·변환·저장·재읽기 검증 후 v3를 정본으로 전환한다. 원본 v2는 이관 성공 확인 전 그대로 남긴다.
- 저장된 충돌 구성은 생성 이미지·레이어를 우선 보존하고, 기준 구성안과 차이가 있으면 ‘복구된 편집본’으로 명시한다. 빈 구성으로 덮지 않는다.
- 캔버스 기준 폭이 없는 옛 레이어는 기존 460px 기준으로 해석하되 ‘기존 배치 확인 필요’로 표시한다. 원래 좁은 화면 좌표를 완벽히 복원했다고 주장하지 않는다.

### 5.2 자동 저장·동시성·용량

- 저장 dirty 판정은 필드별 dependency 나열 대신 document revision 기준이다.
- 변경 후 짧게 모아 저장하되 연속 타이핑 중에도 30초 이내 checkpoint를 남긴다. 타이핑마다 최대 대기 시간을 초기화하지 않는다.
- 저장 시작 revision만 ACK한다. 저장 중 새 수정이 생겼으면 dirty 상태를 유지한다.
- 탭/서버 동시 저장은 revision 비교로 오래된 덮어쓰기를 막는다. 충돌 시 양쪽 사본 보존 후 복구할 수 있게 한다.
- IndexedDB quota·손상·쓰기 실패를 사용자에게 알린다. 실패한 자동 저장은 저장 완료로 표시하지 않는다.
- 현재 30일 보관 정책은 유지하되 목록에 만료 기준을 표시한다. 활성 작업·미완 서버 작업은 자동 청소에서 제외한다. v3 마이그레이션 중에는 레거시 purge를 먼저 돌리지 않는다.
- 새 정책으로 보관 기간을 줄이거나 사용자 파일을 일괄 삭제하지 않는다.

## 6. 참조·설정·생성 입력 계약

### 6.1 정체성과 연출 분리

제품: 형태·비율·색·재질·라벨·로고·부품/마감은 고정. 카메라 각도·거리·배경·조명은 변경 가능.

캐릭터: 종류(person/animal/character/object), 얼굴 또는 고유 특징, 실루엣·신체 비율·무늬·브랜드 의상/소품은 고정. 표정·자세·시점은 변경 가능. 사람 전용 신체 표현을 동물·사물에 적용하지 않는다.

- 사용자 연출 지시는 identity constraints에 추가된다. 역할 지시 전체를 삭제하거나 정체성보다 우선하지 않는다.
- 보존 대상에 정체성을 바꾸라는 지시가 섞이면 충돌을 알려 수정하도록 한다. 비슷한 새 제품으로 조용히 대체하지 않는다.
- 실물 제품은 생성 입력에서 앵커를 끄는 기능을 제거한다. 과거 `preserveProduct=false` 초안은 참조 역할과 원형 보존 확인 단계로 이관한다. 무형 서비스의 분위기 앵커는 제품 보존과 다른 역할이다.
- 인물 업로드와 저장 캐릭터가 동시에 지정되면 명시적으로 적용 대상을 선택하게 한다. 우선순위로 하나를 조용히 버리지 않는다.
- 저장된 각도는 정체성 증거다. 같은 각도를 그대로 복제하라는 지시로 사용하지 않는다. 추가 각도가 필요하나 자료가 없으면 불확실 상태를 허용하고 사용자 원본 대조를 요구한다.

### 6.2 첨부 예산과 전송 확정

- 서버에서 참조 목록과 모델 상한을 확인하고, 실제 보낼 manifest를 확정한 다음 프롬프트 이미지 번호를 생성한다.
- 상한 초과는 예약/유료 제출 전에 구체적으로 알린다. 초과분을 `.slice()`로 버리지 않는다.
- 긴 디자인 레퍼런스는 한 페이지의 조각으로 처리한다. 조각 수·각도 수까지 예산에 포함한다. 자동 축약은 어떤 부분을 사용할지 사용자가 알 수 있는 방식만 허용한다.
- 실제 사용 manifest에 asset ID/hash, 역할, 순서, source page와 slice 정보를 저장한다.
- 단건·배치·대표 이미지·리디자인 생성/수정은 같은 검증 계약을 사용한다. 역할 표현과 모델 능력 제한을 공유하되 각 도구의 전체 도메인을 합치지는 않는다.
- 인물 필수 여부는 system과 JSON에서 일치시킨다. 참조가 없으면 알리고 대체 인물을 자동 생성하지 않는다.

### 6.3 설정 화면

| 필드 | 기획 입력 | 생성 입력 | 목표 처리 |
|---|---|---|---|
| 대상·불편·특징·차별점·필수 문구 | 전체 | 승인 카피·장면 | 유지, 필수 문구 포함 여부 검증 |
| 판매/문의/홍보 목적 | 전체 | 승인 메시지 | 신규 명시 입력, 기본 purchase |
| 채널·시즌 | 전체 | 배경 정보 | 유지, 조용한 절단 대신 길이 제한 표시 |
| 문구 강도 | 전체 | 승인 카피 | 유지, 사실 범위 확대 금지 |
| 미확인 정보 처리 | 전체 | 근거 관문 | 이미지·텍스트 동일한 의미로 구현 |
| 디자인 분위기 | 전체 | 공통 디자인 | 현재 ‘톤’ 명확화 |
| 그림체 | 전체 | 실제 모델 지시 | 기획과 생성 양쪽 전달 |
| 구성·문구 요청 | 전체 | 승인 결과 | 현재 추가 지시에서 분리 |
| 이미지 연출 요청 | 장면 기획 | 장면·reference 지시 | 정체성 보존보다 우선하지 않음 |
| 화면비 | 배치 기획 | 실제 크기·방향 | horizontal/vertical/square와 픽셀 일치 |

입력 칸의 최대 길이는 서버와 UI가 공유한다. 현재 판매자 500자 제한은 보이게 표시하고 초과 시 수정 요청한다. 입력을 몰래 자르지 않는다.

`auto` 그림체의 레퍼런스를 제거/비활성화하면 유효한 기본 그림체로 복구하고 알린다. 새 레퍼런스 첨부는 명시적인 활성 상태로 시작한다.

## 7. API 경계·정산: 즉시 보호와 영구 복구

### 7.1 즉시 수정할 기존 API

- 인증 후 크기 제한을 적용하고 JSON/multipart를 읽는다. Content-Length가 없는 chunked 요청도 수신 바이트 상한으로 막는다.
- operation·model·ratio·section·country·age·reference 등 입력을 런타임 스키마로 검증한 뒤 예약한다. enum 오류는 400, 과대 입력은 413이다.
- 배치 상한 초과는 400으로 명시한다. 클라이언트와 서버는 같은 표를 사용한다.
- 예약 후 전체 작업에 단일 오류 경계를 둔다. 동기 옵션 조립도 경계 안에 포함한다.
- 원래 실패 원인과 정산 오류를 별도로 기록한다. 실패 처리 중 finalize가 다시 실패해 원래 오류를 덮거나 세 번 finalize하지 않게 한다.
- 전부 실패/부분 성공/완료를 구분한다. 배치 200 자체를 성공으로 보지 않고 명시 상태를 판정한다. 키·인증·한도 등 전역 오류면 남은 배치를 멈춘다. 특정 섹션 오류면 나머지 결과를 보존한다.
- 일괄 재시도 key를 보존하되, 영구 job 조회가 연결되기 전에는 ‘중복 차감 방지 완료’로 표시하지 않는다.
- `settleAiUsage`로 성공 결과를 보호하는 응급 수정은 가능하지만, 정산 대기 기록·복구가 없으면 §8 완료가 아니다.

### 7.2 비용과 한도

- 이미지 실행 정보: provider, model, endpoint, quality, width/height, mode, priceVersion, quote, actual attempts를 한 객체에서 만든다.
- 대표 이미지·단건·배치·리디자인·수정이 같은 계산기를 사용한다. 예약과 확정에 하드코딩한 1을 사용하지 않는다.
- 한 번의 ‘전체 생성’은 논리 작업 단위로 예상 금액을 계산한다. 내부 청크/섹션 분할 때문에 올림이 반복되지 않는다. 부분 성공 시 성공 결과의 같은 단가 스냅샷 합계를 한 번 올림해 확정한다.
- QA 재생성 실패 비용과 사용자 차감은 별도다. 기존 정책대로 고객에게 제공한 성공 결과만 차감하되 실제 모든 제공자 비용은 기록한다.
- 비용 알 수 없음은 0원이 아니라 unknown/pending이다. 폴백 실제 모델로 기록한다.
- 기획·레퍼런스 분석·전사 성공/실패를 LLM meter에 연결한다. 이미지 크레딧 0이어도 원가 기록은 남긴다.
- 모델 선택이 이미지 제공자만 바꾸는 것인지 기획 제공자도 바꾸는 것인지 분리한다. 리디자인 이미지 선택이 fal 고정 모델에 무시되지 않게 한다.
- 요청 남용 제한과 유료 사용량을 분리한다. 잘못된 입력은 생성 분석 한도에 포함하지 않되 API rate limit은 적용한다. 제공자 장애는 성공 분석 한도를 소모시키지 않는다.
- 현재 시간당 분석 제한 설정은 재사용하고 레퍼런스 분석·전사에도 명시된 LLM 작업 한도를 적용한다. 팀/사용자별 권한·한도는 기존 규칙을 따른다.

## 8. 화면 밖에서도 복구되는 생성 작업

### 8.1 데이터와 권한

새 서버 테이블은 상세페이지 영구 복구에 필요한 최소 범위로 추가한다. 정확한 SQL은 W4에서 작성·검증하고 이 계약을 만족해야 한다.

| 목표 테이블 | 핵심 값·제약 |
|---|---|
| `pdp_documents` | user/team/project, schema version, current revision, 문서 JSON, optimistic version |
| `pdp_document_revisions` | document ID + revision unique, 승인 스냅샷, createdBy, 참조 asset 목록 |
| `pdp_generation_jobs` | user/team/document/revision, logical idempotency key unique per user+operation, fingerprint, operation, 실행 스냅샷, 예약 ID, generation/settlement/persistence 상태, lease |
| `pdp_generation_items` | job+section+attempt unique, provider request ID, 실제 모델·크기, output path, QA 결과, 오류, 호출별 원가 |

- 자산은 기존 Supabase Storage의 사용자 ID로 시작하는 경로를 사용한다. 상세페이지 namespace와 private 정책을 적용한다. 라이브러리에는 보존된 자산을 참조/등록하며 임시 외부 URL만 남기지 않는다.
- DB JSON에 API 키나 base64 대량 이미지를 넣지 않는다. 불변 asset ID와 hash를 보관한다.
- 테이블 GRANT, RLS, service-role 함수 권한, 팀 접근을 함께 검사한다. 다른 사용자의 job ID만 알아서는 결과나 정산 상태를 바꿀 수 없어야 한다.
- 예약과 job 소유권·operation·quote 연결은 서버가 정한다. 클라이언트가 consumedUnits나 예약 소유자를 제출하지 않는다.
- 로컬 `LOCAL_STORE=1`에는 같은 repository 계약의 로컬 구현을 둔다. 운영 Supabase 값을 로컬에 채우지 않는다.
- 사용자가 열어 이관한 초안만 서버 문서로 저장한다. 전체 브라우저 데이터를 몰래 업로드하지 않는다.

### 8.2 상태 전이

```text
validated → reserved → submitting → submitted → generating
          → result_available → persisted → reviewing
          → completed / review_required / failed / partial

settlement: not_started → pending → settled / retry_required
persistence: pending → stored / retry_required
submission: known / uncertain
```

- 공급자 제출 직전 의도를 저장하고 제출 성공 request ID를 즉시 저장한다.
- 제출 타임아웃 뒤 공급자 request ID를 확보하지 못하면 `submission=uncertain`이다. 공급자 멱등 지원을 검증하지 않고 같은 유료 호출을 자동 재전송하지 않는다. 사용자에게 상태 확인 중으로 표시하고 운영 확인 대상으로 남긴다.
- fal의 기존 `createFalQueueClient`와 업로더를 재사용한다. 다른 도구의 프로젝트 상태 기계를 그대로 가져오지 않는다.
- 출력 URL 확보 뒤 다운로드·스토리지 저장 실패는 그 결과 URL/request ID로 재시도한다. 새 이미지 생성으로 바꾸지 않는다.
- 생성 결과와 정산은 독립 상태다. 결과를 보여주면서 ‘저장 처리 중’/‘사용량 확정 중’을 알릴 수 있다. 확보한 결과를 오류로 덮어 버리지 않는다.
- provider completed만으로 사용자 영구 저장 완료라고 표시하지 않는다.
- lease 만료·프로세스 재시작 이후 기존 provider request를 조회한다. lease claim은 DB에서 원자적으로 처리한다.

### 8.3 API·브라우저·실행기

- `POST /api/pdp/jobs`: 승인 document revision과 operation, 대상 section IDs, 논리 요청 key를 받는다. 같은 key+같은 fingerprint는 기존 job 반환, 같은 key+다른 fingerprint는 409.
- `GET /api/pdp/jobs/:id`: 소유권 확인 후 상태·부분 결과·실패 이유·정산·저장 상태를 조회한다. 조회 자체가 유료 생성을 제출하지 않는다.
- `POST /api/pdp/jobs/:id/stop`: 미제출 item만 중단한다. 이미 제출한 결과 회수·원가 기록은 계속한다. 중지가 공급자 비용 취소를 보장하지 않음을 표시한다.
- 문서 GET/PUT은 revision 충돌을 409로 처리하고 양쪽 사본을 보존한다.
- 기존 generate 라우트는 단계적으로 job 생성 어댑터로 전환한다. 신구 화면을 지원하는 동안 이중 제출하지 않는다.
- 브라우저는 진행 표시와 조회만 담당한다. `useRunningJobs`에 PDP job을 등록하되 브라우저가 꺼져도 실행은 이어진다.
- 기존 `apps/worker/src/index.ts`는 수집 전용이다. 여기에 무거운 생성을 섞지 않는다. `apps/worker`의 별도 PDP entrypoint 및 systemd unit을 만들고 의존성을 명시한다. 기본 실행 concurrency는 1, 이미지 디코드·검수도 순차 처리한다.
- 운영 실행기 설치·health 확인 전에 브라우저 폴링 의존 제거를 배포 완료로 선언하지 않는다.

### 8.4 예약 만료와 재정산

현재 예약은 약 10분 후 만료 처리될 수 있다. worker가 더 오래 도는 job을 그대로 기존 만료 로직에 맡기지 않는다.

- job lease가 살아 있고 실제 실행 중인 서버 요청만 예약을 갱신할 수 있다. 사용자 전체 예약이 아니라 해당 job의 예약만 갱신한다.
- 예약 갱신·만료 청소·확정을 같은 잠금 규칙으로 직렬화하고 팀 예산도 함께 검증한다.
- 중복 확정은 추가 차감하지 않는다. 이미 만료된 예약의 늦은 성공은 자동 무시하거나 임의 새 예약으로 덮지 않는다. 결과는 보존하고 settlement retry로 남긴다.
- W4 migration에서 late settlement의 일회성 처리와 사용량 요약 일치를 구현한다. 서비스 역할만 실행 가능하며, 서버가 보관한 실제 job 성공 결과와 quote가 근거다. 새 생성 요청으로 위장해 다시 예약하지 않는다.
- 최종 비용 기록이 실패한 경우도 재처리 대상으로 남긴다. 정산만 완료됐다고 원가 기록까지 완료됐다고 하지 않는다.
- SQL 중복 확정·동시 갱신/만료·팀 한도·사용자 접근 테스트 통과 전 job 경로를 기본으로 켜지 않는다.

## 9. 기획·근거·승인 화면

### 9.1 입력 방식과 상품 종류 분리

- 이미지/텍스트는 입력 방식이다. 실물/서비스/디지털/기타와 판매/문의/홍보 목적은 별도로 받는다.
- 사진 경로도 제품 판독 뒤 같은 판매 브리프·구성안·근거 계약에 합류한다. 텍스트 경로의 ‘무형 상품’ 고정 지시를 제거한다.
- 참고용 외형 없는 실물 입력은 임의 제품을 실제 제품처럼 생성 승인하지 않는다. 실제 제품 자료 부족을 표시하고 원본 제공 또는 개념 시안임을 명시하는 흐름으로 처리한다.
- 구성안은 고정 5~6/4~7장 강제가 아니라 전달해야 할 사실과 구매자 질문으로 선택한다. 초기 기술 상한은 현행 전체 요청 상한 이하로 유지하고 UI/서버가 같은 상수를 사용한다. 최소 1섹션도 의도된 구성이라면 허용하되 필수 정보 부족을 검사한다.
- 인물 필수·후기 카드·베네핏 3개는 모든 상품의 고정 조건에서 제거한다. 실제 근거가 있는 후기만 사용한다.

### 9.2 사실과 추정

- `GroundedFact`: id, source asset/text range, 원문, normalized fact, source type, confidence, user confirmation을 갖는다.
- 사진 판독 사실·판매자 입력·텍스트 원문을 같은 근거 목록에 연결한다. 시각 추정 재질/효능을 확인 사실로 자동 승격하지 않는다.
- ‘필수 문구’는 반드시 포함해야 하는 요청이지만 그것만으로 객관적 사실 인증이 되지 않는다. 출처/사용자 확인 상태를 함께 다룬다.
- `omit`: 근거 없는 사실 문장을 생략하고 무엇을 뺐는지 표시.
- `ask`: 빈칸·질문을 명시하고 답변 후 진행.
- `sample`: 시안에만 예시 표시. 사용자 확인 전 승인·최종 생성으로 넘어가지 않는다. 금지된 허위 주장은 확인 버튼만으로 허용하지 않는다.
- 문구 수정은 근거 바인딩을 무효화하고 다시 확인한다. 원문에 인용 문자열이 있다는 사실만으로 문장 전체가 입증된 것으로 처리하지 않는다.

### 9.3 구성안에서 볼 수 있어야 하는 것

- 전체 전략과 대상·목적, 섹션 역할/목표, 실제 제목·부제·모든 불릿·신뢰/반론 문구, 장면, 사용할 참조, 근거 상태.
- 레이아웃·디자인 상세는 접어서 보이되 실제 생성에 쓰는 값과 같은 것을 표시한다.
- 섹션 추가·삭제·순서 변경과 개별 카피 수정, 전체 전략 기반 재기획을 구분한다.
- 변경 후 기존 심사 결과는 stale 표시. ‘이전 구성안 심사 통과’를 새 구성안에 붙이지 않는다.
- `scorecard`의 작성자 자기평가를 독립 심사나 판매 효과 점수로 표시하지 않는다.
- 생성 버튼은 승인 snapshot을 만들고 비용·참조·모델을 확인한 뒤 job을 제출한다.

## 10. 검수 계약

### 10.1 구성안 심사

- 7개 고정 criterion이 정확히 한 번씩 있어야 complete다. 모르는 값·중복·누락은 `incomplete`, 호출 실패는 `unavailable`이다.
- 상태는 `pass | fail | weak | incomplete | unavailable | stale`을 구분한다. 미검사를 통과로 바꾸지 않는다.
- 설득 흐름 심사와 사실 대조는 입력을 구분한다. 사실 대조에는 사용자 원문·상품 판독·증거를 제공한다.
- 수정 루프는 더 나은 complete 결과를 채택한다. 빈 심사 penalty=0을 개선으로 취급하지 않는다. 전체 deadline·호출 수 상한을 함께 둔다.
- LLM 출력은 required 필드·enum·중복·길이를 검사한다. 선형 JSON 추출을 사용하고, 잘림은 명시 오류다. 모델 종료 이유·응답 크기를 남긴다.
- 오류 종류로 재시도 여부를 판정한다. 한국어 메시지에 ‘JSON’ 문자열이 있는지로 판정하지 않는다. 유료 이미지 호출은 동일 재시도 유틸에 무조건 넣지 않는다.

### 10.2 이미지·정체성 검수

- 생성과 QA는 동일 `ApprovedCopy`를 사용한다. 제목·부제·불릿·신뢰문구·실제로 사용할 기타 문구를 모두 포함한다.
- QA 입력에 승인 제품·캐릭터 자료와 fixed identity constraints를 포함한다. 동물/캐릭터/사물도 해당 종류의 동일성 검사 대상으로 취급한다.
- 결과 상태: `passed | failed | review_required | unavailable`. 검수 실패는 통과가 아니다.
- 검수 인프라 실패는 검수만 재시도한다. 처음부터 이미지 재생성으로 넘어가지 않는다.
- 자동 이미지 재생성은 확인된 결함에만 적용하고 기존 상한을 유지한다. 과거 결과도 자산으로 보존한다.
- 제품 외형/라벨/정체성 불일치는 자동 완성본 승인 금지. 사용자에게 원본과 결과를 나란히 보여준다. 불확실하면 불확실이라고 표시한다.
- QA는 확률적 판단이다. 보이지 않는 면의 정확한 형상을 증명할 수 없다. 절대적인 제품 원형 보존이 필요하면 실제 각도 자산 또는 원본 합성으로 전환하며, 새 각도 생성만으로 보증하지 않는다.
- 페이지 전체 확인은 섹션 간 디자인·중복·정보 누락·필수 문구를 점검한다. 단일 이미지 QA만으로 전체 페이지 통과를 선언하지 않는다.

리디자인 분석 실패 시 `diagnostic_summary`를 사용자에게 표시하고 이미지 유료 제출 전에 중단한다. 빈 분석으로 계속 그리지 않는다.

## 11. 완성본·편집·내보내기

- 문서 좌표계를 원본 이미지 픽셀 또는 정규화 좌표로 고정한다. 화면 크기는 viewport scale일 뿐 저장 좌표가 아니다.
- bounds/clamp는 controlled state 갱신에도 적용한다. 정렬로 폭이 바뀌어도 캔버스 밖으로 나가지 않는다.
- 신규 레이어는 겹치지 않게 오프셋/선택 위치로 배치한다. 드래그 중 임시 상태와 저장 commit을 분리한다.
- 실제 제공 폰트 이름으로 통일한다. 로드 확인·export font ready를 검증하고 미제공 폰트를 선택지에 두지 않는다.
- `renderSection(document, sectionId, outputSpec)` 하나를 갤러리 완성본·이어보기·라이브러리 완성본·다운로드에 사용한다.
- 레이어 없는 원본 다운로드는 원본 바이트를 유지한다. 레이어가 있으면 원본 크기 또는 명시된 출력 규격으로 합성하고 큰 폭을 작은 화면 폭으로 축소하지 않는다.
- 참고 이미지 저장은 원본이라는 라벨을 유지한다. 완성본 저장과 의미를 섞지 않는다.
- 단건·ZIP은 같은 렌더러, 같은 픽셀 규격을 사용한다. 한번에 모든 섹션을 디코드하지 않고 순차 합성한다.
- 그림자 blur·줄바꿈·font fallback·object-fit은 실제 브라우저 이미지로 비교한다. 라이브러리 지원표나 소스 문자열만으로 통과시키지 않는다.
- 확대보기는 한 뷰어만 소유한다. ESC/화살표 이벤트가 겹치지 않게 한다.
- 이미지 로드 오류·다운로드 실패를 표시한다. objectURL은 다운로드 시작 이후 안전한 시점에 해제하고 불필요한 장기 메모리 점유도 방지한다.

## 12. 경계·성능·운영 범위

- 업로드 제한의 기존 20MiB를 디코드된 입력 예산의 출발값으로 사용한다. JSON wire는 base64 팽창과 metadata 예산을 별도로 계산해 같은 정책에서 파생한다. Caddy 설정은 해당 경로에 한정해 적용하고 다른 도구의 업로드를 막지 않는다.
- Content-Length만 신뢰하지 않는다. 수신 스트림·파일 수·MIME signature·이미지 픽셀·PDF 페이지/전사 스트립 수를 제한한다. 숫자는 실제 대표 긴 페이지로 메모리 측정 후 정책 상수와 UI에서 일치시킨다. 상한 확정 및 측정 결과가 없는 상태로 W8 통과하지 않는다.
- 디코드는 sequential/concurrency=1 기본이다. 서버 메모리는 배포 시 실측하고 오래된 911MB 여유값을 현재 사실로 쓰지 않는다.
- 앞 4쪽/4장/40스트립 같은 절단이 필요하면 처리 범위를 보여주고 선택받는다. 조용히 잘라 완전 분석으로 표시하지 않는다.
- 레퍼런스 목록은 pagination을 제공한다. 200개 이후 보이지 않게 숨기지 않는다. 무제한 AI 분석·업로드는 회원별 rate/용량 정책에 연결한다.
- 클라이언트에서 사용하는 순수 타입·상수와 서버 제공자/프롬프트 진입점을 분리한다. 운영 번들 노출을 실제 Linux 빌드에서 확인한 후 필요한 범위만 변경한다.
- 사용하지 않는 프롬프트 조립기는 실제 import/호출 경로와 외부 공개 사용 여부를 확인하고 제거한다. 살아 있는 조립기 동작을 시험한다.
- PostgreSQL·Next·Caddy 전역 설정을 추정으로 변경하지 않는다. 권한·배포·서비스 작업은 해당 단계 산출물과 테스트로 구분한다.

## 13. 실행 순서·산출물·합격 기준

모든 W 작업은 **미착수**다. 각 작업의 실패 시험→수정→해당 시험 통과→통합 검증 순서를 지킨다. 보고서의 소스 문자열 검사를 그대로 늘리는 방식으로 대체하지 않는다.

| 작업 | 선행 | 실제 수정 범위 | 종료 기준 |
|---|---|---|---|
| W0 기준 고정 | 없음 | 원문 ID와 현행 코드 대조, 기존 시험/대표 fixture, 동시 작업 격리 | §14의 모든 행에 처리 상태, 기준 SHA, 재현 또는 검증 계획 |
| W1 손실·예약 응급 수정 | W0 | draft 저장/정규화/복원, dirty 저장, 재분석 덮어쓰기, API 검증/정산 경계 | T-SAVE, T-SETTLE, T-INPUT. 이 단계만으로 서버 복구 완료 아님 |
| W2 작업 정본·단계 | W1 | 문서 v3, reducer/selectors, 단계 전이, 섹션 UUID·장면, 레거시 이관 | T-STATE, T-SECTION, T-MIGRATE, 실제 양쪽 모드 왕복 |
| W3 Fable·실행 설정·참조 | W2 | purpose별 LLM 선택, 참조 manifest, 실제 모델 실행 계약, 가격 계산·메타데이터 | T-MODEL, T-REF, T-COST. 실제 Fable 두 입력 연결 확인 |
| W4 영구 생성·복구 | W1~W3 | job/revision SQL·repository·worker/API·queue·정산 재처리·실행기 설정 | T-JOB, T-SQL, 재시작/응답 유실/lease/expired settlement |
| W5 승인·근거·검수 | W2~W4 | 모드 공통 evidence, 승인 copy, reviewer completeness, 동일성/QA 실패 구분 | T-REVIEW, T-IDENTITY, T-EVIDENCE |
| W6 완성본 렌더링 | W2 | 공통 합성, 좌표·폰트·뷰어·다운로드·라이브러리 | T-EXPORT, T-EDITOR, 화면과 파일 시각 비교 |
| W7 기획·설정 UX | W2/W3/W5 | 상품 종류·목적, 옵션 의미, 전략/구성 편집, 전체 페이지 확인 | T-PLAN, 필수 문구·목적·양쪽 모드 사용자 여정 |
| W8 경계·성능·미확인 종결 | W3~W7 | 업로드/전사 제한, 파싱·bundle, 미조사 저장 용량, docs 정합성 | T-LIMIT, T-PARSE, T-BUNDLE 및 모든 검증 행 종결 |
| W9 종단 검증·릴리스 | W1~W8 | 회귀, 실제 생성, migration/worker 배포 runbook, 운영 검증 | §16 체크 전부 완료. 사용자 배포 지시 시 실행 |

W6은 W4와 코드상 독립적으로 진행 가능하지만 현재 동시 작업 파일과 충돌을 피한다. 여러 에이전트 실행 자체를 이 문서가 요구하지 않는다.

### 13.1 주요 파일 소유 범위

- W1/W2: `app/create/{PdpMakerClient,TextModeFlow,PdpEditor,pdp-drafts,draft-input,scenario-sections}` 및 새 document state 모듈. 전면 파일 분할을 선행하지 말고 상태 경계를 먼저 만든다.
- W3: `lib/pdp/providers`, `pdp.image-options`, `pdp.reference-policy`, `pdp.image-provider`, `lib/redesign/image-generator`, `redesign-core` 생성/수정 어댑터, `credit-cost` 호출 계약.
- W4: `lib/pdp/jobs/*`와 repository·worker entrypoint·신규 숫자 timestamp migration. 기존 미추적 수동 SQL 파일은 읽기 근거 외 수정·실행하지 않는다.

## 15. 구현 작업의 안전 경계

- 첫 구현은 W0→W1이다. 안정된 초안·API 오류 경계 없이 대규모 상태 재작성이나 모델 전환을 먼저 배포하지 않는다.
- 한 변경 묶음에서 결과 보존·과금·모델·UI 전체를 동시에 바꾸지 않는다. W 작업 안에서도 독립 실패 시나리오 단위로 커밋한다.
- 기능 플래그는 단계 전환에 필요한 `PDP_DOCUMENT_V3`, `PDP_JOBS_ENABLED` 두 범위만 두고 기본은 미이관 경로다. 새 문서가 생성된 뒤 rollback 시 v3 데이터를 삭제하지 않는다.
- 배포 rollback은 새 제출을 끄되 진행 중 job 회수·정산 worker는 끝까지 유지한다. 이전 코드가 새 문서를 못 읽으면 읽기 전용 복구/내보내기 경로를 남긴다.
- migration은 additive 우선, 백필은 사용자별/작업별 checkpoint로 수행한다. 레거시 컬럼·저장소 삭제는 이번 필수 범위에서 제외한다.
- 필요한 운영 설정·실행기·DB 변경은 설계·로컬 검증과 구분해 적용 기록을 남긴다. 현행 운영 DB에 적용됐다고 추정하지 않는다.
- 이 문서 작성 단계에서는 제품 코드·환경변수·DB·실제 LLM 호출을 변경하지 않는다. Fable은 확정 목표이며 실제 적용 완료는 W3에서 증명한다.

## 16. 최종 합격 및 인수인계

필수 사용자 여정:

1. 실물 제품 + 캐릭터 + 긴 디자인 참조 → 기획 → 문구/장면 수정 → 일괄 생성 → 단건 재생성 → 저장/새로고침 → ZIP/라이브러리.
2. 텍스트 서비스 → 미확인 사실 답변 → 대표 이미지 → 섹션 추가/삭제 → 이전 단계 복귀 → 최종 생성.
3. 사진 없는 실물 설명 → 원본 부족 안내 → 실제 제품 자료 보완 → 정체성 확인.
4. 리디자인 PDF → 전사 범위 확인 → 선택 모델 생성 → 중간 실패·이어 만들기 → 섹션 수정 → 저장.
5. 생성 중 화면 이동·브라우저 종료·네트워크 단절·worker 재시작·DB 정산 장애 → 같은 결과 복구, 중복 유료 제출 없음 또는 불확실 제출 명시.
6. 다른 사용자/팀의 문서·job·asset·정산에 접근 불가.

릴리스 조건:

- §14의 모든 행이 수정 완료 또는 검증 후 제외이고 증거 링크가 있다. 미확인 고위험 항목을 남긴 채 전부 완료라고 하지 않는다.
- 관련 단위·동작·통합 시험과 typecheck를 통과한다. 기존 880개 같은 옛 결과를 현재 증거로 재사용하지 않는다.
- 실제 Fable 이미지/텍스트 기획 연결을 검증한다. 모델 ID를 config에 썼다는 사실만으로 완료하지 않는다.
- 대표 제품/캐릭터 샘플의 원본 대조와 최종 렌더링을 사람이 확인한다. 각도별 미검증 범위를 명시한다.
- Linux CI build 사용. Windows/운영 EC2에서 빌드하지 않는다. 배포 요청 시 [DEPLOY.md](../../DEPLOY.md)를 다시 읽고 실행한다.
- 신규 worker active, 기존 web health, 작업 resume·정산 retry, 실제 릴리스 내용 및 DB 적용을 별도 확인한다.
- 최종 인수인계에는 기준/완료 SHA, 변경된 행, RED/GREEN 증거, migration 적용 여부, 배포 버전, 실생성 검증, 잔여 제한을 적는다.

이 설계의 완료는 문서 작성 완료를 뜻한다. 시스템 개선 완료는 W0~W9와 위 조건을 충족한 시점이다.
