# 비용 전략실 — 생성량·운영비·수익을 한 화면에서

작성: 2026-09-22 · 상태: 로컬 구현·검증 완료 (아래 구현 기록 참고) · 조사 기준: `b58e4ac`

사용자 요청: 기존 시스템을 다시 확인하고, API뿐 아니라 EC2·Supabase까지 포함해 100크레딧의 제공량과 회원 증가에 따른 지출을 예상한다. 현재 무료/최저 요금에서 시작해 유료 전환·증설 이후도 계산한다. 프론트엔드까지 설계한다.

추가 요청 반영: 복잡한 상세 계산과 함께 쉽게 읽을 수 있어야 하며 **통합해서 보고 싶다**. 별도 간단 계산기나 성장 탭을 만들지 않고, 기존 비용 전략실의 기본 화면을 통합 요약으로 구성한다. 아래 설계는 이 요청까지 반영한 정본이다.

이 문서는 구현 계약의 초안이다. 현재 서비스 동작, 이번에 제안하는 계산 정책, 운영에서 확인하지 못한 사실을 구분한다. 서비스 코드·DB·요금제·인프라는 이번 설계 작업에서 변경하지 않는다.

화면 시안: [통합 요약 HTML 시안](../../cost-lab/growth-design-preview.html). 기존 링크를 유지했다. 시안은 예시 조건으로 동작하며 운영 계산기나 청구 견적이 아니다.

## 1. 재확인한 현재 시스템

경로는 저장소 루트 기준이다. 기존 미추적 문서·SQL은 조사 기준 커밋의 구현으로 간주하지 않았다.

| 영역 | 실제 구현과 근거 | 설계에 미치는 영향 |
|---|---|---|
| 관리자 화면 | `apps/web/app/admin/layout.tsx`의 `requireAdmin`, `cost-lab/page.tsx`, `cost-lab-frame.tsx` | 관리자 접근 유지, 앱 셸·제목을 다시 만들지 않음 |
| 계산기 제공 | `app/admin/cost-lab/doc/[file]/route.ts`, `lib/admin/cost-lab.ts` | HTML allowlist, 404 접근 차단, no-store, 테마 토큰 주입 유지 |
| 기존 UI | `app/admin/cost-lab/assets/index.html` | 월 정액제·충전형·생산량 견적·시장 비교 4개 탭. 공유 fragment·HTML 다운로드·로컬 비교안 존재 |

| 원가 장부 | `lib/cost.ts`, `202609100004_llm_cost.sql` | 이미지 수×`model_prices` 현재 단가 + 기록된 `llm_usd`. 모든 비용을 공급사 청구서와 대조한 장부가 아님 |

### 1.1 실제 차감 경로별 차이

| 작업 | 예약·차감 규칙 | 구현 근거 |
|---|---|---|
| 포스터 / Easy | 기획과 이미지를 각각 올림. 기획 없이 생성하는 모드 존재. 이미지 variants는 합산 후 올림 | `api/poster/projects/[id]/{plan,generate,status}/route.ts`, `app/poster/plan-cost.ts`, `app/easy/cost.ts` |
| SNS 새 생성 | 이미지 예상값 + `llmCostUsd(1 + generatedCount)` 예약. 확정은 이번 회차 이미지 비용 + `llmCostUsd(1 + made)` | `api/sns/projects/[id]/generate/route.ts`, `lib/sns/settle.ts` |
| SNS 카드 재생성 | 예약은 `llmCostUsd(generatedCount)`, 확정은 위 공통 settle 규칙. 슬롯 수와 완성 카드 수도 다를 수 있음 | `api/sns/projects/[id]/cards/[index]/route.ts`, `app/sns/cost-estimate.ts` |
| PDP 섹션 | 단건/배치 모두 `imageCreditUnits(model, count)` 사용. 현재 해당 라우트는 크기 인자를 넘기지 않음. 성공 개수로 확정 | `api/pdp/images/{route.ts,batch/route.ts}` |
| 캐릭터 후보/추가 각도 | 원가로 예약하지만 성공 시 이미지 개수로 차감. 각도 예약에서도 `clampCandidates(0)`은 1로 됨 | `api/characters/route.ts`, `lib/characters.ts` |
| 캐릭터 개별 각도 | 위 신규 생성과 달리 실제 모델의 원가 환산으로 확정 | `api/characters/views/route.ts` |
| 리디자인 | 생성은 공급자 별 단가×성공 개수 환산. 부분 수정은 원가로 예약하고 성공 시 **1크레딧** 확정 | `api/redesign/{generate,edit-section}/route.ts` |
| 무료 분석 | PDP 분석/글 기획 등 0크레딧 경로 존재. 원가가 0이라는 뜻은 아님 | `api/pdp/{analyze,plan-from-text}/route.ts` |

그러므로 `회원 수 × 100 × $0.05`는 모든 기능의 최대 비용이 아니다. 예외를 평균 단가 하나로 없애지 않는다. 이 설계에서 실제 차감 정책 자체를 고치지는 않는다.

현재 SNS 확정은 슬롯 호출 수가 아니라 완성 카드 수를 `billableImages`로 기록하고 `llmUsd`를 직접 넘기지 않는다. 따라서 기존 관리자 장부를 API 실제 지출의 완전한 정답으로 가져오지 않는다. 이 지적은 비용 예측의 입력 신뢰도에 관한 것이며 별도 장부 수정 작업을 포함하지 않는다.

### 1.2 저장·전송 경로

| 종류 | 현재 저장 동작 | 예측 처리 |
|---|---|---|
| 포스터 | `posterAssetPath`에 generationRequestId 포함. PNG 원본과 별도 WebP 미리보기 | 성공한 재생성도 새 파일로 누적 |
| SNS | `lib/sns/runtime.ts`에서 카드 번호별 경로에 upsert. 미리보기도 교체 | 재생성 호출비는 증가하지만 같은 경로 파일 수는 증가하지 않음. 크기 변화·잔여 파일은 따로 가정 |
| 참고 이미지/캐릭터 | `reference-images.ts`, `characters.ts`에서 원본·미리보기 저장 | 생성 외 업로드량과 후보의 실제 저장 여부를 따로 입력 |
| 일반 라이브러리 | `server-library.ts`에서 인코딩·저장·미리보기 생성, 명시적 삭제 처리 | 실제 저장 평균 바이트 사용. 무조건 원본 PNG 크기로 계산하지 않음 |
| PDP 초안 | `app/create/pdp-drafts.ts`는 IndexedDB, 초안 30일 정리 | 브라우저 삭제를 Supabase 자동 삭제로 해석하지 않음. 클라우드 저장률 별도 |
| 리디자인 | 브라우저 프로젝트 저장 + `redesign-wizard.tsx:autoSaveSections`의 라이브러리 업로드 | 생성 완료와 클라우드 저장 성공을 구분. 수동 저장/중복 업로드 가능성은 실측 전 가정 |
| 이미지 조회 | 포스터/라이브러리 file route에서 Supabase download → EC2 Response, private max-age=60 | Supabase outbound와 EC2 outbound를 별도 측정. 브라우저 캐시 적중은 둘 다 줄일 수 있음 |

`library`, `characters`, `references` 등 버킷을 합한 실제 저장량이 필요하다. 확인한 코드에서 계정별 저장 GB 한도와 서버 전역 자동 보관기한은 찾지 못했다. EC2는 AI 모델을 직접 돌리는 GPU 서버가 아니지만 이미지 가공·전송·워커 업무가 있으므로 무료 API 대행 서버로 취급할 수 없다.

### 1.3 기존 계산기의 어긋남과 검증 경계

- HTML에 단가가 복사되어 있다. 리디자인 `ro=.19`와 서비스 `redesign-openai=.165`가 다르다. HTML의 기획/글 비용도 현 서비스의 호출 구성과 직접 연결되어 있지 않다.
- `nano-banana-2`의 코드 `flatUsd=.08`만 보고 HTML `.12`를 오류라고 하면 안 된다. `resolutionMultiplier=1.5`가 적용되어 실제 `unitPrice()`는 `.12`다.
- 모델/단가 변경 시 HTML과 독립 prepaid 양쪽이 함께 갱신되도록 할 필요가 있다.
- 재실행 결과: `verify.cjs` 159개, `verify-wallet.cjs` 82개, 관련 Vitest 5파일 79개 통과. 이는 현재 계산/접근 제어 계약의 검증이지 공급사 청구액·운영 DB·서버 수용량 검증이 아니다.
- 운영 정보 미확정: 현 EC2 사양·청구액·무료 혜택, Supabase 요금제/compute·기존 사용량·조직 공유 범위. 앞선 조회에서 현재 AWS 설정은 위키의 EC2를 찾지 못했다. 삭제 또는 사양 변경으로 단정하지 않는다.

## 2. 제품 범위와 설계 결정

1. 기존 첫 탭 `overview`를 **통합 요약**으로 표시한다. 새 성장 탭이나 별도 간단 계산기를 만들지 않는다. 경로는 `/admin/cost-lab` 그대로다. 기존 충전형·생산량 견적·시장 비교 도구는 유지한다.
2. 첫 화면에서 “1인 월 100크레딧, 회원 100명이면 몇 장 만들고, API·서버·DB 비용을 합쳐 얼마가 나가고 얼마가 남는가?”에 답한다. 세부 계산은 같은 화면 아래 접힌 영역에서 설정한다. 판매가 0원은 무료 제공이며 입력하지 않아도 지출부터 볼 수 있다.
3. 기본은 **현재 서비스 차감 기준**. 제안 요금/충전형 크레딧을 몰래 가져오지 않는다.
4. 수요 예측, 요금제 한도, 성능 판단을 별도 결과로 계산한다. 회원 수만으로 `t3.micro는 100명까지` 같은 표를 만들지 않는다.
5. **혜택 적용 예상 지출 / 혜택 없이 유지할 비용 / 누적 지출**을 분리한다.
6. 요금제 유지안과 전환 가정안을 나란히 비교한다. 계산기는 AWS/Supabase 플랜을 실제 변경하지 않는다.
7. 1차 구현은 수동 기준값+공식 가격표 기반이다. AWS/Supabase 결제 API 연결·운영 DB 조회·새 DB 테이블·권한 변경은 포함하지 않는다.
8. 보관 기간 입력은 시뮬레이션 가정이다. 실제 삭제 정책이나 파일 정리 작업을 만들지 않는다.
9. 설계안/운영 사실/요금표 출처를 값마다 보존한다. 미확인 값은 `null`이며 0으로 바꾸지 않는다.

## 3. 사용자가 입력하는 조건

모든 세부 항목을 처음부터 노출하지 않는다. 필수 입력 → 접히는 상세 설정 순서다.

### 3.1 첫 진입

처음에는 회원 수·1인당 제공량·판매가(0원이면 무료)만 보여준다. 그 아래 사용 정도 `가끔 사용 / 보통 사용 / 모두 소진`을 둔다. 첫 사용의 예시에서는 회원 수가 유지된다고 가정하고 증가율은 0%다. 증가율·요금제·파일 크기 등은 한 줄 조건 요약에 표시하고 `세부 조건 펼치기`에서 수정한다.

사용 정도는 실측이 아니라 이름 붙인 가정이다: 가끔=활성40%·활성회원 소진50%, 보통=활성70%·소진80%, 모두 소진=활성100%·소진100%. 버튼 아래 숫자를 항상 적는다. 상세에서 다른 값을 입력하면 `직접 설정`으로 표시하고 숨겨서 가장 가까운 preset에 맞추지 않는다. 모델·실패·보관·가격 설정은 이 버튼으로 바뀌지 않는다.

현재 서비스 예측은 실제 차감 정책에서 시작한다. 기존 저장된 가격 설계안을 열면 그 정책과 조건을 유지하고 `제안 차감 정책`으로 표시한다. 사용자의 현 상태는 “무료·최저 요금 사용 중, 상세 미확인”으로만 안내한다. 임의 t3.micro/Free를 현재 계정 사실로 저장하지 않는다. 기본값으로 계산해 보는 경우 `예시 조건`을 명시한다.

필수 입력이 없으면 생성량은 계산하되 총비용은 `계산한 항목 합계 + 미입력 항목`으로 표시하고 전체 이익을 확정하지 않는다. 예시를 불러오면 화면 상단과 내보내기에 `예시 조건`을 유지한다. 항목을 덜 보여주는 것과 계산에서 비용을 빼는 것은 다르다. 통합 요약과 상세 내역은 같은 계산 결과를 사용한다.

### 3.2 회원과 사용량

| 입력 | 기본/정의 |
|---|---|
| 시작 월·예측 기간 | 다음 완전한 달, 12개월. 1~36개월 선택. 월 길이는 실제 달력 사용 |
| 가입 회원 수 | 예시 100명. 신규/탈퇴를 반영한 월별 표 입력 가능 |
| 활성률 | 해당 월 실제 사용하는 회원 비율. 예상 활성 회원=floor(가입 회원×활성률) |
| 1인 월 크레딧 | 예시 100. 사용자별 한도이며 서로 남은 크레딧을 합쳐 쓰지 않음 |
| 활성 회원 소진율 | 활성 회원만의 사용 목표. 비활성 회원과 두 번 할인하지 않음 |
| 지급 방식 | 월 갱신 / 1회 지급 비교. 기본은 실제 월 갱신. 1회 지급은 월초 신규 코호트별 잔액 이월 |
| 무료/유료 구분 | 필요 시 2그룹. 각 그룹의 회원·활성률·quota·기능 비중 독립. 이미 가입 수에 포함된 무료 회원을 또 더하지 않음 |
| 성장 | 고정 / 월 증가율 / 월별 직접 입력. 직접 표가 계산 정본, 증가율은 표를 만드는 편의 기능 |

팀 잔량이 필요한 경우 별도의 월 팀 사용 상한으로 개인 사용 합계를 제한한다. 팀 예산 초과 수요는 미실행으로 표기하고 AI 비용을 청구한 것으로 계산하지 않는다. 팀 배분을 설정하지 않은 기본 예시는 개인 한도만 적용했다고 표시한다.

### 3.3 작업 프로필

통합 요약의 초기 예시는 포스터 한 장·표준형·1024 정사각·기획 없음으로 시작한다. 사용자가 작업 종류를 바꾸면 아래 상세 설정을 연다.

- 이미지 모델·비율·해상도·참조 수·기획 유무·variants.
- SNS: 완성 카드 수, 그대로 넣는 카드, 카드별 생성 슬롯. 슬롯 호출량과 최종 카드 수 분리.
- PDP: 섹션 수, 실제 배치 크기와 분할 횟수. 큰 묶음을 임의로 한 번에 올림하지 않는다.
- 캐릭터: 후보 수·보관 후보 수·각도·sheet·개별 각도 추가를 구분.
- 사용자 재생성 횟수(별도 차감), 서비스 부담 재시도율(추가 원가), 최종 실패율/실패 비용 비율을 분리.
- 무료 분석은 월 활성 회원당 횟수/단가로 추가. 0크레딧 활동을 무한 반복 가능한 생성량으로 세지 않는다.
- 혼합 사용의 비중은 **완료 작업 건수 비중**. 이미지 장수 비중/크레딧 비중으로 바꾸어 읽지 않는다.

### 3.4 현재 인프라와 저장

- AWS: 리전, OS/아키텍처, 인스턴스·개수·시간 단가, EBS 할당 GB와 단가, 공인 IPv4 수, 송신 요금 구간, 기타 요금. 기본 비교 후보는 x86 `t3.micro → t3.small → t3.medium`와 직접 입력. 이는 비용 비교 후보이며 성능 보장표가 아니다. ARM 전환을 자동 추천하지 않는다(현 배포에 linux-x64 의존성 존재).
- AWS 무료 혜택: 모름 / 기존 기간·사용량 혜택 / 잔액형 크레딧 / 없음. 적용 대상 요금, 남은 잔액·시간, 만료일, 자동 유료 지속 가정 여부.
- Supabase: Free/Pro/직접 입력, 프로젝트별 compute·DB 할당 디스크, spend cap, 조직 내 다른 프로젝트의 사용량/compute. 과금 주기를 모르면 달력월 가정 표시.
- 초기 Storage GB, DB 실제 사용량, DB 할당 디스크, EC2 기존 사용/할당 디스크를 각각 입력. 초기 값의 관측일 포함.
- 원본/미리보기 평균 바이트, 클라우드 저장률, 추가 업로드, 보관/삭제 가정, 재생성 저장 방식.
- 월 조회/다운로드 횟수, 브라우저 캐시 적중률, Supabase CDN 캐시 적중률, 경로별 EC2 중계 비율, 참조 재사용 다운로드량.
- 모든 단가와 평균 파일 크기는 출처·관측일·`공식 요금/실측 입력/가정/미확인` 표시. 파일 평균값은 생성 해상도와 함께 보관.

## 4. 계산 계약

### 4.1 작업 수와 크레딧

`creditUnits`, `unitPrice`, `estimatePosterCost`, `llmCostUsd` 등 현재 pure 함수에서 예측용 가격 스냅샷을 만든다. UI의 별도 수식으로 모델 이름/단가를 재작성하지 않는다.

각 작업 프로필은 `steps[]`를 반환한다. 단계별 `reservedCredits`, `chargedCredits`, `apiCostUsd`, `providerImageOutputs`, `deliveredImages`, `storageEffect`를 가진다. 작업 시작 필요 잔액은 `max(앞 단계 누적 차감 + 이번 단계 예약)`이다. 실제 SQL의 예약 상한/확정 제한도 테스트 기준에 포함한다.

월별 활성 회원 한 명에 대해:

1. 실제 사용 가능 잔액 Q와 목표 차감 예산 B=floor(Q×소진율)을 구분한다.
2. `이미 차감한 값 + 작업 차감 <= B`, `Q - 이미 차감한 값 >= 작업 시작 필요 잔액`이면 실행한다.
3. 단일 작업은 산술식으로 계산. 혼합은 가능한 작업 중 `실행횟수 / 목표비중`이 가장 작은 작업을 선택한다(동률은 고정 id 순). 실행 가능한 유료 작업이 없으면 종료한다.
4. 작업당 최소 차감이 양수인 경우에만 이 반복에 넣는다. 무료 분석은 별도 유한 횟수다.
5. 코호트별 1인 결과에 인원수를 곱한다. 개인별 나머지를 다른 회원에게 넘기지 않는다. 1회 지급 모드는 코호트 잔액을 다음 월로 넘긴다.
6. 입력 소진율을 다 쓰지 못한 경우 실제 예상 차감과 남은 크레딧을 함께 반환한다.

1회 지급 비교에서는 신규 가입 월과 남은 잔액으로 코호트를 나눈다. 같은 잔액의 회원 중 활성 인원만 차감한 새 코호트로 옮기고 비활성 인원의 잔액은 유지한다. 월 갱신 모드에서도 팀 제한 때문에 일부만 실행할 수 있으면 개인 단위 실행 수를 보존한다. 모든 사람의 잔액을 하나의 평균 잔액으로 합치지 않는다.

예: 리디자인 수정은 Q=100/B=100에서 예약 4·차감 1이면 97회 후 잔액 3. Q=100/B=10이면 10회 가능하다. 시작 잔액을 목표 B로 잘못 바꾸면 7회로 틀린다.

서버 부담 재시도·최종 실패는 완료 작업의 크레딧 권리를 줄이지 않고 원가/호출량에 추가한다. 사용자가 누르는 재생성은 별도 유료 작업으로 크레딧 예산 안에서 계산한다. 두 종류를 한 배수로 합치지 않는다.

### 4.2 API 비용

정상 완료 작업 J, 기본 이미지 공급자 비용 I, 글 비용 L, 서비스 추가 이미지 시도율 a, 최종 실패율 f(전체 작업 중 실패 비율), 실패 1건 비용 비율 c라면 기존 계산기와 호환되는 가정식:

`ApiUsd = J × [I × (1 + a + f/(1-f) × c) + L × (1 + f/(1-f) × c)]`

이는 정상 완료 추가 시도와 최종 실패 작업을 겹치지 않는 집단으로 가정한 기대값이다. f<1, UI 상한 95%. 비용 비율 c와 실패 시 파일 생성 비율은 별도 입력이다. 비용 발생이 곧 저장 성공이라는 가정을 하지 않는다. 부분 성공 비중이 있으면 성공 파일·과금 호출·최종 차감을 별도 프로필로 지정한다.

함수의 fallback 경로 단가를 확정할 수 없으면 원가 범위 또는 단가 미확인으로 남긴다. 요금표의 값은 공급사 실청구 확인값이 아니라 `코드 기준 예상`이다.

### 4.3 저장 재고와 보관

기본 단위는 bytes, 요금표 변환은 해당 공급자 기준(기본 decimal GB=10^9). 월말 GB를 이미지 수×원본 크기만으로 계산하지 않는다.

`월말 저장 = 월초 저장 + 새 고유 파일 바이트 + 교체 순증 바이트 + 추가 업로드 - 삭제 바이트`

- append: 포스터 회차별 원본/미리보기, 추가 업로드 등. 성공한 재생성도 신규 저장.
- overwrite: SNS 동일 카드 경로. 기존 파일과 교체 파일의 차이만 재고 변화. 재생성 API/전송비는 그대로 발생.
- browser-only: PDP 초안 등은 클라우드 저장으로 세지 않음. 클라우드에 저장하는 비율 별도.
- 후보/중간 결과: 공급자만 보관하는 임시 출력과 우리 Storage에 올린 파일 분리.
- 원본·미리보기·복사본·잔여 파일 증분을 별도 내역으로 표시. 청구 Storage에는 전부 포함.
- 기본 보관은 계속 보관. N개월 보관은 생성 월 코호트가 N개월 뒤 월초에 삭제된다는 시나리오. 초기 저장의 나이를 모르면 자동 삭제하지 않는다. 초기분 삭제 계획은 따로 받는다.
- 계정 탈퇴는 파일 삭제와 같은 사건이 아니다. 별도 삭제 계획이 없으면 재고 유지.

overwrite 효과는 기존 원본/미리보기 바이트와 신규 바이트를 함께 가진다. 기존 크기를 모르면 `순증 미확인`으로 표시하거나 동일 크기 교체라는 명시적 가정을 사용한다. 확장자 변경·이전 파일 미삭제처럼 새 경로가 생기는 경우는 append 잔여 파일 항목으로 계산한다. 기본 파일 생성량과 재생성 횟수만으로 모든 경로를 추정하지 않는다.

예측 엔진은 일 단위 균등 유입으로 월별 GB-hours를 적분한다. 초기 재고는 하루 전체, 해당 일 유입/삭제는 정오 발생 근사다. UI에 `월말 보관량`과 `월평균 과금 용량`을 분리한다. 불규칙한 대량 업로드는 날짜별 일회 이벤트로 입력 가능하게 한다.

Supabase Storage 한도/청구는 기간 평균 GB-hours 기준이다. 월말 1GB 돌파를 곧 청구 한도 초과일로 표시하지 않는다. 월말은 저장 계획 지표, 평균 사용량은 요금제 검토 지표다. 정확한 공급자 제한 시점은 유예 정책도 있어 날짜로 보장하지 않는다. [Storage 과금 근거](https://supabase.com/docs/guides/platform/manage-your-usage/storage-size)

### 4.4 DB 용량

DB는 이미지 bytes와 분리한다. `초기 DB 데이터 + 신규 회원 메타 + 작업/시도 기록 + 로그/기타 월 증가량 - DB 정리량`으로 실제 사용량을 추정한다. Storage 파일 삭제가 로그/프로필 삭제를 뜻하지 않는다.

Free의 DB 한도는 데이터 크기, 유료 DB 디스크 비용은 **할당한 디스크 GB-hours**다. WAL·시스템 여유를 포함한 할당 계획을 별도로 입력한다. 파일 저장량을 8GB DB 한도와 비교하지 않는다. [DB 디스크 과금 근거](https://supabase.com/docs/guides/platform/manage-your-usage/disk-size)

### 4.5 전송량

요청 경로를 구분한 작은 표로 계산한다.

| 경로 | Supabase egress | EC2 egress |
|---|---|---|
| Storage → EC2 → 브라우저 | 다운로드 바이트 | 전달 바이트 |
| Storage → 브라우저 직접 | 다운로드 바이트 | 없음 |
| Storage → EC2 → AI 공급자 | 참조 다운로드 바이트 | 실제 공급자 업로드 바이트 |
| 공급자 → EC2 → 브라우저 | 없음 | 이미지/base64 응답 바이트 |
| EC2 → Storage | Storage ingress | AWS에서 과금되는 송신량은 리전/경로 요금 설정에 따름 |

base64는 해당 응답 경로에만 4/3 근사를 적용하며 저장 파일에도 중복 적용하지 않는다. PNG 재인코딩/복사본은 실제 출력 크기 입력을 따른다. 사용자 조회 외에 생성 응답과 참조 재사용도 반영한다.

브라우저 캐시 적중은 서버 요청 자체를 줄인다. Supabase CDN 캐시 적중은 남은 Storage egress를 cached/uncached로 나눈다. 두 종류의 캐시 비율을 같은 것으로 쓰지 않는다. 초기 추정에서 CDN 적중률을 모르면 0% **가정**을 쓰고 근거 칸에 표시한다.

뷰 수는 신규 이미지뿐 아니라 보관 중인 이미지의 재조회도 포함한다. EC2 업로드 전송은 공급자별 과금 경로를 선택하고 모르면 부분 비용으로 표시한다. AWS의 무료 송신량은 계정 내 다른 서비스가 소비한 잔량을 입력받아 적용한다.

### 4.6 AWS 비용과 혜택

`정상 AWS 원가 = 인스턴스 시간 + EBS 할당 용량/IOPS 등 + IPv4 시간 + 경로별 송신 + CPU 초과 크레딧 + 기타 설정 항목`

시간 단가는 리전·OS·아키텍처·구매방식·확인일과 묶는다. 지역 미선택/단가 미확인일 때 임의 서울 가격을 확정하지 않는다. 1차는 on-demand Linux 후보만 사전 지원하고 예약/Spot은 직접 입력 비교로 둔다. T 계열 CPU 초과요금은 측정 없으면 `추가 가능 비용 미반영` 상태다. [EC2 요금](https://aws.amazon.com/ec2/pricing/on-demand/) · [T3 특성](https://aws.amazon.com/ec2/instance-types/t3/) · [IPv4 요금](https://aws.amazon.com/vpc/pricing/)

혜택은 적용 가능한 line item에만 적용한다. 사용량 할인 후 적격 비용에 잔액형 크레딧을 한 번만 차감한다. 날짜별 만료·월별 다른 AWS 서비스 사용분을 반영하며 잔액은 음수가 될 수 없다. 무료 시간과 신규 크레딧 제도를 무조건 중복 적용하지 않는다.

AWS의 2025-07-15 이후 신규 계정 제도는 종전 12개월 사용량 혜택과 다르다. 현 계정의 종류·잔액·유효일은 사용자 입력이며 가입만으로 $200 전액이 있다고 가정하지 않는다. 무료 플랜 종료 뒤 유료 지속도 **시나리오 선택**이지 자동으로 서비스가 계속되는 운영 사실이 아니다. [AWS Free Tier FAQ](https://aws.amazon.com/free/free-tier-faqs/)

| 일반 / 캐시 egress | 각각 5GB | 각각 250GB |
| DB 기준 | 데이터 500MB | 프로젝트당 기본 디스크 8GB |
| MAU 포함 | 50,000 | 100,000 |

초과 단가는 카탈로그에 저장한다: Storage $0.00002919/GB-hour, gp3 DB disk $0.000171/GB-hour, uncached $0.09/GB, cached $0.03/GB, MAU $0.00325/명. 단가의 확인일·URL을 결과와 함께 내보낸다. [요금표](https://supabase.com/pricing) · [Storage](https://supabase.com/docs/guides/platform/manage-your-usage/storage-size) · [Disk](https://supabase.com/docs/guides/platform/manage-your-usage/disk-size)

compute는 Micro $0.01344/h, Small $0.0206/h, Medium $0.0822/h를 비교 후보로 둔다. Pro 기본료에 포함된 월 $10 compute credit은 **조직당 한 번**, compute에만 적용한다. 하나의 Micro가 매달 정확히 $10이라고 고정하지 않고 월 시간 수를 사용한다. [Compute 과금](https://supabase.com/docs/guides/platform/compute-and-disk)

`Supabase 비용 = 조직료 + max(0, 모든 프로젝트 compute - 월 compute credit) + 프로젝트별 디스크 초과 + 조직 합산 파일/egress/MAU 초과 + 선택 부가서비스`

공유 조직/프로젝트이면 다른 앱 사용량과 다른 프로젝트 compute를 먼저 포함해 **계정 전체 예상 청구액**을 계산한다. 이어 설정한 배분 비율로 MCS 부담액을 표시한다. 둘을 더하지 않는다. 공유 범위를 모르면 포함량이 이 앱 전용이라는 가정이 화면에 남는다. MAU는 가입 회원 수가 아니라 월 활성 고유 사용자이며 여러 앱의 중복 사용자는 별도 입력한 조직 고유 수가 정본이다.

Free 한도를 넘는다고 Free에 초과 단가를 붙이지 않는다. Free/지출 상한 유지안은 `한도 검토 필요·원하는 사용량 유지 불확실`로 표시한다. 유예 기간은 구현에서 임의로 숫자를 만들지 않는다. Pro + 상한 해제 가정안에서만 초과요금을 산정한다. compute 자동 증설도 공급자 보장처럼 표시하지 않는다. [비용 제한](https://supabase.com/docs/guides/platform/cost-control) · [Egress 한도](https://supabase.com/docs/guides/platform/manage-your-usage/egress)

### 4.8 전환 시나리오와 서버 성능

**요금 유지안**과 **성장을 수용하는 가정안**을 각각 실행한다. 같은 수요를 넣고 요금/성능 전제만 바꾼다. 예측에서 한도 초과 수요가 있어도 실제 처리된 수요라고 말하지 않는다.

- 한도 기반 Free→Pro 후보: 월평균 파일/누적 egress/DB 데이터/MAU 중 하나라도 해당 한도를 초과하는 첫 과금 주기. 해당 월 시작에 유료 전환한다고 가정하여 전환 월 기본료를 전액 반영한다. 중도 전환 청구서를 정확히 재현하지 않는 보수적 월 예산이다.
- 무료 혜택 종료: 날짜/크레딧 잔액 소진에서 산출. 실제 서비스 중지/유료 지속은 계정별 선택으로 표시.
- EC2/DB compute 증설: 사용자가 지정한 월별 변경 일정, 입력한 실측 기준, 또는 아래 **명시적 부하 가정으로 산출한 추천안**을 사용한다. 실측이 없어도 후보·비용을 제시하되 `가정 기반 추천`과 `실측 기반 추천`을 구분한다. 회원 수만으로 자동 결정하지 않는다.
- 한 번 유료/상위 단계로 간 뒤 예측 엔진이 자동 강등하지 않는다. 다운그레이드는 명시적 일정으로만 비교한다.

성능은 `미측정 / 입력한 검증 범위 안 / 범위 초과` 세 상태다. 월 사용량만으로 평균 동시성을 계산할 때 `피크 작업 도착률 × 작업 소요시간`은 외부 요청 진행량의 근사이며 EC2 CPU 사용량이 아니다. CPU 처리시간·이미지 가공 peak RAM·DB 지연/RPS·공급자 rate limit을 별도로 측정해야 처리 가능 여부를 판정할 수 있다.

측정 입력에는 하드웨어·작업 종류·해상도·동시 작업 수·p95·실패율·최대 RSS·CPU credit 관측일을 붙인다. 다른 사양/프로필이면 재사용할 수 없는 표본임을 표시한다. DB connection 수를 사용자 수 한도로 변환하지 않는다. 현재 worker는 수집용이며 이미지 전체를 조절하는 큐라고 표시하지 않는다.

### 4.8.1 추천 사양·교체 시점·가격까지 제시

추가 사용자 요청: “100명일 때 어떤 모델로 업그레이드하고 비용이 얼마인지도 판단하고 싶다.” 따라서 `미측정`만 표시하고 끝내지 않는다. 비용 예측 위에 **구성 추천 기능**을 둔다. 추천 대상은 AI 모델이 아니라 EC2 인스턴스 사양과 Supabase 플랜/compute다. AI 모델 선택은 기존 작업 프로필이다.

추천은 다음 순서로 계산한다.

1. 회원/활성률/생성 사용량 → 월 생성 작업·조회·전송·저장 증가량.
2. 피크 동시에 생성하는 회원 비율 또는 직접 입력한 동시 작업 수 → 피크 진행 작업 수. 시작 단계에서는 이 값도 이름 붙인 부하 가정으로 제공한다. 소진율이 같은 사람들의 실행 시각이 모이는 정도는 별도다.
3. OS·웹·워커 기본 메모리 + 피크 작업당 추가 메모리 + 이미지 다운로드/변환 동시성 → 여유율을 포함한 RAM 요구량.
4. 측정된 CPU 초/작업·피크 처리율이 있으면 CPU 요구량, DB 지연/RPS·연결/메모리가 있으면 DB compute 요구량을 별도 산출한다. 없으면 해당 자원은 `검증 전`으로 유지한다.
5. 요금/저장/전송 한도를 먼저 적용한 뒤, 알려진 자원 요구를 만족하는 호환 가능한 후보를 가격 순으로 제시한다. 추천안·한 단계 여유안·현재 유지안의 비용을 같은 수요에서 비교한다.
6. 현 사양이 확인되었을 때만 `유지/업그레이드`와 차액을 표시한다. 현 사양 미확인이면 `추천 구성 / 현재 구성 입력 시 차액 계산`으로 표시한다.

메모리 추천의 예시 식:

`필요 RAM GiB = (기본 사용 GiB + 피크 작업 수 × 작업당 추가 GiB) / 목표 최대 메모리 사용률`

초기 시안용 **검증되지 않은 가정**은 기본 1GiB, 작업당 추가 0.25GiB, 목표 최대 사용률 70%다. 이는 현 서버 실측값이나 공급자 보장치가 아니다. 해상도·섹션 병렬 수·레이아웃 합성·워커 부하가 다른 작업 프로필에는 동일 값을 자동 재사용하지 않는다. 범위의 상단값으로 여유안을 만들 수 있으나 통계적 신뢰구간이라고 부르지 않는다.

- 같은 가입자100명이어도 피크 생성1건이면 `(1+.25)/.7 ≈ 1.79GiB` → t3.small 2GiB가 메모리 기준 후보.
- 가입자100명·활성70명·피크 동시 생성 비율3% 가정이면 `ceil(70×.03)=3건`, 필요 약2.5GiB → t3.medium 4GiB가 메모리 기준 후보.
- 이 예에서 Small→Medium은 RAM이 늘지만 vCPU는 둘 다2개다. CPU 병목이면 Medium으로 올리는 것만으로 해결된다고 추천하지 않는다.
- 실제 글로벌 생성 대기열/동시 제한은 현재 없다. 추천 계산이 가정한 3건을 운영 서버가 강제하는 것처럼 표현하지 않는다. 예상 초과 수요는 한 단계 여유안과 대기열 필요 여부를 별도 표시한다.
- 저장 한도가 원인일 때 Supabase Free→Pro를 제시한다. DB 성능 근거 없이 회원100명이라는 이유만으로 Micro→Small/Medium을 강제하지 않는다. compute 상향은 DB 부하 가정 또는 실측에 근거한다.

상태는 `assumption-based / measurement-based / insufficient-profile`이다. 전자는 후보와 가격이 있지만 처리 능력은 미검증, 후자는 입력한 사양·프로필의 검증 범위 안, 마지막은 알려진 프로필 밖이라 구체 추천을 보류한 상태다. 가격 확인 여부는 이 상태와 독립적이다. `공식 단가 확인·성능 가정`을 동시에 표시할 수 있어야 한다.

### 4.8.2 서울 리전 가격 근거와 100명 예시

### 4.9 합계와 기간

- 비용 통화는 원 통화 금액을 유지하고 마지막 표시에서 고정 입력 환율로 변환. 반올림은 표시 단계에서만.
- `정상 운영원가`에는 무료 혜택을 적용하지 않은 비용을 표시. `예상 청구 지출`에는 적격 혜택을 적용.
- 공급자 세금/해외결제 수수료는 별도 입력. 기존 판매 VAT·PG는 매출 계산용이므로 API/인프라 비용에 자동 재사용하지 않음.
- 전체 비용이 완전할 때만 1인당/1장당 전체 비용을 계산. 회원 0/이미지 0이면 분모 0은 `—`.
- 1·3·6·12개월 선택은 월별 결과 중 선택 월과 누적 합계만 바꾸며 조건 자체를 변경하지 않음.

### 5.1.1 사용 흐름

1. 저장된 시나리오 또는 명시적으로 불러온 예시를 연다. 필수 미입력 상태를 0원으로 숨기지 않는다.
2. 회원 수·제공량을 바꾸면 생성량/비용/이익이 함께 갱신된다. 판매가 변경은 실제 서비스 차감 정책에서 생성량을 바꾸지 않는다.
3. `가끔/보통/모두`는 사용 가정만 바꾼다. `모두 소진`은 지출 스트레스 비교이며 서버 부하 보장은 아니다.
4. 100/500/1000명 비교는 회원 수만 바꾼 같은 조건을 계산한다. 가입 수=동시 사용자 수로 해석하지 않는다. 월 증가율을 설정한 경우 비교 시작 인원만 바꾼다고 표시한다.
5. 자세히 알고 싶을 때 `세부 조건 펼치기`로 내려간다. 모델·요금제·파일 크기를 바꾸면 상단 요약도 즉시 바뀐다.
6. 상세를 접거나 다시 열어도 값/선택 월/정책이 유지된다. `간단 모드 기본값`으로 되돌리는 동작을 넣지 않는다.

### 5.3 상태·반응형·접근성

- 최초: 인프라 미입력. 예시 불러오기는 명시적 버튼. 0원 확정 총액을 보여주지 않음.
- 편집: 숫자의 빈 문자열/음수/범위 밖 값은 해당 필드 오류. 계산 결과에는 `입력 수정 필요`를 표시하고 마지막 유효 결과와 구분. 음수를 몰래 0으로 clamp해 정상값처럼 보이지 않음.
- 한도 초과: 유지안 결과를 보존하면서 전환 가정안 비교 버튼. 실제 플랜 변경 동작 없음.
- 이전 시나리오: 새 성장 설정은 미설정으로 열기. 옛 고정비가 서버비인지 확인 없이 분해하지 않음.
- 저장 실패: 로컬 저장 제한을 토스트+인라인으로 알리고 JSON/HTML 내보내기는 계속 제공.
- 통합 요약: 핵심 입력 3열·결과 4열, 모바일 1~2열. 상세를 펼친 Desktop ≥1100px: 320px 입력 + 나머지 결과, 결과 최소 너비 0. 768~1099px: 입력 접기 가능. <768px: 조건 패널 상단 accordion, 지표 1~2열, 월별 표만 가로 스크롤.
- 부모/iframe 이중 세로 스크롤을 추가하지 않는다. 기존 frame 높이 측정 유지. 입력 패널 sticky는 내부 스크롤을 또 만들지 않음.
- 기존 Pretendard·`--background`, `--foreground`, `--primary`, `--border`, `--warning`, `--destructive` 토큰 사용. 색만으로 한도 초과/미측정을 구분하지 않음.
- 탭은 role=tablist/tab/tabpanel, 방향키/Home/End, 선택 상태. 모든 수치 입력에 label·단위·오류 연결. 그래프는 표 대체와 키보드로 월 선택 가능.
- 결과 갱신은 입력 종료 후 150ms debounce. 합계 요약만 aria-live=polite, 표 전체 재읽기 금지. 모달/서랍 닫기 후 원 버튼에 초점 복귀.

### 5.4 생성량·인프라·손익을 함께 계산

통합 요약과 기존 가격 도구는 공통 시나리오를 읽는다. 새로 계산한 인프라 비용을 다른 탭에 복사/적용하는 버튼은 두지 않는다. 선택 월과 가격 정책에 따라 자동 반영한다.

- 월 손익의 공급자 비용은 `MonthForecast.costs`에서 한 번만 합산한다. 기존 `calculate()`의 paidAi/freeAi를 또 더하지 않는다. 소득·VAT·PG·지원비 계산은 기존 함수에서 재사용할 순수 부분을 분리한다.
- 인프라 비용은 `manual-total` 또는 `itemized` 중 하나만 활성화한다. 예전 fixed가 무엇인지 모르면 기존 합계 직접 입력으로 유지한다. 항목별 계산으로 전환할 때 한 번만 기존 비용에 서버·DB가 포함됐는지 표시하고 기타 고정비를 분리한다. 기존 82,800원에 서버·DB 비용을 다시 더하지 않는다.
- 유료 고객 매출은 해당 그룹의 결제 수×판매가다. 무료 고객은 매출0·비용만 발생한다. 월정액은 활동 여부와 관계없이 구매한 계약 기준, 충전형은 기존 인식매출/미사용 잔액 규칙을 유지한다.
- 통합 화면의 요금 기준은 `무료 제공 / 월 정액 / 충전형`으로 명확히 선택한다. 충전형 선택 시 1크레딧=1원의 가상 정책, 실제 서비스 선택 시 $0.05 원가 단위의 크레딧을 유지한다. 서로 자동 환산하거나 섞지 않는다. 시안은 무료 제공·월 정액 예시만 표현한다.
- 전체 이익은 VAT 제외 매출 - PG - API - 인프라 - 지원비 - 기타 비용이다. 기존 작업 마진과 전체 이익률을 다른 지표로 유지한다. 무료일 때 이익은 음수로 보이며 매출 분모0의 이익률은 `—`.
- 정상 원가/혜택 적용 비교는 **같은 수요**에 적용한다. 혜택이 줄었다고 제공 장수를 자동 줄이지 않는다.
- protected/allocate 제안 정책에서 인프라 증가→차감량 증가→사용량 감소→인프라 감소라는 순환을 만들지 않는다. 현재 사용 중인 제안 차감표를 고정한 상태로 성장 예측한다. 사용자가 `제공량 다시 설계`를 실행할 때에만 선택 월 운영비를 입력으로 차감표를 한 번 갱신한다. 이 도구의 상품 설계 동작은 실제 서비스 설정을 변경하지 않는다.
- 필수 비용 미입력이면 `확인한 비용`만 보여주고 전체 이익은 미확정. 한도 초과 유지안도 정상 운영 가능액으로 표시하지 않는다.

공통 시나리오는 회원 그룹·작업 프로필·인프라·선택 가격 정책·선택 월을 갖는다. 기존 main/wallet/production은 해당 도구별 입력 projection을 사용한다. 현재 편집한 입력만 공유 상태에 반영한다. 충전형의 월 고객 수를 조용히 정액제 고객 수로 덮어쓰는 동기화를 만들지 않는다. 요금 기준을 바꿀 때 각각의 저장된 상품 조건은 유지하고, 활성 조건만 통합 요약에 표시한다.

## 6. 구현 구조와 데이터 계약

### 6.1 파일 구성 제안

기존 iframe을 유지하고 **새 성장 계산은 TypeScript pure engine**으로 분리한다. 기존 모든 HTML UI를 React로 다시 만들지 않는다.

```text
apps/web/lib/admin/cost-forecast/
  types.ts                 입력·결과·근거·버전
  usage.ts                 개인/코호트별 작업·잔액 시뮬레이션
  work-profiles.ts          현재 경로별 예약/차감/호출/저장 효과 어댑터
  inventory.ts             일별 저장 재고·DB·GB-hours
  transfer.ts              경로별 전송·캐시
  infrastructure.ts        AWS·Supabase 요금·혜택·전환
  sizing.ts                가정/실측 부하 → 추천 구성·여유안·근거·검증 범위
  forecast.ts              월별 파이프라인·합계
  catalog.ts               공식 인프라 가격 snapshot + 출처
  schema.ts                검증·v1/v2→v3 복원
  browser-entry.ts         window.MCSForecast 노출, DOM/네트워크 없음
  __tests__/               수치 사례·경계·서비스 함수 대조
scripts/build-cost-forecast.mjs   esbuild로 pure entry 번들·HTML 삽입/검증
apps/web/app/admin/cost-lab/assets/index.html    통합 요약·접히는 상세·입출력 어댑터
apps/web/app/admin/cost-lab/assets/prepaid.html  공통 단가 동기화·링크 스키마
docs/cost-lab/README.md                         계산 경계·운영 기준 입력법
```

기존 HTML에는 `<script id="forecast-engine">`의 생성 영역을 둔다. 빌드 스크립트는 인프라 카탈로그와 pure 모델 단가/작업 estimator에서 가져온 값을 넣는다. 런타임에 TS 파일을 fetch하거나 API 키를 전달하지 않는다. `server-only` import가 번들에 들어오면 빌드 실패시킨다.

현재 공통 단가가 browser-safe 파일과 server 파일에 섞여 있으면 순수 부분만 추출해 어댑터가 참조한다. 동작 변경 없이 서비스와 대조 테스트를 먼저 통과해야 한다. 이번 작업에서 예약/정산 버그 수정과 합치지 않는다.

생성 스크립트 `--check` 모드는 현재 HTML에 들어 있는 번들과 재생성 결과가 같은지 검사한다. CI에서 stale이면 실패. 정상 실행 시에만 생성 영역 교체, 시장 조사 JSON 등 다른 영역 보존. 날짜 같은 비결정적 값은 빌드마다 생성하지 않고 명시적 카탈로그 메타데이터를 사용한다.

기존 `MODELS`와 공통 추정 상수도 같은 어댑터에서 생성한다. `BASE_ROWS`의 작업 가정은 사용자 설정이며 단가와 구분한다. 바뀐 서비스 단가를 적용할 때 기존 159/82개 검증 중 옛 값에 묶인 assertion만 근거와 함께 갱신한다. 기존 요금 설계 공식은 유지한다.


`forecast()`가 반환한 월별 비용과 `BusinessInput`을 `summarizeBusiness()`에 넣어 `UnifiedMonthResult[]`를 만든다. UI의 요약·상세·규모 비교는 이 결과 객체를 읽는다. 회원 수만 바꾸는 비교도 같은 파이프라인을 다시 실행한다. manual-total은 인프라 합계를 대체하지만 사용량/한도 예측은 계속 계산한다. price를 바꾸어도 실제 차감 기준의 수요는 변하지 않는다.

`serviceability`는 요금 한도, `capacity`는 성능 근거다. 하나가 정상이어도 다른 하나를 정상으로 바꾸지 않는다. 미확인 초기 저장/조회값은 그 값에 의존하는 재고·요금 결과에도 null로 전파한다. 위 타입에서 참조한 하위 타입의 필드는 §3·§4의 입력을 그대로 정규화한다. 회원·작업량·파일 크기는 유한 수, 날짜 유효성·범위·그룹 중복·비중 0을 검증한다. 최대 입력 크기 256KB, 36개월, 20개 입력 그룹/프로필, 100개 전환 이벤트로 제한한다. 대규모 회원 수는 인원별 반복이 아니라 코호트 곱으로 처리한다. 1회 지급에서 생성되는 내부 잔액 코호트는 입력 그룹 수와 별개이며 같은 잔액/조건끼리 병합한다.

### 6.3 저장·공유 버전

기존 wrapper는 `{schema:'mcs-cost-lab', version:2, main, production, wallet, view}`다. version 3에 `forecast`, `business`(활성 요금 기준·상품 조건), `infraCostMode`, `summaryUi`(상세 펼침·선택 월), 카탈로그 snapshot을 추가한다.

- v1 순수 main과 v2 wrapper를 모두 읽는다. 새 forecast는 미설정, 기존 입력은 그대로 복원.
- 알 수 없는 미래 버전은 오류로 안내하고 현재 편집 내용을 덮어쓰지 않음.
- 기존 localStorage key의 비교안을 비파괴 마이그레이션. 기존 raw 값을 읽고 검증 성공한 항목만 새 key에 복사. 원본 삭제하지 않음.
- 링크/다운로드/비교안에 공통 예측 조건·선택 월·전환안·직접 단가·카탈로그 버전을 포함. 기존 활성 탭 공유 동작 유지.
- snapshot을 복원하면 당시 단가로 재현. 현재 요금표가 다르면 `최신 표로 다시 계산`을 별도 실행하고 결과 차이를 보여줌.
- 긴 링크는 12KB 초과 시 JSON/HTML 다운로드 안내. URL query가 아니라 fragment 사용. API 키·실 계정 ID·회원 개인정보는 스키마에 없음.
- 문자열 렌더는 textContent/escape 사용. JSON script 삽입은 `<` 등을 escape하여 `</script>`가 문서를 닫지 못하게 함. 기존 테마 메시지 origin 검사 유지.
- 사용자 입력 출처 링크는 http/https만 허용하고 javascript/data URL은 거부. 입력값을 근거로 네트워크를 자동 호출하지 않음.
- 기존 문서 allowlist/no-store/관리자 체크, Next standalone 파일 추적을 유지. 별도 공개 자산 라우트를 만들지 않음.

### 7.2 UI 인수 조건

1. 예시와 실측 입력은 어떤 화면·다운로드에서도 구분된다.
2. 회원 수/사용률/모델/보관 기간 변경 시 월별 지출·파일·전환 사유가 같은 결과 객체에서 함께 바뀐다.

### 10.1 통합 요약 보완 검증

사용자 추가 요청에 따라 같은 시안에 통합 요약과 접히는 상세를 적용했다. 별도 간단 페이지나 성장 탭은 만들지 않았다.

- Chromium에서 요약↔상세 입력 동기화, 같은 월의 비용·생성량 일치, 판매가에 따른 무료/유료 예시 손익을 확인했다.
- 사용 정도 preset, 상세의 직접 설정 표시, 모델 변경, 회원 규모 비교 버튼, 음수 입력 오류와 복구, 상세 접기/펼치기 시 값 보존을 확인했다.
- Free 한도 초과 시 요약도 비용 확인 필요·이익 미확정으로 바뀌는 것을 확인했다.
- 1440px·1024px·390px에서 문서 전체 가로 넘침 없음. 라이트/다크·모바일 스크린샷을 열어 확인했고 JavaScript 오류는 없었다.
- 이번 수정도 설계서·HTML 시안 두 파일에만 해당한다. 제품의 공통 손익 엔진·기존 도구 통합·배포는 아직 구현하지 않았다.

### 10.2 추천 구성 보완 검증

서울 공식 EC2 공개 가격 데이터와 Supabase 공식 요금을 확인하고 §4.8.1~2를 추가했다. 시안은 통합 요약 아래에 추천 구성 비교를 표시한다. 100명·활성70%·동시3%·메모리 예시에서 t3.medium, 기본료 86,885원(730시간·환율1,380원)으로 계산되는 것을 브라우저에서 확인했다. 작은 부하의 Small 후보, 후보 RAM 범위를 넘는 경우의 추천 보류, 비교 창과 1440/1024/390px 가로 넘침 없음·JS 오류 없음을 확인했다. 스크린샷으로 배치를 점검했다. 현 구성 운영비와 추천 기본료 비교를 구분하며, 제품 구현에서는 선택된 추천 구성을 공통 월별 비용 엔진에 연결한다. 실제 부하 검증이나 서버 변경은 하지 않았다.


## 11. 구현 기록 (2026-09-22)

사용자의 구현 요청에 따라 기존 `/admin/cost-lab`에 통합 요약과 접히는 상세를 연결했다. 순수 계산 엔진은 `apps/web/lib/admin/cost-forecast/`, UI 원본은 `apps/web/app/admin/cost-lab/source/`다. `scripts/build-cost-forecast.mjs`가 브라우저 번들과 서비스 모델 단가를 기존 오프라인 HTML에 삽입한다. 상품·성장·인프라·서버 추천·v3 저장/공유를 연결했고 실제 크레딧 차감 API나 SQL은 변경하지 않았다.

구현에서 명시적으로 구분한 사항:

- 원가가 발생한 공급자 출력 / 성공 결과 / 실제 저장 파일 / 업로드·응답 전송은 각각 계산한다. 부분 성공과 기획 반복 요청의 올림도 입력 가능하다.
- 구매 묶음 크레딧은 `creditPerPurchase`, 실제 월 한도는 단독 quota로 구분한다. 팀의 남은 잔액도 시작 예약을 충족해야 한다.
- 실측 배지는 사양·동시 작업 수·날짜뿐 아니라 같은 작업 프로필 signature가 맞아야 유지된다. 모델/해상도가 바뀌면 가정 기반으로 내려간다.
- DB 성능 등급은 사용자가 선택한 compute/변경 일정으로 계산한다. RAM 근거에 따른 자동 사양 추천은 EC2이며, DB는 Free/Pro의 저장·전송 등 한도 전환과 처리 성능 검증 상태를 구분한다.
- 단독 가입 회원을 입력하는 기본 화면과 기존 정액제·충전형 상품 조건은 전환 시 보존한다. 추천 EC2 선택과 항목별 인프라는 공통 월별 손익에 반영한다.
- 기존 모델 단가 복사본의 리디자인 $0.19는 현재 코드의 $0.165로 동기화했다. 기존 기능별 글 비용/작업 구성은 여전히 사용자 조정 가능한 가정이며 새 실제 차감 어댑터와 구분한다.

검증: 새 계산 44개, 관리자 문서/접근 제어 33개, 기존 계산 159개·충전형 82개·시장 데이터 대조 통과. 전체 workspace 타입 검사 통과. 실제 관리자 페이지/문서 라우트·iframe 200, 예시/미입력 상태, 추천 비용 반영, 상품 모드 간 값 보존, v3 비교안·fragment·독립 HTML 왕복, 모바일/다크·입력 오류 복구를 Chromium에서 확인했다. 재실행 가능한 UI smoke는 `docs/cost-lab/verify-forecast-browser.py`다.

전체 테스트에서 1건은 기존 미추적 SQL을 파일명 정렬상 최신 정의로 읽는 문제로 실패했다. `reserve-operation-whitelist.test.ts`와 해당 마이그레이션은 이번 작업에서 변경하지 않았다. 세부 원인과 명령은 `docs/cost-lab/README.md`에 기록했다. Windows에 Linux/WSL 빌드 환경이 없어 Linux standalone 빌드는 실행하지 못했고 릴리스 CI에 생성물 최신성·계산 회귀 검사를 추가했다. 배포·운영 DB 적용·서버 증설은 수행하지 않았다.
