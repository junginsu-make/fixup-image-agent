# 판매 지식 RAG + 구성안 심사 루프 (프로젝트 G)

작성일: 2026-07-27

## 왜 필요한가

이 서비스의 값어치는 이미지가 아니라 **팔리는 구조를 설계하는 것**에 있다.
이미지만 만들 거라면 사용자는 fal.ai 를 직접 쓰면 된다.

그런데 지금 구성안(blueprint)은 이렇게 만들어진다.

1. LLM 이 브리프를 읽고 구성안을 한 번에 써낸다
2. 같은 호출 안에서 자기가 `scorecard` 로 점수를 매긴다

**자기채점은 검증이 아니다.** 같은 호출, 같은 맥락에서 나온 점수는 방금 쓴 글을
스스로 칭찬하는 것에 가깝다. 실제로 화면에 그 점수가 그대로 나가고 있다.

그리고 "무엇이 잘 팔리는가"에 대한 근거는 프롬프트에 박아둔 규칙 몇 줄이 전부다.
검증된 판매 지식이 아니라 내가 적어둔 문장이다.

## 지금 있는 것 (2026-07-27 확인)

| 자산 | 상태 |
|---|---|
| Neon pgvector 저장소 | 살아 있음. `knowledge_documents` / `knowledge_chunks` |
| `indexKnowledgeDocument` / `retrieveKnowledge` | `packages/redesign-core/src/rag.ts` 에 구현됨 |
| 임베딩 | OpenAI `text-embedding-3-small`, 1536차원 |
| 인덱싱 경로 | `POST /api/redesign/knowledge` (관리자 인증 + `KNOWLEDGE_ADMIN_KEY`) |
| **저장된 문서** | **0건** |
| PDP 쪽 지식 사용 | 없음 |

즉 **그릇은 있는데 내용물이 없고, PDP 는 그 그릇을 쳐다보지도 않는다.**

## 설계

> **구현 중 설계가 바뀐 부분 (2026-07-27)**
>
> 아래 2~6번은 "판매 원칙을 검색해서 넣는다"를 전제로 썼는데, 만들어 재보니 틀렸다.
> 원칙 문서를 pgvector 에 넣고 실제 질의 형태(브리프 + 심사 항목)로 검색하니
> 11개 절이 전부 유사도 0.25~0.40 에 몰렸다. 하한을 걸면 심사에 꼭 필요한
> 반론·신뢰 원칙이 잘려 나갔고, 순위도 믿을 수 없었다 — "누구에게 파는가" 질의에
> 차별점 절이 1위로 나왔다.
>
> 원인은 단순하다. **원칙 문서는 4.4k자로 작고, 심사자는 여섯 항목을 모두 본다.**
> 일부만 뽑는 검색은 여기서 손해다.
>
> 그래서 **원칙은 프롬프트에 통째로 넣는다.** `packages/pdp-core/src/pdp.sales-principles.ts`
> 가 단일 출처다. RAG 검색은 나중에 실제로 잘 팔린 페이지 **사례**가 쌓였을 때 쓴다.
> 그때는 브리프와 비슷한 사례만 뽑아야 하므로 검색이 맞다.
>
> 1번(종류 구분)과 유사도 하한은 그대로 살아 있다. 사례가 들어올 자리이고,
> 하한은 무관한 질의를 실제로 0건으로 걸러내는 것을 확인했다.
> 청크 나누기는 크기 기준에서 문서 구조 기준으로 바꿨다 — 크기로만 자르니
> "대상 고객을 좁히는 방법" 질의가 0건이었다. 문서에 그 절이 통째로 있는데도 그랬다.

### 1. 지식에 종류를 붙인다

`knowledge_documents` 에 `kind` 를 추가한다. 값은 `sales` 와 `redesign`.

리디자인 쪽 지식은 기존 상세페이지를 전사한 텍스트다. 판매 원칙과 성격이 전혀 다르다.
한 통에 섞어두고 검색하면 판매 원칙을 찾을 때 남의 페이지 문구가 딸려 나온다.

기존 행은 `redesign` 으로 채운다. 기존 호출부의 동작은 바뀌지 않는다.

### 2. 유사도 하한을 둔다

지금 `retrieveKnowledge` 는 무조건 상위 K건을 돌려준다. 지식이 얇을 때
**전혀 무관한 조각이 "검증된 판매 지식"이라는 이름표를 달고 프롬프트에 들어간다.**
이건 없느니만 못하다.

`minSimilarity` 를 두고 미만은 버린다. 남는 게 없으면 지식 없이 진행한다.
지식이 없는 것과 엉뚱한 지식이 있는 것은 다르다.

### 3. 심사자를 분리한다

구성안을 만든 호출과 **다른 호출**로 심사한다. 심사자에게는 구성안과 검색된
판매 원칙만 주고, 브리프를 쓴 맥락은 주지 않는다.

심사 항목은 여섯 가지다. 상세페이지가 실패하는 지점에서 뽑았다.

| 항목 | 무엇을 보는가 |
|---|---|
| 대상 | 누구에게 파는지가 구체적인가. "누구나"는 실패다 |
| 문제 | 그 대상이 실제로 겪는 불편을 짚었는가 |
| 차별점 | 경쟁자도 똑같이 말할 수 있는 문장은 차별점이 아니다 |
| 반론 | 살까 말까 망설이는 이유를 정면으로 다뤘는가 |
| 흐름 | 섹션이 순서대로 하나의 설득이 되는가. 나열은 실패다 |
| 행동 유도 | 무엇을 하라는 것인지 분명한가 |

각 항목은 `pass` / `weak` / `fail` 과 근거, 그리고 수정 지시를 낸다.

### 4. 미달이면 다시 만든다

`fail` 이 하나라도 있으면 지적사항을 구성안 프롬프트에 실어 다시 만든다. **최대 2회.**

2회를 채우고도 남은 지적은 **숨기지 않고 화면에 보여준다.** 통과한 척하는 것이
가장 나쁘다. 사용자가 보고 직접 고칠 수 있게 한다.

`weak` 만 남으면 재생성하지 않는다. 되돌이표가 된다.

### 5. pdp-core 는 DB 를 모른다

지식 검색은 **라우트에서** 하고, 결과를 문자열로 `planFromText` 에 넣는다.
기존 `TextPlanDeps` 주입 패턴 그대로다.

이렇게 하면 pdp-core 테스트가 DB 없이 돈다. 지금 121건이 그렇게 돌고 있고
그 성질을 잃고 싶지 않다.

`rag.ts` 를 별도 패키지로 빼지 않는다. 지금 필요하지 않다. 라우트가 두 패키지를
모두 import 하는 것은 앱 계층에서 자연스럽다.

### 6. 초기 지식은 직접 쓴다

`docs/knowledge/sales-principles-ko.md` 에 한국 이커머스 상세페이지 판매 원칙을
정리해 넣고 인덱싱한다. 이후 실제로 잘 팔린 페이지를 넣으면 같은 통에 쌓인다.

시작이 내가 쓴 문서라는 점을 숨기지 않는다. 실제 판매 데이터가 쌓이기 전까지의
출발점이고, 대체될 것을 전제로 만든다.

## 흐름

```
사용자 텍스트
   │
   ├─ (1) 브리프 추출              LLM 1회
   │
   ├─ (2) 판매 지식 검색            pgvector, kind=sales, 하한 미달 버림
   │
   ├─ (3) 구성안 생성 (지식 포함)    LLM 1회
   │
   ├─ (4) 심사                     LLM 1회  ← 별도 호출
   │        fail 있음 → (3) 으로, 최대 2회
   │
   └─ 구성안 + 심사 결과
```

## 비용

**실측(2026-07-27).** 들기름 예시로 끝까지 돌린 결과 **3회 호출에 107초**였다.
호출당 약 35초다. 처음 추정한 "심사 1회 약 10초"는 틀렸다 — Gemini 3.1 Pro 는
구성안처럼 긴 JSON 을 낼 때 그보다 훨씬 오래 걸린다.

| 경우 | 총 호출 | 소요 |
|---|---|---|
| 한 번에 통과 | 3회 (브리프·구성안·심사) | 약 107초 (실측) |
| 1회 재생성 | 5회 | 약 180초 (환산) |
| 2회 재생성(최악) | 7회 | 약 250초 (환산) |

라우트의 `maxDuration` 은 300 이다. 최악의 경우가 250초라 여유가 크지 않다.
재생성 상한을 2회보다 늘리면 상한에 닿는다. 늘리지 않는다.

이미지 생성이 6장에 288초 걸리는 것과 비슷한 수준이다.
구성안 품질이 이미지 6장의 값어치를 좌우하므로 쓸 만한 거래다.

## 하지 않는 것

- **이미지 레퍼런스 RAG** — 프로젝트 H 로 미룬다. 텍스트 지식과 이미지 검색은
  검색 방식도 저장 형태도 다르다. 한 번에 하면 둘 다 어설퍼진다.
- **심사 결과로 이미지 재생성** — 심사는 구성안(글) 단계에서 끝낸다.
  이미지까지 물리면 한 번 돌릴 때마다 비용이 뛴다.
- **사용자별 지식 분리** — 지금은 공용 지식 하나다. 사용자가 자기 지식을
  올리는 것은 수요가 확인된 뒤에 한다.

## 단계

| 단계 | 내용 | 검증 |
|---|---|---|
| G1 | `kind` 컬럼 + 유사도 하한 | 마이그레이션 후 기존 리디자인 검색이 그대로 도는지 |
| G2 | 판매 원칙 문서 작성 + 인덱싱 | 문서 건수·chunk 수 확인, 실제 질의로 검색 결과 확인 |
| G3 | 심사 모듈 (`pdp.review.ts`) | 단위 테스트. 통과/미달/재생성 종료 조건 |
| G4 | `planFromText` 연결 + 라우트 + 화면 | 브라우저로 끝까지. 심사 결과가 화면에 나오는지 |

각 단계는 앞 단계 없이 성립하지 않는다. 순서대로 한다.
