### W4-a·W4-b — 무엇을 값으로 잴 수 있게 했나

`apps/web/lib/pdp/jobs/{state,claim}.ts`. **DB·네트워크를 모르는 순수 함수다.**

세 축이 서로 독립이라는 것이 핵심이다(설계 §8.2).

```
생성(generation) · 정산(settlement) · 보존(persistence)
```

- 정산이 실패해도 결과는 살아 있다. `result_available` 에서 `failed` 로 가는 길이 아예 없다
- 그림을 받았어도 저장 전에는 `done` 이라고 말하지 않는다
- 저장이 실패하면 **그 결과로** 다시 시도한다. 생성 축을 되돌리지 않는다 — 되돌리면 두 번 낸다
- 제출이 불확실하면(`submission=uncertain`) 자동 재전송하지 않는다. 공급자 멱등을
  확인하지 않았고, 확인 없이 보내면 두 번 낸다. 사람이 볼 일로 남긴다
- **생성이 끝났어도 정산·보존이 남으면 `isTerminal` 이 거짓이다.** 워커가 여기서
  손을 떼면 크레딧이 영영 안 닫힌다

멱등은 요청 key 만으로 판단하지 않고 **내용의 지문**을 함께 본다.
같은 key + 같은 지문이면 기존 작업을, 다른 지문이면 409 다. 끝난 작업도 같은
내용이면 그것을 돌려준다 — 다시 만들면 두 번 낸다. 섹션 **순서**는 지문에서 뺐다.
정렬을 바꾸는 날 같은 작업이 두 번 만들어지지 않게.

### SQL 이 하는 일과 안 하는 일

**기존 것을 한 글자도 안 건드린다.** 새 표 둘과 새 함수 둘만 더한다.
`generation_events` 의 제약도 `reserve_generation` 본문도 그대로다 — 그래서 이
SQL 을 먼저 적용해도 옛 코드가 그대로 돈다(아무도 이 값을 안 읽는다).

새 함수 둘은 설계 §8.4 가 요구한 것이다.

- `renew_pdp_job_lease()` — 예약은 10분 뒤 만료된다. 워커가 더 오래 도는 작업을
  그 로직에 맡기면 아직 만드는 중에 예약이 풀려 다음 요청이 `concurrent_limit` 에
  걸린다. **살아 있는 워커의, 그 작업의 예약만** 늘린다
- `settle_expired_pdp_job()` — 만료 뒤에 결과가 나오면 `finalize_generation` 이
  그 행을 안 건드려(`status`가 `reserved`가 아니다) **결과는 있는데 차감이 안 된다.**
  새 예약을 만들지 않고 그 행을 한 번만 성공으로 고쳐 적는다

`finalize_generation` 이 이미 중복 확정을 막고 있음을 확인했다(`if v_event.status =
'reserved'`). 설계 §8.4 의 「중복 확정은 추가 차감하지 않는다」는 이미 만족된다.

### 방향 수정 — 워커를 만들지 않기로 했다 (2026-09-17 17:4x, 사용자 승인)

설계 §8 은 워커(별도 실행기 + systemd)를 전제로 쓰였다. 그런데 **워커 없이도
실질적인 문제는 해결된다.**

핵심은 이것이다 — **브라우저가 끊겨도 서버는 하던 일을 끝까지 한다.** 지금은 그
결과를 돌려줄 곳이 없어서 버려질 뿐이다. 결과를 표와 스토리지에 적어 두면
탭을 닫아도 되찾을 수 있다.

| 상황 | 워커 없이 | 워커까지 |
|---|---|---|
| 탭 닫았다 돌아옴 | 되찾음 | 되찾음 |
| 새로고침 | 되찾음 | 되찾음 |
| 컴퓨터가 꺼짐 | 되찾음 | 되찾음 |
| 한 묶음이 5분을 넘음 | 잘림(한 묶음은 5분 안에 끝난다) | 됨 |
| 그 순간 서버가 재시작 | 그 건 유실 | 이어서 함 |

**워커를 미루는 이유는 위험이다.** 운영 서버는 RAM 911MB 에 여유 445MB 이고
(`pdp.upload-budget.ts` 머리말), 거기에 새 상시 프로세스를 올리면 지금 도는
서비스가 죽을 수 있다. 얻는 것(뒤 두 줄)보다 잃을 수 있는 것이 크다.

표와 저장소 코드는 워커를 나중에 얹을 수 있게 만들어 두었다(`lease`·`claimNext`).

이에 따라 설계 §8.3 의 `POST /jobs` 와 `POST /jobs/:id/stop` 은 **지금 만들지
않는다.** 제출을 기존 생성 라우트가 하므로 주문 창구가 따로 필요 없고, 워커가
없으니 중단할 대상도 없다. 지금 만들면 죽은 코드다 — 워커를 들일 때 함께 만든다.

  누락은 전부 `incomplete`, 못 받았으면 `unavailable`
- **안 본 항목을 fail 보다 무겁게 센다**(`missing * 1000`). 빈 심사가 「fail 하나
  있는 온전한 심사」보다 좋아 보이던 것을 뒤집었다
- `needsRevision` 이 불완전한 심사도 다시 받게 한다
- `normalizeReview` 가 **몇 개를 버렸는지**(`droppedCount`)와 **모양이 틀렸는지**
  (`malformed`)를 남긴다. 안 남기면 「전부 엉뚱한 이름」과 「아무것도 안 냄」이
  같은 빈 목록이 된다
- `qaStatusOf()` — `passed | failed | review_required | unavailable`.
  **fail-open 자체는 맞다**(검수가 흔들린다고 이미 값을 치른 그림을 버릴 수 없다).
  다만 그 사실을 숨기지 않는다. 경고(minor)는 지금까지대로 통과다
- 화면이 「검수 못 함」을 보여 준다. 경고 뱃지와 **따로** 둔다

### 덤으로 잡은 것 — 재작성이 앞 결과를 날렸다

시험을 고치다 드러났다. 심사가 불완전해 재작성을 돌렸는데 **그 호출이 빈 응답을
받으면 던져서, 이미 만들어 둔 멀쩡한 구성안까지 함께 사라졌다.** 사용자는 몇 분을
기다린 끝에 「구성안을 만들지 못했습니다」만 보고 값도 이미 치렀다. 바로 아래
`runReview` 가 실패해도 진행하는 것과 같은 판단으로 고쳤다.

### 옛 시험 셋이 결함을 고정하고 있었다

| 시험 | 무엇을 고정했나 |
|---|---|
| 「응답이 통째로 망가져도 죽지 않는다」 | `needsRevision === false` 를 기대 — **「죽지 않는다」를 「통과다」로 적었다** |
| 「QA 호출이 실패하면 fail-open」 | `qa.passed === true` 를 기대 |
| 「심사 비교」 | 가짜 기준 이름(`c0`·`c1`)으로 **두 개만** 만들어, 다섯을 안 봤는데 「전부 통과」로 읽혔다 |

셋 다 뜻을 바로잡았다. 첫 둘은 **그림은 그대로 주되 상태만 사실대로 적는다**로,
셋째는 실제 기준 이름을 쓰도록.

변이 5종(불완전을 통과로·빈 심사 벌점 0·QA 못 돌린 것 무시·늘 통과로 적음·재작성
실패가 앞 결과 날림)이 모두 잡힌다.

- pdp-core 655 통과. 웹 2,930 통과 / 6 skip. 타입 0건

## W5 이어서 — 사진 경로의 근거 게이트 (K-09·U-12)

### 두 겹으로 새고 있었다

근거 검사(`verifyEvidenceStructure`)가 **글 경로에서만** 돌았다. 사진 경로는
같은 스키마로 `evidence` 를 받으면서 아무도 안 봐서, 지어낸 인용·금지된 주장·
안 채운 질문이 그대로 통과했다.

그런데 **검사를 붙여도 안 잡혔다.** 파고드니 더 앞에서 새고 있었다 —
`normalizeSection` 이 필드를 하나씩 나열하는데 `evidence` 와 `evidenceVersion`
이 그 목록에 없어, **모델이 근거를 보내도 통째로 버려졌다.** 볼 것이 없으니
검사가 할 일도 없었다.

같은 사고가 그 함수 바로 아래 주석에 이미 적혀 있다 — 「필드를 하나씩 나열하지
않는다. 실제로 그렇게 잃었다(2026-07-30)」. 그때는 레퍼런스와 캐릭터였고 이번엔
근거다.

### 고친 것

- `normalizeSectionEvidence()`·`normalizeCopyTarget()` 을 `pdp.evidence` 로 빼서
  **두 경로가 같은 손질을 쓴다.** 글 경로에만 있던 비공개 함수였다
- 사진 경로가 근거를 보존한다(`normalizeSection`)
- 구성안이 나온 뒤 **같은 검사를 돌리고 같은 정책으로 메운다**(U-12 의
  「사진·글 모드에서 정책이 다름」이 이것으로 함께 풀린다)
- **모르는 `kind` 는 `sample` 로 떨어뜨린다.** `quoted` 로 두면 「원문에 있다」는
  주장이 근거 없이 서고 그 문장이 확인 없이 나간다

### 사진 경로의 「원문」은 무엇인가

글 경로는 사용자가 친 글이 원문이다. 사진에는 그런 것이 없다. **사용자가 직접
적은 것**(판매자 브리프·추가 정보)을 원문으로 삼는다(`photoSourceText`).

**사진에서 읽은 것은 원문이 아니다.** 「가죽으로 보인다」는 추정이고, 그것을
인용 근거로 삼으면 모델이 본 것을 사용자가 말한 것처럼 둔갑시킨다
(설계 §9.2: 「시각 추정 재질/효능을 확인 사실로 자동 승격하지 않는다」).

### 소스 문자열로는 「결과를 쓰는가」를 못 잰다

변이로 확인했다 — 검사를 부르고 **결과를 버려도** 문자열 시험은 통과했다.
그래서 `analyzeProduct` 를 실제로 돌려 **결과물이 달라지는지** 재는 시험을
더했다. 지어낸 인용이 정책대로 처리되는지 본다.

- 변이 3종(근거를 다시 버림·검사 결과를 버림·모르는 종류를 quoted 로)이 모두 잡힌다
- pdp-core 691 통과. 웹 2,936 통과 / 6 skip. 타입 0건

## W5 이어서 — 제품을 못 읽었으면 그렇다고 말한다 (U-13)

### 재는 함수는 있었고, 아무도 안 불렀다

`isProductReadingUsable` 은 만들어 두고 **내보내기 목록에만** 있었다. 사진이
흐릿하든 제품이 안 보이든 결과는 똑같이 「완성」으로 나왔다. 사용자는 근거 없는
카피를 확인된 사실로 읽는다.

### 세 낱말인 이유

「읽었다/못 읽었다」 둘로는 부족하다.

| | 사진 판독 | 사용자가 적은 것 | 뜻 |
|---|---|---|---|
| `usable` | 쓸 만함 | — | 제품에서 출발한 카피다 |
| `thin` | 부실 | **있음** | 사용자가 적은 것에 기댄다. 확인이 필요하다 |
| `unfounded` | 부실 | 없음 | **딛고 설 것이 아예 없다** |

정말 위험한 것은 마지막이다. 그때 나오는 문장은 전부 지어낸 것이다.

**사용자가 적은 글의 품질은 재지 않는다.** 잴 수 없다. 있는가 없는가만 본다.

### 이름표만 붙이면 안 부르던 때와 같다

그래서 판단이 **그 자리에서 쓰인다** — `unfounded` 면 「예시로 채우기」를
「물어보기」로 내린다.

그 정책은 「사용자가 확인하고 고칠 것을 전제로」 한 것이다. 근거가 아예 없으면
예시가 곧 페이지 전체가 된다 — 통째로 지어낸 페이지를 건네고 검수를 사용자에게
떠넘기는 꼴이다. **내리기만 한다**: 「빼기」를 고른 사람에게 지어낸 문장을 주는
일은 없다.

내렸으면 **화면이 그 사실을 말한다.** 고른 대로 안 했는데 조용하면 사용자는
예시가 채워진 줄 알고 넘어간다.

### 쓸 만할 때는 아무 말도 하지 않는다

멀쩡한 결과에 「확인하세요」를 붙이면 모든 화면에 붙는 것과 같아진다. 그러면
정말 위험한 화면에서도 사용자가 그 문구를 넘긴다.

### 같은 사고가 초안 저장에도 있었다

`normalizeGeneratedResult` 도 필드를 하나씩 나열한다. 새 필드를 목록에 안 넣으면
조용히 버려진다 — **이번 주에만 세 번째**다(심사 결과 `review`, 근거
`evidence`, 이번 `productReadingStatus`). 초안을 다시 열면 경고가 사라져 근거
없는 카피가 확인된 것처럼 보였다.

### 문구 판단을 그리기에서 뗐다

이 저장소에는 jsdom 이 없다. 문구가 컴포넌트 안에 있으면 「쓸 만할 때 아무 말도
안 하는가」, 「내린 사실을 말하는가」를 **잴 방법이 없다.**
`product-reading-notice.ts` 가 정하고 `.tsx` 는 그리기만 한다.

### 리뷰가 잡은 것 — 고친 자리가 아무도 안 지나는 길이었다

독립 리뷰가 REQUEST CHANGES 를 냈고, **여섯 건 모두 옳았다.** 둘은 이 작업의
목적 자체를 무너뜨리는 것이었다.

**① 초안 보존이 화면 경로에서 안 먹었다.** 화면은 초안을 늘 문서로 바꿨다가
되돌려 읽는다(`draft-repository` → `documentToDraft`). 그런데 `PdpDocumentV3` 에
자리가 없어 거기서 사라졌다. **`pdp-drafts` 에 넣은 보존은 아무도 지나지 않는
길에 있었다.** 새로 쓴 왕복 시험이 통과한 이유는 저장소 계층을 건너뛰고
`savePdpDraft`/`getPdpDraft` 를 직접 불렀기 때문이다.

같은 실수를 **이번 작업 안에서 또 했다** — K-09 에서 「소스 문자열로는 결과를
쓰는가를 못 잰다」를 배워 놓고, 이번엔 「저장소를 직접 부르면 화면이 쓰는 길을
못 잰다」에 걸렸다. 시험이 지나는 길과 사용자가 지나는 길이 다르면 시험은 아무
말도 하지 않는다. 이제 화면을 실제로 띄워 `ScenarioEditor` 가 **받는 값**을
본다(`draft-ui.test.tsx`, v3 켬/끔 두 갈래).

**② 화면이 하지 않은 일을 했다고 말했다.** 「빈칸으로 두었습니다」라고 단정했는데,
내린 정책은 근거 검사에 걸린 섹션에만 적용된다 — `verifyEvidenceStructure` 는
근거 딱지가 없는 섹션을 통째로 건너뛴다. **모델이 딱지를 안 붙이면 한 칸도 안
비워진다.** 그 상태에서 「치웠습니다」를 띄우면 사용자는 위험한 문장이 사라진 줄
알고 그대로 발행한다 — **원래 문제보다 나쁘다.**

그래서 **정한 것이 아니라 한 것을 적는다**(`copyGapOutcome`):

| 칸 | 뜻 |
|---|---|
| `requested` | 사용자가 고른 것 |
| `applied` | 실제로 쓴 것 |
| `cleared` | **실제로 비운 칸 수** |

화면은 `applied !== requested && cleared > 0` 일 때만, 그것도 **몇 곳인지**
말한다.

**③ 내림 규칙이 두 벌이었다.** 화면이 현재 토글값으로 「내렸다」를 되짚었다.
사용자는 결과를 본 뒤에도 정책을 바꿀 수 있어, 바꾸면 없던 말이 뜨거나 있던
말이 사라졌다. 이제 서버가 적은 것만 본다. 규칙도 한 벌로 돌아왔다.

**④ 배선 시험이 문자열 대조라 빈 배선을 못 잡았다.** `toContain("productReadingStatus")`
는 타입 선언 줄만 있어도 통과한다. `ScenarioEditor` 를 mock 해서 **받은 값**을
검사한다.

**⑤ 「대상: 30대 여성」한 줄이 근거가 됐다.** 제품에 대한 근거는 0인데 보호가
꺼졌다. 화면 흐름상 가장 채우기 쉬운 칸이라 구멍이 늘 열려 있었다. 이제
**제품을 말하는 칸만** 센다(`productFactText`: 특징·차별점·추가 정보). 인용을
대조하는 원문은 그대로 전부 잇는다 — **두 물음은 다르다.**

**⑥ 되살린 값에 허용값 검사가 없었다.** 이웃 필드는 전부 화이트리스트를 건다.

- 변이 6종이 모두 잡힌다 — 문서 왕복에서 다시 버림 · 안 비웠는데 치웠다고 함 ·
  대상 칸을 근거로 셈 · 채운 칸도 비운 것으로 셈 · 고른 정책을 한 일로 적음 ·
  화면에 안 넘김
- pdp-core 715 통과. 웹 2,953 통과 / 6 skip. 타입 0건

## W7 — 몇 장인지는 상품이 정한다 (U-14)

### 프롬프트가 모든 상품에 같은 옷을 입혔다

| 고정 조건 | 어디 |
|---|---|
| 「5~6개의 핵심 섹션」 | 사진 경로 |
| 「섹션은 4~7개」 | 글 경로 |
| 「베네핏은 3개 고정」 | 사진 경로 |
| 「bullets 한국어 3개」 | 섹션 템플릿 |
| 「리뷰 섹션은 … 후기 카드 6~12개 우선」 | 사진 경로 |
| 「첫 번째 섹션은 반드시 매력적인 모델이 제품과 함께 연출된 컷」 | 사진 경로 |

할 말이 세 가지인 제품에도 여섯 장을 요구하면 **나머지 세 장은 채우려고
지어낸 것**이 된다. 그 자리에서 나오는 문장이 「사용 후 일상이 조금 더
가벼워집니다」 같은 것들이고, 같은 프롬프트에 그런 문구를 하나씩 금지한 흔적이
남아 있다. **증상을 막았을 뿐 원인은 장수 강제였다.**

### 후기 지시는 자기 자신과 부딪혔다

「후기 카드 6~12개 우선」 바로 아래에 「근거 없는 효능·인증·수치·**후기 개수**를
만들지 말 것」이 있었다. 한 프롬프트 안에서 서로 반대말을 하고 있었다.
이제 **판매자가 알려준 후기가 있을 때만** 그 섹션을 만든다.

### 풀면 강제를 코드로 옮겨야 한다

지금까지 장수를 막는 것은 **프롬프트 문구뿐**이었다 — 코드에는 상한이 한 줄도
없었다. 문구는 부탁이지 강제가 아니다. 모델이 서른 장을 내놓으면 서른 장이
그대로 생성 대기열에 들어가고 **한 장마다 값이 나간다.**

그래서 장수를 푸는 대신 상한을 코드로 지킨다 — `MAX_PLANNED_SECTIONS = 10`,
두 경로의 파싱 지점에서 `clampSections`. 최소 장수는 강제하지 않는다
(설계 §9.1: 「최소 1섹션도 의도된 구성이라면 허용」).

### 하한으로 지키던 것을 이름으로 지킨다

전에는 「4개까지 허용하면 반론이 가장 먼저 빠진다」는 이유로 하한을 5로 올렸다
(기존 결정). 그런데 **장수는 반론이 있는지 확인하지 않는다** — 다섯 장을 만들되
전부 자랑인 페이지도 그대로 통과한다. 늘어난 것은 길이뿐이었다.

보호를 두 겹으로 옮겼다.

1. 프롬프트가 **반론 섹션을 이름으로** 요구한다(그대로 둠)
2. `sectionPlanGaps` 가 **결과물에 망설임을 다루는 문장이 있는지** 실제로 본다.
   없으면 화면이 말한다

시험도 바꿨다 — 「하한이 5인가」 대신 「다섯 장이지만 반론이 없는 구성이 잡히는가」.

### 막지 않는다. 말할 뿐이다

적은 장수가 의도된 구성일 수 있다. 그리고 `SectionPlanGaps` 는 **지금 화면의
구성안**을 본다 — 서버가 준 값이 아니라. 사용자가 아래에서 고치면 저절로
사라진다.

### 리뷰가 잡은 것

통과(APPROVE) 였지만 네 가지를 고쳤다.

**① 글 경로는 보호가 실제로 얇아졌다.** 「반론 섹션은 반드시 넣는다」는 사진
경로 프롬프트에만 있었다. 글 경로가 잃은 것은 4~7장 하한이고, 새로 생긴 것은
막지 않는 화면 안내뿐이었다 — 위 문단의 「이름으로 요구한다(그대로 둠)」는
사진 경로에만 해당하는 말이었다. **글 경로에도 같은 한 줄을 넣었다.**

**② 「부른다」와 「결과를 쓴다」를 또 문자열로 쟀다.** `toContain("clampSections(")`
는 그 낱말이 파일 어딘가에 있다는 것만 말한다. 넘치는 응답(14장)을 실제로
넣어 **두 경로 모두 10장이 나오는지** 본다. 변이로 확인했다 — 부르고 결과를
버리면 이제 잡힌다.

**③ 화면이 그 상자를 띄우는지 아무도 안 쟀다.** 컴포넌트 시험은 직접 렌더할
뿐이라, `ScenarioEditor` 의 배선 한 줄을 지워도 전부 통과했다. 인자까지 한
문자열로 본다.

**④ 내 변경이 어긋나게 만든 주석** 둘(`api/library` 의 「보통 4~7장」)을 고쳤다.

### 남긴 판단

**상한 10을 무엇 이하로 잡았나.** 설계는 「현행 전체 요청 상한 이하」라고 했는데
저장소의 후보가 둘이다 — 라이브러리 한 작업 20장, 요청당 묶음 2~6장.
**라이브러리 20장을 기준으로 삼았다.** 묶음 상한은 한 번에 보내는 수라 화면이
알아서 쪼개고(`chunkForModel`), 페이지 전체 장수와는 다른 물건이다.

**자르는 것을 알리지 않는다.** 14장 중 4장을 버려도 사용자는 모른다. 빈자리
정책을 내릴 때와 달리 **여기서 덮은 것은 사용자의 선택이 아니라 모델의
과욕**이다. 사용자는 14장을 요청한 적이 없다. 알림을 붙이면 사용자가 하지도
않은 일을 설명받는다.

  부르고 결과를 버림** · 모든 섹션에 신뢰 문구 요구 · 화면이 안 그림 ·
  **화면 배선만 제거** · 글 경로 고정 장수 되돌림

## W2/W5/W7 — 페이지 전체가 같은 디자인을 따른다 (U-15)

### 통일 장치가 한쪽 경로에만 있었다

섹션 이미지는 **서로를 모른 채 각각 생성된다.** 앵커 이미지에는 글자가 없어
서체를 전달할 수도 없다. 그래서 무엇을 공유할지 한 번 정해 모든 섹션에 실어
보내야 한다 — 안 그러면 섹션마다 서체가 바뀌고 색이 바뀌고 등장인물이 바뀐다.

그 장치(`designSystem`)가 **글 경로에만 있었다.** 사진 경로는 섹션마다
`style_guide` 를 제각각 적었다. 프롬프트가 「전체 통일 스타일」이라 적어 두긴
했지만, **여섯 섹션이 각자 자기 문장을 쓰면 통일될 수가 없다.**

### 새 섹션은 형제를 베꼈다

`createSectionFor` 가 `sections.find(s => s.style_guide)?.style_guide` 로
형제 것을 통째로 복사했다. 그 형제를 사용자가 고치거나 지우면 **계승이 조용히
끊긴다** — 새 섹션만 다른 서체·다른 인물로 만들어지고, 그 사실은 **이미지가
나온 뒤에야** 보인다. 한 장에 값이 드는데 그때는 이미 늦다.

이제 공용 디자인을 **직접** 받는다. 형제가 옛 디자인을 들고 있어도 지금 것을
받는다. 공용 디자인이 없는 옛 초안은 전처럼 형제에게서 물려받는다.

### 싣기는 멱등이어야 한다

다시 기획할 때마다 같은 문장이 쌓이면 프롬프트가 길어지고, 디자인을 바꿨을 때
**옛 서술과 새 서술이 함께 남아** 모델이 어느 쪽을 따를지 알 수 없게 된다.
그래서 붙이기 전에 표지(`DESIGN_SYSTEM_MARKER`)부터 뒤를 걷어낸다.

### 표지만 보면 옛 디자인이 통과한다

`sectionsMissingDesignSystem` 은 표지가 있는지가 아니라 **지금 디자인의 서술과
같은지**를 본다. 표지만 보면 옛 서체·옛 인물을 든 섹션이 「받았다」로 통과하고,
그 섹션만 다른 모습으로 만들어진다.

### 왕복은 지금도 살아남지만 묶어 뒀다

문서·초안 왕복은 펼치기(`...doc.blueprint`)로 옮겨서 `designSystem` 이
살아남는다. 그런데 **이번 세션에서 필드를 하나씩 나열하는 자리에 세 번
걸렸다**(심사 결과 · 근거 · 판독 상태). 누군가 이 자리도 나열로 바꾸는 날 새
섹션이 조용히 다른 서체로 만들어지기 시작한다 — 변이로 확인했고, 나열로 바꾸면
시험이 잡는다.

### 리뷰가 잡은 것 — 진단해 놓고 그 줄을 안 고쳤다

**① 프롬프트가 `style_guide` 를 두 번, 반대로 정의했다.** 앞에
`DESIGN_SYSTEM_RULES` 를 놓아 「서체·색·등장인물은 designSystem 이 정한다」고
해 놓고, 뒤에서 여전히 「전체 통일 스타일 … **서체 인상**을 적을 것」이라
말했다. **뒤에 있는 쪽이 이긴다** — 섹션마다 서체를 또 정하고, 그 제각각인
글이 공용 서술 **앞에** 남았다. 통일하려고 만든 장치가 통일을 못 시켰다.

부끄러운 것은 두 가지다. 그 자리 주석이 **이미** 「`style_guide` 설명이 한
프롬프트에 두 번, 다른 어휘로 있으면 안 된다 … 뒤에 있는 쪽이 이긴다」고
적어 뒀고, 새 모듈 머리말에는 내가 **바로 그 문장을 진단해 놓고** 고치지
않았다. 이제 섹션 필드는 「그 섹션만의 연출」로 좁혔고, **정의가 한 벌인지**
재는 시험을 붙였다.

**② 컷 타입 우선이면 공용 디자인이 통째로 사라졌다.** `style-first` 는
`style_guide` 를 버리고 장면을 새로 짠다. 그 안에 페이지 공용 디자인이 함께
실려 있어서, **한 섹션만 컷 타입 우선으로 두면 그 섹션만 다른 서체·다른
사람으로** 만들어졌다 — U-15 가 막으려던 바로 그 실패인데 새 검수는 구성안
글자만 봐서 「전부 받았음」이라고 말했다. 토글은 섹션마다 따로다.

컷 타입이 덮어야 하는 것은 그 섹션의 **구도**지 페이지 전체의 서체가 아니다.
`designSystemPartOf` 로 공용 서술만 남긴다.

**③ 경고는 뜨는데 고칠 길이 없었다.** `style_guide` 는 화면 어디에서도 못
고친다. 「N개 섹션이 공용 디자인을 받지 않았습니다」는 읽고 넘길 수밖에 없는
말이었고, 바로 아래 「아래에서 직접 고칠 수 있습니다」는 **거짓말**이었다.
「모든 섹션에 페이지 디자인 적용」 버튼을 붙였다 — 값이 안 드는 순수 함수다.

**④ 스키마와 규칙 문구가 아직 두 벌이었다.** 글 경로에 지역 사본이 남아,
사진 경로에만 「사람이 안 나오는 페이지면 `cast` 는 빈 문자열」이 있었다(U-14 와
어긋난다). 지웠다. 시험도 `toContain("pdp.design-system")` 로 **import 줄만**
보던 것을 공용 상수 자체를 대조하게 바꿨다.

**⑤ 편집창이 열리는 날의 함정**을 함수 주석에 남겼다. 표지는 문장 끝에 붙으므로
사용자가 그 뒤에 적으면 다음 `applyDesignSystem` 한 번에 사라진다. 지금은
`style_guide` 입력이 없어 안전하다(`PdpEditor` 는 읽기만 한다).

  문서 왕복을 나열로 바꿈 · **두 번째 정의를 되돌림** · **컷 타입 우선이 공용

## W2/W7 — 전략을 고치는 것과 구성을 다시 짜는 것 (U-11)

### 고쳐도 아무 일이 안 일어났다

「전체 전략」은 그냥 글상자였다. 고쳐도 **섹션은 그대로다.** 그런데 화면이 그
사실을 말하지 않아, 사용자는 전략을 고치고 다음 단계로 넘어가 **고친 전략이
반영된 줄 알고** 이미지를 만든다. 한 장에 값이 드는데 나온 그림은 옛 전략을
따른다.

반대편에는 「설정 바꿔 다시 만들기」뿐이었다. 그것은 업로드 화면까지 되돌려
구성안을 통째로 버린다 — 공들여 고친 문구도 함께 사라진다.

**고친 전략으로 구성만 다시 짜는 길이 없었다.**

### 셋으로 갈랐다

| 하는 일 | 무엇이 바뀌나 |
|---|---|
| 전략 칸 고치기 | 요약만. 섹션은 그대로 — **화면이 그렇게 말한다** |
| 이 전략으로 구성 다시 만들기 | 그 전략에서 출발해 섹션을 새로 짠다 |
| 설정 바꿔 다시 만들기 | 업로드로 돌아가 처음부터 |

설계 §4.2 가 「전체 전략 수정은 요약 수정이다. 섹션 재설계는 별도의 동작이며
이전 revision을 보존한다」고 적은 자리다.

### 지시는 맨 앞에 둔다

긴 규칙 뒤에 붙이면 묻힌다. 심사 지적(`buildRevisionDirective`)을 맨 앞에 두는
것과 같은 이유다. 그리고 「조금 고치라」가 아니라 **「이 전략에서 출발해 새로
짜라」**고 말한다 — 앞엣말이면 모델이 옛 구성을 손보는 쪽으로 간다.

전략 칸은 사용자가 자유롭게 쓰는 글이라 프롬프트 구분자(`===`)를 지운다.

### 되돌릴 수 있다

재기획 직전 구성을 들고 있다가 한 번 되돌릴 수 있다. **초안에는 저장하지
않는다** — 화면을 다시 열면 「방금 다시 짰다」는 맥락이 사라지고, 그때 되돌리기
단추만 남으면 무엇으로 돌아가는지 알 수 없다.

### 지나가다 만든 결함 하나

`onClick={handleAnalyze}` — 인자를 받게 고친 순간 **클릭 이벤트가 첫 인자로
들어가** 전략 지시가 될 뻔했다. 시험도 처음에는 못 잡았다. 인자 없이
`onClick()` 을 불렀기 때문인데, **브라우저는 늘 이벤트를 넘긴다.** 시험이 실제
클릭처럼 이벤트를 넘기게 고치니 그제야 잡혔다.

### 리뷰가 잡은 것 — 되돌리기가 남의 작업을 덮을 수 있었다

**① `previousPlan` 이 어느 작업의 것인지 몰랐다.** A 를 다시 짠 뒤 B 를 열면
**A 의 되돌리기 단추가 살아 있고**, 누르면 B 위에 A 의 유료 이미지가 앉는다.
리뷰가 화면을 띄워 실측으로 잡았다. 작업을 갈아 끼우는 두 자리
(`resetWorkspace`·`handleLoadDraft`)에서 버린다.

작업 id 로 대조하는 방법도 해 봤다가 **뺐다** — 저장 안 한 작업이 자동 저장으로
id 를 받는 순간, 같은 작업인데도 단추가 사라진다.

**② 되돌리기만 보관본을 안 팠다.** 다시 짠 뒤 이미지를 만들고 돌아와 되돌리면
**그 유료 이미지가 통째로 사라진다.** 다른 모든 덮어쓰기 자리는
`preserveBeforeReplacement` 를 지나는데 여기만 빠져 있었다.

**③ 실패하면 엉뚱한 화면에 떨궜다.** 보관 실패 시 늘 편집기로 보냈는데, 구성
화면에서 누르는 길이 생기며 어긋났다. 게다가 오류 문구는 업로드 화면에서만
그려져 편집기에서는 **아무 설명이 없다.** 왔던 화면으로 돌려보낸다.

**④ 새로고침하면 안내가 거짓말이 됐다.** 「이전 구성으로 되돌릴 수 있습니다」는
초안에 저장되는데 단추는 안 남는다. 「저장된 작업에 보관했습니다」로 바꿨다 —
그쪽이 사실이고, 실제 보존은 보관 초안이 한다.

**⑤ 전략 칸에 길이 제한이 없었다.** 서버는 2000자에서 막는다. 긴 글을
붙여넣으면 설명 없는 400 을 만난다. `MAX_STRATEGY_LENGTH` 를 **화면과 서버가
함께** 쓴다.

**⑥ 안내문이 사진 경로에만 떴다.** 「전략만 고치면 섹션은 그대로」라는 사실은
글 경로에서도 참인데, 단추 조건 안에 들어 있어 **글 경로 사용자는 그 사실
자체를 못 봤다.** U-11 이 고치려던 오해가 거기 그대로 남아 있었다.

**⑦ 주입 소독을 한 벌로.** `===` 만 지웠는데, 이 저장소의 지시문이
`[사용자 추가 정보]:` 꼴이라 **줄머리 라벨을 흉내내면** 사용자 글이 시스템
지시로 읽힌다. `sanitizePromptText` 로 합쳤다. 막아 주는 것이지 증명해 주는
것이 아니라, 마지막 지시는 사용자 글 **뒤**에 둔다.

**⑧ 빨개질 수 없는 시험 하나를 지웠다.** `toContain("onRestorePreviousPlan={")`
는 삼항을 뒤집어도 통과한다. 실제 보장은 화면을 띄우는 시험이 한다.

## W2/W3 — 「제품 보존」을 꺼도 제품 사진은 간다 (U-03)

### 토글이 입력을 지웠다

`shouldSendAnchor` 는 「레퍼런스가 있고 제품 보존을 끄면」 `false` 를 돌려줬다.
그러면 **제품 사진이 아예 안 실린다.** 모델은 레퍼런스만 보고 **제품을
지어낸다.**

화면은 그것을 이렇게 말했다 — 「대신 섹션마다 제품 모습이 **조금씩 달라질 수
있습니다**」. 사실은 「**다른 제품이 나옵니다**」였다.

설계 §9.1(U-03): 「실물 product 역할의 **보존 불변**」.

### 원래 근거는 여전히 참이다

앵커를 뺀 데는 실측 근거가 있었다 — 참조가 둘이면 모델이 절충한다. 배경과
글자는 레퍼런스(네이비+옐로)를 따랐는데 **제품 라벨만 앵커 성향으로 크림색이
남았다.** 앵커를 빼니 라벨까지 레퍼런스를 따랐다.

그 문제는 사라지지 않았다. 다만 **해법이 틀렸다** — 절충을 없애려고 입력을
지웠고, 그 대가로 제품 자체를 잃었다. 지금은 **지시로** 푼다.

| 토글 | 역할 | 뜻 |
|---|---|---|
| 켬 | `identity` | 형태·색·재질·라벨을 모두 지킨다 |
| 끔 | `shape-only` | 색·마감은 레퍼런스를 따르고, **형태와 라벨 글자는 지킨다** |

**형태만이어도 라벨 글자는 지킨다.** 글자가 바뀌면 그건 다른 제품이고, 없는
브랜드를 지어낸 것이 된다.

**레퍼런스가 없으면 끄든 켜든 `identity` 다.** 따를 디자인이 없는데 색을 풀면
제품이 아무 색이나 된다.

### 기본값은 지킨다

`buildReferenceRoleDirective` 에 역할을 안 주면 `identity` 다. 옛 호출자가
**조용히 보존을 잃으면 안 된다.** 변이로 확인했다 — 기본값을 `shape-only` 로
뒤집으면 시험 5건이 빨개진다.

### 옛 동작을 지키던 시험 둘을 바꿨다

지우지 않고 **반대 방향으로 다시 썼다.** 왜 바뀌었는지(원래 근거는 참이지만
해법이 틀렸다는 것)를 시험 주석에 남겼다.

### 리뷰가 잡은 것 — 앵커가 늘 실물인 것은 아니었다

**① 글 경로의 앵커는 우리가 만든 대표 이미지다.** 「언젠가 실물 없는 입력이
들어오면」이라 주석을 달았는데 **이미 들어와 있었다** — `TextModeFlow` 가
`originalImage` 자리에 keyVisual 을 넣고, 그 뒤 단계는 사진 경로와 완전히 같다.

그래서 제 변경은 강의·코칭의 대표 이미지를 「판매 중인 제품, **라벨 글자까지**
철자 그대로 지켜라」로 선언하게 만들었다. 거기엔 헤드라인 글자와 임의의 소품이
박혀 있다 — **그 글자가 페이지 전체에 되풀이된다.** 전에는 그 경우 앵커가 빠졌으니
**새로 만든 손상**이다.

세 번째 역할 `mood-only` 를 두고, 앵커가 무엇인지(`anchorKind`)를 화면에서
서버까지 실어 보낸다. 그리고 `shouldSendAnchor` 에 **진짜 판단이 돌아왔다** —
실물 사진은 언제나 보내고, 만들어 낸 대표 이미지는 디자인 레퍼런스가 있으면
보내지 않는다(둘 다 보내면 원래 실측이 말한 그 절충이 일어난다).

**② 화면이 미검증 동작을 사실로 단정했다.** 「제품의 색과 마감을 레퍼런스에
맞춥니다」라고 썼는데, **`shape-only` 가 실제로 색을 넘기는지는 실측하지
않았다.** 오히려 같은 패키지의 2026-07-30 실측은 반대 방향이다 — 「정체성은
첨부된 이미지가 지킨다. 설명이 필요 없다」, 제품 보존 지시가 **아예 없는
조건에서도** 정체성이 유지됐다.

즉 이 변경은 **측정된 손상(제품 날조)을 미측정 가설과 맞바꿨다.** 맞바꾼 것은
옳다고 본다 — 최악이어도 「레퍼런스 색이 덜 반영된다」에 그친다. 다만 **고친
이유가 「화면이 사실 아닌 말을 했다」였는데 방향만 바꿔 같은 종류의 말을 쓸
뻔했다.** 문구를 「조정될 수 있습니다」로 낮추고, 한계를 두 머리말에 적었다.

**③ `shouldSendAnchor` 가 장식이었다.** 게이트를 통째로 걷어내도 787건이 전부
통과했다 — 판단처럼 보이는데 판단이 아니었다. ①을 고치며 살아났고, 이제
걷어내면 잡힌다.

**④ 새 규칙 블록이 4줄 중 3줄 무시험이었다.** 「형태만 지킨다」는 역할인데
**「형태」를 재는 시험이 0건**이었다. 기존 블록처럼 문장째로 재는 루프를 붙였다.

**⑤ 머리말 둘이 옛 설계를 설명한 채 남았다.** 새 함수 주석만 고치고 파일
머리말은 「빼는 것이 해법」으로 읽혔다. 반대 근거(2026-07-30 실측표)와 새 가설이
**같은 화면에 있어야** 다음 사람이 오해하지 않는다.

**⑥ 옛 근거를 든 시험 주석이 한 곳 더 있었다**(세 번째 자리).

## W3 — 둘 다 골랐으면 물어본다 (U-04)

### 조용히 하나를 버렸다

인물 사진을 올리고 저장 캐릭터도 고르면, 서버가 **말없이 업로드 쪽을 쓰고
캐릭터를 버렸다.** 코드 주석은 「업로드한 사진이 우선이다 — 사용자가 방금 고른
쪽이다」라고 적어 뒀는데, **구성안 화면에서는 캐릭터가 더 나중일 수도 있다.**

어느 쪽이든 문제는 같다 — 사용자는 자기 선택이 무시된 것을 **이미지가 나온
뒤에야** 안다. 그리고 한 장에 값이 든다.

설계 §6: 「명시적으로 적용 대상을 선택하게 한다. **우선순위로 하나를 조용히
버리지 않는다.**」

### 「둘 다 쓰기」는 선택지가 아니다

2026-07-30 실측에서 얼굴 참조가 둘이면 모델이 절충해 **제3의 인물**을 만들었다.
그래서 하나만 쓰는 것 자체는 맞다. 틀린 것은 **말없이 고르는 것**이었다.

### 안 골랐을 때는 전과 같게 둔다

`resolvePersonSource` 는 선택이 없으면 업로드를 쓴다 — 지금까지의 동작이다.
**이미 저장된 초안이 조용히 달라지면 안 된다.** 대신 화면이 그 사실을 보여
준다(「고른 캐릭터는 이 페이지에 나오지 않습니다」).

**없는 것을 고르면 있는 쪽을 쓴다.** 캐릭터를 고른 뒤 그 캐릭터를 빼도 옛
선택이 남아 있을 수 있는데, 그때 아무도 안 나오면 「사람이 나오는 섹션」이
통째로 빈다.

### 배선은 다섯 칸

화면 상태 → 구성안 화면(고르기) → 편집기 → `page-wire` → zod → 서버.
어느 한 칸이 빠지면 고르기가 아무것도 안 바꾼다. **변이로 칸마다 확인했다.**

### 리뷰가 잡은 것 — 고른 대로 그려 놓고 틀린 답안지로 채점했다

**① 주 경로가 실제로는 실패했다.** 참조를 담는 자리만 고치고, **프로필
뽑기·재시도 상한·동일 인물 검증 세 자리는 옛 조건을 그대로** 뒀다. 그래서
캐릭터를 고르면 그림은 캐릭터로 그려 놓고 검증은 **업로드 얼굴과 대조** —
당연히 불일치라 **세 장을 태우고 요청이 실패**한다. 회원 과금은 막히지만 fal
비용은 나간다.

**그리고 내 시험이 그것을 덮었다.** stub 을 `isSamePerson: true` 로 고정해서
검증이 도는지 안 도는지가 안 보였다. 더 나쁜 것은 **그 자리에 내가 적은
주석**이다 — 「업로드 인물이 있으면 프로필 뽑기와 동일 인물 검증이 함께 돈다.
그 둘이 통과해야 그림이 나오므로 한 응답으로 셋을 다 만족시킨다.」
**그 문장이 곧 버그 신고였는데 우회로 썼다.**

이제 `isSamePerson: false` 로 두고 **호출 횟수**를 잰다. 검증이 돌면 세 장이
나오므로 한 장인지 본다.

**② 안 쓸 사진을 애초에 안 넘긴다.** `buildSectionImageOptions` 의 주석이 이미
「이 섹션에 안 쓰는 사진은 아예 넘기지 않는다」고 말하는데, 캐릭터를 고른 경우가
빠져 있었다.

**③ 글 경로에 같은 충돌이 살아 있었다.** 사진 모드에서 인물을 올린 뒤 글 모드로
바꾸면 **그 사진이 남는다.** 거기서 캐릭터를 고르면 둘이 되는데 고를 칸이 없었다.
게다가 `PdpTextDraftState.personSource` 를 만들어 놓고 **읽는 곳도 쓰는 곳도
없었다** — 다음 사람에게 「여기 배선돼 있다」는 거짓 신호다. 배선했다.

**④ 화면 → 편집기 칸에 시험이 0건이었다.** 섹션 이미지는 **편집기에서만**
만들어지므로 그 줄이 빠지면 고르기가 아무것도 안 바꾸는데, 3,014건이 전부
통과했다. 진행 문서에 적은 「다섯 칸을 변이로 확인했다」에서도 이 칸만 빠져
있었다.

**⑤ 문구가 거짓이었다.** 「고른 캐릭터는 **이 페이지에** 나오지 않습니다」 —
올린 사진을 대표컷에만 쓰면(`hero-only`) 나머지 섹션에는 캐릭터가 나온다.
사용 범위를 함께 받아 갈라 말한다.

**⑥ 웹 시험이 통과인데 exit 1 이었다.** 내가 더한 시험만 `preparedImage`+
`modelImage` 를 함께 실어 초안 적용이 8틱을 넘겼고, unmount 뒤에 콜백이 깨어나
unhandled rejection 이 났다. 「3,014 통과」는 건수로는 맞지만 **명령은
실패**였다.

**⑦ `identityCheckPlan`** 의 주석이 U-04 이후 거짓이 됐고, 그 근거가 정확히 ①의

## W3 — 자동 각도는 판단이 아니라 낱말 대조다 (U-05)

### 판정처럼 말했다

화면은 「자동은 섹션 설명을 **읽어** 어울리는 각도를 하나씩 고릅니다」라고
말했다. 실제로는 정규식 몇 개를 대조하고, 아무것도 안 걸리면 **한 각도로
굳는다.** 리디자인 경로는 섹션 설명이 늘 비어 있어 **언제나** 그 자리다.

규칙이 나쁘다는 말이 아니다 — 잘 돈다. 나쁜 것은 **판단처럼 보이게 말한
것**이다. 사용자는 「AI 가 봤겠지」 하고 넘기고, **왜 이 각도인지 물을 생각을
못 한다.**

설계 §9.1(U-05): 「자동 정책을 설명하고 사용자 override 유지.
**AI 판정처럼 표시하지 않음**」.

### 규칙을 표로 내고 문구를 그 표에서 짓는다

`ANGLE_KEYWORD_RULES` 하나가 판단이자 안내문의 근거다. 규칙이 늘면 문구도 따라
는다 — 두 벌로 적으면 한쪽만 고치는 날이 온다.

문구는 **낱말 → 각도**로 적는다. 규칙 이름을 쓰면 「뒷모습 → 뒷모습」처럼
헛돈다. 사용자가 알고 싶은 것은 **어떤 말을 적으면 어느 각도가 오는가**다.

### 만들어 두고 안 부르면 같은 결함이다

`explainAngleForSection` 은 「왜 그 각도인지」를 돌려주는데 처음에는 아무도
안 썼다 — U-13 으로 고친 것과 같은 꼴이다. 구성안 화면이 섹션마다 쓴다.

**아무 낱말도 안 걸린 경우를 보여 주는 것이 더 중요하다.** 그때는 기본값 하나로
굳는데, 모르면 「설명을 고치면 각도가 바뀌겠지」 하고 헛수고한다.

### 리뷰가 잡은 것 — 쪽지가 그 헛수고를 만들었다

**① 쪽지가 화면에 없는 칸을 가리켰다.** 자동이 읽는 것은 `layout_notes` 인데
구성안 화면에는 그 칸이 없었다. 사용자는 바로 위 「이미지 방향」(`prompt_ko`)에
「뒷모습」을 적고도 각도가 안 바뀌는 것을 이해할 수 없다 — **막겠다던 헛수고를
쪽지가 만들었다.**

읽는 칸을 화면에 냈다(설계 §9.3: 「실제 생성에 쓰는 값과 같은 것을 표시한다」).
문구도 「레이아웃 메모에서」로 못 박고, 기본값일 때는 **할 일**을 알려 준다.

**② 배선 시험이 바깥 전달을 못 봤다.** 안쪽 JSX 한 덩이만 재는데 그 값들은
바깥에서 온다. 게다가 프로퍼티가 **선택**이라 타입 검사도 안 잡았다 — 기능이
통째로 사라져도 3,030건이 전부 통과했다. 필수로 바꿔 컴파일러가 잡게 했다.

**③ 가장 잘 보이는 줄이 아직 판정 어투였다.** `describeCharacterChoice` 의
「각도 자동. **섹션에 맞는 장면을 골라 씁니다**」는 캐릭터를 고른 직후 두 화면에
**늘 떠 있다** — 모달 안 문구보다 훨씬 자주 보인다. 그리고 리디자인에서는
**사실도 아니었다.** 옛 어투를 지키던 시험도 함께 바꿨다.

**④ 죽은 필드와 헛도는 시험.** `rule.label` 은 화면이 `characterAngleLabel` 로
바뀐 뒤 쓰는 곳이 없었고, 유일한 시험은 `length > 1` 이라 **빈 문자열로 만들지
않는 한 빨개질 수 없었다.** 게다가 값이 갈렸다(「뒷모습」 vs 「뒷면」). 지웠다.

**⑤ 리디자인 안내가 손으로 적은 사본이었다.** 기본값을 바꾸면 그 줄만 거짓이
되고 잡는 시험이 없었다. 같은 상수에서 짓는다.

**⑥ 규칙 표가 변경 가능한 채로 나갔다.** `as const` 를 붙였다.

## W1/W7 — 입력을 몰래 자르지 않는다 (U-08)

### 세 가지가 어긋나 있었다

| 자리 | 무엇 |
|---|---|
| 화면 | 제한이 **없었다.** 사용자는 얼마든지 적는다 |
| `normalizeSellerBrief` | **말없이 500자에서 잘랐다** |
| zod | 넘치면 「요청이 올바르지 않습니다」 한 줄. **어느 칸이 왜 걸렸는지 없이** |

사용자는 501번째 글자부터 사라진 문장을 **알 길이 없다.** 그 말이 페이지에 안
나와도 원인을 짐작 못 한다.

### 「그 밖에」 칸은 더 이상했다

**기획은 길이 제한이 없고 이미지 생성만 500자**였다. 같은 화면 칸인데 501자를
적으면 구성안은 나오고, **이미지를 만들 때** 400 이 난다 — 그때는 이미 구성안을
손봐 둔 뒤다.

### 자르는 대신 경계에서 막고, 막기 전에 말한다

설계 §6: 「입력 칸의 최대 길이는 **서버와 UI가 공유한다** … **입력을 몰래
자르지 않는다.**」

- 상수 한 벌(`pdp.input-limits`)을 zod 와 화면이 함께 쓴다
- `normalizeSellerBrief` 는 이제 **다듬기만** 한다
- 화면이 글자 수를 보여 준다. **평소에는 안 보인다** — 모든 칸에 「0/500」이
  떠 있으면 아무도 안 읽는다. 8할을 넘겨야 나온다
- 넘치면 분석을 막고 **왜 못 누르는지, 몇 자를 줄여야 하는지** 말한다.
  막기만 하면 서버가 말없이 되돌려보내던 때와 다를 것이 없다

### 옛 동작을 지키던 시험을 바꿨다

「지나치게 길면 자른다」가 초록이었다. 그 걱정(한 칸이 프롬프트를 밀어낸다)은
여전히 참이지만 **해법이 틀렸다.** 왜 바뀌었는지를 시험 주석에 남겼다.

### 리뷰가 잡은 것 — 내가 만든 회귀

**① 입구가 둘인데 문지기가 하나였다.** 업로드 화면 단추는 막았는데, 구성안
화면의 「이 전략으로 구성 다시 만들기」는 그 문지기를 안 지난다. 그리고 내가
**`additionalInfo` 에 없던 상한을 새로 붙였으므로**, 501자를 담은 옛 초안
— 전에는 기획에 상한이 없어 그런 초안이 생길 수 있었다 — 을 열어 거기서
누르면 **조용한 400** 이 난다. **없애려던 바로 그 화면이다.**

함수 머리에서 막는다. 문구도 단추 아래와 **같은 것**을 쓴다.

**② 500 의 세 번째 사본과 거짓 주석.** `pdp.image-prompt.ts` 가
`MAX_PAGE_CONTEXT = 500` 을 따로 들고 있었고, 그 주석은 「판매자 브리프도 같은
이유로 500자에서 자른다」고 했다 — **내가 방금 없앤 동작을 근거로 들고 있었다.**
공유 상수로 갈고, 여기는 **마지막 그물**임을 적었다.

**③ 서버가 정말 막는지 재는 시험이 0건이었다.** 「같은 상수를 쓴다」를 소스
문자열로만 재서, 상한을 **스무 배로 늘려도 3,046건이 전부 통과**했다. 라우트를
직접 불러 400/200 을 잰다.

**④ 접근성.** 단추와 이유가 이어져 있지 않아 화면을 못 보는 사용자에게는 그냥
안 눌리는 단추였다(`aria-describedby`).

**⑤ `labels` 열쇠를 좁혔다.** `Record<string, string>` 이면 오타가 조용히 기본
이름으로 떨어진다.

### 남은 구멍(이번 변경이 만든 것은 아니다)

글 경로에는 이 칸들이 **아예 없는데**, 사진 모드에서 적어 둔 `additionalInfo`
state 는 모드를 바꿔도 남아 이미지 생성 때 `pageContext` 로 실려 나간다. 501자면
거기서 막히는데 **그 칸이 화면에 없어 고칠 수 없다**(사진 모드로 되돌려야 나온다).
`page.pageContext` 상한은 전부터 있었으므로 이번 회귀는 아니다 — 별도 항목으로
남긴다.

  안 봄 · 넘쳐도 분석 허용 · 안내가 늘 보임 · zod 가 손으로 적은 500 으로
  되돌아감 · **재기획 입구 문지기를 뺌** · **서버 상한을 스무 배로** ·
  **배경 칸 상한을 다시 뺌**

## W3/W7 — 구성 요청과 장면 요청은 다른 일이다 (U-06)

### 적었는데 아무 일도 안 일어났다

「추가 지시」 칸이 **하나뿐**이었고, 그 값은 **이미지 생성에만** 갔다. 칸의
예시도 장면 지시다 — 「배경은 밤, 창밖에 네온」.

그래서 사용자가 「섹션을 다섯 개로」나 「존댓말로 써 주세요」를 적으면
**아무 일도 안 일어난다.** 기획은 그 말을 본 적이 없고, 이미지 프롬프트에
실려 가서는 그릴 수 있는 것이 없다. **적었는데 안 된 이유를 알 수 없다.**

### 그림체도 기획이 몰랐다

기획은 **사진인지 그림인지 모른 채** 장면을 쓴다. 「제품을 손에 들고 웃는 인물
사진」이라 적어 놓고 결과는 일러스트가 된다 — 설계 §6.3 이 그림체를 「기획과
생성 **양쪽 전달**」이라 적은 이유다.

### 칸을 둘로 가른다

| 칸 | 어디로 | 무엇을 정하나 |
|---|---|---|
| 구성·문구 요청 | **기획** | 섹션 구성과 카피 |
| 이미지 연출 요청 | 생성 | 그림 |

**옛 초안의 값은 장면 지시로 남긴다.** 지금 와서 구성 요청으로 읽으면 사용자가
적은 적 없는 뜻이 생긴다.

### 요청이 근거를 무르게 하지 않는다

「효능을 강조해 주세요」 한 줄로 없는 사실이 생기면 안 된다. 요청은 **무엇을
어떻게 쓸지**를 정하지, 무엇이 사실인지를 정하지 않는다.

### `auto` 그림체는 단정하지 않는다

레퍼런스의 결을 따르는 값이라, 기획이 「사진이다」라고 단정하면 어긋난다.

### 남은 것(이번 변경이 만든 것은 아니다)

글 경로에는 그림체·지시 칸이 **아예 없는데**, 사진 모드에서 고른 `look` state 는
모드를 바꿔도 남아 이미지 생성에 실려 나간다. U-08 에 적은 `additionalInfo` 와
같은 모양이다.

### 리뷰가 잡은 것 — 뒤에 있는 반대말이 이긴다

**① 새 칸의 대표 예시가 프롬프트 뒤쪽에서 덮였다.** placeholder 는 「예: **섹션을
다섯 개로**」인데, 뒤쪽 `sectionCountRules()` 는 「**장수를 먼저 정하지
않는다**」고 굵은 글씨로 말한다. **U-06 이 고치려던 그 증상이 새 칸의 대표
예시에서 그대로 재현될 뻔했다.** 이제 구성 요청이 있으면 「사용자가 지정했으면
그 수를 따른다(기술 상한 10장)」를 그 블록 **안에서** 말한다.

**② 그림체 규칙이 「광고 사진 느낌으로 기획할 것」에 먹혔다.** 그 줄은 「# 섹션
구성 원칙(**강제**)」 블록 안, 내 규칙보다 **뒤**에 있었다. 일러스트를 고른
사용자에게 그 줄은 「그림으로 기획하지 마라」다. 이 저장소가
`pdp.reference-policy` 주석에 **실측으로** 적어 둔 함정이다 — 「우선순위 한
줄로는 못 이긴다」. 그림체에 따라 「광고 이미지」로 가른다.

**③ 새로 시작해도 구성 요청이 안 지워졌다.** 바로 옆 `setUserInstruction("")`
은 있는데 새 칸만 빠졌다. 이제 이 값은 **유료 기획 결과**를 바꾸고, 그 칸은
스크롤 아래에 있어 사용자가 못 본다 — A 제품 요청이 B 제품 기획에 실려 나간다.
이 저장소가 `attachmentIntents`·`previousPlan` 에서 **이미 두 번 겪은** 자리다.

**④ 화면이 서버 상한을 몰랐다.** U-08 에서 고친 것이 새 칸에서 되살아났다.

**⑤ `auto` 인데 레퍼런스가 없으면 없는 그림을 따르라고 말했다.** 레퍼런스를 뺐는데
값이 `auto` 로 남으면, 기획 프롬프트에 **그림 한 장 없이** 「첨부한 레퍼런스를
따르라」가 실린다 — 모델은 없는 것을 상상해 `style_guide` 를 채운다.
`resolveLook` 으로 되돌린다.

**⑥ 화면→요청 운반 두 줄이 무시험이었다.** 지우면 사용자는 적고 저장되고
새로고침해도 보이는데 **서버로는 안 간다.** 두 인자 모두 optional 이라 타입도
안 잡는다.

**⑦ dirty 판정에 새 칸이 빠졌다.** 사진을 올리기 전에 구성 요청부터 적고 화면을
떠나면 경고 없이 사라진다.

- 변이 10종이 모두 잡힌다 — 기획 프롬프트에 안 실음 · 빈 지시도 블록을 만듦 ·
  auto 도 사진이라 단정 · 요청 조립이 빠뜨림 · 문서 왕복이 버림 · **광고 사진
  문장을 되돌림** · **장수 규칙이 사용자 지정을 무시** · **auto 를 안 되돌림** ·
  **화면이 운반 두 줄을 안 넘김** · **초기화가 구성 요청을 안 비움**

## W3/W5 — 바꿔 달라고 적었는데 조용히 무시됐다 (U-18)

### 맞는 설계가 낳은 침묵

「이 그림을 어떻게 쓸까요」 칸은 제품·인물 참조에도 붙는다. 거기에 「제품 색을
파란색으로」를 적으면 역할 규칙이 막는다 — 「never change the product or
character to satisfy this instruction」.

**그것 자체는 맞다.** 한 줄로 제품이 다른 물건이 되면 안 된다. 문제는 **아무도
그 사실을 말하지 않는다**는 것이다. 사용자는 적었는데 안 바뀐 이유를 모른 채
다시 적고, 또 적고, 이미지 값을 그만큼 치른다.

설계 §6.1: 「보존 대상에 정체성을 바꾸라는 지시가 섞이면 **충돌을 알려
수정하도록 한다.**」

### 세 판을 거쳤다

**첫 판(낱말 대조)** — **칸의 placeholder 자체**가 걸렸다. 「뚜껑 **색**은 그대로
두고 각도만 **바꿔** 주세요」는 색을 **지키라는** 말인데 「색」과 「바꿔」가 한 글
안에 있었다. 내가 실측으로 잡았다.

**둘째 판(「…을/를」만)** — 리뷰가 잡았다. **배경 색**을 바꿔 달라는 말에 경고가
떴고(배경은 바뀌는 것이 맞다), 「제품 색상을 **바꾸지 말아** 주세요」라는 **가장
협조적인 지시**에도 경고가 떴다. 반대로 도착지에 실린 것(「뚜껑을
**빨간색으로**」)과 조사 없는 한 줄 지시(「색 바꿔줘」)는 통째로 놓쳤다.

**지금 판** — 다섯 단계로 본다.

1. **지키라는 마디는 건너뛴다** — 「그대로 두고」·「건드리지 말고」·「바꾸지 마」
2. **바꾸라는 꼴**이 있어야 한다. 없으면 그냥 언급이다
3. **바꿀 대상**을 찾는다. 조사가 있으면 그것, 없으면 동사 앞 낱말
4. 대상이 **장면의 것**(배경·바닥·조명…)이면 건너뛴다
5. 대상이나 **도착지**(「…으로」)에 지킬 것이 있으면 충돌

실사용 문장 **36건**으로 재서 전부 맞췄고, 그대로 fixture 로 굳혔다.

### 오탐이 미탐보다 나쁘다

멀쩡한 지시에 경고가 뜨면 사용자는 그 경고를 넘기게 되고, **그러면 정말 충돌인
날에도 넘긴다.** 그래서 막지 않고 알리기만 한다 — 낱말 대조라 틀릴 수 있다는
것을 함수 머리말에 적었다.

### 리뷰가 잡은 나머지

**제품 경고가 구성안으로 넘어가면 사라졌다.** 그 칸은 업로드 화면에 있고 화면째
사라지는데 **지시는 그대로 실려** 생성까지 간다. 인물·레퍼런스는 구성안에도 칸이
있어 따라오는데 제품만 안 따라왔다 — 설계의 「수정하도록 한다」가 거기서 끊긴다.

**배선 시험이 변이에 안 걸렸다.** anchor 와 person 을 **맞바꿔도 통과**했다 —
제품 칸에 「같은 사람으로 그리기로 한 자리」라는 딴 경고가 뜨는데도. 칸과 역할을

**문구가 미착수 항목을 약속했다.** 「각도는 여기서 바꿀 수 있습니다」라고 했는데

바꿨다.

## W2/W3 — A 계열 넷 (A-10 · A-11 · A-14 · A-16)

### A-10 — 따를 그림이 없는 `auto`

`auto` 는 「붙인 레퍼런스의 결을 따른다」는 뜻이다. 그런데 레퍼런스를 빼거나
토글을 꺼도 **값은 `auto` 로 남았다.** 화면은 그 단추를 흐리게 만들 뿐이라
사용자는 여전히 `auto` 가 골라진 것을 보면서 **무엇을 따르는지 알 수 없다.**

서버 쪽은 U-06 에서 막았다(`resolveLook`). 여기서는 **화면의 값 자체**를
되돌리고 **그 사실을 알린다** — 값만 되돌리면 고른 것이 혼자 사라진 것처럼
보인다.

**사람이 고른 결은 안 건드린다.** 일러스트·애니는 레퍼런스가 없어도 혼자 선다.

### A-11 — 새 레퍼런스가 꺼진 채로 들어왔다

값만 갈아 끼웠다. 앞 레퍼런스에서 토글을 꺼 뒀다면 새로 붙인 것도 **꺼진
채로** 들어와, 붙여 놓고 안 쓰이는 일이 생긴다(설계 §6.3: 「새 레퍼런스 첨부는
명시적인 활성 상태로 시작한다」).

### A-14 — 목록을 못 불러오면 고른 캐릭터가 사라졌다

로드가 실패하면 `setCharacters([])` 로 빈 목록이 되고, 고른 캐릭터를 그 목록에서
찾으므로 **아무것도 안 골라진 것처럼 보인다.** 그런데 `selectedId` 는 그대로
남아 생성 요청에 실려 나간다.

두 가지를 **구분해서** 알린다 — 목록을 못 가져온 것(다시 불러오면 된다)과
그 캐릭터가 지워진 것(다시 불러와도 안 나온다). 같은 말로 뭉개면 사용자가
무엇을 해야 할지 모른다.

**서버도 막는다.** 전에는 캐릭터를 한 장도 못 불러오면 `undefined` 를 넘겨
**그 캐릭터 없이** 그림을 만들고 값을 받았다. 사용자는 캐릭터를 골라 뒀으니
나올 줄 알고, 나온 그림에는 다른 사람이 있다(설계 §6.2: 「참조가 없으면 알리고
대체 인물을 자동 생성하지 않는다」).

**단건과 배치 둘 다** 막았다 — 한쪽만 막으면 다른 쪽으로 샌다. 배치는 여러 장을
한 번에 만드는 자리라 조용히 넘어가면 값이 그만큼 나간다.

**각도 하나가 없다고 막지는 않는다.** 캐릭터가 「뒤」를 안 가진 것은 정상이다.
한 장도 못 불러왔을 때만 막는다.

### A-16 — 잠금이 유일한 방어였다

비동기 결과를 붙일 때 `sectionKeys[itemIndex] === sectionKey` 로 찾았는데, 그
배열은 **생성을 시작할 때의 것**이다(클로저). 도는 동안 순서가 바뀌면 인덱스와
키의 짝이 달라져 **엉뚱한 섹션에 이미지가 박힌다.**

지금은 순서 변경·삭제가 잠겨 있어 그 창이 안 열린다 — 설계도 「현재 UI 잠금은
유지」라 했다. 문제는 **잠금이 유일한 방어**라는 것이다. 잠금을 안 거는 길이
하나 생기면 조용히 되살아나고, 그때 사용자가 보는 것은 「왜 이 섹션에 저 그림이」다.

함수로 빼고 `sectionKeysRef` 를 쓴다. 오래된 배열을 넘기는 것이 **눈에 보이고**,
값으로 잴 수 있다.

### 리뷰가 잡은 것 — 제목에 적힌 경우를 안 막았다

**① A-10 이 「참조 제거」를 안 막았다.** 항목 제목이 「**참조 제거** 뒤 auto만
남아」이고 설계도 「제거/비활성화」라 둘을 함께 적었는데, 나는 **비활성화(토글)만**
걸었다. 「레퍼런스 빼기」 단추를 누르면 `look` 은 `auto` 로 남는다 — **A-10 이
묘사한 증상 그대로다.**

같은 일에 화면이 두 가지로 반응했다 — 토글을 끄면 알림이 뜨는데 빼기를 누르면
아무 말이 없다.

**② 그것을 지켜 줄 시험이 값을 안 쟀다.** 리뷰가 변이로 확인했다 — 되돌린 값을
**버려도 4/4 통과**했다. 까닭이 둘이다: 배선을 소스 문자열로 재고, `setNotice`
가 `return` **앞**에 있어 값과 무관하게 뜬다.

이제 그림체 단추의 **눌린 상태**를 잰다(`data-look` + `aria-pressed`). 같은
파일의 A-11 시험은 처음부터 값을 재서 변이에 걸렸다 — 대조가 분명했다.

**③ A-16 이 절반이었다.** 일괄 경로(`setSections` 업데이터 안)가 여전히 오래된
클로저였다. **긴 쪽이 더 급하다** — 일괄은 묶음을 여러 번, 수 분 동안 돈다.
그리고 그 시험도 처음엔 안 잡혔다(제어문자 하나가 정규식에 섞여 들어갔다).

**동기로 읽는 자리는 클로저가 맞다.** 렌더 중에는 그 값이 지금 값이다. 그래서
`setSections` 업데이터 안만 본다.

**④ 옛 초안이 깨진 짝을 되살렸다.** 이 변경 전에 저장된 「`auto` + 레퍼런스
없음」이 복구 없이 복원된다.

**⑤ 업데이터 안에서 `setNotice` 를 불렀다.** 업데이터는 순수해야 한다. 콜백을
`look` 선언 아래로 옮겨 없앴다.

**⑥ 재시도 중 문구가 뒤집혔다.** `setFailed(false)` 로 시작해서, 다시 불러오기를

순간 거짓말을 한다.**

**⑦ 실패했는데 「캐릭터를 만들어 두면」이라고 했다.** 목록을 못 가져온 것뿐인데

## W1/W8 — 못 만든 분석이 한도를 먹었다 (C-9)

### 아무것도 못 받았는데 한 칸이 사라졌다

분석은 시간당 열 번으로 묶여 있다(`ANALYZE_HOURLY_LIMIT`). 그 수를 세는 곳은
Postgres 함수 `reserve_generation` 인데, `pdp_analyze` 행을 **전부** 세고
`error_code = 'reservation_expired'` 하나만 뺐다.

그래서 키가 안 꽂혀 있거나 공급자가 죽어 있어도 한 칸이 사라진다. 운영자가 키를
빠뜨린 채 배포한 날, 사용자는 열 번 눌러 보고 **한 시간 동안 막힌다.** 받은 것은
없다.

### 가르는 기준은 하나다 — 모델이 일했는가

전부 면제하면 실패를 만들어 내며 한도를 무한히 우회할 수 있다. 설계가 「정책
분리 수정, **남용 제한은 유지**」라 적은 이유다.

- **면제**: `AI_KEY_MISSING` · `AI_KEY_INVALID` · `AI_MODEL_ACCESS_DENIED` ·
  `AI_QUOTA_EXCEEDED` · `AI_PROVIDER_UNAVAILABLE` · `INVALID_IMAGE_PAYLOAD` ·
  `reservation_expired`
- **소비**: `AI_RESPONSE_INVALID` · `PDP_ANALYZE_FAILED` · `TEXT_INPUT_INSUFFICIENT` ·
  성공 · **모르는 코드**

`INVALID_REQUEST` 는 일부러 소비 쪽이다. 요청 모양이 틀린 것은 `readPdpRequest` 가
**예약 전에** 되돌려 보내 행 자체가 안 생긴다. 예약 뒤에 그 코드가 나오는 자리는
**모델이 쓴 설계도를 못 읽은 경우**뿐이라 값은 이미 나간 뒤다.

**모르는 코드는 먹는 쪽으로 둔다.** 새 코드가 생겼을 때 조용히 우회로가 되는
것보다, 한 번 더 기다리는 쪽이 낫다.

### 장애에 이름이 없어서 면제할 수가 없었다

연결 실패·502·과부하가 전부 `PDP_ANALYZE_FAILED` 로 떨어졌다. 그 통은 **우리 쪽
버그도 함께 담는 통**이라 통째로 면제하면 모델 값을 다 쓰고 터진 경우까지
공짜가 된다. 그래서 `AI_PROVIDER_UNAVAILABLE`(503)을 새로 만들었다.

라우트의 바깥 catch 도 고쳤다. `"invalid_request"` 한 줄로 닫고 있었는데, 거기
오는 것은 요청 모양 문제가 아니라 키가 없거나 레퍼런스를 자르다 터진 경우다.

### 천장은 둘, 문구는 하나, reason 은 둘

- **한도**(기본 10/시간): 면제 목록을 빼고 센다
- **남용 천장**(한도의 열 배 = 100/시간): 면제 여부와 무관하게 **모든 시도**를 센다

사용자가 할 일은 어느 쪽이든 「잠시 후 다시」로 같으니 문구는 하나로 뒀다. 다만
reason 은 갈랐다(`analysis_rate_limit` / `analysis_abuse_limit`) — 한도를 올려야
하는 상황과 남용을 봐야 하는 상황은 할 일이 정반대인데, reason 까지 같으면
운영에서 구분할 길이 없다.

### 면제 목록이 두 곳에 있다

코드(`pdp.analysis-quota.ts`)와 SQL(`v_exempt_codes`). 한쪽만 고치면 한도가
뚫리거나 멀쩡한 사용자가 한 시간을 기다린다. 이 저장소는 같은 일을 이미 겪었다
— 작업 종류 목록이 세 곳에 있었고 2026-09-08 에 한 곳만 넓혀 예약이 통째로
거절됐다. `analysis-quota-migration.test.ts` 가 두 벌을 글자 단위로 맞댄다.

돈이 오가는 함수를 통째로 다시 쓰는 마이그레이션이라, 팀 한도·동시 생성 제한·
월 한도·화이트리스트·`max_reserve_units()` 가 그대로 남아 있는지도 같은 시험이
지킨다.

### 내가 깨뜨린 시험 — 선택자가 파일 하나를 골랐다

`ad-cost.test.ts` 3건이 빨개졌다. 「`ad_export` 가 적힌 최신 마이그레이션 파일
**하나**」를 골라 그 안에 check 제약·예약 함수·단가가 다 있는지 봤는데, 예약
함수를 다시 정의하는 파일은 화이트리스트를 그대로 옮겨 적으므로 내 파일이
골라졌다.

지키려던 것은 「한 파일에 다 있다」가 아니라 **「지금 실제로 걸려 있는 정의들이
서로 안 어긋난다」**이다. **각 정의별 최신 파일**을 찾도록 고쳤다 — 오히려
가드가 세졌다.

### 리뷰가 잡은 것 — 매처 두 개가 느슨하거나 죽어 있었다

**① 숫자 정규식이 죽어 있었다(CRITICAL).** `\b(502|503|504)\b` 라고 적었는데
파일에 박힌 것은 **리터럴 백스페이스**였다. 「백스페이스 문자를 찾아라」가 되어
**절대 참이 되지 않는다.** 그 줄을 통째로 지워도 22건이 다 통과했다 — 내가 쓴
다섯 사례가 전부 낱말 절(`service unavailable`·`bad gateway`·`overloaded`)로도
걸렸기 때문이다. **숫자 절에 걸리는 사례가 0건이었다.**

## W8 — 레퍼런스를 올리는 문에 문지기가 없었다 (C-7 앞부분 · C-10-c)

### `await req.json()` 한 줄이 전부였다

`/api/pdp/style-references` 는 본문을 끝까지 읽고, base64 를 그대로 창고에
올렸다. 용량 상한도 없고 그림인지 보는 눈도 없다. 딱지가 `image/png` 면 글자
몇 개라도 PNG 로 저장돼 목록에 깨진 칸으로 남았다.

더 나쁜 것은 크기다. **16383×16383 단색 PNG 는 수백 KB 로 눌린다.** 펼치면
1GB 가 넘는다. 작은 파일 한 장으로 서버를 넘어뜨릴 수 있었다.

삭제는 빈 본문·잘못된 id 에 500 을 돌려주고, **남의 것을 지우라고 해도 성공**
이라고 답했다.

### 세 가지를 갈라 답한다 (C-10-c)

- 형식 오류(빈 본문 · id 없음 · UUID 아님) → **400**. 표에 물어볼 것도 없다
- 있지만 내 것이 아님 → **404**
- 없음(한 번도 없었거나 이미 지움) → **200, `deleted: false`**

마지막이 멱등 삭제 정책이다. 사용자가 원한 상태가 이미 이루어져 있으므로
오류가 아니다.

**순서가 중요하다.** 먼저 내 범위에서 지우고, 지울 것이 없었을 때만 주인을
묻는다. 주인을 먼저 묻던 판은 정상 경로에 왕복이 하나 더 들고, 무엇보다 **모든
삭제가 남의 행 존재 여부를 묻는 길**을 열어 두었다.

### 숫자를 두 번 틀렸다

**① 픽셀 상한 12MP.** `image-encoding.ts` 에 실측이 있어 그대로 가져왔는데,
그 값은 **무손실 재인코딩**이 그림 전체를 메모리에 올리기 때문에 나온 수다.
이 길은 그 인코딩을 안 탄다. 무엇보다 **상세페이지 레퍼런스가 1080×15000
(16.2MP)** 이라 이 기능의 주 사용 사례가 통째로 막힌다. 직접 재서 40MP 로
바꿨다 — 39.7MP 에서 문지기 0ms, 조각내기 88ms·RSS +1MB, 사본 72ms·+1MB.

**② 본문 상한 8MiB.** 지어낸 수였다. 설계 §12 가 「기존 20MiB 를 출발값으로」
라고 정해 둔 것을 되돌려 썼다.

두 상한 모두 **화면이 먼저 말한다.** 전에는 413 을 받고 나서야 얼마까지
되는지 알았다. 화면과 서버가 상수 하나를 함께 읽는다(설계 §12 「정책 상수와
UI 에서 일치」).

### 리뷰가 잡은 것 — 재는 줄이 죽어 있었다

**① 손으로 세는 줄에 영영 닿지 않았다(HIGH).** `limitInputPixels` 를 걸고 그
아래에 「라이브러리를 믿지 않고 우리가 센다」는 줄을 뒀는데, `metadata()` 가
머리말만 보고 **먼저 던진다.** 그래서 413 을 정하는 유일한 근거가 libvips 의
영어 오류 문구(`"exceeds pixel limit"`)였다. 문구가 바뀌거나 로캘이 끼면 413 이
조용히 400 으로 바뀐다. 그 세 줄을 지워도 14건이 다 통과했다.

직접 재서 확인했다 — 8000×5001 은 `limit=40MP` 에서 던지고 `limit=false` 에서
통과한다. **상한을 끄고 우리 숫자로만 판정**하도록 고쳤다. 머리말만 읽으므로
(0ms) 꺼도 안전하다. 이제 그 줄을 지우면 시험이 빨개진다.

**② 새 서버 함수 둘이 시험 0건(MEDIUM).** 라우트 시험이 저장소 모듈을 통째로
흉내 내서, 「멱등이다」의 실제 근거인 `Boolean(row)` 가 무방비였다. `deleted` 를
늘 참으로 바꿔도, 주인 조회에서 `.eq("id", id)` 를 빼도 전부 통과했다.
`style-reference-wiring.test.ts` 에 실제 구현을 재는 시험 일곱을 더했다.

**③ 40MP 의 근거 서술이 인용한 원문과 반대였다(MEDIUM).** `GRID_MAX_PIXELS` 의
주석은 「**낯선 바이트를 받는 문이 아니라서** 넉넉하다」고 적혀 있는데, 새
문지기는 스스로를 바로 그 문이라 선언하면서 그 상수를 근거로 삼았다. 숫자는

**약속은 내림한 쪽으로 한다** — 「20MB 까지 된다」고 해 놓고 20MB 가 막히는
것이 그 반대보다 훨씬 나쁘다.

**⑤ 흉내가 실제에 없는 칸을 만들어 냈다(MEDIUM).** 라우트 시험의 mock 이

## W3/W8 — 레퍼런스 분석이 장부 밖에 있었다 (C-4-b · C-7 뒷부분)

### 돈은 나가는데 아무 데도 안 적혔다

레퍼런스를 올리면 그림을 읽어 서술을 만든다(글 모델 한 번). 그 호출이 계량기
밖이라 **원가 집계에서 $0** 이었다. 예약도 없으니 횟수 제한도 없다 — 같은
그림을 천 번 올려도 막는 것이 아무것도 없었다.

### 칸을 나눴다

설계는 「현재 시간당 분석 제한 설정을 **재사용**」하라고 했다. 그런데 상세페이지
분석 칸(10회/시간)을 그대로 쓰면 **레퍼런스를 스무 장 정리하다가 그날 기획이
막힌다.** 하는 일도, 값의 크기도 다르다.

그래서 세는 방식(`reserve_generation`)만 같이 쓰고 작업 종류를 나눴다
(`reference_analyze`, 60회/시간). 60은 `MAX_USER_REFERENCES`(40, 글 모델이 한
번에 보는 수)에서 나왔다 — 목록을 통째로 새로 채우는 일이 한 시간 안에 한
번은 되어야 한다.

SQL 에서는 시간당 세는 갈래를 `operation = p_operation` 으로 바꿨다. 리터럴
하나를 지웠을 뿐이라 `pdp_analyze` 의 동작은 그대로다.

### 예약이 요청 식별자를 요구한다

화면 세 곳에 `x-idempotency-key` 를 더했다(`SectionGallery` 는 `apiJson` 을
거쳐 이미 붙는다). **이 저장소는 같은 사고를 2026-09-08 에 겪었다** — 예약
쪽만 넓히고 부르는 쪽을 빠뜨려 이미지 만들기가 100% 거절됐다.

### 200개 뒤를 숨기지 않는다

`count: "exact"` 로 **가진 수**를 세고 `?limit=&offset=` 으로 쪽을 넘긴다.
관리 화면에 「더 보기」, 배지는 `보이는 수 / 전체`, 라이브러리는 끝까지
따라가고(20쪽 상한), 고르기 창은 다 안 보여 주고 있으면 말한다.

### 리뷰가 잡은 것 — 고치려던 것의 정반대를 만들었다

**① 기본 쪽 크기가 200 이 아니라 1 이었다(CRITICAL).** `searchParams.get()` 은
없을 때 `null` 이고 `Number(null)` 은 **0** 이다. `?? 200` 이 0 을 「준 값」으로
보아 기본값이 안 먹고, 조이기가 1 로 만들었다. **부르는 화면 셋이 전부
`limit` 을 안 붙인다** — 목록이 통째로 한 장이 되고, 「더 보기」를 239번 눌러야
240장을 본다. 「200개 뒤를 숨기지 않겠다」던 변경이 **1개 뒤를 숨겼다.**
고치기 전보다 나쁘다.

시험 87건이 전부 통과했다. **쿼리를 만드는 쪽과 읽는 쪽 사이를 아무도 안
쟀기 때문이다** — 화면 시험은 `fetch` 를 통째로 흉내 내서 `limit` 을 안 보고,
저장소 시험은 인자 없이 불러 기본값 경로만 봤다. 라우트 `GET` 을 부르는 시험이
한 건도 없었다. 그 자리를 채웠다.

**② 모델이 한 번도 안 돌았는데 한 칸을 먹었다(MEDIUM).** 열쇠가 없으면
`analyzeStyleImage` 는 모델을 안 부르고 빈 서술을 준다. 그대로 성공으로 닫으면
운영자가 키를 빠뜨린 날 사용자가 60칸을 전부 잃고도 서술을 하나도 못 받는다 —
**C-9 가 막으려던 바로 그 상황**이다.

`finalize_generation` 은 성공으로 닫으면서 오류 코드를 남길 수 없다. 그래서
모델이 안 돈 경우는 「분석 실패」로 적는다. 레퍼런스는 저장됐고 크레딧은 0 이라
사용자가 잃는 것은 없고 응답은 200 이다. **계량기가 안 감싼 경우는 먹는 쪽으로
둔다** — 「안 돌았다」와 「못 쟀다」는 다르다.

**③ 지운 뒤 숫자가 거짓말을 했다(MEDIUM).** 배지가 「보이는 수 / 가진 수」인데
삭제가 보이는 수만 줄였다. 3장 중 1장을 지우면 「2 / 3장」이 되어 **1장이
어딘가 숨어 있다**고 말한다. 고치기 전 배지는 이 경우 맞았으니 회귀다. 겸사
**응답을 안 읽고 목록에서 치우던 것**도 고쳤다 — 서버가 거절해도 화면에서는
사라지고 새로고침하면 되살아났다.

**④ 못 불러온 것을 「0장」이라고 했다(MEDIUM).** 이제 화면이 수를 단언하므로
같은 모양으로 두면 레퍼런스가 사라진 것처럼 보인다. 저장소가 실패를 구분해
올리고 라우트가 500 으로 답한다.

## W5/W8 — 다시 물으면 될 일을 12초 태우고 포기했다 (D-3 · D-5 · D-6)

### 잘린 답 하나가 12초를 먹었다 (D-5)

모델이 답을 끝까지 못 쓰면 닫히지 않은 JSON 이 온다. 그때 쓰던 추출기는
**끝에서부터 한 글자씩 줄여 가며 매번 `JSON.parse` 를 다시 돌렸다.** 길이의
제곱이다.

실측(2026-09-20, 닫히지 않은 설계도):

| 길이 | 걸린 시간 |
|---|---|
| 10KB | 125ms |
| 25KB | 627ms |
| 50KB | 2,274ms |
| 100KB | **12,100ms** |

기획 응답 상한이 32,768토큰이라 100KB 짜리 잘린 답은 드물지 않다. 그 12초는
**아무것도 못 찾고** 끝나고, 그동안 Node 는 한 요청에 묶여 다른 사용자도 못
받는다. **멀쩡한 답은 첫 시도에 통과하니 아무도 몰랐다** — 가장 급할 때만
터진다.

한 번만 훑는 판으로 바꿨다. 괄호 깊이가 0 으로 돌아오는 자리가 첫 온전한 값의
끝이고, 거기서 한 번만 읽어 본다. **글자 안의 괄호는 세지 않는다** —
`{"a":"}"}` 에서 한 글자 일찍 끝내면 못 읽는다.

### 다시 물어야 할 때 안 물었다 (D-3 · D-6)

재시도 장치는 있었다. **그런데 아무것도 그 장치에 닿지 못했다.**

**① 호출 층(D-6).** 재시도 여부를 `error.message` 로 정했다 — 「JSON」·
「Unexpected token」 같은 엔진 글자를 찾는다. 그런데 설계도 파싱은 그 오류를
잡아 **한국어 문장으로 바꿔** 던진다(「AI 응답을 해석하지 못했습니다.」).
찾는 글자가 사라졌으니 **한 번도 안 걸렸다.**

**② 라우트 층(D-3).** 「`INVALID_REQUEST` 이고 detail 에 section 이 있으면」
다시 부르게 돼 있었다. 그런데 분석 경로에는 그 코드를 던지는 자리가 없다 —
섹션이 비면 `AI_RESPONSE_INVALID` 다. 코드가 안 맞아 **역시 한 번도 안 걸렸다.**

「있는 줄 알았던 그물이 두 겹 다 없었다.」

### 판단을 한 곳에 모았다

`pdp.retry-policy.ts` 가 **코드로** 정한다. 지금 다시 묻는 것은
`AI_RESPONSE_INVALID` 하나다.

- 공급자 장애·사용량 초과는 여기 없다. 그쪽은 **기다렸다** 부르는 것이 맞고,
  그 기다림은 호출 층의 backoff 가 따로 한다
- **모르는 코드는 안 묻는다.** 다시 부르는 것은 공짜가 아니다. 한도
  면제(`pdp.analysis-quota`)가 모르는 것을 「먹는 쪽」에 두는 것과 같은
  이유, 반대 방향이다

빈 설계도 판정을 **파싱 자리로 옮겼다.** 재시도 바깥에 있어서 빈 답이 그대로
끝났기 때문이다. 이제 같은 코드로 다시 묻는다.

라우트의 죽은 재시도 고리는 **걷어냈다.** 코어가 두 번까지 다시 묻는데 라우트가
그 위에 또 걸면 한 요청에 모델을 여섯 번 부른다. 그 일이 다시 일어나지 않도록
「라우트는 한 번만 부른다」를 시험으로 잠갔다.

**① 재작성이 실패하면 멀쩡한 설계도까지 버렸다(HIGH).** 빈 섹션 판정을 파싱

감싸지 않는다 — **그림 만드는 호출도** 감싸고, `fal.ts` 가 「200 인데 몸통이
JSON 이 아니다」에 똑같이 `AI_RESPONSE_INVALID` 를 던진다. 코드로 재시도를 열자
그 길이 1회에서 3회가 됐다. **fal 은 200 을 줬으니 세 장은 이미 과금**됐고,
성공한 장수만 세는 장부에는 0장으로 남는다 — C-9 가 없애려던 그 모양이다.

재시도 정책을 층별로 갈랐다(`retriableByCode`, 기본 꺼짐, 설계도 호출만 켠다).

**시험이 왜 못 잡았나**: 분석 경로 시험이 전부 `skipFirstImage: true` 라 그림
호출을 한 번도 안 지났다.

비율로 재던 성능 시험은 지웠다. 리뷰가 300회 돌려 보니 놀고 있는 기계에서도

## W1/W3 — 화면은 목록인데 서버는 아무 글자나 받았다 (D-8)

### 설계가 예로 든 두 값은 이미 묶여 있었다

「country/age 등 enum 경계 부족」이라 적혀 있는데, `modelCountry`·`modelAgeRange`
는 `options` 스키마에서 이미 `z.enum` 이다. W1 의 `readPdpRequest` 작업이
들어오면서 닫힌 것으로 보인다. **남아 있던 것은 「등」 쪽이었다.**

### 원하는 톤

화면은 칩 일곱 개다. 사용자가 고를 수 있는 것은 그 일곱뿐인데 서버는
`z.string()` 이었고, **그 값이 이미지 프롬프트에 그대로 실린다** —
`Overall tone: ${desiredTone}.`

즉 화면을 거치지 않은 요청이 **프롬프트에 아무 문장이나 심을 수 있었다.**
길이 제한도 없었다. 같은 화면의 다른 칩들(비율·그림체·스타일·국가·나이·
출력 모드)은 전부 `z.enum` 인데 이 칸만 빠져 있었다.

목록을 코어로 옮겨 한 벌로 뒀다(`IMAGE_TONES`). 두 벌이면 **화면이 보여 주는
값을 서버가 거절하는 날**이 온다.

### 이미지 연출 요청

바로 옆 칸인 「구성·문구 요청」은 화면과 서버가 같은 상한을 쓰는데, 이 칸만
**양쪽 다 없었다.** 게다가 이 값은 프롬프트 **맨 앞과 맨 뒤에 두 번** 들어간다.

옆 칸과 같은 상한(`MAX_STRATEGY_LENGTH`)을 양쪽에 걸었다.

### 상한을 새로 거는 자리는 옛 초안을 만난다

상한이 없던 시절에 저장된 초안이 복원되면, 화면 칸은 넘친 값을 담은 채 멀쩡해
보이고 **만들기를 누를 때 설명 없는 400** 이 난다. **U-08 에서 내가 똑같이
낸 회귀다.** 그때 얻은 규칙을 그대로 적용했다 — 넘친 칸을 먼저 짚어 준다
(`overLimitFields` 가 긴 지시 두 칸도 본다).

### 시험이 변이를 놓쳤다

처음에는 화면 소스에 `IMAGE_TONES` 라는 **글자가 있는지**만 봤다. 목록을 손으로
다시 적어도 import 줄이 남아 있으면 그대로 통과했다(변이 S3 가 살아남았다).
**값으로 재도록** 고쳤다.

### 리뷰가 잡은 것 — 문지기가 반대쪽 문에 걸렸다 (D-8 후속)

**`userInstruction` 은 기획 요청에 아예 안 실린다.** `buildAnalyzeRequest` 가
싣는 것은 `planInstruction`·`additionalInfo`·`sellerBrief`·`desiredTone` 이고,
「이미지 연출 요청」은 `buildPageWire` 를 거쳐 **만들기 요청에만** 간다.

그래서 내가 건 문지기는 정확히 어긋나 있었다.

- **잘못 막았다**: 그 칸 하나가 넘치면 기획이 중단되고 화면이 「올리기」로
  되돌아갔다. 그 요청은 그 칸을 싣지도 않는다
- **못 막았다**: 정작 그 칸을 싣는 만들기·일괄은 그대로 서버까지 가서
  「요청이 올바르지 않습니다」 한 줄로 400 이 났다. **그 화면에는 그 칸을
  고칠 입력란조차 없다** — 사용자는 어느 칸인지도 모르고 그 자리에서 풀 수도
  없다

기획 쪽 문지기는 기획이 싣는 칸만 보게 좁혔고, 만들기 쪽에 따로 문지기를 뒀다.
**어디서 고치는지까지 말한다** — 「기획 화면에서 줄인 뒤 다시 눌러 주세요」.

돈은 안 샜다. `readPdpRequest` 가 `reserveAiUsage` 앞이라 크레딧은 예약 전에
되돌아간다. 손해는 과금이 아니라 막다른 골목이었다.

### 남은 것 (리뷰가 짚은 후속)

- **첨부 지시 네 칸이 무경계다.** `intents.anchor·person·style` 에 `.max()` 가
  없고, `styleReference.intent`·`description` 은 스키마에 **선언조차 없다**
  (`image` 가 `.passthrough()`). 화면(`AttachmentIntentField`)도 안 막는다.
  이 값들은 `pdp.reference-policy.ts` 에서 **그 자리의 고정 규칙 문구를 통째로
  밀어내고** 대신 앉는다 — `userInstruction` 보다 힘이 세다. **D-8 의 「등」에
  이쪽이 더 어울린다.** 같은 U-08 함정(옛 초안)이 있으므로 `overLimitFields`
  와 함께 다뤄야 한다
- **만들기 쪽 문지기에 시험이 없다.** 이번에 넣은 `lengthBlockedMessage` 는
  변이로 확인하지 않았다. 다음 차례에 `react-test-renderer` 로 실제 렌더해
  값으로 재야 한다
- **`InputLengthHint` 도 아직 소스 문자열 대조다.** 리뷰 실측으로 변이 3종이
  살아남는다 — 속성을 같은 글자의 주석으로 바꾸기 · 힌트 삭제 · 힌트의
  `limit` 바꾸기

## 이번 세션이 만든 빚 넷을 갚았다 (D-8 마무리)

### ① 만들기 쪽 문지기에 시험이 없었다

구현만 하고 검증을 못 붙인 채 커밋했던 자리다. 판정을 순수 함수로 빼고
(`app/create/image-request-length.ts`) 값으로 재는 시험 12건을 붙였다.

시나리오 화면(`PdpEditor`)은 html2canvas·JSZip·react-rnd 를 들이므로 이
저장소(jsdom 없음)에서는 못 띄운다. 그래서 **두 입구가 그 문을 지나는지**는
덩이로 잘라서 본다 — 문지기가 `apiJson` **앞에** 있는지까지 잰다. 글자 두 개를
따로 찾으면 순서가 뒤바뀌어도 통과한다.

### ② 첨부 지시 네 칸이 무경계였다 — D-8 의 진짜 「등」

「이 그림을 어떻게 쓸까요」는 제품·인물·디자인 세 자리에 붙고, 디자인
레퍼런스에는 `styleReference.intent` 로 한 번 더 실린다. **넷 다 상한이
없었고**, `styleReference.intent`·`description` 은 스키마에 **선언조차
없었다**(`image` 가 `.passthrough()`).

그런데 이 값은 `userInstruction` 보다 **힘이 세다.** 사용자가 적으면
`pdp.reference-policy` 가 **그 자리의 고정 규칙 문구를 통째로 빼고** 대신
앉힌다 — 「우선순위 한 줄로는 못 이긴다」는 판단 때문이다. 즉 화면을 거치지
않은 요청이 **역할 규칙을 지우고 아무 문장이나** 그 자리에 넣을 수 있었다.

`ATTACHMENT_INTENT_MAX_LENGTH = 500` 으로 묶었다. **긴 지시 칸(2000)보다
짧다** — 적힌 만큼 규칙이 사라지기 때문이다. 칸의 예시가 「뚜껑 색은 그대로
두고 각도만 바꿔 주세요」 한 줄이라 배경 칸과 같은 500이면 넉넉하다.

상한이 칸마다 달라져서 `overLimitFields` 의 표에 `limit` 을 실었다. 두 문지기가
**각자 제 요청이 싣는 칸만** 본다 — 기획은 `styleIntent` 하나(그쪽만 싣는다),
만들기는 넷 전부.

### ③ InputLengthHint 시험이 소스 문자열 대조였다

리뷰가 실증한 변이 셋이 살아남았다 — 속성을 **같은 글자의 주석**으로 바꾸기,
안내 **삭제**, `limit` 을 **다른 상수**로 바꾸기. 셋 다 화면에서는 안내가
사라지거나 틀린 수를 말하는데 시험은 초록이었다.

**띄워서 값으로 재도록** 바꿨다(`length-hint-wiring.test.tsx`). 넘친 옛 초안을
복원해 「N자를 줄여」가 뜨는지 본다. 변이 5종이 모두 잡힌다.

### ④ TONE_OPTIONS 의 타입이 넓었다

`string[]` 로 못 박아 칩 비교(`tone === "AI 자동 추천"`)의 오타를 tsc 가 못
잡았다. `as const` 로 좁히고, 손으로 적은 문자열을 `TONE_AUTO_LABEL` 로 바꿨다.
목록을 코어에 한 벌로 둔 이 작업의 취지에 어긋나던 마지막 한 줄이다.

## W1/W4 — 한 문장이 세 상황을 덮고 있었다 (E-6-2-a · E-6-2-b)

### 「새로고침 후 다시 시도해 주세요」가 거짓말이었다 (E-6-2-b)

화면은 같은 섹션을 다시 만들 때 **같은 요청 식별자**를 쓴다
(`PdpEditor` 의 `retryRequestKeysRef`). 두 번 과금되지 않게 하려는 장치다.

그 식별자로 다시 오면 `reserve_generation` 은 무조건 `duplicate_request` 를
주고, 앱은 한 문장으로 답했다. 그 한 문장이 **서로 다른 세 상황**을 덮었다.

| 표의 상태 | 실제로 일어난 일 | 사용자가 할 일 |
|---|---|---|
| `reserved` | 아직 돌고 있다(두 번 눌렀다) | **기다린다** |
| `succeeded` | 끝났는데 결과가 화면에 못 왔다 | 다시 만들면 **값이 또 나간다** |
| `failed` | 실패로 끝났다 | 새로 만들면 된다 |

**「새로고침」은 셋 중 무엇도 풀지 못한다.** 특히 가운뎃줄이 나쁘다 —
「다시 시도」라고 하면 사용자는 **한 번 더 낸다.**

설계가 적은 「**header 존재 = 결과 복구 아님**」이 정확히 이것이다. 확인해
보니 단건 생성은 결과를 되찾는 길이 **아예 없다** — 일괄만 job 을 남기고
(`images/batch/route.ts:134`), 그 job 도 `PDP_JOBS_ENABLED` 가 꺼져 있다.

마이그레이션은 안 건드렸다. `generation_events` 의 그 행을 한 번 더 읽으면
상태를 알 수 있다. **중복일 때만** 읽는다 — 한도에 걸린 것은 표를 안 읽어도
할 말이 정해져 있고, 모든 거절에 왕복을 걸면 가장 자주 나는 거절이 제일
느려진다.

모르는 경우에는 **단정하지 않는다.** 표를 못 읽었으면 「잠시 뒤에도 결과가
안 보이면 새로 만들어 주세요」다 — 「새로고침하면 된다」고 하지 않는다.

### 안 닫힌 예약은 어떻게 풀리는가 (E-6-2-a)

「실패해도 0장으로 확정하면 된다」는 말은 **정산이 돌았을 때만** 참이다.
정산이 아예 안 도는 길이 있다 — 프로세스가 죽거나, 플랫폼이 시간 초과로
요청을 끊거나, 정산 RPC 자체가 흔들리는 경우다. 그때 행은 `reserved` 로 남고
**그 사람의 크레딧을 묶는다.**

푸는 것은 앱이 아니라 SQL 이다. 따로 도는 청소기가 없고, **다음 사람이 예약을
거는 그 순간에** 묵은 자리를 치운다. 그래서 그 한 줄이 사라지면 아무도 안
치운다. 그런데 **아무도 그것을 재지 않았다.**

계약으로 잠갔다 — 치우는 일이 한도 판정보다 **먼저**인지, 예약분은 만료 전
것만 세는지, 월 한도는 성공한 것만 세는지, 정산이 예약한 자리에만 쓰는지,
실패에 이유가 반드시 남는지(그 이유가 C-9 의 한도 판정을 가른다).

### 검증

- 변이 5종이 모두 잡힌다 — 옛 한 문장으로 되돌림 · 끝난 요청도 기다리라고 함 ·

## W1/W2/W8 — 재 보니 63MB, 약속은 지키는 코드가 없었다 (E-6-3-a · E-6-3-b)

### 대표 최대 초안을 쟀다 (E-6-3-a)

설계가 「**대표 최대 초안으로 측정**」하라고 적은 그대로 재 봤다
(2026-09-21, 섹션 10장 · 원본 2.5MB · 인물 2.0MB · 레퍼런스 4.0MB · 만든 그림
1.6MB×10).

| 초안 수 | 크기 |
|---|---|
| 1개 | **63.4MB** |
| 5개 | 316.8MB |
| 10개 | 633.6MB |
| 20개 | **1,267MB** |

거의 전부가 그림이다(63.2MB). 그중 **21.3MB 는 중복**이다 — `editorState` 가
섹션 그림을 한 벌 더 담는다. 스무 개면 1.27GB 라, 브라우저 저장 한도에 닿는
것이 드문 일이 아니다.

**기존 사본은 안 잃는다**는 것도 확인했다. 저장은 `store.put` 한 번이라 실패
하면 IndexedDB 가 트랜잭션을 통째로 취소한다. 잃는 것은 이번 변경분뿐이다.

문제는 **그때 하는 말**이었다 — 「작업을 저장하지 못했습니다」 한 줄. 무엇을
하면 되는지가 없고, 30초마다 자동 저장이 같은 실패를 되풀이한다. 용량이 찬
경우를 갈라, **무엇을 하면 되는지와 무엇이 안 날아갔는지**를 함께 말한다.

### 지키는 코드가 없는 약속 (E-6-3-b)

화면은 「저장한 지 30일이 지난 작업은 자동으로 삭제됩니다」라고 말한다. 실제로
걸려 있다(`PdpMakerClient:1186`). 그런데 청소를 부르는 줄이 이랬다.

```ts
if (!documentV3Enabled) await purgeExpiredPdpDrafts(...)
```

**새 저장소(v3)를 켜면 청소가 아예 안 돈다.** 그리고 `document-store.ts` 에는
청소 함수가 **없었다.** 이관하면서 청소만 뒤에 남은 것이다 — 설계가 「이관 순서
검증」이라 적은 자리가 정확히 여기다.

지금은 `PDP_DOCUMENT_V3` 가 꺼져 있어 겉으로 드러나지 않는다. **켜는 날
약속이 거짓이 된다.**

옛 것과 같은 판단으로 청소를 새로 만들었다 — 기준은 `updatedAt`, 열어 둔
작업은 남기고, 실패해도 조용히 넘어간다. 그리고 **둘 다 부른다**: 새 저장소를
켜도 이관 전에 만든 옛 초안이 남아 있을 수 있고, 둘 다 그 약속의 대상이다.

### 검증

- 변이 5종이 모두 잡힌다 — v3 일 때 청소 안 함 · 열어 둔 작업도 지움 ·
  청소가 아무것도 안 지움 · 용량 초과를 못 알아봄 · 화면이 문구를 안 씀
- 시험이 **시계를 되돌려** 옛 기록을 만든다. `savePdpDocument` 가 저장할 때마다
  `updatedAt` 을 지금으로 찍기 때문이다 — 그것을 모르고 만든 첫 판은 빨개졌다
- 웹 3,262 통과 / 6 skip. 타입 0건

### 남은 것

**`editorState` 의 그림 중복(21MB)은 안 건드렸다.** 초안 하나의 3분의 1이라
줄일 값이 크지만, 그 값을 읽는 자리가 여럿이라 따로 다뤄야 한다. 용량이 실제로
문제가 되면 여기가 첫 번째 후보다.

## W7 — 글로 시작하면 무엇을 팔든 무형 취급이었다 (K-08)

### 축이 둘인데 하나로 붙어 있었다

글 입력 경로의 프롬프트가 이렇게 못 박혀 있었다.

- 「너는 **무형 상품**(강의·코칭·구독·소프트웨어·커뮤니티)의 판매 기획자다」
- 「**무형 상품이다.** 만질 수 있는 제품 사진을 전제하지 마라.」

그리고 모델이 고르던 `offeringKind` 의 값도 **전부 무형**이었다. 실물이 들어갈
칸이 아예 없다.

그래서 **사진이 없을 뿐인 실물**을 글로 설명한 사람은, 「만질 수 있는 제품을
전제하지 마라」는 지시를 받은 기획을 돌려받는다 — 제품 자리에 은유가 들어간다.
사진 없는 실물은 드문 경우가 아니라 **가장 흔한 경우**다.

설계 §9.1: 「이미지/텍스트는 **입력 방식**이다. 실물/서비스/디지털/기타와
판매/문의/홍보 목적은 **별도로 받는다.**」

사진으로 시작하느냐 글로 시작하느냐는 **입력 방식**이고, 파는 것이 만질 수
있느냐는 **상품 종류**다. 둘을 붙여 두면 「사진이 없다 = 무형이다」가 된다.

### 모를 때는 모른다고 둔다

기본값을 무형으로도 실물로도 두지 않았다. 어느 쪽으로 단정해도 절반은 틀리고,
틀린 쪽은 페이지 전체가 어긋난다. 안 고르면 프롬프트가 **「사용자가 쓴 말에서
읽히는 대로」** 라고 말한다.

목적(판매/문의/홍보)도 따로 받는다. 상세페이지라고 다 파는 것은 아닌데,
문의를 받으려는 페이지에 「지금 구매」를 깔면 읽는 사람이 할 일을 못 찾는다.

### 본보기도 고쳤다

입력 칸의 예시 셋이 **전부 무형**이었다(요가 클래스·세무 상담·견적서 앱).
칸을 만들어 두고 본보기로 반대 신호를 보내면 소용이 없다 — 실물을 파는 사람은
이 길이 자기 것이 아니라고 읽는다. 천연 비누를 하나 넣었다.

### 시험이 두 번 구멍을 드러냈다

**① 요청에서 프롬프트까지의 배선을 아무도 안 쟀다.** 규칙도 맞고 프롬프트
조립도 맞는데 그 사이가 끊겨 있으면 소용이 없다. 변이로 확인했다 —
`productKind` 를 브리프에 안 싣게 바꿔도 시험이 전부 통과했다. `planFromText`
를 실제로 돌려 프롬프트를 받아 적는 시험으로 메웠다.

**② 화면이 값을 보내는지도 안 쟀다.** 두 줄을 빼도 다 통과했다. 덩이로 잘라서
본다.

### 검증

- 변이 8종이 모두 잡힌다 — 고정 지시 되살림 · 실물도 무형 규칙으로 ·
  고른 값을 브리프에 안 싣기 · 화면이 값을 안 보냄 · 칩을 지움 ·
  브리프 프롬프트에 종류 안 넘김 (뒤의 셋은 **구멍을 메운 뒤에야** 잡혔다)
- pdp-core 1,028 통과. 웹 3,273 통과 / 6 skip. 양쪽 타입 0건

### 남은 것

`offeringKind`(모델이 글에서 고르는 세부 유형)는 그대로 뒀다. 값 목록이 전부
무형이라 실물을 고르면 `other` 로 떨어지는데, 그 값을 쓰는 곳이
`pdp.product-anchor` 하나뿐이고 거기서는 `productKind` 가 더 정확한 근거다.
정리하려면 그 자리를 함께 봐야 한다.

## W8 — 조립기는 맞는데 그것이 나가는지는 아무도 안 봤다 (X-05 · X-08)

### 반대쪽을 재야 했다 (X-05)

D-10 에서 호출 그래프를 훑어 보니 **지울 것이 없었다** — 죽은 줄 알았던
조립기가 다 살아 있었다. 그러니 남은 일은 반대쪽이다: 시험이 **실제로 나가는
것**을 재고 있는가.

`buildAnalyzePrompt` 를 직접 불러 문자열을 보는 시험이 **일곱**이나 있다.
그런데 그것이 **그대로 나가는지**는 아무도 안 봤다 — 조립기는 맞는데 서비스가
다른 글을 보내면 그 일곱은 전부 초록이다.

`analyzeProduct` 를 실제로 돌려 모델에 간 것을 받아 적는 시험을 뒀다. 규칙이
실려 나가는지, **참조가 제 차례로 가는지**(제품이 첫 그림이어야 「이 제품」이
어긋나지 않는다), 안 붙인 참조가 안 새는지를 잰다.

### 다시 세지 않고, 되돌아가면 빨개지게 (X-08)

셋 다 이미 고쳐져 있다. 미해결로 다시 세는 대신 **회귀를 막는 자물쇠**로 뒀다.

| 과거 수정 | 잠근 것 |
|---|---|
| style guide 중복 | 모든 섹션이 **같은 하나**의 공용 디자인을 단다 |
| key visual 모델 | 고른 모델로 가고, 안 고르면 기본 모델이다 |
| 참조 크기 체인 | 등록 경로도 기획과 **같은 규칙**으로 자른다 |

세 번째가 진짜 구멍이었다. 기획 쪽은 시험이 있었는데(`pdp-analyze-route.test.ts`),
**등록 경로는 흉내가 옵션을 통째로 버려서 아무도 안 쟀다.** 그 자리에서
`shrinkWhole` 을 빼도 모든 시험이 통과했다.

### 시험을 쓰다 배운 것

공용 디자인 fixture 를 **실제와 다른 모양**으로 적었다가 빨개졌다. `palette` 는
배열이고, 아무 칸도 안 차면 `normalizeDesignSystem` 이 통째로 `undefined` 를
돌려준다 — 그러면 `applyDesignSystem` 이 섹션을 그대로 통과시킨다. 진짜 모양을
안 보고 짐작해 적은 대가다.

## W8/W9 — 문서가 실제와 달랐고, 잰 값이 흩어져 있었다 (X-06 · X-09)

### 소개 문서의 네 줄이 다 틀렸다 (X-06)

`README.md` 의 이미지 모델 표가 이랬다.

| GPT Image 2 (기본) | 4 | … |
| Nano Banana Pro | 3 | … |
| Nano Banana | 1 | … |

실제 목록은 **일곱**이고, **기본 모델(`gpt-image-2.5-flare`)이 표에 아예
없었다.** 「기본」이라 적힌 것은 기본이 아니고, 가중치도 한 줄 틀렸다

`docs/landing.md` 가 「모델 가중치는 README 를 보라」고 가리키므로 **이 표가
유일한 출처**다. 틀린 채로 두면 값을 묻는 사람마다 틀린 답을 얻는다.

**시험으로 잠갔다.** 모델은 앞으로도 늘고 준다 — 사람이 표를 손으로 맞추는 한
또 갈린다. 목록과 어긋나면 `pdp.model-doc.test.ts` 가 빨개진다.

주장이다. 안 잰 것도 그 문서에 남겼다(브라우저별 저장 한도, 정확한 토크나이저

## W8 — 고치는 길에는 시험이 한 건도 없었다 (X-03 · X-07)

### 값과 품질이 어긋났던 길인데 (X-03)

`generate.test.ts` 는 있는데 **`edit-section` 시험은 하나도 없었다.** 그런데
이 길에는 이력이 있다 — 옛 직접 호출은 `quality: "low"` 로 보내면서 값은
`max` 기준으로 받았다(F-7-5).

그 뒤 「새로 만들 때와 같은 길(fal)로 고친다」로 바꿨는데, **그 배선이 실제로
도는지는 아무도 안 봤다.** 통로를 넘겨도 옛 길로 떨어지면 같은 어긋남이
되살아나고, 겉으로는 그림이 나오니 아무도 모른다.

`editSection` 을 실제로 돌려 제공자에 간 것을 받아 적는다 — 통로를 주면 그
통로로 가는지, **직접 호출을 안 하는지**, 사용자가 적은 말과 원본이 실리는지,
통로가 없을 때만 옛 길로 떨어지는지.

### 되던 두 가지를 잃지 않게 (X-07)

둘 다 맞게 돌고 있어 「고칠 것」이 아니라 **「잃지 말 것」**이다.

**① 섹션 매핑.** 새 문서는 UUID 로 식별하고 모델이 준 이름은
`sourceSectionId` 에 남긴다. 모델 이름이 겹쳐도 갈라지고, 이미 안정된 id 는
이어받는다 — 다시 매기면 만든 그림이 엉뚱한 섹션에 붙는다.

**② 보는 것과 받는 것.** 스타일 조립기를 화면과 내보내기가 함께 쓴다.

### 주석이 과장하고 있었다

머리말이 「**네 개**는 화면 표시와 내보내기가 함께 쓴다」고 적혀 있었는데,
재 보니 **셋뿐이다.** 도형은 내보내기가 `backgroundColor`·`borderRadius` 를
**직접 적는다**.

지금은 두 곳이 같은 값을 내지만, **한쪽만 고치는 날 조용히 갈린다** — 글
상자에서 막으려던 바로 그 꼴이다. 렌더링 본체라 이번에 안 고쳤고, **사실을
주석과 시험 양쪽에 적었다.** 누가 합치면 그 시험이 빨개지고, 그때 목록에
넣으면 된다.

## W5/W7 — 분석이 실패해도 돈은 나갔다 (F-7-3)

### 지어낸 결과로 유료 생성을 돌렸다

`analyzeSource` 가 **어떤 실패든 잡아서 만들어 낸 결과**를 돌려줬다.

```ts
product_inferred: { category: "업로드 자료 기반 추정", confidence: 0.4 },
page_blueprint: [],                                    // ← 비어 있다
strategy: "원본 자료의 제품컷/USP/근거를 보존하고…",     // ← 일반론
```

그 상태로 생성이 그대로 돌고 **장마다 값이 나간다.** 사용자는 자기 자료를 한
번도 안 읽은 페이지를 받고 그 값을 낸다.

더 나빴던 것은 **아무도 그 사실을 몰랐다**는 점이다. 실패는
`diagnostic_summary` 라는 글에만 남는데, 그 값을 읽어 화면에 띄우는 곳이
**한 군데도 없었다**(2026-09-21 확인).

예약은 생성 **앞**에 있다. 여기서 멈추면 크레딧은 0으로 닫히고 사용자는
아무것도 잃지 않는다. 그래서 던지게 바꿨다.

### 리뷰가 찾은 나머지 절반 — 200 인데 본문이 빈 경우

**터지는 실패만 실패가 아니었다.** 분석이 비는 길은 둘인데 catch 는 던지는
쪽만 잡는다.

```ts
const text = data.output_text || extractOpenAIText(data);  // ""
return parseMaybeJson(text);                               // { summary: "" }
```

`parseMaybeJson` 은 **절대 안 던진다.** `{ summary: "" }` 가 정상 반환으로
catch 를 지나쳐 그대로 생성으로 흐르고, 프롬프트에 `분석 요약: {"summary":""}`
가 박힌 채 장마다 값이 나간다. 설계 §14.5 가 쓴 말 그대로의 「**빈 분석**으로
유료 생성」인데, 그쪽이 안 막혀 있었다.

지어낼 수 있는 상황이 아니다 — 기획 모델은 추론 모델이라 추론 토큰을 다 쓰면
200 에 빈 `output_text` 를 주고, Google 쪽은 안전차단이면 `candidates` 가 빈다.
**실측으로 재현했다**: 첫 응답만 `{"output_text":""}` 로 주니 `generateImage`
가 호출됐다.

`isUsableAnalysis` 로 보고 비면 던져서 **같은 catch 로 합류**시킨다. 사용자가
보는 말도, 상태도, 크레딧도 터진 실패와 같아야 한다.

### 고칠 수 있는 실패를 「잠시 후 다시」로 뭉개고 있었다

처음 고친 판은 모든 실패를 502 「잠시 후 다시 시도해 주세요」로 덮었다. 그런데
제공자가 **4xx 로 거절한 것은 다시 시도해도 영원히 안 된다** — 키가 틀렸거나,
조직 인증이 안 됐거나, 올린 그림 형식이 안 맞는 경우다.

`humanizeProviderError` 가 그 셋에 대해 **무엇을 하면 되는지**를 이미 적어
두었는데(「최신 키를 다시 입력해주세요」, 「Verify Organization 을 완료한 뒤
15분」), 전부 502 로 덮으면 그 안내가 **도달할 수 없는 글**이 된다.

| 상태 | 주는 것 |
|---|---|
| 4xx (429 제외) | `humanizeProviderError(원문)` · 400 |
| 429 | 「잠시 후 다시」 · 502 |
| 5xx · 네트워크 | 「잠시 후 다시」 · 502 |

### 「오류 표시」가 기본 경로에서 증발하고 있었다

「나머지 섹션 생성」은 자기 자신을 한 장씩 다시 부른다. 여덟 장 채우기는
요청 여덟 번이고 분석도 여덟 번이다. 한 번 실패하면 이렇게 됐다.

1. 안쪽이 `setToast("업로드한 자료를 분석하지 못했습니다…")`
2. 곧바로 바깥이 `setToast("일괄 생성 결과: 성공 4장 · 확인 필요 1장…")`

**2 가 1 을 덮는다.** 끊어 알리려고 한 일이 기본 경로에서 통째로 사라진다.
이유를 앞에 붙이고 숫자를 뒤에 두게 바꿨다(`batch-summary.ts`).

같은 이유로 **문구도 고쳤다.** 「크레딧은 사용되지 않았습니다」는 다섯째에서
멈췄을 때 앞 네 장이 이미 차감됐으므로, 사용자가 읽는 단위에서는 거짓이다.
「**이 요청에는** 크레딧이 사용되지 않았습니다」로 한정했다.

### 시험을 쓰다 배운 것

**내 시험이 엉뚱한 줄을 보고 있었다.** 「안쪽 catch 가 이유를 남기는가」를
`wizard.toContain("lastGenerateErrorRef.current =")` 로 적었는데, 루프 앞에
**초기화**하는 줄이 따로 있어서 catch 의 저장을 통째로 지워도 초록이었다.
변이에서 드러났고, 실패를 다루는 자리만 잘라 보게 고쳤다.

처음 스텁은 **모든** fetch 를 터뜨렸다. 그러면 「분석에서 멈췄다」와 「그냥 다
실패했다」를 구별하지 못한다. 첫 호출만 터뜨리고 그 뒤는 멀쩡히 답하게 좁혔다 —
뒤가 멀쩡한데도 그림이 한 장도 안 나와야 분석 자리에서 멈춘 것이다.

### 남은 빚

**분석에 재시도가 없다.** 전에는 삐끗해도 (나쁜 방식으로) 계속 갔지만 이제는
하드 스톱이다. 여덟 장 경로는 분석이 여덟 번 도니 일시 오류를 만날 기회가
여덟 배고, 한 번 걸리면 뒤가 통째로 안 만들어진다(앞 장은 보존, 크레딧 정상).
분석은 글 모델 호출이고 비 2xx 는 과금되지 않으므로 지역 재시도가 싸고
안전하다. **공용 재시도를 끌어다 쓰면 안 된다** — 그건 fal 유료 그림 호출도
감싸서 1→3회 과금 사고를 냈다(D-6).

## W3/W8 — 전사가 장부 밖에 있었다 (F-7-9)

### 라우트가 로그인만 봤다

`transcribe-strips` 는 이랬다.

```ts
const auth = await authenticateApiMember();
const body = await req.json();
const result = await transcribeStrips({ ... });
```

- **예약이 없다.** 시간당 한도가 없다. 같은 페이지를 천 번 전사해도 막는 것이 없다
- **계량기가 없다.** `transcribeStrips` 에는 `onUsage` 가 **아예 없어서**,
  제공자가 준 토큰 수가 받아 적을 자리 없이 버려졌다. 원가 집계에서 전사는 $0
- **본문 상한이 없다.** 스트립은 base64 그림이고 배치 하나가 10MB 다

값이 작지 않다. 화면이 원본을 스트립 마흔 장까지 자르고(`MAX_STRIPS_TOTAL`)
배치당 여덟 장씩 보내므로, **한 페이지를 전사하면 호출이 다섯 번까지** 간다.

### 칸을 나눈 이유

전사 한 번이 다섯 칸까지 먹는다. `pdp_analyze`(시간당 열 번)와 같은 칸을 쓰면
**원본 한 장 전사하고 나면 그날 기획을 못 한다.** 세는 방식만 같이 쓰고 칸은
나눈다 — 레퍼런스 분석에서 세운 것과 같은 판단이다.

| 작업 | 시간당 | 근거 |
|---|---|---|
| `pdp_analyze` | 10 | 전과 같다 |
| `reference_analyze` | 60 | 한자리에서 스무 장을 올리는 일이 정상 |
| `redesign_transcribe` | 60 | 한 페이지 = 호출 다섯. 열 번 전사 = 50, 여유를 얹음 |

### 화면이 열쇠를 안 보내고 있었다

예약은 `x-idempotency-key` 를 요구하는데 전사 클라이언트는 그것을 안 보냈다.
그대로 뒀으면 **모든 배치가 400** 이다.

그런데 이 길의 실패는 조용하다 — `runTranscription` 의 catch 가 실패한 배치를
「[구간 전사 실패]」 자리표시로 바꾼다. 전사는 「됐다」고 하면서 내용이 통째로
비고, **그 빈 전사로 기획이 돈다.** 배치마다 새 열쇠를 준다(같은 값을 돌려
쓰면 두 번째부터 `duplicate_request`).

### 손으로 적은 기대값을 SQL 대조로 바꿨다

`hourly-limit.test.ts` 의 「SQL 이 세는 작업과 같은가」가 기대값을 **글자로**
적어 두었다.

```ts
expect(Object.keys(HOURLY_LIMITS).sort()).toEqual(["pdp_analyze", "reference_analyze"]);
```

그러면 이 시험은 「SQL 과 같은가」가 아니라 「내가 적은 것과 같은가」를 물을
뿐이다. 앱과 SQL 을 함께 고치고 여기만 안 고치면 빨개지지만, **그 반대(앱만
고치고 SQL 을 빠뜨림)는 못 잡는다.** 그것이 2026-09-08 에 실제로 난 사고다.
SQL 의 시간당 갈래를 읽어 대조하게 바꿨다.

### 사본을 하나로 합쳤다

토큰을 꺼내는 일(`usage.input_tokens` / `usageMetadata.promptTokenCount`)을
기획만 알고 있었다. 전사에 같은 것을 한 벌 더 적으면 한쪽만 고치는 날 갈린다.
`usage.ts` 한 곳에 두고 양쪽이 쓴다.

### 마이그레이션이 필요하다

`202609210001_transcribe_operation.sql` — check 제약·화이트리스트·시간당 갈래
셋에 `redesign_transcribe` 를 더한다. **SQL 을 먼저, 코드는 그다음이다.**
뒤바뀌면 전사가 「사용량을 확인하지 못했습니다」로 막힌다.
