# W8 검증 산출물 — 실제로 잰 값들

설계 §14.6(X-09): 「운영 번들/토큰/용량/줄바꿈 등 미확인 | **'검증 후 제외'도
측정 근거 필요** | W8 검증 산출물」.

설계 §12: 「숫자는 실제 대표 긴 페이지로 **메모리 측정 후** 정책 상수와 UI 에서
일치시킨다. **상한 확정 및 측정 결과가 없는 상태로 W8 통과하지 않는다.**」

이 문서는 그 요구에 대한 답이다. **값만 적지 않고, 다시 재는 법을 함께 적는다** —
재현할 수 없는 숫자는 근거가 아니라 주장이다.

측정일: 2026-09-20 ~ 09-21 · 가지 `fix/pdp-integrated-improvement`
환경: Windows 11 · Node 24.17 · sharp 0.35.4 / libvips 8.18.6 · Next 15

## 1. 운영 번들 — 서버 프롬프트가 브라우저로 내려갔는가

**결과: 내려갔었다. 고친 뒤 0.**

화면 컴포넌트 열다섯이 `@fixup/pdp-core` 배럴을 들인다. 대부분 상수 하나를
쓰려고 들이는데, 번들러가 나머지를 못 지워 프롬프트 전문이 같이 실렸다.

| 표식 | 고치기 전 | 고친 뒤 |
|---|---|---|
| `never change the product…` | 청크 1개(96KB) | **0** |
| `USER INSTRUCTION for composition` | 1 | **0** |
| `design_system` | 1 | **0** |
| `Overall tone:` | 1 | **0** |

원인은 둘이었다. 배럴 안의 `const controller = new PdpController()`(불러오는
순간 실행되는 부작용)와, 패키지가 `sideEffects: false` 를 안 밝힌 것.

**다시 재는 법**

```bash
cd apps/web
NEXT_DIST_DIR=.next-check npx next build
grep -rl "never change the product" .next-check/static/chunks/   # 0줄이어야 한다
rm -rf .next-check
```

`NEXT_DIST_DIR` 로 폴더를 갈라야 한다. 그냥 빌드하면 dev 서버가 쓰는 `.next` 를
덮어써 사용자 화면이 500 이 된다.

**원인을 잠근 시험**: `packages/pdp-core/src/pdp.bundle-boundary.test.ts`
(번들 자체는 운영 빌드가 필요해 시험에서 못 잰다. 원인 두 가지를 잠근다.)

## 2. 토큰 — 기획 응답 상한 32,768 의 근거

**결과: 대표 응답이 약 10,463토큰. 옛 상한 8,192 로는 잘린다.**

섹션 10장 · 섹션마다 불릿 4개와 근거 6개 · `prompt_en` 420자를 담은 대표 응답:

| 잰 것 | 값 |
|---|---|
| 응답 길이 | 19,984자 (한글 4,686자) |
| 추정 토큰 | 약 **10,463** |
| 현재 상한 32,768 대비 | 32% |
| 옛 상한 8,192 였다면 | **128% — 잘린다** |

이것이 D-7 에서 기획 호출만 상한을 올린 이유다. 2026-09-17 에 텍스트 기획이
111초를 쓰고 잘려 죽은 사고가 이 숫자에 해당한다.

추정은 「한글 1자 ≈ 1.3토큰, ASCII ≈ 3.5자당 1토큰」으로 했다. **정확한
토크나이저가 아니다** — 자릿수를 확인하는 용도다. 상한이 실측의 3배라 자릿수
오차를 견딘다.

**다시 재는 법**: `apps/web/lib/pdp/providers.ts` 의 `PLANNING_MAX_TOKENS` 를
바꾸기 전에 위 구성으로 응답 길이를 재고, 실측의 **2배 이상** 인지 확인한다.

## 3. 용량 — 대표 최대 초안과 브라우저 저장 한도

**결과: 초안 하나가 63.4MB. 20개면 1.27GB.**

섹션 10장 · 원본 2.5MB · 인물 2.0MB · 레퍼런스 4.0MB · 만든 그림 1.6MB×10:

| 초안 수 | 크기 |
|---|---|
| 1개 | **63.4MB** |
| 5개 | 316.8MB |
| 10개 | 633.6MB |
| 20개 | **1,267MB** |

거의 전부가 그림(63.2MB)이고, 그중 **21.3MB 는 중복**이다 — `editorState` 가
섹션 그림을 한 벌 더 담는다.

**기존 사본은 안 잃는다.** 저장은 `store.put` 한 번이라 실패하면 IndexedDB 가
트랜잭션을 통째로 취소한다. 잃는 것은 이번 변경분뿐이다.

**남은 위험**: 브라우저 저장 한도는 기기·브라우저마다 다르다. 20개 규모에서
한도에 닿는 것이 드문 일이 아니므로, 용량 초과를 갈라 말하게 했다
(`apps/web/app/create/draft-save-failure.ts`).

## 4. 줄바꿈 — `white-space: pre-wrap` 미해석 주장

**결과: 전제가 성립하지 않는다. 그 스타일이 안 걸려 있다.**

지적은 「html2canvas 가 `pre-wrap` 을 미해석한다」였다. 실제 브라우저에서
레이어 span 의 `whiteSpace` 를 읽어 보니 **`null`** 이다 — 그 스타일 자체가 안
걸린다. 미해석 여부를 따질 대상이 없다.

같은 측정에서 B-12-e(`objectFit` 미반영)도 화면·원본 비율 차 **0.0000** 으로
나와 제외했고, B-10(그림자)은 기본 설정에서 그림자가 없어 제외했다.

**측정 산출물**: `docs/bugs/pdp-validation/w6-*.txt` · `w6-*.cjs`

## 5. 곁가지로 잰 것 — 손상 JSON 추출

D-5 에서 잰 값이라 여기 함께 남긴다.

| 길이 | 옛 판(제곱) | 지금(선형) |
|---|---|---|
| 10KB | 125ms | |
| 25KB | 627ms | |
| 50KB | 2,274ms | |
| 100KB | **12,100ms** | **100ms 미만** |

**단, 이 입력은 현재 운영에 도달하지 않는다.** 공급자 층이 이미 파싱된 객체를

`pdp.response-parse.ts` 머리말에 적었다 — 방어 장치가 제곱이면 막으려던 것이
그대로 공격이 된다.

## 6. 드래그 한 번이 얼마나 일하나 (B-12-c)

**결과: 저장 시계가 프레임마다 움직였다. 1초 드래그에 61회.**

레이어를 끌면 `onDrag` 가 프레임마다 `updateOverlay` 를 불렀다. 그 값이
`onDraftStateChange` 로 올라가 부모(`PdpMakerClient`, 2,000줄)가 다시 그리고,
부모는 초안 전체를 다시 조립해 저장 시계에 넣는다.

| 잰 것 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 저장 시계 수정 횟수(1초 드래그) | **61회** | **2회** |
| 시계가 하는 일 | 2.8ms (프레임당 0.05ms) | 0ms |

**JS 일 자체는 싸다.** 프레임당 0.05ms 면 값을 내는 쪽이 아니다. 값을 내는
것은 **부모 트리를 초당 60번 다시 그리는 쪽**인데, 그것은 브라우저 없이 못
쟀다(아래 「안 잰 것」에 남긴다).

그래서 고친 근거는 「느리다」가 아니라 **「할 필요 없는 일을 한다」**이다 —
놓기 전의 중간 좌표는 저장할 값이 아니다. 설계도 그렇게 적었다: 「**임시
state/commit 분리**」.

**다시 재는 법**

```
W8 대표 초안(섹션 10장·원본 2.5MB·인물 2MB·만든 그림 1.6MB×10)을 만들고,
레이어 좌표만 바꾼 초안을 60번 `DraftSaveClock.observe(draftChangeValues(…))`
에 넣어 `clock.revision` 을 읽는다.
```

측정에 쓴 시험은 `apps/web/app/create/__tests__/layer-preview.test.ts` 의
「저장 수」 묶음이 그대로 값으로 재 둔다.

**그 시험이 재는 것은 시계의 성질이지 편집기가 아니다**(2026-09-21 리뷰).
`DraftSaveClock.observe` 는 참조를 비교하고 `draftChangeValues` 는
`overlaysBySection` 객체를 그대로 값으로 내놓는다. 그래서 좌표를 0으로 고정한
60프레임도 `revision = 61` 이 나온다 — 숫자가 말하는 것은 「**새 객체가 60번
올라왔다**」이다. 고치기 전 편집기가 프레임마다 새 `overlaysBySection` 을
만들었으므로 61회는 사실이지만, **이 고침이 되돌아가도 그 시험은 안 빨개진다.**
편집기 쪽 회귀는 같은 파일의 「편집기가 그 조립기를 쓴다」 묶음이 막는다.

## 7. 아직 안 잰 것

정직하게 남긴다.

- **브라우저별 저장 한도 실측.** 위 3번은 초안 크기만 쟀고, 어느 브라우저가
  몇 GB 에서 거절하는지는 안 쟀다. 용량 초과를 다루는 길은 만들어 뒀다
- **정확한 토크나이저 기준 토큰 수.** 위 2번은 추정이다. 상한이 실측의 3배라
  지금 판단에는 충분하다
- **`editorState` 그림 중복(21MB)을 줄였을 때의 실제 절감.** 읽는 자리가
  여럿이라 손대지 않았다
- **드래그 중 React 재렌더 비용**(B-12-c). 프레임마다 부모가 다시 그린다는
  것은 코드에서 1:1 로 따라오지만, 그 **렌더가 몇 ms 인지**는 브라우저가
  있어야 잰다. 사용자 dev 서버가 떠 있어 이번에는 띄우지 않았다. 재려면
  W6 의 `w6-*.cjs` 처럼 실제 화면에서 React Profiler 로 드래그 1초를 잰다
