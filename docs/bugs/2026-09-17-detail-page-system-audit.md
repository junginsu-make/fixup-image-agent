## 1. 핵심 판단

판매 기획과 디자인을 위한 지시는 구체적이다. 제품 관찰, 대상 고객, 문제, 차별점, 반론, 설득 흐름, 디자인 통일, 문구 검수까지 다룬다.

그러나 **규칙을 프롬프트에 적어 놓는 것과 결과가 그 규칙을 지켰다고 보장하는 것은 다르다.** 화면 상태 전달·복원에 누락이 있고, 심사와 검수는 실패하거나 불완전해도 통과할 수 있다.

현재 평가는 다음과 같다.

| 평가 대상 | 판단 |
|---|---|
| 판매용 초안 제작 구조 | 구체적인 기반이 있다 |
| 작업을 안전하게 이어가는 기능 | 수정·복원·화면 이동·재시도에 결함이 있다 |
| 상품 사실과 결과물 품질 보장 | 입력과 사용자 검토에 의존하며 검증 공백이 있다 |
| 실제 구매 전환 개선 | 이번 조사에서 성과를 입증하는 데이터는 확인하지 못했다 |

이 문서는 운영 장애 발생 횟수나 실제 피해액을 입증하지 않는다. 코드상 결함, 모의 실행 결과, 설계상 한계, 미검증 사항을 구분한다.

## 2. 시스템과 데이터 흐름

### 2.1 경로별 처리

| 경로 | 흐름 |
|---|---|
| 이미지로 시작 | 제품 사진·판매 정보 → 제품 판독 및 구성안 → 별도 심사·수정 → 사용자 구성안 편집 → 섹션 이미지 생성·검수 → 편집·저장·다운로드 |
| 텍스트로 시작 | 자유 설명 → 판매 브리프 → 구성안·문장별 근거 → 별도 심사·수정 → 사용자 확인 → 대표 이미지 생성·승인 → 공통 섹션 생성·편집 |
| 리디자인 | 원본 이미지·PDF → 변환·텍스트 전사 → 분석·이미지 생성 → 추가 생성·부분 수정 → 저장·다운로드 |

새 상세페이지는 `apps/web/app/create`, API는 `apps/web/app/api/pdp`, 생성 엔진은 `packages/pdp-core`에 있다. 리디자인은 별도 화면·API·`packages/redesign-core`를 사용한다.

### 2.2 저장과 생성의 책임

- 새 상세페이지 초안: 브라우저 IndexedDB. 계정 라이브러리 저장은 별도다.
- 리디자인 작업 저장: 브라우저 IndexedDB에 수동 저장한다.
- 리디자인 이미지: 생성 직후 라이브러리에 자동 업로드를 시도한다. 성공을 보장하거나 실패를 알리는 처리는 부족하다.
- 새 상세페이지 이미지 결과: 요청 응답을 화면이 받아 편집기 상태에 넣는다. 해당 경로에는 결과를 먼저 서버에 영구 보존하고 재조회하는 구조가 없다.
- 공통 진행 작업 관리 `useRunningJobs`: 조사 시 사용처는 SNS·포스터이며 `/create`에는 연결돼 있지 않았다.
- 크레딧 예약: 예약 시간에 생성하는 기능이 아니라 생성 중 사용량을 임시 확보하는 내부 처리다. 응답 반환·결과 저장·정산은 각각 별도의 실패 지점이다.

## 3. 두 모드의 전문성과 차이

| 항목 | 이미지 모드 | 텍스트 모드 |
|---|---|---|
| 실제 기본 전제 | 사진이 있는 실물 상품 | 무형 상품·서비스 |
| 상품 이해 | 사진 사실을 구성안 응답 앞부분에 정리 | 독립된 판매 브리프를 먼저 생성 |
| 추가 입력 | 대상, 불편, 특징, 차별점, 강조사항 등 | 자유 설명, 표현 강도, 정보 부족 처리 정책 |
| 섹션 수 지시 | 5~6개 | 4~7개 |
| 심사 후 수정 | 최대 1회, 심사 점수가 개선되면 채택 | 최대 2회, 150초 수정 예산 확인 |
| 문장별 근거 데이터 | 텍스트 모드와 같은 체계 없음 | 인용·수사·질문·예시 구분 |
| 공통 디자인 | 섹션별 스타일 지시·공통 참조에 의존 | 별도 `designSystem`을 정규화해 섹션에 전달 |
| 이미지 기준 | 업로드한 제품 사진 | 생성·승인한 대표 이미지 |

섹션 수와 디자인 규칙은 주로 모델에 주는 지시다. 반드시 해당 개수·항목이 갖춰졌는지 검사하는 강제 조건으로 보아서는 안 된다.

### 3.1 이미지 모드

`ProductReading`은 제품 종류, 보이는 사실, 라벨 문구, 시각적 특징, 모르는 정보를 구분한다. 사진에서 알 수 없는 판매 정보는 `SellerBrief`의 별도 칸으로 받는다. 이 구분은 합리적이다.

한계:

- 판매자 입력은 전부 선택 사항이다. 타깃·차별점이 없어도 생성하므로 AI 추론 비중이 커진다.
- 판독 품질을 판단하는 `isProductReadingUsable`은 존재하지만, 조사 시 실제 생성 흐름의 호출은 없고 export와 테스트만 확인됐다.
- 상품별 구성을 선택하는 전용 규칙보다 공통 광고 문법에 의존한다.
- 사진 분석 프롬프트에는 5~6개 섹션, 베네핏 3개, 첫 섹션의 인물 연출, 후기 카드 선호 등의 지시가 있다. 모든 상품에 최적이라는 근거는 확인하지 못했다.
- 근거 없는 후기를 만들지 말라는 규칙과 후기 카드 구성을 선호하는 지시가 함께 있어, 근거가 부족한 상품에서 모델이 조정해야 할 부담이 있다. 실제 허위 후기 생성이 이번에 관찰됐다는 뜻은 아니다.

### 3.2 텍스트 모드

브리프에는 상품명·유형·한 줄 소개·대상·문제·기대 결과·차별점·예상 반론·가격 포지션·톤·추정 사항·사용자 원문을 담는다. 이후 구성안과 문장별 근거를 만들고, 미확인 내용을 사용자에게 보여준다.

장점은 기획 단계 분리와 근거 표시다. 반면 정보가 부족해도 되묻지 않고 합리적으로 채우라는 정책이므로, 실제 고객 조사나 경쟁사 분석을 대신하지 않는다.

원래 설계는 무형 상품용이다. 현재 UI의 일반적인 ‘사진 없이 설명으로 시작’ 안내와 범위가 다르다. 의도된 과거 설계와 현재 제품 설명의 불일치로 이해해야 한다.

## 4. 상세페이지 구조화 방식

### 4.1 판매 흐름

`pdp.sales-principles.ts`의 판매 원칙 전체를 구성안 생성과 심사에 전달한다. 이 단계는 성공 사례를 검색해 최적 구성을 학습·선택하는 구조가 아니다.

```text
관심 유도 → 고객 문제 → 기대 변화 → 차별점·근거 → 반론 해소 → 마지막 확신
```

상세 지시는 대상의 구체성, 상황 중심 문제 표현, 경쟁 상품과의 차별성, 확인 가능한 근거, 짧은 카피, 서체·색·인물의 통일 등을 포함한다. 마지막에 가짜 구매 버튼을 그리지 않도록 하며, 실제 구매 버튼은 판매 플랫폼이 담당한다.

### 4.2 중간 산출물

| 항목 | 의미 |
|---|---|
| `executiveSummary` | 전체 판매 전략 |
| `section_name`, `goal` | 섹션 역할과 목적 |
| `headline`, `subheadline`, `bullets` | 실제 판매 문구 |
| `trust_or_objection_line` | 신뢰 확보·망설임 해소 문구 |
| `prompt_ko`, `prompt_en` | 사용자용 장면 설명과 생성용 지시 |
| `layout_notes`, `style_guide` | 배치·디자인 |
| `reference_usage` | 제품 참조 방식 |
| `compliance_notes` | 표현 주의사항 |
| `evidence` | 텍스트 모드의 문장별 근거 |

### 4.3 이미지 제작과 검수

구성안을 JSON 이미지 프롬프트로 변환하고 제품·인물·디자인 참조를 함께 전달한다. 현재 화면의 기본 출력은 카피까지 이미지 안에 그리는 `full-image`다. 엔진에는 `editable`도 있으나 화면에서 기본 방식으로 제공되는 것과 구분해야 한다.

HTML/CSS처럼 좌표·서체·여백을 확정적으로 배치하는 것이 아니라 생성 모델이 지시를 해석해 그린다. 따라서 구체적 지시만으로 문구 정확성·디자인 일관성을 보장할 수 없다.

이미지 QA는 승인 원고와 비교해 미승인 브랜드, 오탈자, 미승인 숫자, 인체 왜곡을 본다. 제목·부제 오탈자 등은 차단하고 일부 경미한 결함은 경고한다. 통이미지의 생성 시도 상한은 기본적으로 2회다. 별도 인물 검증 조건도 있다.

다만 최종 페이지 전체를 합쳐 모든 섹션의 서체·색·중복 문구·설득 흐름·정보 누락을 종합 검수하는 절차는 확인하지 못했다. 단일 이미지 검수와 전체 페이지 품질은 구분해야 한다.

## 5. 기존 발견 7개 — 번호 유지

### 1. 구성안 수정이 편집기에 반영되지 않을 수 있음

- 조건: 편집기 → 구성안으로 돌아가 문구·섹션을 수정 → 편집기로 재진입.
- 원인: 구성안은 `result.blueprint`를 바꾸지만 편집기는 기존 `editorDraftState.sections`를 우선 사용한다.
- 영향: 수정·추가·삭제한 내용이 실제 생성에 반영되지 않을 수 있다.
- 근거: `PdpMakerClient.tsx`의 구성안 변경·확정 처리, `PdpEditor.tsx`의 초기 `sections` 선택.
- 검증 수준: 코드 흐름 확인. 실제 브라우저 조작 재현은 미실시.

### 2. 초안에 생성 설정이 온전히 보존되지 않음

- 누락: `imageModel`, `characterId`, `characterAngles`, `preserveProduct`, `startMode`. 비교 기준인 `analyzedBlueprint`도 복원하지 않는다.
- 영향: 새로고침 후 기본값 사용, 같은 화면에서 다른 초안 로드 시 이전 작업 설정 잔류, 이미지 방향 수정 연결 누락 가능.
- 근거: `pdp-drafts.ts`, `draft-input.ts`, `PdpMakerClient.tsx`의 저장·불러오기.
- 검증 수준: 저장 형식과 전달·복원 코드 확인.

### 3. 텍스트 작업 중간 상태 유실

- 원인: 텍스트·브리프·구성안·대표 이미지가 `TextModeFlow` 내부 상태에만 있고 부모 초안에는 저장되지 않는다.
- 영향: 컴포넌트가 사라졌다 다시 나타나면 내부 데이터는 초기화되는데 부모 `textStage`는 남을 수 있다. 단계와 내용이 불일치하거나 빈 화면이 될 수 있다.
- 근거: `TextModeFlow.tsx`, `PdpMakerClient.tsx`의 조건부 렌더링.
- 검증 수준: 상태 수명과 저장 경로 확인.

### 4. 새 상세페이지 생성 중 화면 이동 시 결과 유실 가능

- 원인: 결과가 편집기 상태로만 들어오고 서버 영구 저장·재조회 및 공통 진행 작업 관리 연결이 없다.
- 영향: 화면이 사라진 뒤 서버 생성·정산이 완료되면 결과를 복구하지 못할 수 있다.
- 근거: `PdpEditor.tsx` 생성 완료 처리, `_components/running-jobs.tsx`와 사용처.
- 주의: 화면 이동이 서버 생성 취소를 의미하지 않는다. README의 화면 이동 설명을 모든 도구에 적용할 수 없다.
- 검증 수준: 코드 확인. 운영 유실 사례·차감 내역은 미대조.

### 5. 일괄 생성 재시도의 요청 식별자가 달라짐

- 조건: 서버 처리 여부를 알 수 없는 통신 실패 후 동일 배치를 재시도.
- 원인: 단건과 달리 배치는 재시도 식별자를 보존하지 않고 `apiJson`이 UUID를 새로 만든다.
- 영향: 첫 요청이 완료됐어도 새로운 생성으로 처리돼 추가 비용·차감이 발생할 수 있다.
- 근거: `PdpEditor.tsx` 배치 요청, `pdp-utils.ts`의 `apiJson`.
- 검증: 실제 `apiJson`의 `fetch`를 실패 대역으로 바꿔 동일 요청 2회를 실행. `attempts: 2`, `retryKeepsSameId: false`.

### 6. 리디자인 정산 오류가 성공 결과를 유실시킴

- 원인: 생성 성공 후 예외를 던질 수 있는 `finalizeAiUsage`를 직접 호출하고, 실패 시 전체 오류 처리로 이동한다.
- 영향: 이미지 생성에 성공해도 오류 응답이 나가며 결과를 받지 못할 수 있다.
- 근거: `app/api/redesign/generate/route.ts`, `lib/membership/api.ts`.
- 비교: PDP 이미지 성공 경로에는 예외를 흡수하는 `settleAiUsage`가 적용돼 있다. 모든 PDP 라우트에 적용된 것은 아니다(13번 참조).
- 검증 수준: 예외 전파 코드 확인. 실제 정산 장애 주입은 미실시.

### 7. 리디자인 자동 저장 실패가 보이지 않음

- 원인: `autoSaveSections`가 HTTP 성공 여부를 검사하지 않고 네트워크 예외도 삼킨다.
- 영향: 생성 결과가 서버에 저장되지 않았는데 사용자가 알지 못한다. 별도 작업 저장 없이 닫으면 결과 유실 가능.
- 근거: `redesign-wizard.tsx`의 `autoSaveSections`, 별도의 `saveCurrentProject`.
- 검증 수준: 응답·예외 처리 코드 확인.

## 6. 추가 발견 8~13

### 8. 텍스트 모드의 UI 범위와 무형 상품 전제 불일치

- 실물 상품 설명도 입력할 수 있지만 브리프와 구성안 프롬프트는 무형 상품을 전제한다.
- 실제 지시: ‘무형 상품이다. 만질 수 있는 제품 사진을 전제하지 마라.’
- 실물 상품 브리프로 실제 프롬프트를 생성해 해당 지시가 그대로 포함됨을 확인했다.
- 영향: 제품 사실·외형 설명보다 장면·감정·은유로 치우칠 수 있다. 실제 생성물에서 항상 발생한다고 단정하지 않는다.
- 근거: `pdp.text-plan.ts`의 `buildBriefPrompt`, `BLUEPRINT_RULES`; `PdpMakerClient.tsx`의 모드 안내.

### 9. 이미지·텍스트 모드의 사실 근거 검증이 비대칭

- 텍스트 모드는 `evidenceVersion: 1` 및 근거 배열을 만들고 검사한다.
- 이미지 모드 구성안에는 같은 체계가 없으며 공통 검사 함수는 버전이 없는 섹션을 건너뛴다. `prompt_en`의 금지 주장 검사 등 다른 검사까지 없다는 뜻은 아니다.
- 이미지 모드의 ‘물어보기’ 정책도 실제 질문 목록 대신 확인 가능한 표현으로 바꿔 쓰라는 지시다. 텍스트 모드의 `ask`와 동작이 다르다.
- 추가 한계: 공통 구성안 심사자는 원본 사진·판매자 브리프·`productReading`을 받지 않는다. 원본 근거와 문장을 대조할 수 없다.
- 검증: 판독 사실에 식별 문구를 넣어 `buildReviewPrompt`를 실행했으나 심사 입력에 포함되지 않았다.
- 근거: `pdp.evidence.ts`, `pdp.product-reading.ts`, `pdp.service.ts`, `pdp.review.ts`.

### 10. 불완전한 심사를 전체 통과로 표시

- 심사 항목: 대상·문제·차별점·반론·흐름·근거·마무리, 총 7개. 일부 오래된 주석·README의 6개 설명과 다르다.
- `normalizeReview`는 전체 항목의 완전성·유일성을 강제하지 않는다.
- 항목 1개가 pass여도 화면은 일곱 항목을 확인했다는 전체 통과 문구를 표시한다.
- 항목 0개면 화면은 숨기며 `needsRevision`은 false다. **0개에서 전체 통과 배지가 보인다는 뜻은 아니다.**
- 검증: 실제 함수와 화면 분기를 대조했다. 실제 `planFromText`에 섹션 1개·심사 1항목·디자인 시스템 없는 모델 응답을 주입했을 때 브리프→구성안→심사 3회로 종료했다.
- 영향: ‘심사 통과’는 요구 항목 전체를 검사했다는 보장이 아니다.
- 근거: `pdp.review.ts`, `ReviewPanel.tsx`, `pdp.text-plan.ts`.

### 11. 이미지 QA 실패가 정상 통과로 처리될 수 있음

- QA 호출·파싱 실패 시 `{ defects: [], parseError: true }`를 반환한다.
- 이전 차단 결함이 없는 첫 시도에서는 생성 루프가 이를 결함 없음으로 처리한다.
- 검증: 실제 `PdpService.generateSectionImageInternal`에 이미지 생성 성공 대역과 QA 오류 대역을 주입했다. 결과는 `passed: true`, `blocking: []`, `warnings: []`, `attempts: 1`이었다.
- 기존 차단 결함이 있던 재시도에서 QA가 실패하는 경우에는 그 결함을 유지하는 예외 처리가 있다. 모든 실패 경로가 무조건 통과하는 것은 아니다.
- 영향: ‘검수하지 못함’과 ‘검수 결과 이상 없음’이 구분되지 않는다.
- 근거: `pdp.qa.ts`, `pdp.service.ts` QA 루프.

### 12. 이미지 생성 원고와 QA 승인 원고 불일치

- 생성 JSON에는 `trust_or_objection_line`이 `reassurance_line`으로 전달된다.
- `buildQaPrompt`의 승인 원고에는 이 문구가 빠진다.
- 검증: 같은 섹션으로 두 함수를 실행했을 때 `sentToImage: true`, `sentToQA: false`였다.
- 영향: 승인된 신뢰 문구의 숫자를 미승인 숫자로 오인하거나 문구 대조를 제대로 못 할 수 있다. 실제 비전 모델의 오판 자체를 재현한 것은 아니다.
- 근거: `pdp.image-prompt.ts`, `pdp.qa.ts`.

### 13. 텍스트 구성안도 정산 오류로 유실 가능

- `/api/pdp/plan-from-text`는 결과 반환 전에 `finalizeAiUsage`를 직접 호출한다.
- 따라서 이미지가 아닌 구성안에서도 6번과 같은 정산 예외 전파가 있다.
- 이미지 분석 라우트의 `settleAiUsage` 적용과 대칭이 아니다.
- 검증 수준: 코드 확인. 운영 DB 장애 주입 미실시.
- 근거: `app/api/pdp/plan-from-text/route.ts`.

## 7. 판매 효과에 대한 평가

확인 가능한 장점은 특징별 메시지와 이미지를 묶고, 고객의 망설임을 다루며, 제작 전에 사람이 카피를 검토할 수 있다는 점이다.

그러나 다음은 확인되지 않았다.

- 생성 페이지가 기존 페이지보다 구매 전환을 높였다는 통제 실험 결과
- 상품별 최적 섹션 수·순서를 선정하는 실측 체계
- 실제 매출·장바구니·구매 데이터를 구성안 개선에 연결하는 피드백 경로
- 이번 조사에서 생성한 대표 표본의 시각 품질 평가

코드·관련 문서 검색에서 근거를 찾지 못했다는 뜻이며, 저장소 밖에 성과 자료가 절대 없다는 단정은 아니다.

판매 원칙의 ‘이 흐름이면 팔린다’, ‘특정 표현이 전환을 높인다’는 문장은 이 서비스의 실측 성과가 아니다. 현재 결과물은 전문가가 검토할 판매용 초안으로 평가하는 것이 타당하다.

외부 근거:

1. [Baymard — 특징별 제품 설명 구조 연구](https://baymard.com/research-articles/structure-descriptions-by-highlights): 주요 특징을 관련 이미지와 함께 설명하면 사용자가 내용을 더 깊이 탐색하는 데 도움이 된다는 사용성 연구다. 단순 상품까지 항상 긴 구성을 사용할 필요는 없다고 구분한다. 이 서비스의 매출 개선을 입증하는 자료는 아니다.
2. [Microsoft Research — Online Experimentation at Microsoft](https://www.microsoft.com/en-us/research/publication/online-experimentation-at-microsoft/): 직관과 실제 효과를 구분하는 통제 실험의 필요성을 다룬다. 생성 페이지의 효과를 판단하려면 동일 상품과 비교 조건을 통제한 성과 측정이 필요하다.

## 8. 수행한 검증과 한계

### 기존 테스트 실행 결과

최초 조사 당시 다음 명령을 실제 실행했다.

```text
pnpm --filter @fixup/pdp-core test
  25 files / 617 tests passed

pnpm --filter @fixup/web exec vitest run app/create app/api/pdp app/redesign app/api/redesign
  23 files / 189 tests passed

pnpm --filter @fixup/redesign-core test
  6 files / 74 tests passed

pnpm --filter @fixup/web typecheck
  exit 0
```

합계 880개 통과. 이는 최초 조사 시점 결과이며 문서 저장 시 새로 실행한 결과가 아니다. 일부 테스트는 소스 문자열을 확인하는 방식이어서 화면 단계 왕복·복원·네트워크 응답 유실을 검증하지 않는다.

### 추가 모의 실행 결과

| 검사 | 결과 |
|---|---|
| 같은 배치 요청의 통신 실패 후 재시도 | 요청 식별자 달라짐 |
| 심사 1항목만 pass | 재작성 없음, UI 전체 통과 분기 |
| 심사 항목 없음 | 재작성 없음, UI 숨김 |

모의 실행은 실제 함수를 사용하고 외부 호출만 대역으로 바꿨다. 유료 AI 호출·프로덕션 데이터 변경은 하지 않았다. 터미널에서 실행했으며 별도 회귀 테스트 파일을 추가한 상태는 아니다.

### 미실시

- 브라우저를 통한 각 사용자 시나리오의 종단 간 재현
- 새 유료 이미지 생성 및 완성 이미지 육안 평가
- 운영 로그·DB 차감 내역과 사용자 증상 대조
- 운영 DB 마이그레이션 적용 상태 및 배포 버전 확인
- 구매 전환율 실측

## 9. 수정 우선순위와 완료 판단 기준

아래는 이번 결함에 대한 후속 수정 순서다. 구현하거나 배포했다는 뜻은 아니다.

1. **결과·비용 보호:** 4·5·6·7·13번. 응답 유실·화면 이동·정산 실패·업로드 실패를 주입하고, 결과 복구와 사용자 안내 및 중복 생성 방지를 확인한다.
2. **작업 상태 일관성:** 1·2·3번. 구성안 왕복, 새로고침, 다른 초안 전환, 텍스트 모드 재진입 후 설정·문구·이미지가 보존되는지 확인한다.
3. **검사 신뢰성:** 9·10·11·12번. 누락 심사와 QA 실패가 통과로 표시되지 않는지, 생성·검수 원고가 같은지 확인한다.
4. **모드 범위 정합성:** 8번. 텍스트 모드가 실제로 지원할 상품 범위와 화면 안내·프롬프트를 일치시킨다.

기존 테스트 통과만으로 완료 판정하지 않는다. 해당 결함의 조건을 직접 검증하고, 코드 완료·운영 반영·실제 생성 품질·판매 효과를 각각 구분한다.

## 11. 추가 조사 및 Claude Code 보고서 대조

2026-09-17 후속 요청에 따라 [Claude Code 전수 리뷰](pdp-full-review-2026-09-17.md)를 읽고 본 보고서 및 후속 대화의 발견을 함께 검토했다. 대조 시작 시 HEAD는 `4497532`였다. 다른 작업의 수정 파일이 있어 이 문서만 갱신했다.

### 11.1 보고서를 해석하는 기준

- Claude 보고서의 64건과 본 보고서의 13건을 더해 총 결함 수로 부르지 않는다. 같은 원인의 증상·중복 지적·잠재 위험·미확인 항목이 섞여 있다.
- 기존 1~7, 추가 8~13 번호는 유지한다. Claude 지적은 A-1, C-1, D-1, 7-4 등 원문 번호로 교차 참조한다.
- 원문에 ‘실측’이라고 적힌 항목도 코드상 계산·모의 실행과 운영 장애 실측을 구분한다.
- ‘인증에 구멍이 없다’, ‘환불 누락이 없다’는 표현은 이번 검토 범위 전체에 대한 보증으로 채택하지 않는다.
- 정산 예외를 삼키는 것만으로 예약 해제·비용 기록·정산 재처리·결과 복구가 모두 해결됐다고 보지 않는다.
- 빈 심사 결과는 재작성이 없고 UI가 숨겨진다. 1항목만 pass인 심사가 전체 통과 문구를 만드는 경우와 구분한다.
- 사진 구성안 심사 후 수정은 코드상 최대 1회다. 원본 생성까지 포함한 횟수와 혼동하지 않는다.

### 11.2 이번에 재확인한 중요한 보완 사항

| 내용 | 근거·수준 | 기존 조사와 관계 |
|---|---|---|
| 실제 초안 저장·읽기에서 첨부 지시·레퍼런스·토글 유실 | Claude A-1. 현재 `savePdpDraft` → `getPdpDraft`를 메모리 `fake-indexeddb`로 독립 실행해 셋 모두 누락 재현 | 기존 2번보다 더 깊은 저장 계층 누락. 반드시 함께 해결 |
| 구성안 재분석 시 이미지·레이어 상태 초기화 | Claude A-2, 현재 화면 처리 대조 | 기존 1~3번의 작업 데이터 보호와 함께 해결 |
| 편집기에서 추가한 섹션의 영어 장면이 빈 값 | Claude A-4, 현재 코드 대조 | 구성안 화면에서 추가한 섹션과 서로 다른 생성 함수 사용 |
| 라이브러리 저장은 편집 레이어를 제외 | Claude B-3, 현재 저장 코드 대조 | 다운로드·미리보기·저장 결과의 일치 문제 |
| 내보내기 크기가 화면 폭 × 2에 의존 | Claude B-1/B-2, 현재 캡처 코드 대조 | 원본 크기와 독립된 내보내기 규격 필요 |
| 리디자인 수정의 생성 경로·품질·예약/확정 수량 불일치 | Claude 7-4~7-6, 현재 라우트·생성 코드 대조 | 실제 사용 모델과 정산을 같은 실행 정보로 묶어야 함 |

초안 왕복 독립 실행 결과:

```json
{"userInstruction":"keep me","attachmentIntents":null,"styleReference":null,"styleReferenceEnabled":null}
```

이는 실제 사용자 브라우저의 DB에 접근한 시험이 아니다. 누락값은 출력할 때 `null`로 표기했다.

### 11.3 직전 대화에서 추가 확인한 참조·설정·편집 문제

- **보존 지시 해제:** 제품 첨부 설명에 ‘왼쪽 배치’ 같은 지시를 넣으면 해당 역할의 기본 변형 금지 문구가 빠진다. `buildReferenceRoleDirective` 실행으로 확인. 사용자의 최신 요구인 ‘각도는 달라도 정체성은 불변’과 충돌한다.
- **보존 검수 공백:** 제품의 원본 대조 검수가 없고, 저장된 캐릭터는 업로드 인물 사진과 같은 동일성 검증 조건을 타지 않는다. 실제 생성 루프에 캐릭터 참조를 넣었을 때 첨부는 anchor/person, 검수 호출은 `pdp_qa`만 나왔다. 실제 생성물 변형을 새로 관찰한 것은 아니다.
- **참조 경쟁:** 업로드 인물 사진이 사용되는 섹션은 저장 캐릭터보다 사진이 우선한다. 디자인 참조가 있고 제품 보존이 꺼져 있으면 제품 앵커가 빠진다. 모델별 첨부 상한 초과 시 뒤쪽 디자인 참조가 잘리는 문제는 Claude D-1과 함께 다룬다.
- **설정 단계 불일치:** 그림체·추가 지시는 최종 이미지 생성에는 전달되지만 사진 구성안 기획 요청에는 전달되지 않는다. 기획 요청과 이미지 연출 요청의 범위를 명확히 해야 한다.
- **화면비 불일치:** 출력 크기는 선택 비율을 따르지만 `buildImageJson`의 `format.orientation`은 vertical 고정이다.
- **새 섹션 이미지 방향 무시:** 구성안에서 새 섹션을 만들면 기본 영어 장면이 채워진다. `mergeArtDirection`은 새 섹션의 영어 장면이 있으면 수정한 한국어 방향을 반영하지 않는다. ‘snowy mountain’으로 고쳤는데 ‘bright clean studio’가 남는 것을 실행 확인했다. Claude A-4의 ‘편집기 새 섹션은 빈 프롬프트’와 별개 증상이다.
- **보이지 않는 최종 문구:** 신뢰·반론 문구는 이미지 생성에 사용되지만 구성안의 일반 편집 항목에는 없다.
- **전체 전략 수정의 한계:** 요약문을 바꿔도 개별 섹션이 자동 재기획되지 않는다. 승인 화면에서 그 차이를 설명하거나 명시적으로 재기획해야 한다.
- **기획 모델:** 현재 코드 기본값 및 로컬 모델 설정은 Claude `claude-sonnet-5`, 실패 시 OpenAI `gpt-5.6-sol`. 심사는 별도 호출이지만 같은 공통 LLM 연결이다. 운영 모델 설정·호출 로그는 미확인.

## 12. 통합 개선 실행안

이 절은 실행 순서와 합격 기준이다. 아직 구현하지 않았다. 주제별로 작은 변경을 나누고, 해당 결함을 먼저 실패하는 동작 시험으로 고정한 뒤 수정한다. 원본 보고서는 증거로 보존한다.

### 단계 1. 저장된 작업과 이미 만들어진 결과 보호

대상: 본문 1~7·13, Claude A-1/A-2/A-8/A-9, C-1/C-2/C-5, 7-2.

첫 변경 묶음:

1. 저장·정규화·복원 필드를 함께 수정하고 이전 초안과의 호환성을 유지한다. 레퍼런스 바이트·지시·토글·모델·캐릭터·각도·제품 보존·작업 모드와 필요한 중간 상태를 실제 IndexedDB 왕복으로 검사한다.
2. 재분석·재생성·섹션 삭제가 기존 결과를 자동 저장으로 덮어 지우지 않도록 직전 상태를 보존한다. 최소한 사용자가 되돌릴 수 있게 한다.
3. 본문 검증을 예약 전에 수행하고, 예약 후 모든 예외 경로에 정리 처리를 둔다. 정산 실패가 원래 오류를 가리거나 성공 결과를 버리지 않게 한다.
4. 저장 성공·실패를 정확히 알린다. 자동 저장이 성공하지 않았는데 성공처럼 보이지 않게 한다.

별도 변경 묶음:

- 응답 유실·화면 이동 복구는 서버 작업 ID와 결과 영구 보존·조회로 해결한다. 단순히 브라우저에 요청 ID를 붙이는 것만으로 완료하지 않는다.
- 같은 작업의 통신 재시도는 저장된 결과를 반환하고, 사용자가 의도적으로 새로 만드는 작업은 새 요청으로 구분한다.
- 생성 성공과 정산 대기를 분리하되 정산 재처리·누락 관측 경로를 마련한다. 정산 예외 무시를 영구 무료 처리로 만들지 않는다.

합격: 저장 후 새로고침·다른 초안 전환·통신 단절·정산 오류를 주입해도 기존 결과가 보존되고, 동일 작업 재시도에서 새 유료 생성이 발생하지 않는다.

### 단계 2. 구성안과 편집기의 작업 상태 통일

대상: 본문 1~3, Claude A-3~A-6/A-12/A-13/A-17/A-18, 직전 대화의 새 섹션 방향 누락.

- 섹션 내용·순서·참조·설정을 담는 작업 데이터에 한 가지 기준을 둔다. 두 화면이 각자의 섹션 사본을 따로 고치지 않게 한다.
- 초안별 안정된 섹션 ID를 사용하고, 한국어 장면 수정과 실제 생성 장면의 관계를 명시한다.
- 구성안과 편집기의 섹션 추가 함수를 공유하고 새 섹션에 필요한 디자인·근거 정보를 일관되게 채운다.
- 텍스트 단계와 내부 데이터가 함께 복원되게 한다. 다른 초안의 비교 기준이 새 작업에 남지 않게 한다.

합격: 이미지·텍스트 양쪽에서 생성 전후 단계 왕복, 추가·삭제·순서 변경, 장면 수정, 초안 재개 후 실제 생성 입력이 화면 내용과 같다.

### 단계 3. 참조와 모델 선택을 실제 실행에 정확히 연결

대상: Claude D-1/D-2, 7-4~7-7, C-3/C-4 및 본문 11.3.

- 제품·캐릭터의 보존 조건은 위치·자세·구도 지시와 분리한다. 사용자 배치 지시가 보존 규칙을 해제하지 않게 한다.
- 제품·캐릭터·디자인 참조가 각각 실제로 쓰이는지 보여주고, 서로 경쟁하거나 빠질 때 조용히 진행하지 않는다.
- 첨부 상한을 요청 전에 검증한다. 실제 전송 배열을 확정한 뒤 그 배열 기준으로 이미지 번호와 역할 지시를 만든다.
- 선택 모델, 실제 제공자·모델·품질·크기, 예약량, 최종 차감, 원가 기록을 같은 실행 정보에서 계산한다. 조용한 모델 대체나 고정 1장 정산을 제거한다.
- 추가 지시와 그림체의 기획 반영 범위를 정리하고, 실제 화면비와 프롬프트의 비율 지시를 맞춘다.

합격: 단건·일괄·대표 이미지·리디자인 생성·수정에서 선택한 모델과 실제 호출이 일치하고, 사용자가 붙인 필수 참조가 누락되지 않는다.

### 단계 4. 검수 결과와 승인 화면을 믿을 수 있게 만들기

대상: 본문 9~12, Claude D-11, 7-3 및 제품·캐릭터 보존 요구.

- 심사는 정해진 항목의 완전성을 검사하고, 검수 불가·미달·통과를 분리한다.
- 생성에 보낸 모든 승인 문구를 같은 데이터에서 QA에 전달한다. 신뢰·반론 문구도 화면에서 확인·수정할 수 있게 한다.
- 문장의 사실 근거를 확인하는 검사에는 원본 근거를 제공한다. 설득력 심사와 사실 대조를 구분한다.
- 제품·캐릭터 동일성 검수 및 사용자의 원본 대조 확인을 연결한다. 제품 외형·라벨·캐릭터 특징을 바꾸는 결과는 자동 승인하지 않는다.
- 검수 실패를 이유로 무조건 유료 재생성을 반복하지 않는다. 검수 재시도와 이미지 재생성을 구분한다.

합격: 검수 호출 실패·일부 항목 누락·잘못된 캐릭터·제품 라벨 변경·승인 문구 누락을 입력했을 때 정상 통과로 표시되지 않는다.

각도 변화에 필요한 원본 정보가 없는 경우에는 보존을 보장한다고 말하지 않는다. 실물의 보이지 않는 면은 추가 사진이 필요할 수 있다. 생성 모델 검수만으로 무변형을 절대 보장할 수 없으며, 엄격한 원형 보존에는 실제 다각도 자산 또는 원본 합성 방식의 적용 범위를 검토한다.

### 단계 5. 화면·저장·다운로드 결과 일치

대상: Claude B-1~B-4/B-6/B-9.

- 화면 폭과 독립적인 편집 좌표·출력 해상도를 사용한다.
- 결과물 미리보기, 라이브러리 저장, 다운로드가 같은 합성 결과를 사용하게 한다. 참고용 원본 저장은 별도 의미를 유지한다.
- 실제 제공하는 폰트 이름을 사용하고, 레이어 없는 원본은 불필요하게 낮은 해상도로 재압축하지 않는다.

합격: 넓은 화면과 좁은 화면에서 같은 초안을 열어도 위치·문구가 같고, 저장한 완성본과 다운로드한 완성본에 같은 레이어가 보존된다.

### 단계 6. 기획 품질과 사용 흐름 정리

대상: 본문 8, 판매 효과 한계 및 사용자 설정 질문.

- 이미지·텍스트는 입력 방식으로 구분하고, 실물·서비스 및 판매·홍보 목적은 별도로 정한다. 두 경로는 동일한 승인 구성안 형식으로 합류한다.
- 대상·문제·특징·차별점 입력은 유지한다. 구성·문구 요청과 이미지 연출 요청을 구분하고, 불명확한 옵션 이름을 실제 동작에 맞춘다.
- 검증 없는 예시 채우기를 최종 판매 문구로 자동 승인하지 않는다.
- 상품에 필요한 정보와 구매자의 질문에 맞춰 구성한다. 모든 상품에 인물·고정 베네핏 수·긴 설득 흐름을 일괄 강제하지 않는다.
- 최종 전체 페이지를 읽고 판단할 수 있는 확인 단계를 둔다. 실제 판매 개선은 별도 성과 데이터로 평가한다.

합격: 대표적인 실물 상품과 서비스 입력을 양쪽 모드로 통과시키고, 승인된 문구·참조·장면·내보내기가 끝까지 연결되는 것을 확인한다. ‘예쁘게 생성됨’과 ‘구매 전환 개선’은 별도 평가로 남긴다.

### 첫 착수 범위

첫 구현은 **단계 1의 첫 변경 묶음: 초안 왕복 보존, 파괴적 덮어쓰기 방지, 예약 이후 예외 처리·정산 오류 격리**로 제한하는 것이 적절하다. 이 범위를 동작 시험으로 통과시킨 뒤 서버 결과 복구 및 단계 2로 진행한다.

진행 중인 포스터·카드뉴스 변경과 섞이지 않도록 별도 브랜치/작업공간에서 구현하고, 변경 묶음마다 검증 근거를 남긴다. 전체 엔진 교체·LLM 변경·파일 정리부터 시작할 필요는 없다.
