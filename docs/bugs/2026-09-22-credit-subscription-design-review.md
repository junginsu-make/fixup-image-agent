# 크레딧 구독 전환 설계 — Codex 2차 리뷰

대상: `docs/superpowers/specs/2026-09-22-credit-subscription-design.md` 1,280줄

검토본 SHA-256: `5ffe352dfc66369b08c8074e305af5d14e82d6c8157e2d7c57d89e50ae746bed`

코드 기준: `b58e4ac`와 현재 로컬 비용 전략실 구현. 커밋된 숫자형 마이그레이션을 대조했다. 미추적 한글 SQL과 PDP jobs 제안은 운영 정본으로 간주하지 않았다.

**판정: 상품 방향은 구현 가능하다. 그러나 현재 문서를 그대로 장부 구현 계약으로 사용하기에는 정산·납부·이행 규칙이 부족하다.** 아래 P1 항목을 먼저 보강해야 한다. 단순한 차감표 변경과 구매 잔액 장부 전환은 분리해서 검증해야 한다.

이번 작업은 리뷰다. 원 설계서·서비스 코드·DB·비용 전략실을 수정하지 않았다. 실제 fal 호출, 운영 DB 조회/변경, PostgreSQL 동시 트랜잭션 실험은 수행하지 않았다. SQL 경합은 코드와 PostgreSQL 잠금 규칙으로 도출한 시나리오이며 운영 재현으로 표현하지 않는다.

## 1. 우선 보강할 사항

### R1 · P1 — 예약 중 만료/회수에 대한 금액 보전과 정산 결과가 없다

근거: 설계 669~670, 815~842, 847~848, 907~915행. 현재 예약 정리는 `202609140001_ad_export_operation.sql`, 확정은 `202607230001_membership_usage.sql:203`이다.

예약은 묶음과 연결되지 않고, 확정 시점에 살아 있는 묶음만 소비한다. 따라서 다음 상황이 가능하다.

1. 월말 23:59에 구독 잔액 10으로 작업을 예약한다.
2. 생성 중 해당 묶음이 만료된다.
3. 확정 때 다른 유효 묶음이 없으면 0만 소비하고 warning으로 끝난다. 다른 구매 묶음이 있으면 원래 예약과 다른 묶음에서 소비한다.

후자는 단순한 무료 제공이 아니라 소비 출처가 바뀌는 문제다. 전자는 `generation_events.consumed_units=10`인데 묶음 소비는 0인 불일치가 생길 수 있다. 부족분 반환값을 어떻게 반영하는지 §6.8에 없다.

또 현재 예약 만료 정리가 먼저 이벤트를 failed로 바꾸면, 늦게 도착한 성공 확정은 기존 `status='reserved'` 가드 때문에 넘어간다. `settleAiUsage`는 정산 오류를 삼키고 결과를 반환하므로 경고만으로 미정산 복구를 보장할 수 없다.

**필요한 결정:** 예약 때 어느 묶음의 몇 units를 확보했는지 기록하거나, 만료/회수 중 예약분을 보전하는 동등한 규칙이 필요하다. 의도적으로 부족분을 면제할 수도 있지만 그 경우에도 예상 차감·실제 차감·면제/미수 사유를 영속적으로 기록해야 한다. TTL 만료만으로 외부 작업이 끝났다고 판단하지 않는다.

### R2 · P1 — `consume_credits` 자체는 멱등하지 않다

근거: 설계 725~737, 803~844, 907~915행.

같은 `(user, request, units)`로 두 번 호출하면 두 번 소비한다. `credit_consumptions`에는 요청별 정산 완료를 보장하는 제약이 없다. `request_id`가 실제 예약에 연결되는 FK도 없다.

**반대 근거도 있다:** 현재 `finalize_generation`은 이벤트를 `FOR UPDATE`로 잠그고 reserved일 때만 업데이트한다. 새 소비 호출을 **그 가드 안에서, 클램프된 금액으로, 같은 트랜잭션에** 넣으면 일반적인 중복 finalize는 막을 수 있다. 따라서 “현재 정상 폴링이 반드시 두 번 차감한다”는 뜻은 아니다.

설계에는 그 위치와 불변식을 명시해야 한다. 재시도는 최초 정산 결과를 반환하고, 다른 금액으로 같은 request를 재사용하면 거부해야 한다. 요청당 정산 헤더/완료 상태와 lot별 명세를 연결한다. `(request_id, grant_id)` unique만으로는 다른 묶음으로 넘어가는 중복 소비까지 막지 못한다.

### R3 · P1 — 묶음의 `ORDER BY`만으로 전체 교착을 막을 수 없다

근거: 설계 820~831행, 새 `credit_consumptions.user_id` FK(729행), 현재 reserve의 profile 잠금과 만료 이벤트 UPDATE, 현재 finalize의 event 잠금.

새 소비 함수를 기존 finalize에 단순 삽입하면 다음 순환이 가능하다.

| 트랜잭션 | 먼저 가진 잠금 | 다음에 기다리는 잠금 |
|---|---|---|
| 늦은 성공 확정 | generation event E, grant G | consumption INSERT의 사용자 FK 검사에 필요한 profile P |
| 새 예약/만료 정리 | profile P (`FOR UPDATE`) | 만료된 event E의 UPDATE |

`E → P`와 `P → E`가 엇갈린다. FK 검사도 잠금에 참여한다. PostgreSQL의 `FOR UPDATE`는 `FOR KEY SHARE`와 충돌한다. [행 잠금 규칙](https://www.postgresql.org/docs/17/explicit-locking.html), [FK 검사 구현](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/utils/adt/ri_triggers.c).

동일한 불변 정렬키를 쓰는 소비 함수끼리의 순서는 도움이 된다. 하지만 reserve/finalize/지급/회수/구독 변경/일괄 작업까지 같은 계정 잠금 순서를 적용해야 한다. **lazy 발급도 회원 잠금과 권한/상태 확인 뒤에** 넣고, 독립 호출 경로도 동일한 규약을 따라야 한다. 잠금 순서와 교착 재시도·멱등 정산을 함께 명시한다.

### R4 · P1 — 납부 확인 없이 매달 구독분이 생긴다

근거: 설계 547~548, 757~765, 866~876행.

`ensure_subscription_grant`는 구독이 active인지와 cancel_at만 본다. 9월분만 계좌이체로 받은 사용자가 active로 남으면 10월·11월에도 자동 지급된다. `paid_through`나 해당 월의 수납/이용권 확정 기록이 없다. started_at도 확인하지 않아 미래 시작 구독에 현재 월 지급이 가능하다.

1차에 PG가 없다는 결정은 유지할 수 있다. 다만 관리자의 수납 확인이 특정 기간의 이용권을 확정해야 하고, lazy 발급은 **확정된 기간만** 지급해야 한다. 당시 플랜·지급량·결제액도 스냅샷으로 남긴다. PG는 나중에 같은 기간 확정 경로를 호출하면 된다. 해지 예약과 즉시 종료의 상태 의미도 구분해야 한다.

### R5 · P1 — 단위 전환과 rollback은 함수만 되돌려 해결되지 않는다

근거: 설계 927~933, 1093~1117행.

예를 들어 월 한도100 중 구단위50을 이미 썼다고 하자. 새 한도를20으로 낮추면 구단위 사용량50 때문에 남은 사용권이 사라진다. 한도를100으로 유지하면 새 기준으로 50장을 더 만들 수 있어 이전의 표준형 잔여10장과 다르다.

한 달의 `generation_events`에 구단위와 신단위가 섞이므로 quota 숫자만 환산해도 해결되지 않는다. 진행 중인 구버전 예약을 신버전 코드가 확정하는 경우도 정의되어 있지 않다. 월 한도 데이터와 사용 기록을 바꾼 뒤 계산 함수만 rollback하면 원래 상태가 되지 않는다.

**필수:** 예약별 pricing version·예약 당시 크기/단가 또는 차감표 스냅샷, 전환 기준시각, 기존 사용/잔여/예약의 변환 규칙, 복귀용 데이터 스냅샷과 역변환/보상 규칙. 팀 사용량에도 동일한 단위 경계를 적용해야 한다. 기존 무료 한도는 모델별 사용 가능량이 달라 일률적인 `/5`가 모든 권리를 보존하지 않는다.

2단계에서 새로 지급하거나 만료된 크레딧도 생기므로, 두 DB 함수만 되돌리고 새 표를 버려두는 rollback은 지급분을 잃거나 월 한도를 다시 열 수 있다. `CREDIT_LEDGER` 플래그의 평가 위치와 DB 함수/앱 버전 조합별 읽기·쓰기 규약이 필요하다.

### R6 · P1 — 팀 잔량의 정의와 잠금이 빠져 있다

근거: 설계 894~898, 935~944행. `202609070005_team_credit.sql`의 `team_units_used`, `effective_quota`와 대조했다.

`team_remaining`은 현재 구현에 없고 이 문서에도 정의가 없다. 기존 helper는 **현재 사용자의 사용·예약을 제외**한다. 개인 식에서 `v_used`를 제거하면서 이것을 그대로 재사용하면 본인이 이미 소비한 팀 예산을 빠뜨린다.

- 개인: `요청 <= 개인 잔액 - 본인 유효 예약`.
- 팀: `요청 <= 팀 한도 - 전체 팀 확정 사용 - 전체 팀 유효 예약`.

각 식에서 본인 예약을 한 번만 빼도록 정의해야 한다. 팀 한도0은 현재 “제한 미설정”이므로 literal 0 잔액으로 바꾸지 않는다.

또 사용자별 profile 잠금은 서로 다른 팀원의 동시 예약을 직렬화하지 않는다. 팀 잔량5에서 두 사람이 각5를 동시에 예약하는 경합에는 팀 차원의 잠금이 필요하다. “팀은 현재 그대로”는 팀 지갑을 신설하지 않는다는 의미로는 가능하지만, 새로운 개인 잔액과 결합하는 검증까지 생략할 수는 없다.

### R7 · P1 — “이미지 1장”의 과금 대상이 아직 모호하다

근거: 설계 560~564, 627~635, 995~1005행. `apps/web/app/sns/cost-estimate.ts`, `packages/layout-core/src/estimate.ts:29`.

카드뉴스 한 카드에 그림 슬롯3개가 있으면 AI 호출3개로 최종 카드1개를 만든다. 현재 함수를 실행해 속도형 슬롯3개의 이미지 원가가 **$0.45**임을 확인했다.

- 최종 카드1개를 1크레딧으로 받으면, 단일 모델의 $0.15가 상한 이내여도 작업 원가는 $0.25 상한을 넘는다.
- 호출3개를 3크레딧으로 받으면 “이미지100장”을 최종 카드100장으로 읽는 오해가 남는다.

캐릭터 후보/선택한 정면/추가 각도/sheet, 그대로 넣는 카드, 컷아웃·리사이즈, 기획만 실행, 사용자 재생성, 서비스 재시도도 표로 정의해야 한다. 특히 기획을 별도 유료로 유지하면 포스터100장을 100크레딧으로 제공한다는 설명과 충돌할 수 있다.

픽셀 문턱 역시 클라이언트 입력 문자열이 아닌 **서버가 결정한 실제 요청 크기**에서 산출해야 한다. 모델별 고정 해상도·첨부 크기 따라가기·공급자 크기 보정 시점을 고려하고 예약에 저장한다. 6백만 픽셀 기준은 아직 가정이다.

## 2. 금액과 조사 결과 정정

### R8 · P2 — 마진 표와 원가 상한은 세금·수수료 전 계산이다

설계 568~617행은 `(판매금액 - 이미지 원가) / 판매금액`에 가까운 값이다. 기존 비용 도구 기본값처럼 판매가1,000원에 VAT10% 포함·PG3.3%를 적용하면, 코드 표준형 원가 $0.21072×1,380원 기준:

| 계산 | 결과 |
|---|---:|
| 모델 원가만 반영한 순매출 대비 마진 | 64.38% |
| 여기에 문서의 장당 글 비용 약11원 추가 | 63.17% |
| 이미지 원가 상한을 $0.25로 허용했을 때 | 58.42% |
| 같은 조건에서 마진65%를 위한 API 예산 | 약 $0.20665 이하 |

이는 조건부 산술 결과이며 판매가·세금·PG 계약을 확정한 것이 아니다. 수동 계좌이체 단계에서 PG=0을 쓰면 다시 계산해야 한다. 서버·무료 제공·실패/재시도까지 포함한 회사 이익률은 별도다. 따라서 “전부70% 이상”, “$0.25면65% 보장”은 현재 문구대로 사용할 수 없다.

### R9 · P2 — 비용 전략실 충돌은 맞지만 비교 금액이 틀렸다

설계 1170~1175행의 `$100 → $500`을 다음으로 정정해야 한다. 기획·재생성 없이 정사각 표준형을 단건 생성하고 100명이 각각100크레딧을 전부 사용하는 조건이다.

| 기준 | 전체 이미지 | 코드 단가 기준 API 비용 |
|---|---:|---:|
| 현재, 이미지당5크레딧 | 2,000장 | **$421.44** |
| 제안, 이미지당1크레딧 | 10,000장 | **$2,107.20** |

5배라는 비율은 이 예시에 맞다. 그러나 모델·크기·기획 유무·묶음 올림에 따라 배수는 달라진다. 크레딧의 $0.05 환산 단위를 이미지 한 장의 API 가격으로 사용하면 안 된다.

### R10 · P2 — 코드 테스트가 DB 단가 변경을 자동 검출하지 않는다

설계 615~617, 1207~1209행. 현재 관리자 `updateModelPrice`는 0~100 범위만 확인하고 `setModelPrice`로 DB를 수정한다. 그 동작이 CI를 실행하거나 저장소 단가를 변경하지 않는다.

또 `model_prices`는 운영자 원가 장부의 단가이며 실제 공급사의 청구액을 제어하는 설정이 아니다. 코드 검사/DB 검사만으로 실제 원가 상한을 보장하지 못한다.

가격 기준 정본과 버전을 정하고, 코드·DB 차이를 검사하는 배포/운영 점검과 관리자 변경 시 검증을 추가해야 한다. 상한 검사는 모델 한 번의 단가뿐 아니라 전체 작업의 호출·크기·기획·재시도 예산을 대상으로 해야 한다. 실제 청구 표본과의 대조는 별도다.

### R11 · P2 — 구독 지급의 uniqueness와 관리자 추가 지급이 충돌한다

설계 695, 711~713, 874~876, 1029~1044행.

`period`가 nullable이므로 `kind='subscription', period=NULL` 행은 같은 사용자에게 여러 개 들어갈 수 있다. PostgreSQL unique의 기본 NULL 의미 때문이다. [공식 설명](https://www.postgresql.org/docs/17/indexes-unique.html).

반대로 모든 구독 지급에 같은 월 period를 넣으면 “구독분 추가”나 중도 업그레이드분은 현재 unique index와 충돌한다. 두 경우의 지급 원천을 별도 정의해야 한다. `order_id`도 unique가 아니고 수동 지급 RPC에 멱등 키가 없어 중복 제출 방지 계약이 없다.

월 정기 지급 / 조정 지급 / 구매 / 보너스의 source key와 unique 규칙, 필수 period·지급액·만료 조건을 명시한다. `credit_consumptions`의 grant 소유자와 request 소유자도 관계 제약으로 묶는다.

### R12 · P2 — lazy 지급과 회원·관리자 조회 계약을 완성해야 한다

설계 881~883, 974~980, 1018~1045행.

발급이 reserve에서만 발생하면 월초에 아직 생성하지 않은 유료 회원의 잔액이0으로 보일 수 있다. 조회에서도 “부를 수 있다”가 아니라, 지급 가능한 수납 기간을 조회에 어떻게 반영할지 정해야 한다. 쓰기 함수는 VOLATILE 진입점에서 실행하고 후속 잔액 조회를 명확히 분리한다. [PostgreSQL 함수 snapshot 규칙](https://www.postgresql.org/docs/16/xfunc-volatility.html).

또 `admin_member_credits(p_user_ids)`는 이미 선택한 회원들의 잔액 조회다. 이것만으로 전체 회원을 잔액/만료순으로 정렬·필터한 뒤 pagination할 수 없다. 목록 RPC 또는 view의 전체 조인·집계·정렬·안정적인 동률 키·count 계약이 필요하다. 먼저50명을 뽑은 뒤 잔액순으로 정렬하면 전체 순위가 아니다.

현재 `usageFromRpc`는 `quota - used - reserved`를 계산한다. quota를 balance로 바꾸면서 이 함수를 그대로 두면 **화면에서 확정 사용을 다시 뺀다**. reserve뿐 아니라 finalize 반환, member/team/admin summary, 캐시·프론트 미리보기를 함께 전환해야 한다.

## 4. 원가 실측과 사실 표현

코드의 `priceCoverage`를 직접 실행했다.

|---|---|---:|
| 1536×1536 | false | $0.40026 |

문서의 fallback 계산은 맞다. 그러나 “더 큰 크기가 싸므로 이 가격일 리 없다”는 실제 청구 근거가 아니다. **과대 추정 확정이 아니라 실가격 미확인**으로 표현해야 한다. 현재 PDP 예약은 크기 인자를 생략해 정사각 기본 가격을 사용하는 점도 구분한다.

0단계는 타당하다. 다만 문서에 적힌 3가지 크기별 요청의 모델·endpoint·t2i/i2i·quality·요청/실제 출력 크기·요청 ID·최종 과금 증거를 남겨야 한다. 호출 성공 응답이나 로컬 예상 단가만을 실제 청구라고 기록하지 않는다. 한 표본으로 모든 크기/참조/재시도 원가를 확정하지 않는다. 이번 리뷰에서는 유료 API 호출을 실행하지 않았다.

관리자 쿼리의 전체 누적 집계와 기간/표현식 인덱스 위험은 코드상 확인된다. 다만 “수백 명이면 느려진다”, 실제 스캔 방식·21회 왕복의 지연 영향은 실행계획/데이터량/측정 없이 확정하지 않는다. `EXPLAIN (ANALYZE, BUFFERS)`와 페이지 요청 계측을 별도 검증 기준으로 둔다.

SQL 정본도 구분해야 한다: 현재 reserve는 `202609140001_ad_export_operation.sql`, finalize는 `202607230001_membership_usage.sql`이다. 9월14일 파일에 두 함수가 모두 있는 것은 아니다. 운영 DB에 실제 적용된 정의는 이번에 조회하지 않았다.

구독분이 항상 먼저 소진된다는 문구도 틀리다. 예를 들어 9월25일 만료 구매분과 10월1일 만료 구독분이 있으면 구매분부터 소비한다. 정렬 규칙은 “종류와 관계없이 만료가 가까운 묶음 우선”으로 설명한다.

약관의 특정 환불 공식이 법령상 의무라는 서술은 별도의 적용 법령·근거 확인이 필요하다. 이 리뷰는 해당 법률 판단을 검증한 것이 아니다.

## 5. 비용 전략실과의 연결 계약

현재 구현은 `business.policy = current | proposed`와 작업별 `proposedCharge/proposedRequired`를 지원한다. 따라서 일부 고정 작업은 제안 차감량을 직접 넣어 비교할 수 있다. 하지만 이것이 **새 구독 설계를 완전히 구현했다는 뜻은 아니다.**

다음 계약을 차감 체계 구현과 함께 정해야 한다.

1. `cost-v1`(원가 환산), `image-v2`(정의가 확정된 장수/크기 등급), 사용자 제안표를 명확히 구분한다.
2. 새 정책은 서버와 계산기가 같은 순수 함수·실제 요청 크기·과금 대상 정의를 사용한다. 과거 snapshot의 구단위 계산은 보존한다.
3. 실제 서비스의 활성 정책과 관리자 비교 정책을 별도로 표시한다. 공통 credit.ts를 변경했다고 옛 예측이 조용히 바뀌면 안 된다.
4. 새 구독 크레딧과 기존 계산기의 **가상 1크레딧=1원 충전형**을 혼동하지 않는다. 새 구매분의 3개월 만료와 구독 월 만료는 별도 지급 코호트 규칙이다.
5. API 단가가 같아도 차감 정책이 바뀌면 생성·저장·전송량이 달라진다. 전체 비용을 다시 계산한다. API 원가5배가 곧 EC2 가격5배라는 뜻은 아니다.

이 리뷰에서 비용 전략실의 기본 정책을 바꾸지 않았다. 먼저 R7의 과금 대상과 이행 정책을 확정해야 두 기준의 자동 비교를 일관되게 구현할 수 있다.
