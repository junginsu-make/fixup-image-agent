# 기준선 — 운영과 비슷한 조건 (2026-09-29)

조건: 시험 서버 A t3.micro(운영과 같은 설정), 시험 DB 는 CPU 1·메모리 1GB 로 제한, A→DB 왕복 약 0.2초(`tc netem`), 가짜 AI(이미지 45초·글 3초).
운영과 다른 점: DB 는 x86(운영 MICRO 는 ARM 공유 코어), 가짜 AI 는 늘 성공.

## 시험 조건 적용 확인 (Task 1)

- DB 컨테이너 제한: `docker inspect supabase_db_sb` → `1000000000 1073741824` (CPU 1개, 메모리 1GB) — 기대값과 일치 (원본 `docs/capacity/raw/2026-09-29-s0/task1-step1-db-limit.txt`)
- A→DB 지연(`tc netem delay 200ms`, A 의 `ens5`, B 의 172.31.26.41:54321 방향만):
  - `curl .../rest/v1/` 왕복 3회: 1.080s / 1.069s / 1.093s (원본 `docs/capacity/raw/2026-09-29-s0/task1-step2-tc-delay.txt`) — 브리프가 적어 둔 기대값(0.19~0.25초)과 **어긋남**
  - 원인을 더 파 보니: 이 엔드포인트(`/rest/v1/` 루트)는 108,226바이트짜리 전체 스키마 설명(OpenAPI 문서)을 돌려준다. 시험 지연이 A 가 내보내는 패킷(요청·ACK)에만 걸리다 보니, 응답이 여러 TCP 조각으로 나뉘면 그때마다 A 의 ACK 가 0.2초씩 밀려 왕복이 여러 번 겹쳐 늘어난다. 브리프를 처음 쓴 시점보다 지금 스키마(테이블 수)가 커져서 응답이 커진 탓으로 보인다
  - 검증을 위해 추가로 잰 값(브리프에는 없는 참고 수치): `time_connect` 0.201초(순수 접속 왕복, 기대한 0.2초와 일치), 작은 응답을 돌려주는 `rpc/version` 호출은 총 0.406초(접속 0.2초 + 요청 1회 왕복 0.2초로 설명됨)
  - 결론: **0.2초 지연 자체는 의도한 대로 걸려 있다.** 다만 브리프가 예로 든 `curl` 명령은 응답이 큰 엔드포인트라 여러 번의 왕복이 겹쳐 표면값이 커 보인다. Task 2 이후 모든 측정치(페이지·API 응답 시간)는 이 실제 지연 조건 그대로 반영된 값이다
  - 가짜 AI(443, 다른 경로) 대조군: 0.0228초 (원본 `docs/capacity/raw/2026-09-29-s0/task1-step2-fakeai-check.txt`) — 기대값(0.05초 미만) 충족, 지연이 DB 구간에만 걸려 있음을 확인
- 되돌리는 명령(이번 작업 끝에서는 실행하지 않고 남겨 둠 — 이후 단계에서 재사용):
  - A: `sudo tc qdisc del dev ens5 root`
  - B: `docker update --cpus 0 --memory 0 supabase_db_sb`

## 메모리 값 (Task 4, S1 — 시험 서버 A 를 t3.medium 으로)

**조건 변경:** 시험 서버 A 를 t3.micro → t3.medium 으로 크기 변경(정지 → `modify-instance-attribute` → 시작). 공인 IP 가 바뀌었다: **43.202.63.50**(사설 172.31.13.128 은 그대로 — B 는 사설 IP 로 A 를 찾으므로 B 쪽 스크립트는 고칠 필요 없음). 재부팅으로 사라진 Task 1 의 `tc netem` 지연을 그대로 재적용했고(`sudo tc qdisc show dev ens5` → `netem ... delay 200ms` 확인, 원본 `docs/capacity/raw/2026-09-29-s1-memory/task4-step1-tc-reapply.txt`), B 의 DB 컨테이너 제한(`docker inspect supabase_db_sb` → `1000000000 1073741824`)도 그대로였다. A 재시작 후 서비스 복구 확인: `systemctl is-active fixup-image-agent caddy` 둘 다 `active`, `curl 127.0.0.1/` → `200`, `free -m` 총 메모리 3832MB(≈4GiB, t3.medium 확인). 원본 `docs/capacity/raw/2026-09-29-s1-memory/task4-step1-resize.txt`.

**측정 방법:** 상세페이지(포스터/카드뉴스) 동시 1·3·6명, `HOLD=150s`, 매 단계 시작 전 `fixup-image-agent` 서비스 재시작(`run-k6.sh`). `unitmem` = `systemctl show fixup-image-agent -p MemoryCurrent`(cgroup, 1초 간격 샘플의 최댓값) — `MemoryHigh`/`MemoryMax` 가 실제로 보는 값이라 이걸 기준으로 삼았다. 각 단계 재시작 0회, heap OOM(`heap out of memory` 로그) 0회, k6 실패율 0.00% 로 모두 동일했다.

### 서버 설정 바꾸기 리허설 (addendum §2, `localhost` 를 운영 도메인 대신 사용)

| 단계 | 결과 |
|---|---|
| 1. 흉내(손으로 만든 두 파일: `fixup-image-agent.caddy`=리다이렉트, `formwith.caddy`=도메인 사이트) | reload 후 `https://localhost/` 200, IP → 308 → `https://localhost/` |
| 2. 잊은 경우(`formwith.caddy` 치우지 않고 install-host.sh 실행) | 종료 1, 안내 문구, 두 파일 sha256 전후 동일, 서비스 무영향 |
| 3. DEPLOY.md 그대로(백업 → 처음 한 번 `mv` → `install-host.sh localhost http://172.31.13.128`) | 성공, 새 방식은 리다이렉트+도메인 사이트를 **한 파일**에 합침(옛 두 파일 방식과 다름, 문서가 예고한 대로), `https://localhost/` 200·IP 308 확인 |
| 4. 되돌리기 → 흉내 상태 확인 → 다시 3번으로 | 되돌린 뒤 3개 파일 sha256 이 흉내 상태와 완전히 일치, 동작도 일치. 재실행한 3번도 성공 |
| 6. 측정 모양으로(`install-host.sh http://172.31.13.128` 한 인자) | IP 200, 흉내·백업 파일 정리 완료 |

**문서 결함으로 세지는 않았지만 기록해 둘 것:** ① `caddy validate` 를 **root 로 직접**
돌리면 그 과정에서 새 로그 파일이 root 소유(0600)로 만들어져, 뒤이은 진짜 reload(caddy
계정으로 돎)가 `permission denied` 로 실패할 수 있다(서비스 자체는 죽지 않고 active 로 남음).
install-host.sh 자신은 `runuser -u caddy` 로 검사하므로 이 문제가 없다 — 사람이 손으로
확인차 `caddy validate` 를 부를 때만 조심하면 된다. ② 정적 파일이 아직 한 번도 동기화되지
