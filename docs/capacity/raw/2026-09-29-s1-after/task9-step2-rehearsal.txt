# Task 9 Step 2 — A 에서 「처음 한 번」 이전 절차 리허설 (addendum §2, 1~6)

시험 서버 A(172.31.13.128)는 도메인이 없어 `localhost` 를 운영 도메인(formwith.fix-up.kr)
대신 썼다. Caddy 는 localhost 를 내부 CA 로 처리해 ACME 시도 없이 HTTPS 를 낸다.

## 1) 흉내 — 손으로 만든 두 파일 상태 재현

- 백업: `/etc/caddy/sites` → `/root/a-sites.orig`
- `fixup-image-agent.caddy` (59B) = `http://172.31.13.128 { redir https://localhost{uri} 308 }`
- `formwith.caddy` (341B) = 옛(952fb7e) Caddyfile.template 을 localhost 로, 로그 파일만
  `formwith.access.log`

첫 reload 시도는 **실패**했다(아래 「부수적으로 발견한 것」 참조). 원인을 고치고 재시도:

```
sudo runuser -u caddy -- caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
→ Valid configuration
sudo systemctl reload caddy → 성공, active
https localhost = 200
http IP redirect = 308 https://localhost/
```

### 부수적으로 발견한 것(DEPLOY.md 결함은 아님 — 내 확인 절차의 실수)

`sudo caddy validate ...` 를 **root 로 직접** 실행하면 캐디파일에 새로 등장한 로그 파일
(`/var/log/caddy/formwith.access.log`)을 검증 과정에서 실제로 열어 **root:root 0600** 으로
만들어 버린다. 그 뒤 진짜 caddy 프로세스(caddy 계정, uid 999)가 reload 로 같은 파일을 열려
하면 `permission denied` 로 reload 자체가 실패한다(`Job for caddy.service failed`, 서비스는
계속 active 상태로 남음 — 죽지는 않았다). install-host.sh 자신은 처음부터
`runuser -u caddy -- caddy validate` 를 쓰므로 이 문제가 없다. 이건 내가 확인용으로 `sudo
caddy validate` 를 직접 부른 탓이었고, 파일을 지우고 `runuser -u caddy` 로 다시 검증하니
정상 동작했다. DEPLOY.md 자체는 이 수동 validate 를 지시하지 않으므로 문서 결함으로 세지
않았다 — 다만 사람이 손으로 확인차 `caddy validate` 를 돌릴 때는 caddy 계정으로 해야
한다는 점은 기록해 둔다.

## 2) 잊은 경우 — formwith.caddy 를 치우지 않고 install-host.sh 실행

```
sha256 BEFORE:
  fixup-image-agent.caddy e5ad4ffc...
  formwith.caddy          48cd6916...

$ sudo bash /tmp/ec2-new/install-host.sh localhost http://172.31.13.128
/etc/caddy/sites/formwith.caddy 에 이미 localhost 로 시작하는 사이트 블록이 있습니다.
docs/DEPLOY.md 「서버 설정 바꾸기」의 처음 한 번 절차를 보세요.
EXIT=1

sha256 AFTER (동일):
  fixup-image-agent.caddy e5ad4ffc...
  formwith.caddy          48cd6916...

systemctl is-active caddy fixup-image-agent → active active (아무것도 안 건드림 확인)
```
기대대로: 종료 1, 안내 문구, 파일 해시 전후 동일, 서비스 영향 없음.

## 3) DEPLOY.md 「서버 설정 바꾸기」를 문서 그대로

```
백업: rm -rf /root/caddy-sites.bak && cp -a /etc/caddy/sites /root/caddy-sites.bak
      && cp fixup-image-agent.service → /root/unit.bak
처음 한 번만: mv /etc/caddy/sites/formwith.caddy /root/formwith.caddy.manual

$ sudo bash /tmp/ec2-new/install-host.sh localhost http://172.31.13.128
Valid configuration
Host files installed for localhost.
Next: create /etc/fixup-image-agent/app.env, then deploy a release.
EXIT=0
```

병합 결과 — 새 install-host.sh 는 리다이렉트 블록과 도메인 사이트 블록을 **한 파일**
(`fixup-image-agent.caddy`)에 함께 쓴다(옛 방식의 두 파일과 다름, 문서가 예고한 그대로):

```
http://172.31.13.128 {
    redir https://localhost{uri} 308
}

localhost {
    ... (정적 캐시 블록 + reverse_proxy + log → fixup-image-agent.access.log) ...
}
```

4단계(app.env: 힙 1536·ALERT_EMAIL 빈칸)는 이미 만족 — 새로 넣을 값 없음.

5~6단계:
```
daemon-reload && restart fixup-image-agent && reload caddy
systemctl is-active fixup-image-agent caddy fixup-image-agent-monitor.timer → active active active
https localhost = 200
http IP = 308 https://localhost/
```
(이 시점엔 아직 새 릴리스를 배포하지 않아 `/var/www/.../static/current` 가 비어 있었다 —
정적 파일·cache-control 확인은 Step 3 배포 뒤 다시 했다. 아래 「관찰」 참조)

### 관찰 — 문서 순서에 대한 참고(결함까지는 아님)

DEPLOY.md 「서버 설정 바꾸기」 6번의 정적 파일 확인은 `/var/www/.../static/current/_next/static/chunks`
에서 조각 이름을 하나 찾는 것으로 시작한다. 이번처럼 **설정 변경을 새 릴리스 배포보다 먼저** 하면
(이번 리허설 순서가 그랬다) 그 디렉터리가 아직 비어 있어 `find` 가 아무것도 못 찾는다. 실제 운영
절차는 보통 이미 정적 동기화가 된 릴리스가 떠 있는 상태에서 설정만 바꾸므로 문제가 안 되지만,
"맨 처음 서버(정적 동기화 이전 릴리스만 있는 상태)에서 설정부터 바꾸는" 순서라면 이 확인은 배포
뒤로 미뤄야 한다. DEPLOY.md 는 이 조합을 명시하지 않는다.

## 4) 되돌리기 → 흉내 상태 확인 → 다시 3번으로

```
목표 상태(caddy-sites.bak) sha256:
  fixup-image-agent.caddy     e5ad4ffc...
  fixup-image-agent.caddy.bak b70caa58...
  formwith.caddy               48cd6916...

$ sudo rm -rf /etc/caddy/sites && sudo cp -a /root/caddy-sites.bak /etc/caddy/sites \
    && sudo cp /root/unit.bak /etc/systemd/system/fixup-image-agent.service \
    && sudo systemctl daemon-reload && sudo systemctl restart fixup-image-agent \
    && sudo systemctl reload caddy
EXIT=0

되돌린 뒤 sha256 (동일):
  fixup-image-agent.caddy     e5ad4ffc...
  fixup-image-agent.caddy.bak b70caa58...
  formwith.caddy               48cd6916...

systemctl is-active fixup-image-agent caddy → active active
https localhost = 200
http IP = 308 https://localhost/
```
해시·동작 모두 1번(흉내) 상태와 일치 — 되돌리기 검증 완료. (이번엔 formwith.access.log 가
이미 caddy 소유로 존재해 reload 가 문제 없이 성공했다.)

다시 3번으로: `mv formwith.caddy → /root/formwith.caddy.manual` 후
`install-host.sh localhost http://172.31.13.128` 재실행 → EXIT=0, https localhost=200,
IP 308 확인.

## 6) 측정 모양으로 되돌리기 + 정리

```
$ sudo bash /tmp/ec2-new/install-host.sh http://172.31.13.128   (한 인자)
Host files installed for http://172.31.13.128.
EXIT=0
daemon-reload && restart && reload → active active active
http IP = 200
사이트 파일: 리다이렉트·도메인 블록 없이 순수 IP 사이트 하나(Task 8 과 같은 모양)로 복귀
```

정리(직접 만든 것만 삭제):
```
sudo rm -rf /root/a-sites.orig /root/caddy-sites.bak /root/unit.bak /root/formwith.caddy.manual
sudo rm -f /var/log/caddy/formwith.access.log
```
정리 뒤 `/root/` 에는 원래 있던 `.bashrc .local .profile .ssh snap` 만 남음 확인.
`/etc/caddy/sites/` 에는 `fixup-image-agent.caddy` + `fixup-image-agent.caddy.bak`(Task 8
산출물, 우리가 만든 게 아니므로 유지) 만 남음.
